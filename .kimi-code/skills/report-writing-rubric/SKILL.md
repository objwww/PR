# 报告写作规约（六要素）

## 一段话的极限：六个要素

任何结论性摘要，一段话只承载这六件事，顺序固定：

**发生了什么 → 根因是什么 → 凭什么判断 → 影响多大 → 有多大把握 → 建议怎么办**

范例（审批域）：

> 本次审批平均耗时从 2 小时升至 8 小时，主因是报销规则变更后审批矩阵未同步，导致大量单据积压在旧财务节点；审批日志、规则版本记录和节点积压统计支持该判断，影响约 320 单、平均延迟 6 小时，置信度高；建议立即更新审批矩阵、清理积压，并增加超时升级机制。

范例（告警域，本系统实测产出）：

> 告警「订单重复创建」触发后，自动调查确认根因：订单服务发生「幂等失效」（幂等机制被绕过，同一请求被重复执行，产生重复记录）：同一 intent 的创单请求被重复执行、幂等 claim 未生效，生成多笔重复订单，重复订单计数升至 2；指标曲线与创单 WARN 日志两处互证一致。判断依据：2 条证据引用，来自日志、指标，多源互证一致。影响面：……。结论置信度：中——仍有 1 条断言未闭环，建议补充取证后再处置。处置建议：拦截重复流量，修复幂等键校验逻辑，对重复数据做对账清理（通用处置方向，按故障类型给出）。

## 分层呈现

- **页面摘要**：一段话，给人快速看（六要素全覆盖）。
- **结构化结论**：问题 / 根因 / 证据 / 影响 / 置信度 / 措施 / 审计，分节落位。
- **详情展开**：时间线、因果链、原始日志、负责人、期限，折叠在后。

## 硬规则（违反即返工）

1. **正文写自然中文**。裸英文故障码（IDEMPOTENCY_BYPASS 之类）、内部枚举、证据 UUID、`{ref:ROLE}` 审计尾注一律不进正文；引用 id 只活在其该在的结构化字段里。故障码/组件/症状展示前必须过中文字典翻译，未命中回退原文、不瞎编。
2. **量化事实优先**。影响面从证据陈述中提取含数字的事实句（"重复订单计数升至 2"）；提取不到就如实写"未量化"，禁止编造数字。
3. **把握如实分级**：高=全部断言闭环可据以处置；中=仍有断言未闭环，先补取证；未定论=无确认根因，不建议据此处置。拿不准就老实说，不猜、不吹满。
4. **建议标注口径**：通用处置方向按故障类型给出时必须标注"通用处置方向，非本系统执行"；本系统动作必须走人工审批链，不冒充已执行。
5. **禁黑话**：不写"双源佐证未满""确定性链不臆造"这类只对作者有意义的行话；每个术语出现处给一句人话解释。
6. **失败说人话**：任何失败/空态/未统计，必须就近写明原因（如"调查未发起（ABSENT）""模型调用被拒（账户欠费）"），不许只摆裸状态码或"未统计"三字。

## 系统内单一事实源

本规约在代码中的唯一权威实现：`control-app/.../alert/application/ReportWritingRubric.java`
（prompt 段 + confidence 检出锚）。修改规约只改该类，prompt 版本与 SixElementsChecker 判定口径随动；改完必须同步 prompt 版本号并补/改对应测试。评测侧的六要素完整率指标（eval_case_six_parts / sixPartsRate）就是本规约的执行度量——目标是每一批都 100%，不许掉到"未统计"而不给原因。
