# 里程碑工作流规范（强制）

当前处理阶段：$milestone（若未指定，先与用户确认当前阶段编号）

## 一、强制顺序（不可跳步、不可并行跨阶段）

每个里程碑必须严格按以下六道工序执行，顺序不得颠倒：

### 工序 1：任务拆解 + 技术方案

输出 `docs/<阶段>-技术方案.md`，方案必须包含以下结构（缺一不可）：

1. **核心问题**：该模块解决什么问题，为什么现在解决
2. **任务拆解**：任务编号（如 M0-T01）、内容、依赖关系、单项验收标准
3. **类设计**：抽象出的类清单（所属 DDD 层、职责、明确不做什么）+ 类交互时序图（mermaid sequenceDiagram）
4. **实现方式**：关键技术点的具体做法（事务边界、幂等机制、状态机等）
5. **数据流与链路图**（mermaid flowchart，语法需经校验：subgraph 不用节点形状语法、标签加引号）
6. **边界条件与不变量**：强制不变量清单 + 显式承认的残余风险（诚实清单）
7. **设计原因**：设计思维/编码思维，关键取舍的依据（优先引用已验证的开源先例，证据入 `docs/OSS-证据清单`）
8. **问题与压力点**：当前方案的已知短板，按压力排序，自然引出下一阶段工作
9. **实际后果记录**：已发生的故障/Bug/事故案例（本项目过程缺陷 + 同构系统前车之鉴）
10. **技术债分析**：不这样做/维持现状的债务累积与修复成本曲线
11. **测试用例设计**：按防线分层——静态架构（ArchUnit）/ 单元 / 组件规则 / 业务场景闭环 / 边界异常 / 部署门，每条用例可回指冻结项或设计条款
12. **验收标准（DoD）**：可客观检查完成与否的条件

### 工序 2：人工确认门 G1（方案门）

方案交用户评审。**未获用户明确确认前，禁止编写任何实现代码。** 用户提出异议则修订方案后再次送审。

### 工序 3：最小模块编码

- 严格按已确认方案与任务清单实现，在目标服务器/目标环境上进行；
- **只实现当前阶段范围**：禁止越级开发、提前实现、擅自扩展需求；发现后续阶段依赖只记录在案（写入方案的"问题与压力点"），不实现；
- DDD 四层（interfaces/application/domain/infrastructure）保持清晰，Controller 不承载核心业务逻辑；
- 优先兼容现有代码与项目结构，不擅自重构、不更换技术栈；
- 代码必须可直接运行，禁止伪代码占位；
- 沿用项目既有基础设施（数据库、中间件），不引入方案外的新依赖。

### 工序 4：部署验证

在目标服务器完成部署：启动自检通过、服务存活、关键链路冒烟通过。部署动作遵守生产纪律（先备份后变更；备份文件只增不删）。

### 工序 5：测试验证

执行方案 §测试用例设计 的完整矩阵并全部通过；失败必须修复后重跑，不允许带病验收。

### 工序 6：人工确认门 G2（阶段门）

向用户提交验收证据（测试结果、部署状态、演示记录）。**只有用户明确说出"当前阶段已完成，可以进入下一阶段"**，才允许开始下一里程碑的工序 1。

## 二、全局红线（任何阶段适用）

- 里程碑严格按 M0 → M1 → M2 → … 顺序，当前阶段未过 G2 门禁，绝对禁止进入下一阶段
- 每次只处理当前阶段范围内的任务
- git 变更（commit/push/reset 等）必须先获用户确认
- 对服务器/生产环境的不可逆操作：先备份、校验备份、用户确认后才执行
- 设计决策需有依据：优先用成熟开源项目的已验证实践佐证（证据记录到 `docs/OSS-证据清单`），不闭门造车
- 系统质量目标：可靠性、可扩展性优先；严格分层（DDD 四层）；**不为炫技而炫技**——成熟模式优先于新颖技巧，能简单解决的问题不引入复杂机制

## 五、过程文档规范（进度与 Bug 记录）

### 进度文档 `docs/PROGRESS.md`（断点续做的唯一入口）

- **每完成一个任务/工序立即更新**，不留到阶段末补记；
- 内容必须足以让任何人（或新会话）无缝接手：当前阶段与工序状态（六道工序各自 done/in_progress/pending）、已完成事项及产物路径、下一步动作、恢复所需的环境锚点（服务器、密钥路径、配置位置、文档索引）；
- 每次更新追加一条带日期的时间线记录，不覆盖历史。

### Bug 记录 `docs/BUGLOG.md`

遇到 Bug 必须当场记录，条目模板（缺一不可）：

```
| 编号 | 状态 | 现象（问题是什么） | 前因后果（触发条件/影响范围/发现路径） | 根因（为什么会发生） | 解决方案（怎么修的） | 预防措施（如何不再犯） | 关联（测试用例/冻结项） |
```

- 根因必须挖到底，禁止只记现象；"解决了但没弄清根因"的条目标注 `根因待查`；
- 修复后必须补一条回归测试，并在条目里登记测试编号；
- 阶段切换时（G2）把本阶段新增 Bug 汇总进技术方案的事故记录章节。

### 工序 3 补充纪律

编码期间每完成一个任务项（如 M0-T01）：① 更新 `docs/PROGRESS.md`；② 有 Bug 当场入 `docs/BUGLOG.md`；③ 再开始下一个任务项。


## 三、阶段切换检查清单（G2 通过后的动作）

1. 将本阶段"问题与压力点"更新为下一阶段的输入
2. 把本阶段新发生的事故/缺陷补入 `docs/` 事故记录
3. 更新冻结文档/证据清单中受影响的条目
4. 开始下一阶段的工序 1
