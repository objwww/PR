## 一、告警积压未处理，现在能看出来吗？

**结论：部分能。任务级积压和通知积压已经可见，但「告警级积压」的四个关键口径看不见。**

### 已经能看出的（现状）

| 积压口径 | 在哪看 | 数据来源 |
|---------|-------|---------|
| RCA 任务积压 + 最老等待 | 监控页「就绪任务积压」卡（`MonitorView.vue:24-28`，readyTasks + oldestReadyWaitSeconds） | `/api/agent-ops/summary` |
| 调查超 SLA | 调查队列顶部横幅（`RunsView.vue:34-38`，overSla + oldestReadyWait） | `/api/rca-runs` summary.sla |
| 处置未认领 | 告警中心「未分派」卡（`AlertsView.vue:19-22`，unassigned）+ 处置中心「未分配」tab（`CasesView.vue:105-107`） | `/v1/incidents/summary`、`/cases/summary` |
| 通知投递积压 + 24h 失败 | 监控页「通知待投 / 24h 失败」卡（`MonitorView.vue:34-42`） | `/api/agent-ops/summary` |
| 卡住/失败的调查 | 队列「待干预」tab 计数（`RunsView.vue:144`，stuck+failed+review+mine 合计） | `/api/rca-runs` buckets |

### 看不出来的（五个缺口，按严重度排序）

1. **FIRING 且未发起调查的告警数**——这是「告警积压未处理」最直观的口径，现在没有任何一个页面给这个数。IncidentTable 有「调查状态」列（`IncidentTable.vue:38-47`，逐行显示 runState 或「未发起」），但要人工扫行；统计条没有「未发起调查 N 条（最老 X 小时）」卡。后端口径现成：incident FIRING 且 `currentRcaRunId is null`，一个聚合查询。
2. **Webhook inbox 积压深度**——`alert_inbox` 表 + `InboxState` 状态机 + `IncidentWaitingRedrive` 重驱都存在（`V3__m1_inbox_reconcile.sql`、`AlertInboxProcessor`），但**全部 12 个 Controller 里没有任何 inbox 读端点**（已逐一核对）。接收了但还没投影/没决策的事件数、最老滞留时长、按 InboxState 分布，UI 完全不可见。webhook 暴涨时第一现场是 inbox，现在只能靠日志。
3. **等待中（waiting/deferred）告警**——领域模型有完整的延迟调查语义：`DeferredPolicy`、`IncidentWaitingRedrive`，且 incident 详情投影已带 `waitingReason` 字段（`IncidentQueryService.java:68`）——**但前端零消费**（全 alert-web 无 waitingReason 引用），列表不展示、不计数。等待中的告警在 UI 上与普通告警无差别，这正是「积压被看见」的盲区。
4. **积压趋势曲线**——监控页趋势图只有「接收/恢复」两条线（`MonitorView.vue:189-199`），没有积压深度随时间的曲线。业界（PagerDuty/Grafana）看积压第一眼是曲线不是瞬时值：接收速率 > 处理速率多久了、积压是涨是消。
5. **积压告警的「年龄分布」**——没有一个「按等待时长分桶」的视图（<15min / 15-60min / 1-4h / >4h）。PagerDuty 队列按最老到最新排序 + 创建时间列就是这个用途；我们有 `oldestReadyWait`（单值）但没有分布。

### 建议落点

- **P0**：告警中心统计条加「未发起调查」卡（后端 summary 加一个计数 + 最老 firstSeen）+ 监控页同口径卡。
- **P0**：监控页加「接收积压」卡：inbox 按 InboxState 计数 + 最老滞留（新端点 `GET /api/agent-ops/inbox`，读 `alert_inbox` 聚合，零写面）。
- **P1**：`waitingReason` 前端消费——AlertsView 加 waiting 筛选 + 行内「等待中：原因」徽章；IncidentDetailView 概览显示等待原因与预计重驱时间。
- **P1**：趋势图加第三条线「未处理积压深度」（FIRING 未解决数按小时桶）；或监控页独立小图。
- **P2**：积压年龄分布直方图（监控页，数据=未处理 incident 按 episodeStartedAt 分桶）。

## 二、评测指标与可靠性机制：我们有什么、缺什么

### 指标面：已有相当完整的一套（六维评估矩阵）

| 维度 | 我们已有（`SixDimEvaluator.java`） | 业界对应 |
|------|----------------------------------|---------|
| 结果 | TP/FP/FN、根因命中率、未决率、沉默惩罚（漏报） | accuracy/precision/recall（Langfuse/Datadog eval） |
| 过程 | 工具调用数、重复等价调用数、错误调用数 | agent trajectory eval（Langfuse agent 评测、DeepEval trajectory） |
| 工具 | 注册工具数、**幻觉工具调用数**、被拒调用数 | tool hallucination / function-call accuracy |
| 成本 | 延迟、prompt/completion/total token、usage 缺失 | token/cost/latency（Langfuse、Datadog OOB 看板） |
| 协作 | claim 采纳/冲突计数 | agreement/disagreement |
| 安全 | policy 拒绝数（approval_required） | guardrail violations |

列表层另有：覆盖率、条件准确率、端到端命中、TP/FP/FN、未决率（`EvalRunsView.vue:31-42`）。**这套比多数业界产品的评测列表更细**——尤其「幻觉工具调用」「沉默惩罚」是很多商业产品都没有的硬指标。

### 可靠性机制面：已是业界 LLM Ops 高配

| 机制 | 我们的实现 | 业界对照 |
|------|-----------|---------|
| 预算控制 | 三段式账本 reserve→commit/release（`RunBudgetLedger`，V13 落库，STEP/TOOL_CALL/EVIDENCE/SUBTASK/TOKEN/REPORT 六种预算）+ `DoomLoopGuard` 防环 | budget guard / rate limiting |
| 失败处理 | lease+epoch+attempt、RETRY_WAIT 退避、DEAD 死信、FAILED_TERMINAL（任务 11 态） | retry/backoff/DLQ |
| 一致性 | 全命令幂等键 + expectedRevision 乐观并发（409 处理在前端已落） | idempotency |
| 对账 | inbox reconcile（V3）、预算滞留对账（`ReconcileBudgetGate`）、LiteLLM spend 对账（`UsageLedgerReconciler`，差异语义 PARTIAL 不猜数） | ledger reconciliation |
| 影子验证 | `Am4ShadowTrigger` + `SnapshotShadowRouter` + `EngineComparisonRecorder`（V32 引擎对比） | shadow testing |
| 渐进发布 | `CanaryRouter` 金丝雀路由 + blast-radius 止损 + 路由决策审计（V31/V35） | canary deploy |
| 发布门禁 | `QualityGate` 五分支：安全违规→簇不足→配对 CI 下界→运行门（延迟/token/错误率）→ELIGIBLE_FOR_CANARY，含统计显著性要求（配对差值置信区间、最少独立簇数） | eval gate / CI 质量门 |

**结论：机制层不缺。缺的是三样「质量语义」能力**：

1. **LLM-as-judge 自动评分**——六维全部是规则/账本判定（对得上账但判不了「结论写得对不对、报告有没有用」）。业界标配是用强模型当裁判对产出打语义分（正确性/完整性/简洁性），再用人工标注校准裁判（judge 与人的一致率）。Langfuse 的做法：evaluator 挂在 trace 上自动跑，score analytics 页同时看机器分与人工分的偏差。
2. **人工评审回路**——`EvalReviewView` 目前是建设中空态（`EvalReviewView.vue` 全文即 EmptyState）。业界（Langfuse annotation queue、Datadog evals review）都是「机器分 → 抽样进人工队列 → 人工分歧样本回流数据集」的闭环。
3. **生产持续评分 / 漂移监控**——我们的评测都在实验批（eval run）上跑；生产 RCA run 没有任何质量分。业界是在生产 trace 上抽样跑 judge + 监控分数漂移（模型/上游变了，准确度悄悄掉）。我们的 SUCCEEDED→review 桶已有人工审查锚点，缺的是把审查结果结构化成分数落库 + 趋势图。

## 三、业界评测怎么搞（调研综述）

### 3.1 评测方法四分类（Langfuse 框架，业界已收敛）

1. **人工标注**（human annotation）：最贵最准，用来做金标集 + 校准裁判；
2. **LLM-as-judge**：批量语义评分，必须用与人工标注的一致率验证过才可信（Langfuse score analytics 专门有 judge-vs-human 一致性视图）；
3. **程序化检查**（programmatic eval）：确定性断言——我们的六维全部属于这类；
4. **用户反馈**：生产 thumbs up/down——我们有 FEEDBACK 命令（`RunDetailView` 报告反馈），但没结构化成评分。

**业界共识**：四类混用——程序化打硬指标、judge 打语义分、人工抽查校准、用户反馈兜底。我们已有一、三（金标数据集 + 六维），缺二、四的闭环。

### 3.2 Agent 轨迹评测

Langfuse/DeepEval 都把 agent 评测分成：**轨迹对不对**（工具选择序列）+ **工具参数对不对** + **最终结果对不对**。我们的过程维（重复调用）+ 工具维（幻觉/拒绝）+ 结果维（TP/FN/根因命中）正好是这三层的结构化版本——这块我们与业界同构，无需追新。

### 3.3 评测进 CI/CD（发布门禁）

业界 prompt/模型变更的流水线（Langfuse「Prompt CI/CD」）：

```
prompt/模型 变更 → 数据集上跑实验 → 对照基线配对评测 → 门禁判定 → 打 label 渐进发布 → 异常秒级回滚
```

对照我们：`EvalGateRunner`（评测门禁运行器）→ `QualityGate`（配对统计门禁）→ `CanaryRouter`（渐进）→ 回滚（config bundle 回退，V35/封存锚备份机制）——**这条链我们整体已建成**（M5-M6 落地，git 台账可见），业界对标的差距只剩两点：
- 实验「从页面/CI 一键发起」——目前 `EvalView.vue:42-44` 发起评测仍是「请走命令行 eval-runner」的占位；
- 门禁结果的趋势可视化（score analytics 式）——实验列表有单点指标，没有跨批次趋势图。

## 四、提示词与 Skill 模板演进

### 4.1 Prompt 版本管理（业界主流模式：版本 + label 注册表）

Langfuse Prompt Management 的模式已成为事实标准：
- 每次修改产生不可变**版本号**；用 **label**（production / staging / latest）标记当前生效版；
- 运行时按 label 拉取（应用不内嵌 prompt 文本）；改 prompt = 提交新版本 → 在数据集上实验 → 达标后把 production label 移过去 → **回滚 = label 指回旧版本**，秒级；
- 与 Git 的取舍（Reddit/社区共识）：**逻辑参数在 Git、文案与大 prompt 在注册表**——注册表换来运行时热更与实验闭环，Git 换来 code review。两者混用最常见。

**对照我们**：prompt/配置已通过 config bundle + `configDigest`（路由 V25 四列）做了版本锚定，run 头显示 engine/config digest——版本化已解决；缺的是**注册表读面**（前端看不到「当前生产 prompt 是哪个版本、改了什么、和上版差在哪」）与**label 式热切**（现状换配置走发布流程，更安全但慢，这是可以保留的差异）。

### 4.2 Agent Skills（Anthropic 模式，正在吃掉「膨胀的 system prompt」）

Anthropic Agent Skills 的核心思想：把能力做成**文件+文件夹**（SKILL.md + 脚本 + 资源），模型按需渐进加载——取代把所有指令塞进 system prompt 的旧做法。演进：
- Skills 可由 `skill-creator` 工具生成/自迭代（agent 自己写自己的技能）；
- SRE 领域已出现技能生态：awesome-sre-skills、Claude 官方 SRE incident responder 配方；
- **HolmesGPT 已 Skills 化**（CNCF sandbox；架构拆解见腾讯云开发者文章：ReAct 多轮调查 + Skills 机制 + 评测）——与我们同赛道，其 custom prompts/playbooks 即「每个告警族一个调查技能模板」。

**对照我们**：我们的对应物是 **AgentProfile + 领域 agents**（`MetricsAgent/LogsAgent/ChangeAgent/SingleToolEvidenceAgent`）+ DAG 任务模板。业界趋势给我们的启示：
- 每个「故障族」（eval datasets 已有 families 概念，`EvalDatasetsView.vue:13-23`）配一个可独立演进**调查技能模板**（提示词+工具白名单+步骤骨架），技能模板本身带版本号进评测——这正是 prompt 演进与评测的接合点：**模板改了→数据集回归→门禁→灰度**；
- 技能模板落成文件目录（而非硬编码），与 config bundle 同轨版本化。

### 4.3 提示词回归测试

业界规则：**任何 prompt/模型/技能模板变更都必须过同一金标数据集**，且门禁看的是「与基线的配对差值」而非绝对分（我们 QualityGate 分支 3 的 CI 下界正是这个语义——已对齐业界最佳实践，这点可以自信）。

## 五、RAG（检索增强）在告警/事故领域的用法

### 5.1 业界形态

事故场景的 RAG 不是通用问答，而是**证据检索**：把 runbook、历史 postmortem、工单、变更记录做成可检索语料，调查时检索 top-k 喂给模型做 grounding。DevOps.com 的实战总结：RAG 系统把诊断时间缩短的来源是「让 LLM 基于真实 runbook/工单推理而非凭预训练记忆猜」。BigPanda/incident.io 的 similar-incidents（相似历史事故检索）是同族能力。

### 5.2 RAG 评测（RAGAS 四指标，业界事实标准）

| 指标 | 测什么 | 我们的对应物 |
|------|-------|------------|
| Faithfulness | 回答是否忠实于检索到的上下文（不编造） | **claim 的 evidence_basis 三元交割（SINGLE_SOURCE / MULTI_SOURCE_CONSISTENT / MULTI_SOURCE_CONFLICT，V17）本质就是结构化 faithfulness**——结论必须挂证据引用，无证据不立论 |
| Answer Relevancy | 回答是否切题 | 六维结果维（根因命中） |
| Context Precision | 检索的上下文有多少是真有用的 | （若引入 RAG 需新增） |
| Context Recall | 该检索到的是否都检索到了 | （同上） |

检索侧另有 MRR/NDCG/Precision@K 评测检索器本身。

### 5.3 对我们的落地建议

- 我们的 claim/evidence 体系是「检索质量的可观测面」：若引入 RAG（首选用途：**相似历史 incident + runbook 检索作为证据源**），每条检索结果以 evidence 身份进 claim 引用链，天然获得 faithfulness 审计（fabricated 引用=无 digest 可验）；
- RAG 评测不必新造指标：RAGAS 四指标映射到六维即可，检索质量（precision/recall@k）进过程维。

## 六、MCP（Model Context Protocol）

### 6.1 业界现状：三大观测平台全部官方支持

- **Grafana OSS MCP server**：LLM 客户端经 MCP 查数据源、traces、dashboard；
- **Datadog MCP server**：官方桥接「Datadog 数据 ↔ 任何支持 MCP 的 agent」，含 incident/monitor 查询；
- **PagerDuty MCP server**：官方口径「MCP 是 AI 工具接入 PagerDuty 的首选方式」，配套 Incident Responder agent 模板（分钟级搭一个值班响应 agent）；
- MCP 自身的可观测性也成体系（OpenLIT 埋点 + Grafana 社区 MCP Server Observability dashboard #25252：传输/协议/工具执行/会话健康）。

### 6.2 对我们的意义（双向）

- **对外暴露（P2，谨慎）**：把我们的查询面（incident/run/报告/评测）做成 MCP server，值班在 Claude/Cursor 里直接问「昨晚的告警处理得怎么样」——PagerDuty 同款玩法；
- **对内标准化（P1，价值更高）**：我们已有四个领域 agent（metrics/logs/change/evidence），工具接入是私有协议。把工具层收敛到 MCP 语义（工具描述/白名单/approval_required 对应 MCP 的 elicitation 权限模型）有三个收益：①工具注册表统一（工具维「注册/幻觉」判定面更干净）②未来接入第三方 MCP 工具（查 wiki/工单/runbook）零成本 ③MCP 工具调用有现成可观测方案；
- 安全红线不变：我们的 approval_required 工具闸门语义比 MCP 默认模型更严，收敛时以我们的白名单为准。
