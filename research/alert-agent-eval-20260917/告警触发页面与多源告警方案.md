# 告警触发页面与多源告警扩充方案

> 日期：2026-09-17
> 问题：现有告警场景少，能否做一个告警触发页面（每个场景对应一类告警、点击即真实产生告警供 Agent 评测）？现有告警源提供哪些场景？国内有哪些告警源？能不能改/扩？
> 输入：现有告警链路代码级摸底 + `国内告警源调研.md`

---

## 0. 一页结论

1. **触发页面不用从零做——`/drills` 故障演练体系就是现成的触发页面**（前端三页 + DrillController + DrillWorker 状态机 + 注入执行器 + incident/run 关联回填全齐），S1~S5 模板已 `execution.ready: true`。当前唯一卡点是 `app.drill.launch-enabled=false`（SAFE-04 停止/恢复链未交付的历史原因），启用=改配置+重启，但启用前必须确认 SAFE-04 是否已解封。
2. **"点击→真实告警"最省力的扩充路线是增强 drill 模板目录**，每加一个场景 = 一条 Prometheus 规则 + 一个注入执行器 + 一个 drill 模板，三件套都有现成范式可抄。
3. **多源告警建议两档建设**：真实链路档（本地起一个夜莺 n9e 做第二告警源）+ 样本回放档（按各源典型 payload 构造 POST 直发 webhook，零依赖覆盖格式差异）。
4. **纪律红线已存在，方案都遵守**：机器 bearer 不进浏览器（页面按钮必须走后端 operator 面 API 中转）；chaos- 前缀流量隔离不动；RCA_SYSTEM/Gatus 通道不进 Incident 管线不动。

## 1. 现状：我们已有哪些告警场景

现有 Prometheus 规则共 **10 条 alert**，4 个规则文件（`deploy/alert/prometheus/rules/`）：

| 类别 | 告警 | 触发方式 | 点击后多快 firing |
|---|---|---|---|
| 业务完整性（靶场 F1/F2/F3） | ArenaDuplicateOrders / ArenaIllegalTransitions / ArenaOrderStuck | chaos-admin 注入（drill S3/S4/S5） | 秒级~300s，**体验好** |
| 业务可用性（otel-demo） | FrontendHttp5xxRateHigh / 5xxRateElevated / CheckoutRpcClientErrorRateHigh | flagd 注入（drill S1/S2） | 慢——page 档 max_firing_wait 1500s，resolved 稀释 ~35min |
| SLO 烧损 | checkout（page/ticket 双档，Sloth 生成） | flagd 注入伴随 | 同上偏慢 |
| 延迟 | FrontendEventLoopP99High | 无注入器 | — |
| 资源容量 | MemoryGateTier1/2/3 | 真实压宿主机内存，无注入器 | — |
| 探测自证 | ArenaDomainProbeDown | 非场景症状 | — |

Gatus 5 个探针**永不进 Incident 管线**（INV-AM5-4），不能当触发通道。

**现有四种真实触发手段**：flagd 侧车注入、arena chaos 注入、合成告警直发 webhook（AM v4 envelope + bearer）、基础设施注入（PG 只读等）。统一驱动层三 Driver 已在 control-app eval 域。

**关键门槛**：直发新 alertname 的 webhook 会进 intake 铸 Incident，但 **run 铸造受 CanaryRouter 白名单门控**——active bundle 白名单不命中则永不铸 run。所以"任意新告警 → Agent 真的跑分析"需要白名单放行，或走 drill 链（drill 用冻结告警名，本身在场景面内）。

## 3. 方案：告警触发页面怎么做

### 3.1 第一步（P0）：解封并增强 drill 体系，而不是新造页面

`/drills` 页面已是"点击触发→真实注入→真实告警→Agent 分析→关联回填"的完整闭环。**先确认 SAFE-04（停止/恢复推进链）是否已交付**：

- 已交付 → 设 `APP_DRILL_LAUNCH_ENABLED=true` + 重启，页面立刻可用；
- 未交付 → 按 milestone-workflow 先补停止/恢复链，这是启用的前置门禁，不要绕。

### 3.2 第二步（P0）：扩编场景目录（三件套范式）

每加一个场景改三个地方，全有现成范式：

1. `deploy/alert/prometheus/rules/*.yml` 加告警规则（可附 promtool 单测，照 `arena-rules-test.yml`）
2. 注入执行器：flagd 侧车（布尔/百分比 variant）或 chaos-admin（新 faultType）或 infra 脚本
3. `eval-scenarios.yml` + `drill-templates.yml` 注册（只增不改纪律）

**按告警分类法扩编建议**（结合 P0 场景扩编结论与夜莺/awesome-prometheus-alerts 语料）：

| 分类 | 场景举例 | 注入方式 | 预期告警速度 |
|---|---|---|---|
| 资源-CPU | CPU 限流/饱和 | 靶场容器 CPU burn（chaos-admin 新 faultType 或 docker exec stress-ng） | 快 |
| 资源-内存 | 内存泄漏 OOM 临近 | 靶场内分配器 | 快 |
| 资源-磁盘 | 磁盘写满/写入失败 | tmpfs 填充 | 快 |
| 依赖-DB | 慢查询、连接池耗尽、PG 只读 | 已有 infra 注入范式（rr2124） | 快 |
| 依赖-下游 | 下游延迟注入、下游 5xx | flagd 扩展或靶场故障点 | 中 |
| 网络 | 丢包/延迟（tc netem） | 容器网络命名空间注入 | 快 |
| 配置 | 错误配置下发 | flagd 路径复用 | 中 |
| 流量 | 流量突增/骤降 | 有界流量发生器调参（TRAFFIC_ENABLED 已有） | 中 |

目标：从 5 场景 → 15~20 场景，每类至少 2 个，page/ticket 双 severity 搭配（ticket 档适合快速演示，page 档留给正式评测）。

### 3.3 第三步（P1）：多源告警——两档建设

**真实链路档**：deploy 里加一个夜莺 n9e 容器作为第二告警源，配几条中文告警规则打同一靶场指标，webhook 回调 → control-app 新增一个 `/webhooks/n9e` 适配端点（格式归一化为内部告警模型，走与 Alertmanager 相同的 intake 门禁）。这是"多源 adapter → 统一事件模型"业界标准做法的最小实现。

**样本回放档**（零依赖、见效快）：按各源真实回调格式（ARMS 的 AM 格式、腾讯云三段嵌套 JSON、华为 SMN、Grafana、夜莺、Zabbix）各准备 2~3 条**录制样本 payload**，页面按钮 → 后端 operator API → 经对应适配器归一化 → 走 intake。这层不需要真的部署各云厂商服务，就能评测 Agent 对**多源格式与字段语义差异**的鲁棒性。

### 3.4 页面形态

在 AppShell 菜单（`AppShell.vue:123` "故障演练"同级）加一个"告警场景触发"视图，或在 `/drills` 内加分类筛选。页面元素：

- 场景卡片按分类分组（资源/依赖/网络/配置/业务完整性/可用性/格式回放）
- 每卡：场景名、告警名、severity、预期 firing 时长、所需注入器状态（flagd/chaos 可达性前置检查）
- 点击 → 调 drill create API（真实场景）或回放 API（样本档）→ 跳到 drill detail 看状态机推进 → 告警 firing → Agent run → 评测结果
- **纪律**：浏览器永远持会话+CSRF（operator 角色），机器 bearer 只存服务端（DrillController:48 已明示此纪律）

### 3.5 需要新建的（清单）

| 件 | 位置 | 备注 |
|---|---|---|
| 场景扩编 ×N | rules/*.yml + chaos-admin faultType + eval-scenarios.yml + drill-templates.yml | 三件套范式 |
| 回放样本库 | control-app resources 下 `eval/webhook-samples/*.json` | 各源典型 payload |
| 多源适配端点 | `/webhooks/n9e` 等，复用 intake 门禁与 fail-closed 模式 | 参照 ControlAlertRouter 的入口判断模式 |
| 回放/触发 operator API | DrillController 扩展或同级新 controller | ROLE_OPERATOR |
| 前端视图 | alert-web/src/views + router + AppShell 菜单 | 复用 api/client.js |
| canary 白名单策略 | 回放/新场景的 run 铸造要过 CanaryRouter | 评测 bundle 白名单纳入新告警名 |

## 4. 风险与门禁

- **SAFE-04 未解封前 drill 不能启用**——这是硬前置。
- 新告警规则全部要有 promtool 单测 + 场景注册表 digest 锚定（现有纪律延续）。
- 回放档告警名加套件后缀防串场（rr 脚本已有此惯例）。
- 多源适配端点沿用现有鉴权/HMAC 模式，不开无鉴权口子。
- Alertmanager 侧无需改路由（无抑制、单 receiver），新告警不会被吞；同名同 service/severity 会归并同组，属预期行为。
