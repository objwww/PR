# 告警故障场景扩展详细设计：场景·改造·指标·数据集构造

> 日期：2026-09-17（v2：业务告警重点扩编）
> 依据：`差距分析与落地建议.md`（P0 场景扩编 / P1 对抗实体化 / P2 过程与 CI）
> 输入摸底：现有 5 场景（S1~S5）、3 故障族（F1 幂等失效 / F2 状态回跳 / F3 超时悬挂）、10 条 Prometheus 规则、eval 域双层评测链路、数据集四分区 schema（V20/V133）
> 性质：设计方案稿，落地需走 milestone-workflow（方案先行 → 人工双门禁 → 最小实现 → 部署验证）
> v2 变更：新增 I 类"业务交易链路"10 个可见场景（S16~S25）+ 2 个 HOLDOUT 业务场景（H7/H8），总量 20→33，**业务类场景占比过半**；里程碑顺序调整为业务扩编先行

---

## 1. 设计总则

### 1.1 数据集四分区语义（沿用 V20/V133 schema，不改结构）

| 分区 | 语义 | 可见性 | 用途 |
|---|---|---|---|
| **TUNING** | 调优集（非训练集——本系统零训练） | Agent 开发者可见、可反复跑 | prompt 协议、rubric、阈值调参的试验田 |
| **VALIDATION** | 验证集 | 可见，限制跑批频率 | 每次变更的回归门（配对 CI） |
| **HOLDOUT** | 测试集 | **RLS 封存，Agent/RAG 身份恒拒**（DatasetPartitionAccessTest 已有） | 从未见过的场景，只在里程碑验收时启用 |
| **REDTEAM** | 对抗集 | RLS 封存 | 注入/越权/外泄/GT 窥探 |

"测试集是从来没有见过的场景"通过**三种留出机制**保证（§6.3 详述）：结构留出（整个故障族不进调优）、参数留出（同族不同参数/目标）、组合留出（复合故障只在 HOLDOUT 出现）。

### 1.2 场景设计七要素（每个场景必须填全，缺一不入注册表）

沿用现有 `eval-scenarios.yml` 的契约纪律（GoldenScenarioRegistry 期望面残缺即拒），扩展为七要素：

1. **scenario_id / 故障族 / 分区归属**（TUNING/VALIDATION/HOLDOUT/REDTEAM + tier SMOKE/REGRESSION/EXPLORE/REDTEAM）
2. **注入实现**：driver（flagd/chaos/infra/netem/traffic）+ 参数 + 流量隔离（chaos- 前缀纪律不动）
3. **告警面**：Prometheus 规则（alertname/expr/severity/labels）+ 预期 firing/resolved 时序窗
4. **GT 结构**：expected_root_cause 三元组（component/fault_type/reason_code）+ expected_symptom_codes + **expected_evidence_checkpoints（新增，过程判定）**
5. **预期 Agent 行为**：应命中的工具序列骨架、应引用的证据源、合理拒答边界
6. **恢复判据**：注入关闭后指标回落窗口、残留检查（GT 与激活同生共死纪律延续）
7. **复杂度标注**：单根因 / 多根因 / 级联 / 间歇 / 慢变化 / 静默（用于分层报告）

### 1.3 扩编目标与业务优先原则

**5 → 33 场景**：可见分区 25 个（S1~S25），HOLDOUT 8 个（H1~H8，只列设计，不进任何调优跑批）。REDTEAM 单独 40 条（四类各 10），不在本文详表（见差距分析 P1）。

**业务告警是第一优先级**：可见 25 场景中业务类（A/B/I 三大类）占 15 个，技术类（C/D/E/F/G/H）10 个。设计逻辑——真实运维中最高价值的 RCA 不是"CPU 满了"（监控自己会说），而是**技术指标全绿但业务不一致**的场景（掉单、错账、超卖），这类场景最考 Agent 的业务语义理解，也是行业评测集（RCA-Bench 电商域）的核心难度来源。

## 2. 故障分类法（Taxonomy）

对标 RCA-Bench 28 类、AIOpsLab、夜莺/awesome-prometheus-alerts 语料，结合靶场实际可注入能力，定 **9 大类**（I 类为 v2 新增重点）：

| 大类 | 故障族 | 可见场景 | HOLDOUT 场景 | 复杂度覆盖 |
|---|---|---|---|---|
| **A 业务完整性** | 幂等失效、状态回跳、超时悬挂 | S3/S4/S5（已有） | — | 单根因 |
| **B 业务可用性/KPI** | 依赖错误率、依赖不可达、下单成功率下跌、断流 | S1/S2（已有）+ S23/S24 | — | 单根因+多因素低剂量 |
| **I 业务交易链路（重点新增）** | 掉单、支付悬挂、重复扣款、对账不平、超卖、消息丢失、消息重复消费、履约积压 | S16~S22、S25 | **H7 金额错算、H8 缓存不一致** | 单根因+并发竞态+静默业务错误 |
| C 资源耗尽 | CPU 饱和、内存泄漏、磁盘写满 | S6/S7/S8 | H2（CPU 参数留出） | 单根因+慢变化 |
| D 依赖退化 | DB 慢查询、连接池耗尽、下游延迟 | S9/S10/S11 | H3（复合双根因） | 单根因→多根因 |
| E 网络 | 丢包/延迟（netem） | S12 | H1（网络分区，整族留出） | 单根因→结构留出 |
| F 配置 | 错误配置下发 | S13 | — | 单根因 |
| G 流量异常 | 流量突增 | S14 | H4（级联传播链） | 级联 |
| H 告警元问题 | 告警风暴、间歇抖动、静默监控盲区 | S15 | H5/H6 | 多根因/间歇/静默 |

设计要点：**可见分区负责"教会"Agent 各族的诊断范式，HOLDOUT 负责考"没教过的"**——H1/H8 是整族没教过（结构留出），H2 是教过族但参数没教过（参数留出），H3/H4/H7 是教过单根因/数量差但没教过组合/金额差（组合留出），H5/H6 是元层面没教过（间歇/静默）。

## 3. 场景详细设计

### 3.0 存量场景（保留，补齐七要素）

| ID | 场景 | 注入 | 告警 | 需补 |
|---|---|---|---|---|
| S1 | paymentFailure 50%（业务错误率） | flagd paymentFailure | FrontendHttp5xxRateHigh + checkout 烧损 | 证据检查点、复杂度标注 |
| S2 | paymentUnreachable（依赖不可达） | flagd paymentUnreachable | FrontendHttp5xxRate* 族 | 同上；firing 慢（1500s）问题在 S1/S2 上标注"长窗场景"，评测编排排到最后 |
| S3 | F1 幂等失效 | chaos-admin F1 | ArenaDuplicateOrders | 证据检查点 |
| S4 | F2 状态回跳 | chaos-admin F2 | ArenaIllegalTransitions | 同上 |
| S5 | F3 超时悬挂 | chaos-admin F3 | ArenaOrderStuck | 同上 |

### 3.1 I 类：业务交易链路（重点，S16~S25）

> 这一类的共同特征：**技术指标全部正常或仅轻微异常，只有业务计数/对账指标暴露问题**。告警面全部落在业务指标上（order-arena 已有 `oa_*` 业务埋点体系，扩展即可）。Agent 必须学会"从业务曲线反推技术根因"，而不是只会查错误日志。

**S16 掉单（支付成功但订单未创建）**（TUNING）
- 故障机理：支付回调处理器故障点吞掉回调——支付侧成功、订单侧无记录。技术面无错误日志（故障点静默丢弃）
- 注入实现：FaultType 新增 F9_CALLBACK_DROP，chaos- 流量的支付回调直接丢弃并记 GT
- 告警规则（新增 `rules/arena-business.yml`）：
  - `ArenaPaymentOrderMismatch`：`increase(oa_payments_success_total[5m]) - increase(oa_orders_created_total[5m]) > 5`，page
- GT：component=order-arena/payment-callback / fault_type=business.order_lost / reason_code=F9_CALLBACK_DROP
- 证据检查点：①对比支付成功数与订单创建数**两条业务曲线**（而非查错误日志——查了也没有）②定位回调处理环节 ③量化掉单量（估计误差 ≤20% 算命中）
- 复杂度：单根因，**业务对账型告警的教学场景**（"技术指标全绿但业务不一致"范式）

**S17 支付悬挂（下单后支付未发起）**（VALIDATION）
- 故障机理：支付网关调用故障点沉默——不发起请求也不报错，订单停在"待支付"积压
- 注入实现：F10_PAYMENT_SILENT
- 告警规则：`ArenaPendingPaymentBacklog`：`oa_pending_payment_orders_current > 20`，for 5m，ticket；持续 15m 升 page
- GT：fault_type=business.payment_pending / reason_code=F10_PAYMENT_SILENT
- 证据检查点：①识别积压订单的年龄段分布 ②排除用户行为解释（对比历史同时段基线）③定位支付发起环节而非支付网关本身
- 与 S5（F3 超时悬挂）构成**鉴别对**：S5 有技术超时痕迹，S17 是沉默悬挂、无错误
- 复杂度：单根因

**S18 重复扣款**（TUNING）
- 故障机理：支付重试故障点跳过幂等检查直接重发扣款——同一订单多笔支付成功
- 注入实现：F11_DOUBLE_CHARGE
- 告警规则：`ArenaDuplicatePayments`：`oa_duplicate_payments_current > 0`，page
- GT：fault_type=business.duplicate_charge / reason_code=F11_DOUBLE_CHARGE
- 证据检查点：①**与 S3 重复订单鉴别**（S3 是订单层幂等失效，S18 是支付层幂等失效——跨层鉴别）②给出受影响订单规模 ③止损建议（冻结重试通道）
- 复杂度：单根因，跨层鉴别对

**S19 三方对账不平（数量差）**（VALIDATION）
- 故障机理：库存扣减与订单数产生偏差（F12_RECON_SKEW 注入库存侧），对账作业发现差异
- 注入实现：F12_RECON_SKEW + **对账作业**（改造点：order-arena 新增定时对账任务，产出 `oa_recon_diff_current` 指标与差异明细查询端点）
- 告警规则：`ArenaReconciliationDiff`：`abs(oa_recon_diff_current) > 0`，page
- GT：fault_type=business.reconciliation_mismatch / reason_code=F12_RECON_SKEW
- 证据检查点：①读对账差异明细（新数据源）②下钻差异类型（缺单/多单/金额差——本场景教"数量差"）③关联同时段其他告警
- 复杂度：单根因，**考多数据源关联**

**S20 库存超卖**（TUNING）
- 故障机理：库存预占故障点跳过原子扣减（check-then-act 竞态），并发下单脉冲下超卖
- 注入实现：F13_OVERSELL + 流量发生器并发脉冲配合（两个 driver 协同——评测编排支持组合注入的雏形）
- 告警规则：`ArenaOversell`：`oa_inventory_negative_total > 0`，page
- GT：fault_type=business.inventory_oversell / reason_code=F13_OVERSELL
- 证据检查点：①确认超卖事实（负库存记录）②识别竞态条件模式（与流量脉冲时间线对齐）③区分"超卖"与"库存数据错误"
- 复杂度：单根因+并发条件，**考竞态推理**

**S21 下单事件丢失（履约未触发）**（VALIDATION）
- 故障机理：消息发送故障点丢消息——订单已创建但履约/通知下游零感知，无错误日志
- 注入实现：F14_EVENT_LOST
- 告警规则：`ArenaFulfillmentGap`：`increase(oa_orders_created_total[10m]) - increase(oa_fulfillments_started_total[10m]) > 10`，ticket
- GT：fault_type=business.event_lost / reason_code=F14_EVENT_LOST
- 证据检查点：①对比上下游业务计数差 ②查消息链路（发送成功率指标）③估计丢失时间窗
- 复杂度：单根因，**无痕丢失型**

**S22 消息重复消费（重复履约）**（VALIDATION）
- 故障机理：消费端先处理后 ack、ack 故障点失败——重复履约/重复通知用户
- 注入实现：F15_DUPLICATE_CONSUME
- 告警规则：`ArenaDuplicateFulfillment`：`oa_duplicate_fulfillments_current > 0`，ticket
- GT：fault_type=business.duplicate_fulfillment / reason_code=F15_DUPLICATE_CONSUME
- 证据检查点：①识别 at-least-once 语义下的幂等缺失 ②**与 S18 重复扣款鉴别**（消息层 vs 支付层，用户体感都是"重复"，根因层不同）
- 复杂度：单根因，鉴别对

**S23 下单成功率 KPI 下跌（多因素低剂量）**（TUNING）
- 故障机理：**不注入单一技术故障**——F1 低比例（2%）+ 下游小延迟（200ms）叠加，每条技术指标单独看都不越阈，但业务成功率从 99.5% 跌到 96%
- 注入实现：复合低剂量注入（chaos F1 低比例参数 + flagd 延迟，双 driver 协同）
- 告警规则（Sloth 业务 SLO）：`ArenaOrderSuccessRateLow`：`sum(rate(oa_orders_success_total[5m])) / sum(rate(oa_orders_total[5m])) < 0.98`，page
- GT：fault_type=business.kpi_degradation / reason_code=COMPOSITE_LOW_DOSE
- 证据检查点：①从业务 KPI 反推技术贡献分解 ②识别多因素叠加 ③**避免强行归因单根因**——输出"双因素贡献拆分"才算满分，只答一个是部分命中（评分器支持部分分）
- 复杂度：**多因素低剂量**——业务 SLO 告警驱动诊断的范式教学

**S24 断流（零订单）**（VALIDATION）
- 故障机理：入口静默——流量发生器归零或入口路由失效，白天基线下 5 分钟零订单
- 注入实现：F16_INGRESS_SILENT 或 TrafficScenarioDriver 发生器归零
- 告警规则：`ArenaOrderZeroFlow`：`sum(rate(oa_orders_total[5m])) == 0`，for 5m，page
- GT：fault_type=business.zero_flow / reason_code=F16_INGRESS_SILENT
- 证据检查点：①**区分"真断流"与"指标采集断了"**（查探针自证指标 oa_domain_probe_up——这是 H6 静默场景的教学前置）②定位入口环节
- 复杂度：单根因，教学-考试对（教 S24 → 考 H6）

**S25 履约超时积压**（VALIDATION）
- 故障机理：履约作业故障点处理变慢——履约 SLA 超时订单积压，下单链路完全正常
- 注入实现：F17_FULFILL_SLOW
- 告警规则：`ArenaFulfillmentSlaBreach`：`oa_fulfillment_overdue_current > 15`，ticket
- GT：fault_type=business.fulfillment_timeout / reason_code=F17_FULFILL_SLOW
- 证据检查点：①积压趋势识别 ②定位履约环节而非下单环节（告警在业务链路下游，诱导归因错误）③SLA 影响量化
- 复杂度：单根因

### 3.2 C 类：资源耗尽

**S6 CPU 饱和（REGRESSION）**
- 故障机理：靶场容器内 CPU burn 线程占满配额，订单处理延迟上升、探针超时
- 注入实现：order-arena 新增 chaos 端点 `POST /chaos/cpu-burn/on?cores=2&durationSec=300`（FaultType F4_CPU_BURN），只对 chaos- 前缀流量所在实例生效；优先 Java 忙等线程实现（免改镜像）
- 告警规则（新增 `rules/arena-resource.yml`）：
  - `ArenaCpuSaturation`：`rate(container_cpu_cfs_throttled_seconds_total{container=~"order-arena.*"}[2m]) > 0.3`，for 1m，ticket
  - 配套症状：`ArenaOrderLatencyP99High`：`histogram_quantile(0.99, rate(oa_order_duration_seconds_bucket[3m])) > 2`，page
- GT：component=order-arena / fault_type=resource.cpu_saturation / reason_code=F4_CPU_BURN
- 证据检查点：①查询容器 CPU 指标 ②排除 DB/下游（对比查询）③定位到容器级而非代码级
- 复杂度：单根因，教学场景（"资源类先查容器指标"范式）

**S7 内存泄漏·慢变化（REGRESSION）**
- 故障机理：泄漏分配器故障点——每 chaos- 请求向静态 List 追加 1MB，堆缓慢爬升，GC 频繁、趋近 OOM；**刻意慢变化**（10~20 分钟爬升曲线），考趋势识别而非瞬时尖峰
- 注入实现：F5_MEM_LEAK，`POST /chaos/mem-leak/on?rateMbPerReq=1`
- 告警规则：`ArenaHeapGrowthAbnormal`：`deriv(jvm_memory_used_bytes{area="heap",container=~"order-arena.*"}[10m]) > 5242880`，for 5m，ticket；`ArenaGcPressureHigh`：GC 平均暂停 >0.2s，ticket
- GT：fault_type=resource.memory_leak / reason_code=F5_MEM_LEAK
- 证据检查点：①识别增长趋势 ②排除流量增长解释（对比请求率曲线）③给出泄漏速率估计
- 复杂度：慢变化（与 S6 尖峰构成同族对照组）

**S8 磁盘写满（REGRESSION）**
- 故障机理：日志狂写故障点把挂载卷写满 → 写单接口失败、写错误上升
- 注入实现：F6_DISK_FILL，`/chaos/disk-fill/on?targetMb=900`；独立 tmpfs 卷隔离，不动宿主盘
- 告警规则：`ArenaDiskUsageHigh`：`> 0.9`，page；配套 `ArenaOrderWriteErrorsHigh`
- GT：fault_type=resource.disk_full / reason_code=F6_DISK_FILL
- 证据检查点：①查磁盘指标 ②关联写错误时间线 ③区分"磁盘满"与"DB 故障"
- 复杂度：单根因

### 3.3 D 类：依赖退化

**S9 DB 慢查询（REGRESSION）**
- 故障机理：慢查询模板（pg_sleep 混合真实查询）注入 chaos- 流量订单查询路径，P99 飙升但无错误
- 注入实现：F7_DB_SLOW，DAO 层延迟代理；参数 `delayMs=1500`
- 告警规则：`ArenaDbQueryP99High`：`> 1.0s`，page；业务侧 ArenaOrderLatencyP99High 联动
- GT：component=postgres / fault_type=dependency.db_slow_query / reason_code=F7_DB_SLOW
- 证据检查点：①从业务延迟下钻 DB 层 ②排除连接池耗尽（活跃连接正常）③给出慢查询指纹
- 复杂度：单根因，根因实体跨层（DB 而非靶场应用）

**S10 DB 连接池耗尽（REGRESSION）**
- 故障机理：F8_CONN_LEAK 连接保持不释放，HikariCP 打满，新请求排队超时
- 告警规则：`ArenaDbPoolExhausted`：`active/max > 0.95`，for 2m，page
- GT：fault_type=dependency.db_pool_exhaustion / reason_code=F8_CONN_LEAK
- 证据检查点：①识别池耗尽 ②**与 S9 慢查询鉴别**（同症状不同根因，二选一必须选对）③定位泄漏调用方
- 复杂度：单根因，与 S9 构成鉴别对

**S11 下游延迟注入（EXPLORE）**
- 故障机理：flagd 新 flag `paymentLatency: "1200ms"`，checkout→payment 固定延迟，无错误率变化
- 注入实现：flagd 侧车复用，**无需新后端代码**
- 告警规则：新增 `CheckoutRpcLatencyP99High` + checkout 烧损 ticket 档
- GT：component=payment / fault_type=dependency.downstream_latency / reason_code=FLAG_PAYMENT_LATENCY
- 证据检查点：①区分延迟型与错误型退化（S1 对照）②定位 payment 而非 checkout
- 复杂度：单根因

### 3.4 E/F/G/H 类：网络、配置、流量、元问题

**S12 网络丢包/延迟（REGRESSION）**
- 注入实现：新增 `NetemScenarioDriver`（eval 域第四 Driver），docker exec 在靶场容器执行 `tc netem add loss 5% delay 200ms`；镜像需加 iproute2（改造点）
- 告警规则：`ArenaNetworkRetransmitHigh`：重传率 >2%，ticket（采集面核查后定稿）
- GT：fault_type=network.packet_loss / reason_code=NETEM_LOSS_5
- 证据检查点：①排除应用层（无错误日志）②查网络层指标 ③给出丢包率估计
- 复杂度：单根因

**S13 错误配置下发（REGRESSION）**
- 故障机理：flagd 下发"合法但错误"配置（重试=0 + 超时=50ms），下游间歇超时爆发
- 告警规则：`CheckoutTimeoutBurst`：`rate(checkout_timeouts_total[2m]) > 5`，ticket
- GT：fault_type=config.bad_rollout / reason_code=FLAG_RETRY_TIMEOUT_MISCONFIG
- 证据检查点：①关联配置变更时间线（change.query 工具，AM6 NATIVE 执行面已有此工具身份）②识别"变更即根因"模式
- 复杂度：单根因，考变更关联

**S14 流量突增（REGRESSION）**
- 故障机理：发生器调参 10 倍基线，资源逐渐饱和、延迟爬升
- 注入实现：新增 `TrafficScenarioDriver`；无新故障代码
- 告警规则：`ArenaTrafficSurge`：订单速率 >3× 基线，info→ticket 升级
- GT：fault_type=traffic.surge / reason_code=LOADGEN_X10
- 证据检查点：①确认真流量增长 ②评估容量水位 ③结论应为"容量事件"而非"故障"——**谨慎结论正面案例**（unresolvedRate 的正确用法）
- 复杂度：单根因，边界教学

**S15 告警风暴（EXPLORE，复合）**
- 故障机理：S6+S9 同时注入（CPU 饱和 + DB 慢查询独立并存），5+ 条告警同组归并
- 注入实现：chaos-admin **复合激活**（改造点：DB 约束放宽为"同 scenario 多 fault 允许"）
- GT：**双根因数组**，两个都命中才算 TP（评分器改造：三元组等值→集合匹配）
- 复杂度：多根因——可见分区唯一的复合场景，教"多根因枚举"输出格式

### 3.5 HOLDOUT 场景（从未见过——只设计，不进调优）

> 以下场景的设计进注册表，但**实例化后任何人不得在 TUNING/VALIDATION 跑批中引用**；RLS 已对 Agent/RAG 身份封存。验收时一次性启用，启用后按年度轮换（§6.3）。

**H1 网络分区（结构留出）**
- S12 只教过丢包/延迟，H1 是完全分区：`tc netem loss 100%` 或 iptables DROP 切断靶场→PG
- 表现与"DB 宕机"高度相似，考是否避免草率下"DB 故障"结论
- 复杂度：族外泛化

**H2 CPU 饱和·参数留出**
- 与 S6 同族，但目标换成 notify-app、核数不同、伴随 IO wait 升高（S6 无此特征）
- GT 的 component/reason_code 都是未见取值，考范式迁移而非背答案

**H3 双根因复合+时间诱导（组合留出）**
- DB 慢查询（S9 族）+ 流量突增（S14 族）同时独立发生，流量突增恰好早 5 分钟——诱导"流量是根因"的错误归因
- 正确结论：流量在容量水位内（非根因）+ 慢查询指纹独立存在（真根因）
- 复杂度：全测试集技术侧最难

**H4 级联传播链（组合留出）**
- payment 资源耗尽 → checkout 超时 → frontend 5xx，三条告警沿调用链传播
- GT 含**因果传播链**（对标 RCA-Bench 因果链要素）；新增**链方向判定**——把 frontend 当根因=方向性错误，比"没找到"扣分更重（评分器需支持）
- 复杂度：级联 3 跳

**H5 间歇抖动（flapping）**
- 下游延迟注入 30s on / 30s off 循环（flagd 定时翻转），告警反复 firing/resolved
- 考识别"间歇性"模式并给出"抖动源"结论，而非逐次告警分别诊断
- 复杂度：间歇——可见分区无任何间歇场景

**H6 静默监控盲区（meta 层）**
- 靶场探针失明（指标停更）+ 真实故障同时发生但**无告警产生**
- 考"评测流量异常但告警静默"时能否识别监控盲区并谨慎拒答——unresolvedRate 高压测试
- 复杂度：静默——考"知道自己不知道"

**H7 金额错算（组合留出，业务侧最难）**（v2 新增）
- 故障机理：价格计算故障点对特定商品类目折扣算错——技术指标全绿、单笔订单流程正常，**只有对账金额差暴露**
- 告警面：仅 `ArenaReconciliationDiff`（金额差类型，S19 教的是"数量差"——同族不同型，组合留出）
- GT：fault_type=business.price_miscalc / reason_code=F18_PRICE_CALC
- 考试点：从对账金额差反推计算逻辑缺陷，需要 Agent 理解"金额差→计算错误"的业务语义跳跃
- 复杂度：静默+业务逻辑缺陷，业务侧全测试集最难

**H8 缓存与 DB 不一致（结构留出）**（v2 新增）
- 故障机理：缓存失效故障点延迟双写——用户读到旧价/旧库存，下单后才发现不一致
- 可见集**无任何缓存族场景**（结构留出）；告警规则：`ArenaStaleReadTotal`：`oa_stale_read_total > 0`（业务侧埋点）
- 考试点：读写路径分离推理——写路径正常、读路径陈旧，根因在缓存一致性而非 DB
- 复杂度：结构留出+读写分离推理

### 5.1 单场景指标（全部确定性判定，零 LLM judge）

| 成本 | 延迟 / token / 调用次数 | 已有 |
| **pass^5** | 同场景 5 轮全对（E4） | 新增 |

### 5.2 聚合指标（维持冻结三指标，加分层报告）

- coverage / conditional_accuracy / end_to_end_hit_rate / unresolvedRate（`ScenarioMetrics.java:8` 公式不动）
- **分层切片**：按故障族 × 复杂度（单根因/多根因/级联/间歇/慢变化/静默）× **业务/技术大类** × 分区出报告——业务大类单独成切片是 v2 重点，单总分掩盖弱项（OpenRCA 2.0 已证明旧基准会饱和失真）
- 回归判定：配对 CI（QualityGate 分支③）不变；场景扩编后统计功效才够

### 5.3 质量门阈值（GateThresholds 版本化新增）

- 证据检查点命中率下限（REGRESSION tier ≥ 0.8 起步）
- pass^5 下限（SMOKE tier 必须 1.0）
- HOLDOUT 启用门槛：VALIDATION 全绿 + 配对 CI 过

## 6. 训练集 / 测试集 / 评测集构造

### 6.1 训练集——明确不需要

本系统是纯 LLM Agent（LiteLLM 网关 + 工具 + RAG），**零训练**。TUNING 分区是 prompt/配置/阈值的"调优集"语义，与业界一致。唯一例外预案：若未来引入训练型组件（告警压缩、告警分类），按 DyAlert/DiagFusion 惯例**按时间滑窗切分**（前段训练、后段测试）或按靶场/数据中心切分，届时单独立项。

### 6.2 评测集（TUNING + VALIDATION + REDTEAM）

- **TUNING**（9 场景）：S3/S4/S5 + **S16/S18/S20/S23（业务 4 个）** + S6/S9/S13——业务完整性、交易链路、资源、依赖、配置五族教学范式；允许反复跑、随意调 prompt
- **VALIDATION**（16 场景）：S1/S2 + **S17/S19/S21/S22/S24/S25（业务 6 个）** + S7/S8/S10/S11/S12/S14/S15——每次变更回归门；与 TUNING **同族不同形态**配对（S16 掉单 vs S17 悬挂、S18 重复扣款 vs S22 重复履约、S9 慢查询 vs S10 池耗尽、S6 尖峰 vs S7 慢变化），保证调优结论在验证集上可检验泛化
- **REDTEAM**（40 条）：注入/越权/外泄/GT 窥探四类各 10，判定全部确定性断言（隔离区落标记=pass），见差距分析 P1

### 6.3 测试集（HOLDOUT）——"从未见过"的三重保证

| 机制 | 内容 | 防泄漏手段 |
|---|---|---|
| **结构留出** | H1 网络分区、H8 缓存不一致：整族不出现在任何可见场景 | 族清单双人评审，注册表 digest 锚定 |
| **参数留出** | H2：同族（CPU 饱和）但不同目标服务、不同强度、伴随特征不同（IO wait） | GT 取值域与可见集零交集，词典（synonym-lexicon）校验 |
| **组合留出** | H3 双根因时间诱导、H4 级联、H5 间歇、H6 静默、**H7 金额差（S19 只教数量差）**：这些（族×复杂度）组合格在可见集为空 | 复杂度矩阵评审 |

**运行纪律**：
1. HOLDOUT 实例化后**任何调优跑批不得引用**（E7 令牌门 + 审计落档）
2. 每个里程碑验收**最多启用一次**；启用过的 HOLDOUT 场景降级为 VALIDATION（见过即污染），同时补设计新 HOLDOUT——**年度轮换制**（业界"基准饱和即换代"，OpenRCA 2.0 教训）
3. Agent/RAG 身份对 HOLDOUT 恒拒已有 RLS 测试（DatasetPartitionAccessTest），扩展覆盖新场景行
4. HOLDOUT 的 GT 双人双签发布（GoldenCandidateService 现有机制复用）

### 6.4 持续生长（防静态失效）

- 195 部署后的真实故障复盘 → RegressionCaseAdmissionService 回流（PENDING_REVIEW → 双签 → ACCEPTED），首批目标 3~5 例进 VALIDATION，**真实业务故障复盘优先**（业务类语料最稀缺）
- 线上影子对照 disagreement 高发模式 → 第二补给源
- 回流案例**只能进 TUNING/VALIDATION**，HOLDOUT 永远由设计产生（生产见过的就不算"从未见过"）
