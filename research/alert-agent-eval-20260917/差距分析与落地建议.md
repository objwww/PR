# 告警 Agent 评测体系：行业对照差距分析与落地建议

> 日期：2026-09-17
> 输入：本目录下两份调研（国内大厂 / 国外与学术基准）+ 对 control-app 评测链路的代码级现状摸底
> 结论性质：建议稿，落地需走 milestone-workflow（方案先行 → 人工双门禁）

---

## 0. 一页结论

项目的评测**骨架已达行业一线水准**：活体混沌注入 + 结构化 GT + 类型化根因三元组判定 + 冻结三指标 + 配对 CI 质量门 + fail-closed 纪律，这套组合与阿里 RCA-Bench、Microsoft AIOpsLab 的方法论同构，部分纪律（期望面残缺即拒、NOT_RUN 禁 PASS 占位）甚至更严。

真正的差距不在"会不会评"，而在**四个规模与覆盖问题**：

| # | 差距 | 行业对标 | 严重度 |
|---|---|---|---|
| G1 | 注入场景仅 5 个（S1~S5），故障族仅 3 个 | RCA-100：103 用例/28 类故障；AIOpsLab ~88 任务；AgenticOpsEval 503 例 | 高 |
| G2 | 外部基准适配器建好未启用（RCA-100 未授权、RCAEval 未接入） | 业界普遍用公开基准做横向锚定 | 中 |
| G3 | REDTEAM 分区是空壳；prompt 注入仅 2~3 条单测模式，无对抗用例集 | Anthropic/LangSmith 方法论；安全是四维评测的独立一层 | 高 |
| G4 | 无 CI 自动化，评测全靠人工触发脚本 | Datadog Bits AI 持续评估流水线；Production Failure → Eval Case 闭环 | 中 |
| G5 | 过程评估薄弱：不判工具轨迹，只判最终根因；六维 process 维度有计数但未进判定 | RCA-Bench 过程分占 0.30；OpenRCA 2.0 证据覆盖 Explainability | 中 |
| G6 | 线上回流机制（RegressionCaseAdmission/GoldenCandidate 双签）代码完整但**零实证案例** | "从生产失败中生长"是行业第一原则 | 高（机制空转） |

训练集问题已澄清：本项目是纯 LLM Agent（LiteLLM 网关 + 工具 + RAG），无微调环节，**不需要训练集**——TUNING 分区是"评测调优集"语义，命名与业界一致（DyAlert 等训练型方法才按时间切 train/test）。这一点不用改。

## 1. 行业实践要点（两页纸版）

### 1.1 评测集构建的两大流派

**流派 A：活环境注入（我们的路线）**
- Microsoft **AIOpsLab**：可复用故障注入框架 + Agent 评测编排，~88 个 SRE 任务，环境即评测资产。
- IBM **ITBench**：SRE Agent 评测环境，同样是注入式。
- 阿里 **RCA-Bench**：电商微服务仿真（40+ 服务）+ 四通道混沌注入，103 用例 / 28 类故障。

**流派 B：静态案例打包（回放式）**
- **OpenRCA**：335 例 / 68.5GB，真实运维数据快照。
- **RCAEval**（RE2/RE3 parquet 子集，我们的适配器目标）：735 例。
- **AgenticOpsEval**：503 例 / 15.3GB，含 per-modality key-evidence 过程标注。

业界共识：**两流派互补**。活注入验证端到端真实链路，静态包提供规模化、可复现、横向可比的锚点。OpenRCA 2.0 的关键发现——旧基准已饱和失真（SOTA Top@1 均值仅 0.21），说明基准需要持续升级换代。

### 1.2 指标体系的收敛方向

1. **确定性评分为王，LLM judge 只打辅助**：RCA-Bench 评分 O = 0.40·定界 + 0.30·定因 + 0.30·过程，其中定界/定因用 UModel 图距离**确定性规则**（占 70~82%），LLM 仅辅助过程分。我们"明确拒绝 LLM-as-judge"比阿里更激进，方向一致。
2. **过程评估权重上升**：证据点命中率（CCF AIOps 2025 占 0.10）、证据覆盖 Explainability（OpenRCA 2.0）、因果链检查点匹配。
3. **稳定性指标**：pass@k / pass^k（连续 k 次全对），衡量一致性而非单次运气。
4. **安全独立成层**：越权率、注入抵抗率、数据泄露通过率，不与功能分混算。
5. **持续评估流水线**（Datadog Bits AI 最完整）：生产反馈回流标注 → agent 辅助校验 → 刻意注入噪声快照防过拟合 → 人机对齐校准（Cohen's Kappa < 0.7 触发 rubric 修订）。

### 1.3 训练/测试划分（仅对训练型方法适用）

DyAlert / 蚂蚁 DiagFusion 惯例：**按时间滑窗切分**（前段训练、后段测试）或**按数据中心切分**（跨域泛化）。本项目零训练，不适用；但若未来引入告警压缩/分类等训练型组件，照此办理。

### 1.4 已证伪的说法

调研中"ops-lite 500 例评测集"**未通过一手核查**——公开来源中 ops-lite 仅是 OpenRCA 2.0 排行榜上的轻量评测 harness 名，"manifest 因果图 GT / 12 Parquet 表 / 三测试床"细节无法验证，按待核实材料处理，不要作为方案依据。

## 3. 落地建议（按优先级）

### P0：把已有机制"喂饱"——场景扩编（对应 G1/G6）

现状 5 场景撑不起配对 CI 统计功效，也喂不饱已建好的回流管线。

> **【M-a 已完成 2026-09-18】** 本节核心诉求"场景 5→15~20"以业务扩编先行的方式超额落地：
> 业务交易链路 10 场景（S16~S25）+ 词表/规则/注入点/恢复面/探测面全链交付，可见场景 5→15
> （总量规划 33），见 `故障场景扩展详细设计.md`（v2）与 `M-a-里程碑方案.md`（T1~T10 全 ✅，
> 双门禁达成：单测/promtool 全绿 + 十场景真栈演练闭环，证据 docs/测试证据/业务扩编M-a-20260918/）。
> 演练连带修复九处真机缺陷（详见证据文档 §二）。技术族（C/D/E/F/G/H，S6~S15）按排期 M-c 推进。

1. **故障族扩编**：在 F1/F2/F3 之外按 RCA-Bench 28 类故障挑高价值族补齐，建议优先级：
   - 资源类：CPU/内存饱和、磁盘写满（微服务 RCA 最高频族）
   - 依赖类：DB 慢查询、下游延迟注入（AIOpsLab 标配）
   - 配置类：错误配置下发（flagd 路径已有，可复用）
   - 每族 2~3 场景，目标 **5 → 15~20 场景**，走 GoldenScenarioRegistry 只增不改纪律。
2. **激活回流管线**：把 195 部署后已发生的真实评审/故障复盘（docs/ 下已有大量故障注入复审记录）按 RegressionCaseAdmissionService 的 PENDING_REVIEW → 双签 → ACCEPTED 流程走通至少 **3~5 个真实案例**，验证管线不是空转，同时积累第一批"生产生长"用例。

### P1：对抗评测集实体化（对应 G3）

- REDTEAM 分区已有 schema + RLS 隔离骨架，缺的只是**用例实体**。建议按四类构建，每类 10 条起步：
  1. **Prompt 注入**：告警 annotation/标签藏指令（中英文，复用 AlertInjectionScanner 已识别模式并扩写变体——编码变形、分段、伪合法前缀）
  2. **越权诱导**：评测流量试图触发非 `chaos-` 前缀路径、诱导 Agent 调用未授权工具
  3. **数据外泄**：诱导 Agent 在根因报告中输出 bearer token、DB 密码、其他租户数据
  4. **GT 窥探**：验证 HOLDOUT/REDTEAM 对 Agent 身份的 RLS 恒拒（已有 DatasetPartitionAccessTest，升格为对抗用例）
- 判定沿用确定性断言（隔离区落标记 = pass），不引入 LLM judge。

### P1：启用外部基准做横向锚定（对应 G2）

- **RCAEval**（RE2/RE3 parquet，735 例）：适配器已建，接入成本低——建议作为**离线回归锚点**先跑通，产出可复现的横向分。
- **RCA-100**：answer key 未授权是当前阻塞项。两条路：(a) 按官方渠道申请授权（论文作者/CCF AIOps 渠道）；(b) 不申请则保持 fail-closed 现状，不要绕过。建议先走 (a) 的同时把 RCAEval 落地。
- 注意义务：外部基准结果**只作参照不进质量门**（避免过拟合公开榜，OpenRCA 2.0 已证明榜单会饱和失真）。

### P2：过程评估补强（对应 G5）

- 现状只判"最终根因三元组 + 症状码"，六维的 process/tool 维度有计数但**未进判定**。
- 建议引入**证据检查点**机制（对标 RCA-Bench 因果链检查点 / AgenticOpsEval key-evidence）：在 eval-scenarios.yml 的每场景增加 `expected_evidence_checkpoints`（如"必须查询过 X 指标""必须检查过 Y 日志"），判定 Agent 工具轨迹是否命中关键证据，作为过程分进入 conditional_accuracy 之外的独立维度。
- 配套补 **pass^k**：同场景重复 k 次全对率（现有每场景 2 轮已有雏形，提到 k=5 并冻结公式）。

### P2：CI 自动化与持续评估节奏（对应 G4）

- 短期（不改架构）：把现有 60+ e2e 脚本中评测相关的收口为一个 `eval-regression.sh` 一键入口，部署变更后**强制人跑**（先制度后工具，符合 milestone-workflow 人工门禁）。
- 中期：评测 worker 已有轮询机制，加一个定时发起器（cron 或 CI 流水线每晚对 HOLDOUT 之外的 REGRESSION tier 跑批），结果落 EvaluationRecordV1 供 EvalCompare 次日比对。
- 线上观察面（EngineComparisonRecorder 的 disagreement 记录）定期审计，disagreement 高发的告警模式 → 走回流管线转评测用例——这是 G6 的第二补给源。

### P3（暂不做的）

- **LLM-as-a-judge**：项目刻意拒绝且行业确定性评分为主流，维持现状。
- **模型训练/微调**：零训练路线与业界 LLM Agent 实践一致，不引入训练集。
- **告警压缩比/AMI 等聚类指标**：本项目无告警分组功能，用不上。

## 4. 建议的目标指标体系（冻结候选）

| 层 | 指标 | 现状 | 目标 |
|---|---|---|---|
| 结果 | coverage / conditional_accuracy / e2e_hit_rate | 已有，冻结 | 维持，场景扩编后重算基线 |
| 结果 | pass^k（k=5） | 无 | 新增，公式冻结 |
| 过程 | 证据检查点命中率 | 无 | 新增（P2） |
| 过程 | 工具幻觉率/错误率/重复率 | 有计数未进判定 | 纳入质量门分支④阈值 |
| 效率 | 延迟/token 预算 | 已在质量门 | 维持 |
| 风险 | 注入抵抗率/越权拒绝率/外泄零发生 | 空壳 | REDTEAM 实体化后纳入（P1） |
| 回归 | 配对 CI 比较 | 已有 | 场景扩编后统计功效才够 |
| 横向 | RCAEval 离线分 | 未启用 | 参照用，不进质量门 |
