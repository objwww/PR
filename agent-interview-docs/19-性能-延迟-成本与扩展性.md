# 19-性能-延迟-成本与扩展性

> 本系列第二十篇。回答开发岗必问的三组数字题：**一次调查多长时间、花多少钱、并发扩大十倍先坏哪**——全部从代码结构推导，不编数字。
> 标注约定同前：【代码事实】/【合理推断】/【设计扩展】/【未确认】。

# 本层要解决的问题

一句话：**时延被结构钉死（步串行×模型秒级）、成本被预算钉死（六维预算+动作序段位分账）、并发被槽数钉死（预置 2）——"先坏哪"的答案是确定性的：模型网关 → 槽位 → PG → 观测层。**

# 先看一个交易告警

> 一次典型的 createOrder 调查（9 步、2 次委派批）的时延与成本结构【按代码结构推演，实测值【未确认】】：
> - **每步**：装配（毫秒，DB 读）+ 模型调用（秒级，大头）+ 工具调用（百毫秒级）+ 结算落库（毫秒）；
> - **委派批**：批裁决（毫秒）+ 子任务固定查询（秒级）+ 唤醒复判——主循环暂停一个"子任务执行窗"；
> - **报告相位**：快照冻结+黑板裁决+组装+验证——**零模型调用**；
> - **成本**：每步预留 ≥1500 token（主调用输出上限 1000）；委派查询零模型；Jev 选材/复核（若开）走独立计费口径；全部落 rca_model_call 按实际 usage 结算。
> 十倍告警量来了：先把 2 个槽占满、任务排队（SLA 排序保证重要的先查），模型网关配额吃紧→熔断/冷却→Defer 增多——**系统以"少查慢查"代替"查询风暴"**。

# 如果没有这一层会怎样

预算无账本=单次调查成本黑洞（模型幻觉循环烧钱无上限）；并发无槽位=告警风暴把模型配额瞬间打爆；无动作序段位=增强调用（Jev/压缩）与主循环的账目混在一起，成本治理无从下手。本层的一切都是"让钱和时间可计算、可封顶、可归因"。

# 代码是怎么做的

## 0. 先给我一句话

性能结构 = "步串行是骨架、委派是唯一并行、槽位是总闸"；成本结构 = "六维预算预留/实扣+动作序段位分账+usage 诚实结算"；扩展结构 = "加槽加实例水平扩、观测面给出容量旋钮"。

## 1. 业务上为什么需要这一层

见"先看一个交易告警"。Agent 服务的单位成本是传统 API 的百倍量级（token 费），时延是分钟级——**容量规划与成本核算不是运维细节，是产品设计的一部分**。

## 3. 输入和输出

本层无独立 IO——它是横切的时间/金钱计量与容量语义。

## 4. 真实代码入口

- **预算六维**：`domain/budget/BudgetKind.java`——`STEP, TOOL_CALL, EVIDENCE, SUBTASK, TOKEN, REPORT`（V13 冻结同集）；**"TIME 不在其中——固定 deadline 语义留在 RunBudget.checkDeadline，不落账本"**（:5）——预算账本与超时钟分家。
- **预算闸**：`RunBudgetGate`（多维准入）+`RunBudget.openRun`（run 开局一次落账）+`BudgetProbe/ReservationKey`（原子预留）；RcaActionGuard 固定序中"原子预留预算（TOKEN 维）→写调用记录并取得发送资格→执行→结算（usage 实扣/确证未发出 release/其余 provisional 保守占用）"（RcaActionGuard.java:24-28）。
- **动作序段位**（成本归因的身份基础）【代码事实，三个保留段互不重叠】：
  - 决策序：每步一序（两位数量级）；
  - **压缩调用：≥10^6**（ContextCompactionService.COMPACTION_ACTION_SEQ_BASE，:56-58）；
  - **Jev 调用：≥2×10^6**（JevEnhancementService.JEV_ACTION_SEQ_BASE，:60-61——"decisionSeq 每步至多两调用"）；
  - **Jev 模型重试：≥3×10^6**（MODEL_RETRY_SEQ_BASE，:62；allowModelRetry 用"该段位无已结算/未结算行"判定一次性——:68-75）。
- **Jev 增强缝**（"小模型降级/模型路由"的实锤，JevEnhancementService.java:35-52 javadoc）：jev-selector（证据选材评分）/jev-reviewer（FINAL 边界复核）两个账本角色；"每次 Jev 调用=TOKEN 维原子预留→rca_model_call PENDING 先行→发送→usage/cost 实扣，**全部计入同一次调查账目**"；费用口径"输入 inputUsdPerMillion USD/百万 token（**Jev 输出免费**，2026-09-20 官方快照），输出按 0 计但不伪称精确账单"；触发边界"run 行 jev_enabled（铸造冻结）+全局 mode≠OFF+客户端在场+池存在冗余（>EVIDENCE_LIMIT 条，JEV-07 短路）"；**"Jev 只出有类型判断，保留权在宿主代码"——保护项永远入窗、低置信不自动转删除、异常/超时一律有界回退"选材回现有窗口、复核放行本次 final，永不打断主链"**。
- **时延估算常量**：TOKEN_ESTIMATE_PER_STEP=1500（BoundedLlmRoleRunner:47）、MAX_TOKENS_PER_STEP=1000、压缩输出 SUMMARY_MAX_TOKENS=2048、Jev 候选裁剪 CANDIDATE_CLIP=600 字符、MAX_SELECTION_INPUT_TOKENS=28_000。

## 6. 一条真实调用链（一次带 Jev 的步的时延与成本分解）

```
第 7 步（Jev SELECT 开启，池冗余）：
  装配前置：jev.selectContext
    → 预算 TOKEN 预留（原子）→ rca_model_call PENDING（roleId=jev-selector,
      actionSeq=2×10^6 段）→ 发送选材评分（输入≤28k token 上限, 候选裁 600 字）
    → 实扣结算（输入计费/输出免费口径）
    → 宿主按预算选材（保护项∪选中项≤20 入窗）      [毫秒~秒级，模型]
  确定性装配（毫秒）→ 守卫六序 → 主模型调用（秒级，大头）
  → 解析 → TOOL_CALL → 工具硬 deadline 执行（百毫秒级）
  → 步末结算：两笔模型 usage 实扣 + 检查点 CAS + 账本终态   [毫秒级]
步时延 ≈ 模型(秒) × 2 + 工具(百毫秒) + DB(毫秒)
步成本 ≈ 主调用 token + Jev 输入 token（独立段位可归因）
```

## 7. 状态机

本层无状态机；容量语义的状态载体是预算账本（预留/provisional/结算/释放四态）与槽位表（空闲/占用）。**"provisional 保守占用"**是成本状态的诚实设计：模型调用发出但结果未知时，预算按保守估计占住——"确证未发出 release"，宁可暂时多占不可超卖。

## 8. 正常业务流程（串行/并行/时延归属全景——第九部分第 15 节清单）

| 问题 | 答案【代码事实+结构推断】 |
|---|---|
| 哪些步骤串行 | 主循环步间严格串行（每步依赖上步观察）；委派批与批之间串行（批次计数）；这是 ReAct 结构的固有代价 |
| 哪些可并行 | 委派子任务与主任务（WAITING 不占主循环）；多 run 之间（槽位并发）；批处理：无显式批（单步单工具），批量语义由聚合工具（logs.aggregate）承担 |

| 有没有缓存 | ✅ 证据级语义复用：MC24 同 digest 复用+payload_digest 去重（06 篇）——不是 TTL 缓存是幂等去重 |
| 有没有模型路由 | ✅ 双层：LiteLLM 上游路由（deploy 配置）+Gateway primary/fallback（熔断/冷却触发，fallback-once） |

## 9. 异常流程（过载与退化路径）

| 过载场景 | 系统行为 | 代码 |
|---|---|---|
| 告警风暴 | inbox 排队→DEFERRED 软背压→调查排队→SLA 晋升 | 02/09 |
| 模型配额紧 | G5 冷却→fallback/Defer→主循环同签名熔断→确定性 FINAL | 15 |
| 模型变慢 | 退避占 deadline→尝试级超时→RETRY_WAIT→run 硬期限 EXPIRED（灰度） | 15/14 |
| 数据源慢 | 工具背压拒绝→TIMEOUT_RETRYABLE→步级消耗 | 06 |
| Jev 拖慢主链 | "异常/超时/契约违约一律有界回退……永不打断主链" | JevEnhancementService:39-40 |
| 压缩拖慢主链 | maybeCompact 全 try-catch+"压缩是优化，有界回退" | 11 篇 |
| PG 慢 | 领取事务失败整拍放弃；收尾失败任务留 LEASED 回收接管 | 09 |

**统一模式**：辅助能力失败=降级继续；主链失败=分层重试有上限；资源耗尽=少查而不是错查。

## 10. 并发问题

指向 10 篇。本篇视角：**并发上限的三个同心圆**——全局槽数（调查并发）⊂ 模型网关配额（调用并发）⊂ 工具池容量（数据源并发）。三层各自有闸，内层先于外层饱和时逐级背压（池满拒绝→计步消耗→步数上限→任务终态）。

## 11. 崩溃恢复

指向 14 篇。成本视角一条：崩溃重做的钱=检查点之后的步数（步级）而非全任务——**预算的"预留/provisional/结算/释放"语义让崩溃时未结算的预留被回收面 release**（"确证未发出 release"），崩溃不会把预算烧成糊涂账。

## 12. 安全

成本与安全的一条交叉：**预算是拒绝服务攻击的保险丝**——恶意/异常告警诱发的大量调查被槽数+预算双重封顶；Jev/压缩等模型增强各自的段位与次数闸防止"增强功能成为成本后门"。

## 13. Agent Harness

性能与成本 100% 是 Harness 职能【代码事实】：模型对 token 无感知（无预算反馈进 prompt——预算耗尽=守卫拒绝，模型连死因都不知道）；时延优化（委派并行/压缩/复用）全是宿主决策。**"Agent 省钱"这个问题在架构上的答案：把它做成 Harness 的预算维度，而不是 prompt 里的一句"请节约"。**

## 14. 可观测性

本层的数字全部有观测出口（18 篇）：attemptLatency（按引擎分桶）、账本 usage/cost（按 roleId/段位归因——**压缩的花费、Jev 的花费、主循环的花费天然分开**）、reconcileScan 时长、槽位水位 gauge、CallTelemetry 逻辑/物理调用比（复用效率）。**"可计算"是本篇一切结论的前提，而可计算靠的是 18 篇的留痕。**

## 16. 设计取舍

**① 为什么步串行不做成并行工具扇出？**
05/16 篇已答（熔断键/结果汇总确定性/预算结算复杂度）。本篇补充成本视角：并行扇出会让"一步的预算预留"变成"一步 N 个并发预留"——TOKEN/TOOL_CALL 两维的原子预留与结算都要重设计。串行是**预算模型简单性**的前提之一——这个代价在 16 篇列过，这里是它的第二张面孔。

**② 为什么 Jev/压缩要独立段位与独立账本角色，而不混进主循环账目？**
成本治理需要归因：'这单调查为什么贵'——答案必须能拆到"主决策 X token、压缩 Y、Jev Z"。段位（≥10^6/2×10^6/3×10^6）是零迁移成本的归因方案：**用编号数学替代维度字段**。代价：actionSeq 的数值空间要预留管理（"偏差登记执行日志"）。这是 10 篇"分型不可互代"哲学在成本维的延伸。

**③ 当前方案最大的边界？**
- 一切实测值（P50/P99 时延、单调查实际成本）依赖运行数据【未确认】——本篇给出的是结构与常量；
- 槽数预置 2 是保守经验值，容量规划靠人工盯 gauge；
- Jev 输出免费的计费口径带时效（"2026-09-20 官方快照"注释自证）——定价漂移需人工跟进。

## 17. 面试背诵卡

【30 秒主答】
"性能结构三句话：时延上，主循环步与步串行，每步是大头模型秒级加工具百毫秒级，委派是唯一并行面，报告相位零模型；成本上，六维预算预留实扣加动作序段位分账——主决策、压缩、Jev 增强、Jev 重试各占一个百万段位，花费天然可归因，还有个 Jev 缝用便宜模型做证据选材和收口复核，输入计费输出免费，异常一律有界回退永不打断主链；扩展上，全局槽位是总闸默认 2，告警风暴的表现是排队加背压而不是查询风暴，扩容就是加槽加实例。如果问先坏哪：确定性的顺序是模型网关配额、槽位、PG、观测层——因为三层并发闸层层独立，内层先饱和时逐级背压。"

## 18. 这一层哪些话不能说

1. ❌ "P50 延迟 X 秒/单次成本 Y 元" → ✅ 实测值未确认——只说结构（步串行×模型秒级）与常量（1500/1000/2048）。
2. ❌ "支持并行工具调用提速" → ✅ 结构性单工具；委派是唯一并行面。
3. ❌ "小模型自动降级" → ✅ Jev 是显式的辅助模型缝（selector/reviewer 角色+独立计费），不是主模型的自动降级；主模型降级是 fallback 路由（同级替换非降智）。
4. ❌ "成本账精确到分" → ✅ usageMissing/taint+"输出按 0 计但不伪称精确账单"（注释原文）。
5. ❌ "QPS 扩十倍加机器就行" → ✅ 加槽加实例是机制，但模型配额/数据源容量是外部约束，需要整体容量评估。
6. Jev 的具体模型与价格数值【未确认——注释快照 2026-09-20】。

# 面试官追问卡

**Q1：为什么把"每步预留 1500 token"这种粗糙估算当预算单位，不按真实 token？**
考什么：预算的哲学。
30 秒答："预留的语义是'保险丝'不是'账单'——它要在**调用前**原子扣减（防超卖），而调用前只有估算可用。估算故意保守（1500 起步、中文 2 字符/token），保守的代价是偶尔少查一步，收益是永不超卖。真账靠 usage 实扣结算，两者的差在'provisional 保守占用'里显式存在。宁可预算粗而安全，不可账单细而超支。"
继续追问 1："结算多退少补吗？"——答："usage 实扣冲销预留；'确证未发出 release'全额退；其余 provisional 保守占用——三态在 RcaActionGuard javadoc 里写全了。"

**Q2：动作序段位（10^6/2×10^6/3×10^6）是不是太 hack 了？为什么不加 purpose 字段？**
考什么：方案权衡的自觉。
30 秒答："是权衡不是疏忽——代码注释自己写了'无独立 purpose 列，保留段即用途标记——偏差登记执行日志'。加字段要迁移+双写+全部账本查询改造；段位方案零迁移（唯一键天然不撞）且归因查询是一个 BETWEEN。承认两点代价：数值空间需要预留管理；可读性差（审计要查常量表）。如果重来且预算允许，purpose 列是更干净的方案——但在'零迁移'约束下段位是最优解。这种'承认 hack 并登记'的透明度本身就是工程成熟度。"
继续追问 1："段位会被用完吗？"——答："决策序两位数量级到 10^6 有十万倍裕度；Jev'每步至多两调用'——按 maxSteps 上限算远够；真不够时升 BASE 是一次版本事件（digest 漂移语义已内建）。"

**Q3：告警风暴时"少查慢查"，业务能接受吗？被挤掉的调查怎么办？**
考什么：过载语义的业务对齐。
30 秒答："接受度来自三层补偿：一，SLA 晋升保证 critical 先查（overdue 越级）；二，被 DEFERRED/WAITING_CAPABILITY 的事故有 waitingReason 显式可见+IncidentWaitingRedrive 在 backlog 回落后自动补铸——'事故不再依赖下一次告警才获得 RCA'（F24 javadoc）；三，全程排队语义是延迟不是丢失——任务在 RETRY_WAIT/READY 队列里有 deadlineAt，真排爆了有对账硬期限兜底显式 EXPIRED。过载时系统明确表达'我在延迟'而不是'我在丢弃'。"
继续追问 1："模型配额被竞品业务打满呢？"——答："G5 配额域冷却按 quotaScope 隔离——域内冷却域外不受累，这要求配额域划分与业务方一致，是部署期决策。"

**Q4：压缩和 Jev 都是"花钱买质量"的增强，怎么决定开不开？**
考什么：成本收益的治理框架。
30 秒答："同一框架三步：一是默认关（两者都默认关——注释明文）；二是收益举证责任在增强方（压缩要 MC34 三臂对照：OFF/确定性/消费；Jev 要影子模式先跑分——'SHADOW 只评分记档不改输入'）；三是灰度放量带随时回退（run 级开关铸造冻结+全局 mode）。共同原则：**增强的复杂性由增强方举证，主链的稳定性不为民调让步**——'永不打断主链'在两个服务里都写了。"
继续追问 1："开了之后怎么知道值不值？"——答："段位分账给了归因（Jev 花费独立可查），消费观测给了效果面（压缩 consumed=false 不计效果），评测面给了质量差——三者拼出 ROI。"

**Q5：如果让你重新设计容量与成本体系会改什么？**【设计扩展——设计题答案，不要说成现网实现】
考什么：REDO。
30 秒答："三处：一是把槽位从静态迁移改成'预算档位驱动'的动态槽（ConfigBundle 已经是配置资产，让槽数跟着走）；二是给每 run 加'成本软顶告警'——现在预算耗尽是硬拒绝，软顶可以在 80% 时触发降级姿态（关 Jev/停压缩）而不是直接断；三是真实 token 统计闭环（18 篇登记的专项），让预算估算从保守猜测进化为校准模型。六维预算、段位分账、槽位总闸三样骨架不动——它们让钱和时间'可计算可封顶可归因'，这三个词就是本层的全部。"

# 5 句话总结

1. **为什么需要**：Agent 服务单位成本百倍于传统 API、时延分钟级——容量与成本是产品设计的内置部分。
2. **核心机制**：步串行骨架+委派唯一并行+槽位总闸；六维预算预留实扣+动作序段位归因+Jev 便宜模型辅助缝。
3. **上下游协作**：横向读 18 篇的留痕（可计算的前提）、纵接 15 篇的背压链（五道闸层层独立）。
4. **最大风险**：实测基线缺失（结构与常量已钉、数字待跑）；Jev 计费口径时效。
5. **最大取舍**：用"串行步+保守预算+静态槽数"换"成本可封顶、时延可解释、过载可优雅"。
