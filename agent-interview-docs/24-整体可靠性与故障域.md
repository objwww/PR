# 24-整体可靠性与故障域

> 本系列第二十五篇，可靠性收官综合篇。回答一个问题：**这个系统的每个依赖挂掉时，"谁会跟着倒、谁只是降级、谁完全无感"——故障域（blast radius）矩阵，以及隐藏在架构里的可靠性分层。**
> 标注约定同前：【代码事实】/【合理推断】/【设计扩展】/【未确认】。

# 本层要解决的问题

一句话：**把"系统可靠吗"拆成"每个依赖挂了之后，接入、状态、调查、发布、评测五个能力面各自处于什么状态"——答案是分层的：接入与状态层永远活着（fail-closed 但不失效），调查层可优雅降级，评测层可以全停不伤生产。**

# 先看一个交易告警

> 想象一个"糟糕的一天"：LiteLLM 网关挂了（模型全不可用）、Loki 半死（日志查询超时）、通知渠道抖动。
> 这一天的系统行为：
> - **接入面**：完全正常——新告警照常验签、落 inbox、投影、铸 run（都不碰模型）；
> - **状态面**：完全一致——全部在 PG；
> - **调查面**：优雅降级——新调查的模型调用失败→Gateway 熔断/冷却→尝试超时→RETRY_WAIT 退避重试；在途调查步数耗尽→确定性 FINAL 诚实收口；日志工具超时→SOURCE_UNAVAILABLE 单独记因→模型换取证方向（change.diff/alert.history）→实在不行 PARTIAL 收口；
> - **发布面**：已 VALIDATED 的报告照常走赢家 CAS 发布（不依赖模型）；
> - **评测面**：全停——但它是消费方不是生产方，生产无损。
> **糟糕的一天结束**：模型恢复→退避中的任务自动重领→调查续走（检查点）——系统自愈，无人值守。

# 如果没有这一层会怎样

耦合的系统里"模型挂=全挂"：告警收不了（如果同步处理）、状态漂移（内存状态丢失）、通知重发（无 outbox）。本项目的可靠性来自一个结构性选择：**按"失败时的正确行为"切分组件边界**——每个依赖的失败模式都被写进了消费它的代码里（fail-closed/退避/换向/单任务降级），而不是写在部署文档里。

**三个结构性事实**【代码事实】：
1. **PG 是唯一硬 SPOF**——compose 单实例（16 篇），挂=全停。但"停"的语义是 fail-closed 零损失：所有状态在库，恢复即续。消除它=PG 高可用（部署决策，机制已兼容）。
2. **模型 API 是软 SPOF**——"调查不可用但系统活着"：接入/状态/发布/评测基建全部独立于模型存活。这是 17 篇"Harness 占 93%"的可靠性读法。
3. **靶场故障域隔离**——order-arena 是独立模块/独立 schema（arena.*），挂掉只影响评测演练；反过来生产故障也不会弄脏靶场。

## 5. 核心对象：降级阶梯（调查面在依赖缺失时的四级表现）

| 级 | 条件 | 行为 | 结果 |
|---|---|---|---|
| 0 全量 | 全依赖健康 | 正常循环 | CONFIRMED/PARTIAL 可能 |
| 1 缺单源 | 某数据源挂 | 模型换取证方向（DOOM_LOOP 反馈明示替代路径） | 多数仍 CONFIRMED，部分缺口进 missing_information |
| 2 缺模型 | 网关挂 | 尝试退避/RETRY_WAIT；在途步数耗尽→确定性 FINAL（零模型） | MODEL_FAILURE_UNRESOLVED/STEPS_EXHAUSTED 诚实收口 |
| 3 硬期限 | 依赖长期不恢复 | 对账面 AUTO_EXPIRE 灰度终止 | EXPIRED/FAILED+QUEUE_DEADLINE |

**"单任务失败=缺源降级 DEAD 续跑"**（NativeInvestigationExecutor javadoc :66-67）——DAG 内单点失败不炸整链，是调查面降级的微观形态。

## 6. 一条真实调用链（"糟糕的一天"的自愈时间线）

```
T0    LiteLLM 挂
T0+秒 在途模型调用失败→Gateway 分类→ breaker 计数→CIRCUIT_OPEN
      新调用快败（不触网）→主循环计步→同签名×2→确定性 FINAL
T0+分 在途任务陆续以 RETRY_WAIT/诚实 FINAL 收口；新领取的任务同样快速失败
      → run 大量 FAILED/未决收口（诚实状态+原因码）
T0+分 对账面：硬期限未到的 run 保持活跃等重试；监控面看到
      模型失败率/熔断状态/Defer 事件（18 篇观测面报警）
T+恢复 LiteLLM 回来
      → RETRY_WAIT 任务到期重领（epoch+1）→ markRunRunning→检查点续走
      → 熔断半开探针→成功→关闭
T+恢复后 系统回到级 0；期间收口的"未决报告"留档可 RERUN
自愈，无人值守；唯一的永久损失=停机窗内未完成的调查需要 RERUN（材料留档）
```

## 7. 状态机

故障域的状态视角：**每个依赖失败在系统里都映射为"状态+原因码"而不是异常日志**——模型挂=FAILED/未决收口（errorClass），数据源挂=SOURCE_UNAVAILABLE 账本行，通知挂=outbox PENDING 积压。**"故障是状态不是异常"**——所以 14 篇的看门狗能用统一的决策表处理一切故障后遗症。

## 8. 正常业务流程（故障演练视角的日常——drill 面在演练什么）

21 篇的 drill 演练的是"靶场故障→Agent 能否找到根因"；本篇的故障域是"系统自身依赖故障→系统能否优雅存活"——两者的可靠性设计同源（状态机+诚实中间态+具名收敛者），但考的对象不同（21 篇已辨析）。

## 10. 并发问题

故障域视角一条：**依赖故障下的并发安全依然成立**——PG 挂时没有并发（全停）；模型挂时任务重试靠 epoch 栅栏；数据源挂时计步重驱靠幂等键。**故障态不是并发规则的例外态**——10 篇的六族原语在降级路径上同样生效（这是"机制优先"设计的回报）。

## 11. 崩溃恢复

本篇是 14 篇的全局视角：14 篇讲"单进程死的恢复"，本篇讲"依赖死的传导与隔离"。合起来构成完整的可靠性叙事：**内部故障（进程/任务）由检查点+租约+看门狗吸收；外部故障（依赖）由降级阶梯+故障域隔离吸收；两者交界处是同一套状态机。**

## 12. 安全

故障期的安全不降级（23 篇）：审计不可达登录判负、验签失败不回落、恢复期权限更紧（FINALIZE 只对可信 PRODUCTION）。**可靠性与安全的交集原则：任何"先绕过安全把服务跑起来"的选项都不存在。**

## 13. Agent Harness

可靠性 100% 是 Harness 职能。模型故障（输出垃圾/拒绝输出/超时）被 Harness 的三层重试+负面清单+确定性 FINAL 全额吸收——**依赖的可靠性被 Harness 转译为"调查质量的分级"（CONFIRMED/PARTIAL/UNRESOLVED），而不是"系统可用性的分级"**。这是 Agent 系统可靠性设计的独特之处：最不可靠的组件（模型）被架构性地挡在了"系统可用性"的定义之外。

## 14. 可观测性

故障域的观测即 18 篇的落地应用：每类依赖故障都有专属信号（SOURCE_UNAVAILABLE 分源记因、CIRCUIT_OPEN/BREAKER_OPEN 事件、outbox 积压 gauge、对账 last_success 停摆告警）——**"糟糕的一天"里值班者看到的不是日志雪崩，而是一组精确的降级指示灯**。

## 15. 性能和成本

故障的成本结构：模型故障窗口内=调查延迟成本（可 RERUN 找回）；PG 故障=全停（但零损失）；数据源故障=单源证据缺失（质量降级）。**成本最贵的故障是"静默错误"（报了错误结论）——这正是 22 篇证据链+20 篇评测存在的理由：可靠性的终极形态不是"不坏"而是"坏了知道自己坏"。**

## 16. 设计取舍

**① 为什么 PG 是唯一 SPOF 却不引入多区域多活？**
规模决定：单机 compose 部署、调查频率分钟级——PG 单点的年可用性已远超业务需求；多活的复杂度（跨区一致性）会污染全部并发原语（10 篇的 SKIP LOCKED/条件写都假设单库）。**SPOF 是否可接受=业务 SLA 与故障损失的乘积**——告警延迟数小时的损失远小于架构复杂度引入的新故障面。诚实边界：这个取舍要随业务量重估。

**② 为什么通知走独立进程（notify-app）而不在 control-app 内？**
故障域隔离：通知渠道的外部依赖（IM/邮件网关）抖动不应影响调查主链；outbox 模式（12 篇）让"通知意愿"与"通知执行"解耦——control-app 只写意愿（事务内），notify-app 独立消费执行（at-least-once）。**把最不可控的外部依赖隔离到最外层进程。**

**③ 当前方案最大的边界？**
- PG 单实例（上述）；
- 单机 compose 部署下 control-app 自身也是单点（多实例机制已备——SKIP LOCKED+租约，部署形态【未确认】）；
- 降级阶梯的"级间切换"靠阈值与反馈环，极端抖动可能在级间震荡（熔断半开探针的抖动）——有冷却窗缓解；
- 依赖健康检测靠被动失败（调用失败才知）+gatus 主动探活（deploy 配置，细节【未确认】）。

## 17. 面试背诵卡

【30 秒主答】
"这个系统的故障域是一张传染矩阵，核心结论三条。第一，唯一硬单点是 PostgreSQL，它挂等于全停，但停的语义是零损失——所有状态在库里，恢复即续走，不丢任务不丢进度。第二，模型 API 是软单点——它挂只停调查：新任务 RETRY_WAIT 退避、在途调查步数耗尽走零模型确定性收口、已验证报告照常发布——接入、状态、发布、评测基建全部独立于模型存活，这也是 Harness 占 93% 的可靠性读法。第三，故障域有物理隔离——评测靶场是独立模块独立 schema，挂了生产无感；通知是独立进程走 outbox 积压不丢。依赖缺失时调查走四级降级阶梯：换取证方向、诚实未决收口、硬期限终止——每种故障都映射成状态加原因码，不是异常日志。一句话：坏了知道自己坏、坏了留下的是状态不是烂摊子。"

## 18. 这一层哪些话不能说

1. ❌ "系统高可用/多活" → ✅ 单机 compose+PG 单实例；机制兼容水平扩展，部署形态未升级。
2. ❌ "任何故障都能自愈" → ✅ 自愈覆盖"有界失败"（重试/检查点）；硬期限/ORPHAN/EXHAUSTED 走诚实终态+人工。
3. ❌ "模型挂了系统不受影响" → ✅ 调查面受影响（这是诚实表述）——不受影响的是接入/状态/发布面。
4. ❌ "故障演练覆盖了系统自身依赖故障" → ✅ drill 演练的是靶场故障考 Agent；系统自身依赖的混沌演练【未确认存在】——两类别混。
5. ❌ "PG 挂了也不丢数据" → ✅ PG 自身的持久性承诺（WAL）不在本系统代码内——系统承诺的是"PG 内的数据即真相"。
6. gatus 探活覆盖面/多实例部署实态【未确认】。

# 面试官追问卡

**Q1：PG 挂了"零损失"这个说法严谨吗？写入中的事务呢？**
考什么：表述的精确性。
30 秒答："严谨说法是'PG 恢复后，系统状态回到故障前的已提交视图，零系统级损失'。写入中的事务由 PG 的原子性保证（全有或全无）——比如收尾大事务被中断就是整体回滚，恢复后由预提交材料/重投/对账面重入。本系统不承诺'PG 不丢数据'（那是 PG 的 WAL 承诺），承诺的是'PG 里有的数据就是全部真相，且一切消费路径幂等'。这两个承诺叠加，把 PG 故障的恢复简化为'等它回来'。"
继续追问 1："等它回来期间业务呢？"——答："告警在 AM 侧按 503 整组重试缓冲；已入调查的按硬期限走 EXPIRED——业务连续性靠上游重试+显式终态，不靠本系统硬撑。"

**Q2：为什么说"模型挂≠系统不可用"是 Agent 架构的独特成就？传统微服务不也这样吗？**
考什么：对比中的洞察。
30 秒答："传统微服务的依赖调用是短事务——挂了重试即可，没有'进行中的长任务'。Agent 系统的核心资产是**分钟级的进行中调查**：传统思路里核心依赖挂了，进行中的任务要么全废要么挂死。本系统的成就是给了进行中任务三种体面的结局：续（检查点）、等（RETRY_WAIT）、诚实收（确定性 FINAL+缺口清单）——**不可用被转译成了质量分级而不是可用性中断**。这靠的是 05/13 篇的检查点与 15 篇的失败分类——是架构性的，不是某个组件的功能。"
继续追问 1："代价是什么？"——答："状态化：每步都要持久化推进（否则无'续'可言）——回到 13 篇的取舍：每步 1~2 次 DB 写换恢复语义。"

**Q3：如果模型 API 时好时坏（抖动），系统会抖成什么样？**
考什么：临界故障的行为推演。
30 秒答："抖动会被三层机制'整流'：网关层退避+jitter 吸收秒级抖动；同签名×2 熔断拦截分钟级确定性失败；attempt 级 RETRY_WAIT 退避吸收更长的中断。系统的外在表现是'调查变慢+部分未决收口'而不是'错误风暴'——因为每次失败的处置都是状态化的（原因码+计数），不是无记忆的重试。最怕的不是抖动是'慢而不死'（每次都超时边缘返回）——那会拖长每步时延直到步数/硬期限兜底，这也是 LIVE_BUT_STUCK（progress 滞后检测）要抓的形态。"
继续追问 1："熔断半开探针抖动呢？"——答："circuitCoolDown 冷却窗限制探针频率——最坏是恢复检测慢半拍，不会放大故障。"

**Q4：评测靶场挂了，正在跑的评测批怎么办？**
考什么：故障域隔离的细节。
30 秒答："分阶段：未注入的案例会在场景驱动/激活失败处显式失败（NOT_PERFORMED 同款诚实）；已注入观察中的案例靠超时形态收口（TIMEOUT_OR_ABSENT 单独标注——'不混入结构失败'，20 篇）；worker 本身不受影响（它不依赖靶场存活，只依赖 PG）。靶场恢复后这些案例重跑即可——评测结论的可信度由 verdict 分类保真，不会把'靶场挂'误判成'Agent 笨'。这正是三态/四类 verdict 存在的又一个理由：**故障要能从评分里洗出去**。"
继续追问 1："会不会污染历史对比？"——答："对比面（EvalCompare）按 runs 对齐，异常形态的 runs 带原因分类——治理面可以选择剔除或标注，机制支持不自动掺入。"

**Q5：如果让你重新设计可靠性体系会改什么？**【设计扩展——设计题答案，不要说成现网实现】
考什么：REDO。
30 秒答："三处：一是 PG 高可用（至少同步副本+自动故障转移）——这是唯一硬 SPOF，业务量上来后第一笔该花的钱；二是依赖健康从被动失败升级为主动探活分级（gatus 已有雏形），把'慢而不死'依赖的降级从步级消耗提前到路由级；三是给'降级阶梯'加自动档位——现在缺源换向靠模型自觉+反馈文案，我会把'源健康度'做成装配器输入（源挂了自动收窄工具白名单，省掉模型的无效尝试）。五条铁律、状态即故障、四级降级阶梯——骨架不动。"

# 这层不要乱说什么

1. 不要说"高可用"——单机部署+PG 单实例是事实。
2. 不要说"任何故障自愈"——自愈覆盖有界失败；终态+人工是设计的一部分。
3. 不要把"零损失"说成"PG 不丢数据"——系统承诺是"库内数据即真相+消费幂等"。
4. 不要把靶场故障和生产依赖故障混为一谈——故障域矩阵里是两行。
5. 不要说"降级无损失"——每级降级丢什么（15 篇）在本篇同样适用。
6. gatus 配置/多实例部署/compose 副本实态【未确认】。

# 5 句话总结

1. **为什么需要**：告警系统在坏日子被最需要——可靠性设计的目标是"坏日子正确"而不是"好日子飞快"。
2. **核心机制**：故障域传染矩阵+四级降级阶梯+"故障是状态不是异常"+快慢双循环恢复。
3. **上下游协作**：对内吸收模型不可靠（转译为质量分级）；对外隔离靶场/通知（故障域物理切割）。
4. **最大风险**：PG 单实例；"慢而不死"依赖的临界抖动；静默错误（靠证据链与评测对冲）。
5. **最大取舍**：用"一切状态落库+一切消费幂等"的架构税，换"任何依赖故障都有具名的、有界的、可恢复的行为"。
