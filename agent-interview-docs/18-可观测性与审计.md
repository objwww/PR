# 18-可观测性与审计

> 本系列第十九篇。回答可观测性的终极问题：**凌晨三点出了问题，工程师怎么把"一次 Agent 调查"从告警进来到报告发出去，一步一步从头串到尾——每一步谁决策的、凭什么决策的、花了多少钱、谁批准的。**
> 标注约定同前：【代码事实】/【合理推断】/【设计扩展】/【未确认】。

# 本层要解决的问题

一句话：**每一次调查天然携带一条 ID 链（inbox→incident→run→task→attempt→callSeq→operation），每个动作在三个面留痕（状态行/账本行/事件链），决策携带溯源块（什么版本什么策略什么模型）——排障=按 ID 链 join，审计=按事件链回放，事后问责=按 provenance 回答。**

# 先看一个交易告警

> 早上九点，有人质疑："昨晚 INC-2024 说 order-service 根因是支付网关超时——这个结论怎么来的？谁批准发的报告？"
> 工程师五步作答：
> 1. 按 incidentKey 找到 incident 行 → currentRcaRunId → run 行（generation、purpose、路由四列——**用的哪个引擎、哪份配置，行上有锚**）；
> 2. 按 runId 拉任务与 attempt——主任务谁领的、租约 epoch 几、耗时多少；
> 3. 按 runId 拉模型账本（rca_model_call）——第几序调用、**实际模型是什么**（actualModel，不是配置里写的）、usage/cost 多少、输入快照 digest 几；
> 4. 按工具明细 API（trace-details）——每次工具调用的参数摘要/返回摘要/证据引用/**拒因原文**（BA-190）；
> 5. 按 runId 回放事件链（per-run seq 连续单调+哈希链验链）——每步决策与状态迁移的顺序事实，附 provenance 块（agentBuildSha/policyVersion/promptVersion/modelId）。
> 结论可信的底线：**事件链哈希校验通过（brokenAtSeq=-1）**——这条调查的历史没有被改过。

# 如果没有这一层会怎样

1. **排障退化成考古**：没有 ID 链与账本，"为什么这次调查查了 40 步还没收口"要靠翻散落日志猜。
2. **成本说不清**：Agent 的 token 花费没有账本就是黑箱——本项目 rca_model_call 带 usage/cost（V128 定价表+V129 回填），且"usage 缺失不猜零（SUCCESS + usageMissing，费用未决走对账）"（RcaModelGateway.java:34-35）。
3. **结论不可问责**：报告说根因是 X，半年后没人能回答"当时凭什么"——provenance 块的存在理由（DecisionProvenance.java:9："半年后可回答'INC-xxx 为什么对 xxx 执行了 xxx'"）。

# 代码是怎么做的

## 0. 先给我一句话

可观测性 = **三面留痕**（状态行=现在、账本行=每次动作、事件链=顺序事实）+ **一个溯源块**（决策的版本身份）+ **一组封闭指标**（无 UUID 标签的聚合面）——三层粒度从"现在什么样"到"为什么是这样"再到"总体趋势"。

## 1. 业务上为什么需要这一层

Agent 系统的排障比传统服务难一层：失败不一定是 bug，可能是"模型这次没想明白"——**没有轨迹与账本，无法区分"系统坏了"和"模型笨了"**，而两者的处置完全不同（前者修代码，后者改 prompt/评测回归）。

## 3. 输入和输出

- **收到**：各写入点的动作事实（带 ID 链）。
- **处理**：三面分流——状态行覆盖式（现在的真相）、账本 append（动作的真相）、事件 append（顺序的真相，双提交语义）。
- **产出**：可 join 的行、可回放的事件流（per-run seq 游标）、可聚合的指标、可验链的哈希。

## 4. 真实代码入口

- **事件账本**：`alert/domain/event/RcaEventAppender.java`（61 行端口）【代码事实】：
  - 双提交语义（M4-11）：`append`=**状态事实**（join 调用方事务，"状态回滚则事件一并回滚"）；`appendIndependent`=**进度事件**（REQUIRES_NEW，"调用方回滚不影响已提交事件"）；
  - 幂等（M4-10）：同 (run_id, event_id) 同 payload digest 重放=幂等返回既有 seq；digest 不同=**冲突显式报错（禁静默 no-op）**；
  - seq：锁 run 行→seq+1→插入同短事务——"同 run 并发追加串行化，seq 连续单调无倒退"；seq 就是 SSE/回放游标；
  - **哈希链验链**（PA-A2/V112）：同 run 全链重算比对；NULL 哈希行（legacy）视为链段边界；**声明口径原文**："tamper-evident **under the assumed DB write boundary**（评审 R9：同库管理员可整链重算；外部 WORM 锚另立增量）"——防篡改能力的诚实边界：防的是"悄悄改"，不防"有权限的重写整链"；
  - append-only："实现不得提供改/删"。
- **溯源块**：`domain/event/DecisionProvenance.java`（PA-A5）——八字段（agentBuildSha/policyVersion/promptVersion/modelProvider/modelId/toolName/toolVersion/toolSchemaHash）；"全字段可选；canonical 键序固定（审计比对面）；**不含任何载荷内容/密钥**（只含身份与版本锚）"；模型面 provenance 由 rca_model_call 行自带（role/version/digest/promptDigest/**actualModel**/routeId）。
- **指标面**：`infrastructure/observability/AlertMetrics.java`（157 行，方法即指标清单）：taskDecision(decision,engine)/attemptFinished(validationStatus,engine)/attemptLatency/engineComparison/fallbackDecision/reconcileScan(channel,success,duration)/reconcileScanSucceeded/reconcileScanObserved(最老活跃年龄,终态下未了断任务)/reconcileDecision/cancelToQuiesce/lateCommitRejected/unknownAction——**"decision 标签为封闭枚举，无 UUID 标签"**（防指标基数爆炸，Orchestrator:305）；gauge 读失败保持上一拍（"假造 0 比缺数更危险"，14 篇）。
- **Trace 查询面**：`interfaces/TraceDetailController.java`（:36-65）——`/api/rca-runs/{runId}/trace-details` 十字段（invocationId/taskId/toolName/callSeq/scopeSummary/resultSummary/evidenceRef/evidenceType/evidenceSource/**reasonDetail**）；"读侧真账本直出（rca_tool_invocation LEFT JOIN rca_evidence），**零造数**"；与 /trace 瀑布（RunQueryService，18 字段契约）配套。

## 7. 状态机

可观测层无自身状态机；它消费的是全部状态机的迁移产物。唯一相关机制：事件的双提交语义让"状态与事件"保持两种一致性——**状态事实与状态同生共死（append），进度事件独立存活（appendIndependent）**——回放时能区分"发生过"和"生效过"。

## 10. 并发问题

1. **同 run 并发追加事件？** 锁 run 行→seq+1→插入同短事务——seq 连续单调无倒退（回放游标的正确性基础）。
2. **事件幂等与并发重放？** (run_id,event_id)+digest 双键幂等——恢复重驱重投同事件=幂等返回既有 seq。
3. **指标基数控制？** 封闭枚举标签+"无 UUID 标签"（run 维度计数合并上报，如 unknownAction）——防 Prometheus 基数爆炸是硬纪律。

## 11. 崩溃恢复

可观测与恢复互为支撑：恢复面的每一步决策（14 篇 11 类）都产生事件与指标；反过来可观测三面是恢复的输入（中间态扫描读状态行，分诊读账本，审计读事件链）。**没有三面留痕，14 篇的看门狗就是盲人**——可观测性在这是恢复的前置条件，不是附加品。

## 12. 安全

1. **审计三问的落点**：谁（auth_event/决策人/机器审批显式身份）、干了什么（事件链+账本）、凭什么的版本（provenance 块）。
2. **防篡改的诚实边界**（R9 口径）：哈希链防"悄悄改"，同库管理员可整链重算——外部 WORM 锚是登记过的增量，不是已有能力。
3. **观测数据的安全分级**：provenance"不含载荷内容/密钥"；模型输入存档含脱敏 prompt；指标无 UUID 高基数标签（防基数攻击/信息泄漏双重动机）。
4. **为什么不能只在 Prompt 里要求模型"如实报告自己的行为"？** 模型的自述不可信——行为审计的每一行都来自 Harness 的账本（它执行时被强制落账），不是模型的自我汇报。

## 13. Agent Harness

可观测是 Harness 的记账面（17 篇三分法）。与模型的关系：**模型无法绕过留痕**——它的每次调用先写账本才有发送资格（"账本不可写=零触网"）、它的每个工具调用 PENDING 先行、它的每步推进过围栏留审计槽。**留痕不是义务是资格**：不记账，就没有下一步。

## 14. 可观测性（元层面——观测自身的观测）

- 看门狗停摆告警（last_success 连续不增长）；
- 对账扫描双通道成功率/时长指标；
- 消费观测（压缩是否真被消费——"consumed=false 不得计入摘要消费后效果"）；
- 陈旧自拒日志（WorkerSchemaFreshnessGuard 状态翻转落，不刷屏）。
**系统假设观测本身会坏——每条观测都有"坏了长什么样"的定义。**

## 15. 性能和成本

- 留痕成本：每步 2~4 行账本+按需事件——单行 insert，与主流程同事务或独立短事务；
- 存储成本：事件/账本随调查数线性增长，分区（V28）+归档（V29）承接；
- 查询成本：Trace 瀑布/明细是索引 join（LEFT JOIN 账本）——运营查询与写路径无锁竞争；
- **QPS×10**【合理推断】：留痕写入随调查数线性，PG 写入在模型网关之后；指标侧无 UUID 标签保证基数恒定——观测层不是瓶颈。

## 16. 设计取舍

**① 为什么三面留痕（状态行/账本/事件链）而不是一套日志系统？**
三者回答不同问题且一致性要求不同：状态行要"事务一致"（与业务同生死）；账本要"资格一致"（PENDING 先行是发送资格）；事件要"顺序一致"（seq 游标）+双语义（状态事实/进度事件）。统一进日志会丢掉事务语义；统一进状态表会撑爆行。**按一致性需求分流存储，而不是按数据类型。**

**② 为什么指标标签禁止 UUID？**
Orchestrator:305 注释"无 UUID 标签"——UUID 标签让指标基数随调查数无限增长（Prometheus 内存与查询雪崩）。聚合维度用封闭枚举（decision/engine/decision 类别），个体事实去账本查——**聚合面与事实面分家，是指标系统的生存纪律**。

**③ 当前方案最大的边界？**
- 哈希链的防篡改边界（同库管理员可重算——外部 WORM 是登记的增量非现状）；
- 真实发送面 token 统计未闭环（11 篇"length/2 近似不能证明总输入下降"——专项待做）；
- Trace 瀑布 18 字段契约+明细 10 字段是两张皮（前端按 invocationId 关联）——查询体验有拼装成本。

## 17. 面试背诵卡

【30 秒主答】
"可观测是三面留痕加一个溯源块。三面：状态行回答'现在什么样'，账本行回答'每次动作的真相'——工具调用带拒因明细、模型调用带 usage 和成本、输入原文有存档；事件链回答'按什么顺序发生的'——per-run seq 连续单调，同事务与独立短事务两种提交语义，还带哈希链防篡改。溯源块是八字段的版本身份——build 号、策略版本、prompt 版本、实际模型——半年后还能回答'这单为什么这么决策'。排障路径五步：事故 ID 定位 run、Trace 瀑布看时间轴、明细 API 看每次工具调用、模型账本看决策与成本、事件链验完整性。指标侧全部封闭枚举标签，禁止 UUID，防基数爆炸。"

## 18. 这一层哪些话不能说

1. ❌ "事件链防篡改，绝对改不了" → ✅ 诚实口径："tamper-evident under the assumed DB write boundary"——同库管理员可整链重算；WORM 是登记的增量。
2. ❌ "接了 APM/SkyWalking 全链路" → ✅ 自建三面留痕+micrometer tick span+OTel 采集，无外部 APM 依赖（deploy 有 otelcol，采样语义【未确认】）。
3. ❌ "成本统计精确" → ✅ usage_missing 诚实位+taint 规则——费用有"未决"状态，不编数。
4. ❌ "日志里什么都有" → ✅ 脱敏纪律：供应商原文不进日志、错误固定文案、provenance 无载荷无密钥——日志是脱敏面，账本是事实面。
5. ❌ "指标想加什么标签加什么" → ✅ 封闭枚举+无 UUID 是硬纪律。
6. OTel 采样率/trace 上下游传播细节【未确认】。

# 面试官追问卡

**Q1：验链发现 brokenAtSeq=37，接下来系统做什么？**
考什么：完整性事故的处置。
30 秒答："如实报告、人工介入——verifyChain 的 ChainReport 给出断链位置（brokenAtSeq）与实际校验行数，系统不会自动'修复'历史——修复篡改历史等于承认历史可重写。处理路径：按 37 之后的事件全部视为存疑，从 37 之前的最近一致点+账本行（账本有独立 digest）交叉重建事实，同时查 DB 审计面定位是谁在什么时刻改的行。这也暴露边界：同库管理员能整链重算——所以 R9 口径登记了外部 WORM 锚作为增量方向。"
继续追问 1："legacy 行的 NULL 哈希怎么处理？"——答："视为链段边界跳过校验，新段从 NULL 尾后首行起算 GENESIS——演进兼容与完整性校验并存。"

**Q2："usage 缺失不猜零"和"taint 整 attempt"，会不会让成本统计没法看？**
考什么：诚实与可用的平衡。
30 秒答："不会没法看，会'有保留地可信'。三层：单调用行带 usageMissing 诚实位；attempt 聚合时 UNKNOWN/usage_missing 行把整个 attempt 标 tainted——这一单的成本显示为'未决'而不是一个编出来的数；评测对比面把 tainted 与 clean 分开统计。看似损失了'一个总数'，换来的是'出现的数字全部可信'——成本数据的价值在可信不在齐全。对账作业（M3-25）事后把未决补齐。"
继续追问 1："负数 usage 呢？"——答："EX-58：负数不可信——按 usage_missing 落账，不进成本计算——供应商 bug 不能污染账本。"

**Q3：per-run seq 做回放游标，和 Kafka offset 比有什么优劣？**
考什么：机制对比能力。
30 秒答："相似点：都是单调游标，支持断点续传。差异三点：一是作用域——seq 是 per-run 的（每个调查独立计数），Kafka offset 是 per-partition 全局流；二是一致性语义——我们的 seq 与状态写入同事务（'状态回滚则事件一并回滚'），天然无脏事件，Kafka 的 exactly-once 要额外机制；三是生命周期——run 终态后 seq 停止，事件链封闭可验（哈希链），流式系统没有'封闭'概念。劣势也明确：吞吐上限低（每 run 串行锁）——但对'一次调查几十个事件'的规模，正确性收益远大于吞吐损失。"
继续追问 1："SSE 推送怎么用这个游标？"——答："RcaEventAppender javadoc 原话：返回值为'本事件分到的 per-run seq（SSE/回放游标）'——前端断线后带 seq 回来续传，事件幂等键保证不重不漏。"

**Q4："决策溯源块"为什么要把 agentBuildSha 都放进去？**
考什么：版本锚的完整性的推理。
30 秒答："因为'当时为什么这么做'的答案经常不在代码里，在'当时跑的是哪个版本'里。provenance 八字段是决策的全部版本语境：代码 build 号+策略版本+prompt 版本+模型+工具 schema——半年后复盘'INC-xxx 为什么拒绝了这个委派'，拿 provenance 一对：当时 policy v7 的规则就是拒 GAP 重复，v8 才放宽——**没有版本锚，规则演进会把历史行为变成不可解释的'玄学'**。纪律是只含身份与版本锚，零载荷零密钥——审计块自己不能变成泄密面。"
继续追问 1："模型面呢？"——答："rca_model_call 行自带 role/version/digest/promptDigest/actualModel/routeId——注意是 actualModel：配置说用 A，实际路由到 B，账面记 B——审计记事实不记意图。"

**Q5：如果让你重新设计可观测层会改什么？**【设计扩展——设计题答案，不要说成现网实现】
考什么：REDO。
30 秒答："三处：一是外部 WORM 锚落地（哈希链头部定期锚到对象存储+时间戳服务），把'同库管理员可重算'的边界真正关掉；二是真实 token 统计闭环（现在 length/2 近似+真实发送面统计'归后续专项'——把专项做掉，成本治理才有硬数字）；三是 Trace 瀑布与明细合并为一个查询（现在前端按 invocationId 拼两张皮）。三面留痕、双提交语义、封闭标签、溯源块这四样是骨架——尤其是'留痕是资格不是义务'这个设计，它是让审计不可绕过的根。"

# 这层不要乱说什么

1. 不要说"防篡改绝对安全"——引 R9 口径（同库管理员边界）。
2. 不要说"全链路 APM"——自建三面+tick span，无外部 APM。
3. 不要把日志和账本混为一谈——日志可丢（脱敏面），账本不可丢（事实面），事件不可改（顺序面）。
4. 不要说"成本有精确数字"——有 usageMissing/taint 诚实机制。
5. 不要说"指标维度随便加"——封闭枚举+禁 UUID 是生存纪律。
6. OTel 采样配置、RunQueryService 瀑布 18 字段清单【部分未核对】——引用机制不引用全部字段。

# 5 句话总结

1. **为什么需要**：Agent 系统必须能区分"系统坏了"和"模型笨了"，且结论要能事后问责——这要求三面留痕+版本锚。
2. **核心机制**：ID 链+状态行/账本/事件链三面（各按一致性需求分流）+provenance 八字段+封闭标签指标。
3. **上下游协作**：消费 12 篇的状态迁移与 04/06 篇的账本纪律；反哺 14 篇恢复面（扫描与分诊的输入）。
4. **最大风险**：哈希链防篡改边界（同库管理员）；token 统计未闭环。
5. **最大取舍**：用"每动作 2~4 行留痕"换"排障五步串链、审计不可绕过、账单可信有保留"。
