# 17-Agent-Harness运行脚手架

> 本系列第十八篇。综合篇：把前 16 篇讲过的全部控制代码收拢成一个概念——**Harness（运行脚手架）**——用第十五部分的 15 项清单逐项核对，并用**本项目自己的行数统计**回答"LLM 之外的部分是不是真正复杂的部分"。
> 标注约定同前：【代码事实】/【合理推断】/【设计扩展】/【未确认】。

# 本层要解决的问题

一句话：**Harness = 把"一个会输出文本的模型"变成"一个可调度、可恢复、可审计、可限权的生产 Agent"所需的全部确定性代码——在本项目里，它是模型接口代码的 15 倍以上。**

# 先看一个交易告警

> 同一个 glm-5 模型 API，两种用法：
> **用法 A**：写个循环，把告警贴给模型，让它"自己调查然后给根因"——这就是没有 Harness。它会在第 3 步开始编造指标数字，第 5 步输出散文，第 8 步宣称找到了根因。
> **用法 B**（本系统）：模型只会收到一封确定性装配的信封，只能在三选一里决策，每个工具调用过七步闸，每步进度落检查点，预算六维封顶，步数耗尽被零模型收口，报告过代码准入才能发布。
> **A 和 B 之间隔着的全部东西，就是 Harness。** 模型 API 的调用代码？全系统 836 行（0.8%）。

# 如果没有这一层会怎样

见"用法 A"。更结构化地说：没有 Harness 的 Agent 有三个不可解的问题——**不可信**（输出无法验证）、**不可续**（崩溃即从头）、**不可管**（成本与权限无边界）。Harness 的 15 项能力就是对着这三个问题逐项修建的堤坝。

# 代码是怎么做的

## 0. 先给我一句话

本项目的 Harness 是一个 10 万行的确定性系统，模型接口只是其中一个 836 行的插件位——**换模型是配置变更+评测回归，换 Harness 是重写系统语义**。

## 1. 业务上为什么需要这一层

模型 API 给的是"下一个 token 的概率分布"；业务要的是"一次根因诊断的确定性服务"。两者之间的转换器就是 Harness——它把概率产物加工成可信产物的每一道工序（解析/校验/限权/记账/恢复/收口）。

## 3. 输入和输出

Harness 无独立 IO——它是"模型请求与系统响应之间的全部翻译与执法"。

## 5. 核心对象：模型侧代码的真实体量【本篇的独家数据，方法论全文公开】

**统计口径**（`control-app/src/main/java`，2026-09-21 工作区）：
- 全部 Java：**802 文件 / 101,095 行**；
- "模型侧代码"（25 个文件：主循环、受控运行器族、装配器、压缩、决策解析、Agent 身份、检查点、模型网关、路由客户端）：**6,740 行 ≈ 6.7%**；
- 其中**真正触网+调用控制的链**（SpringAiRouteClient 236 + RcaModelGateway 204 + ModelGateway 396）：**836 行 ≈ 0.8%**。

**诚实的方法论声明**【合理推断，口径如下】：行数是粗粒度代理指标——6,740 行里的 ContextAssembler（1300 行）本身是零 LLM 的确定性装配、PrimaryClaimAdmission 是纯代码准入、PrimaryCheckpointCommitService 是并发控制——它们"面向模型"但本质是 Harness 逻辑。**所以真实的"模型专有代码"比 6.7% 还要小**；即使按最宽松口径（6.7%），Harness 也占 93% 以上。这个数字不与任何网络流传的百分比挂钩——它是本仓库行数统计的直接结论，方法论如上，可复核。

## 6. 一条真实调用链（"换一个模型"要动多少代码？——Harness 可替换性的试金石）

```
换模型 = 改 LiteLLM 路由配置（deploy/alert/litellm/config.yaml）
       + 放大 step-max-tokens（若推理模型，如 deepseek 系 reasoning token 教训）
       + 跑评测回归（eval 面：六维评分+三臂对照+红队标注）
       + Prompt 工作台调整策略 prompt（配置 Bundle 灰度）
代码改动：0 行（模型侧协议是硬契约 PROTOCOL_SUFFIX，与具体模型解耦）
风险改动：全部在评测面验证——"如果模型换了，怎么证明没退化"就是 eval 面存在的意义
反证：模型相关的翻车修复（glm-5 八步 JSON 解析失败→协议硬契约；deepseek reasoning
      token→max_tokens 配置放大）都以"配置/协议"收场，不动 Harness
```

**这就是"Harness 是系统真正复杂部分"的可操作含义：模型是插件，Harness 是宿主。**

## 7. 状态机

Harness 自身无统一状态机——它是十几台状态机（12 篇）+ 六层钟（15 篇）+ 五身份空间（10 篇）的**合集名**。本篇给"Harness 三分法"作为记忆框架【合理推断，基于代码结构】：
- **执法面**（不许做什么）：白名单/Schema/预算/权限/状态机/负面清单；
- **记账面**（做了什么必须记下来）：三账本/事件哈希链/检查点/输入存档；
- **恢复面**（坏了怎么办）：双租约回收/看门狗/四阶段分诊/灰度模式。
三个面分别回答"不可信/不可管/不可续"三问题——第 1 节的堤坝比喻的工程版。

| 阶段 | Harness 在做 | 模型在做 |
|---|---|---|
| 开局 | 预算开户/编译落图/检查点初始化 | — |
| 每步前 | 装配信封/守卫六序校验/预算预留/账本先行 | — |
| 模型调用 | 计时/熔断/降级路由/usage 结算 | 产出一个决策 JSON |

**模型在整条时间线上的"自主权"=第 3 行的一个 JSON。其余每一行都是 Harness。**

## 9. 异常流程

Harness 自身失败的处理（元问题）：
- Harness 组件 fail-fast 于装配期（注册表空/围栏缺件/执行器缺绑定——"装配缺失即启动失败，fail-closed"）；
- 运行期 Harness 异常按通道隔离（"单拍失败下拍重试""独立容错不炸主循环"——各循环的 catch 纪律）；
- Harness 决策全留痕（决策事件+封闭枚举），Harness 故障有停摆告警（14 篇 last_success）；
- **Harness 不可降级为"没有"**：围栏缺件=启动失败，不是"先跑着再说"——这是与"优化可降级"（压缩）的本质区别：**正确性组件不可降级，优化组件才可降级**。

## 10. 并发问题

指向 10 篇。Harness 视角一条：五身份空间（epoch/revision/configEpoch/decisionSeq/callSeq）是 Harness 的"并发语言"——**模型完全不知道这套语言的存在**，它只见"提交成功/被拒"。并发复杂性被 Harness 全额吸收。

## 11. 崩溃恢复

指向 14 篇。Harness 视角一条：**恢复面是 Harness 最"贵"的部分**（快回收+看门狗+分诊+灰度），而它存在的原因恰是"模型不可靠+进程会死+外部依赖会抖"三个前提——给足了这三个前提，恢复面的复杂度是下界而非过度设计。

## 12. 安全

指向 03/04 篇。Harness 视角一条：**安全是 Harness 的排他领域**——模型的一切输出在被赋予身份（digest/decisionSeq）之前不构成"行为"，而身份赋予是 Harness 的权力。**没有 Harness，"模型安全"这句话在语法上就不成立**（无法回答"谁在做什么"）。

## 13. Agent Harness 与 Evaluation Harness 的分界【第十五部分要求明确区分】

| | Agent Harness | Evaluation Harness |
|---|---|---|
| 职责 | 把模型运行成可靠 Agent | 准备场景/跑批/采轨迹/评分/对比版本 |
| 本项目载体 | control-app 的 alert+调度+持久化+审批面 | eval 包+drill 包+order-arena 靶场+arena-chaos-admin |
| 库身份 | control_app | **eval_app**（V2/V45/V93/V106/V157 授权面独立） |
| 失败语义 | fail-closed 终态 | 评分/对比/回归门 |
| 交叉点 | 质量门禁（结构验证）与评测共享判据；评测跑的是同一个 Agent Harness | 六维 sink/ScenarioDriver/GoldenCandidate（20/21 篇） |

**一句话分界**：Agent Harness 让单次调查可信；Evaluation Harness 让"一类调查的质量"可信——前者是运行时，后者是质量基建，同仓不同身份。

## 14. 可观测性

Harness 的自我观测（元可观测）：对账面 gauge+停摆告警（看门狗监督自己）、决策事件哈希链（决策不可篡改）、输入存档（模型行为可逐字节复盘）、消费观测（优化是否真被消费）。**Harness 假设自己也会出错，所以给自己也装了黑匣子**。

## 15. 性能和成本

- Harness 的运行成本：每步 2~4 次 DB 写+若干条件校验——相对模型调用（秒级+token 费）是零头的零头；
- **成本控制本身是 Harness 的职能**（预算六维/步数/批上限/缓存复用）——"Agent 成本治理"这个问题在架构上的答案就是"放进 Harness"；
- 行数统计的运维含义：93% 的代码不随模型换代重写——**模型迭代速度与系统稳定性的解耦，是这套架构最大的财务收益**【合理推断】。

## 16. 设计取舍

**① 为什么自研 Harness 而不用 LangChain/LangGraph/AutoGen？**
代码事实给了三个理由：一是本系统的核心机制（槽+任务同事务、检查点 revision CAS、账本 PENDING 先行、审批五步事务）全部是 PG 事务语义——框架的内存编排模型装不下；二是"不可自由生 Agent/禁运行时注册"的结构纪律与框架的动态性相反；三是评测驱动开发（每个机制都有对应 eval 维度）要求 Harness 完全可控。代价：自研成本（本系列 17 篇的体量）——但对"告警 RCA 这个具体业务"，这笔成本买的是完全的可审计与可恢复。

**② 为什么说"如果模型换了，怎么证明没退化"的答案是 eval 而不是 Harness 改造？**
因为 Harness 与模型的接口被压缩到一个点（决策 JSON+信封）——接口足够窄，模型替换的爆炸半径就被限制在"决策质量"内，而决策质量恰好是 eval 的测量对象。**接口窄=可测性好=可替换性**。这是 05 篇"自研协议而非框架 function calling"取舍的回报。

**③ 当前方案最大的边界？**
- 自研 Harness 的知识门槛：17 篇文档的体量本身就是边界（新人上手成本高）；
- 模型侧 6.7% 的代码里仍有模型耦合残留（PROTOCOL_SUFFIX 按模型行为调优过——协议本身有模型经验成分）；
- "行数占比"是结构性证据不是质量证明——Harness 的 93% 里也有好坏之分（本系列的"设计取舍"节就是在评这部分的好坏）。

# 面试官追问卡

**Q1：你说 93% 是 Harness——这个数字有什么用？工程决策里怎么用它？**
考什么：度量的用途意识。
30 秒答："三个用途：一是成本预估——模型迭代（换供应商/升级版本）的工程成本被限制在 6.7% 的面上+评测回归，这是可承诺给管理层的数字；二是风险定位——线上事故按'模型行为'与'系统行为'分流，模型侧问题（协议遵循/决策质量）走 prompt/配置+评测通道，Harness 问题走工程通道，不互相甩锅；三是架构演进判断——任何'引入框架重构'的提案，要证明它能替代这 93% 里的哪些机制，通常一列清单提案就自己撤回了。数字本身不重要，数字背后的'接口窄则替换易'才重要。"
继续追问 1："这 6.7% 里你最担心哪部分？"——答："协议后缀 PROTOCOL_SUFFIX——它有模型经验成分（按真实模型的失败模式调优），换模型时它是最可能需要动的'代码'。这也是为什么它的变更要过评测门。"

**Q2：Hook 这一项你说"有定向回调无通用总线"——这算达标还是缺失？**
考什么：对"能力 vs 纪律"的辨析。
30 秒答："对生产系统是达标，对通用平台是缺失——而本系统不是平台。五处定向回调（心跳探针/意图推进/审批自动 plan/摘要消费/在途取消）覆盖了实际需要的生命周期点；通用总线引入的'任何人任何时刻可挂钩子'能力，会破坏两个更重要的性质：执行路径可枚举（12 篇写点最小化）和禁运行时扩展（注册表哲学）。**缺失的能力是显式设计决策，不是遗漏**——面试时我会主动这么讲。"
继续追问 1："真需要新生命周期点怎么办？"——答："加一个具名回调接口+装配点，走代码评审与评测——和新增工具七步同律。扩展的代价是显式的，这正是要的。"

**Q3：Harness 这么厚，模型能力升级（比如长上下文百万 token）会稀释它的价值吗？**
考什么：Harness 价值的本质辨析。
30 秒答："不会，因为 Harness 修的堤坝大多与上下文长度无关：检查点/租约/恢复修的是'崩溃与并发'，审批/权限修的是'执行权'，账本/哈希链修的是'可审计'，预算修的是'成本边界'——模型窗口扩大只影响 11 篇的上下文治理那一篇的参数（窗口可以放宽），其余堤坝的原因一个都没消失。真正会被稀释的只有'因为模型记不住才需要的补偿'——而本系统的设计里这类补偿本来就少（我们从未依赖对话记忆）。相反，模型越强，'它的错误越隐蔽'，准入/评测这些 Harness 的重要性反而上升。"
继续追问 1："那模型会幻觉出合法 JSON 吗？"——答："会，幻觉一个'语法完美、语义越权'的决策恰恰是 Schema 拦不住的——这正是准入面（引用越界/降级/同源归并）存在的理由：它拦的是语义层越权，与模型多聪明无关。"

**Q4：整个系统最大的技术难点是什么？（高频总题）**
考什么：全局提炼。
30 秒答："我认为是'**有界自主**'的工程化：把一个概率组件放进确定性系统，还要求崩溃可恢复、并发安全、成本有界、行为可审计。具体到实现，最难的三个点：一是检查点提交围栏——五层防护（锁序/四元围栏/revision CAS/actionKey 幂等/审计槽）保证'任意一步崩溃重驱动从原样续走'，这是全系统恢复语义的根；二是错误两族+三层重试的边界设计——每个失败归到正确的处置层，错一层就是事故；三是把上述一切做成可评测——每个 Harness 机制都对应 eval 维度，质量门禁让行为变化可量化。模型本身反而不是难点——它是被治理的对象。"
继续追问 1："哪个设计是你自己做的？哪些是框架能力？"——答："本系统没有 Agent 框架——95 篇清单里的机制全部是仓库内代码（每篇都有文件行号），不存在'框架自带'的部分；真正外部的只有 Spring Boot/Spring AI/PG/Flyway 这些基础设施。ownership 问题的答案结构：机制设计在仓库里可指认，基础设施是公开件——这也是我把每篇都钉代码锚的原因。"

**Q5：如果让你重新设计 Harness 会改什么？**【设计扩展——设计题答案，不要说成现网实现】
考什么：REDO 收官。
30 秒答："我会改三件'工程性'的事：一是把五身份空间类型化（编译期防混用，10 篇已提）；二是给 Harness 建立自己的'冒烟评测'——现在评测针对调查质量，Harness 自身的回归靠单测+集成测试，可以补一层'混沌事件→恢复断言'的演练套件（drill 面已有雏形）；三是文档即代码——本系列 17 篇的矩阵/清单应该从代码生成骨架，防文档漂移。而'模型接口窄化''纪律集中咽喉''诚实中间态'这三个设计根基，重做一百次也保留——它们不是实现选择，是这套系统能被信任的定义。"

# 这层不要乱说什么

1. 不要引用"98% Harness"之类外部数字——引自己的：0.8%/6.7%/93%+，方法论可复核。
2. 不要说"我们用了某 Agent 框架"——自研且有行号。
3. 不要把"行数占比"说成"价值占比"——结构证据而已。
4. 不要说"模型无关"——PROTOCOL_SUFFIX 有模型经验成分（诚实边界）。
5. 不要说 Harness 能力"都齐了所以完美"——各篇取舍节列的边界依然成立。
6. 统计基于 2026-09-21 工作区，数字随代码演进漂移——引用时带时点。

# 5 句话总结

1. **为什么需要**：模型给概率分布，业务要确定性服务——中间的全部转换与执法就是 Harness。
2. **核心机制**：15 项能力（执法面/记账面/恢复面三分法）逐项落码，接口压缩到"一个决策 JSON+一封信封"。
3. **上下游协作**：上接模型（插件位 836 行），下接 PG 与外部依赖；与 Evaluation Harness 同仓不同身份。
4. **最大风险**：自研的知识门槛；协议里的模型经验残留；占比≠质量需持续评审。
5. **最大取舍**：用"十万行自研 Harness"换"模型可替换、行为可审计、崩溃可恢复"——模型迭代与系统稳定的解耦。
