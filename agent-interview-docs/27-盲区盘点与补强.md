# 三、点名七空档的两套答案（一套=项目实现可讲行号；二套=设计题/基础）

## 3.1 Memory（记忆）

**一套（项目实现，11 篇+）**：
"我们的 Memory 是'工作记忆'：四个槽——假设、已排除、缺口、反证——由宿主从检查点提案史和裁决拒绝史**确定性重建**，append-only 深冻结落 `rca_working_memory`，检查点只存 memoryId/digest 引用；'[EX]' 前缀是可信排除印记，防止污染继承。它刻意**不是**业界说的长期记忆：调查没有用户态、没有跨会话——这是设计取舍：记忆的每一条都要能溯源到账本事实，跨会话记忆做不到。"

**二套（设计题）**：
"如果要做跨会话长期记忆，我会分三类处理：情景记忆（历史调查）我们已经有了——rca_history.search 结构化过滤召回；语义记忆（runbook）走固定语料库；真正缺的是'可泛化的经验'——设计上我会从评测回归资产和人工反馈里**结构化蒸馏**（本项目 Skill 候选面就是这个方向的雏形），而不是做向量记忆库——因为无验证的记忆写入等于把幻觉固化。遗忘/降级策略用引用衰减+策展下架，不用自动删除。"

## 3.2 RAG（检索增强）

**一套（项目实现，需补强的最大盲区）**：
"我们有 RAG 工具但**刻意不做向量检索**：三个知识工具——runbook.catalog（目录检索）、runbook.fetch（按登记 id 取正文）、rca_history.search（历史判例结构化过滤）。语料库是 digest 寻址的固定语料：目录资产和文档资产走 release_asset 表，Run 构造期钉住 catalog digest——新发布不换旧引用（R07 固定快照），有效期窗排除过期条目（R03），目录缺席是 SOURCE_UNAVAILABLE 与'无匹配'分码（R12）。四条红线里最重要的一条：**RAG 结果只进 Findings 参考区——零 LLM、零策略语义，'仅参考'标记由执行器携带**。不走向量的理由：语料小而固定、digest 寻址可验证、向量召回的幻觉面进模型上下文代价太高。同族还有一个 PG tsvector 全文检索实验做历史面搜索，默认关、无迁移。"（锚：RunbookCorpusStore.java:15-32、DirectReadToolCatalog:35、HypothesisSearchService:13）

**二套（设计题）**：
"如果语料规模涨到固定目录不可维护，我会升级为混合检索：pgvector（部署已预留容器）做语义召回+关键词过滤+**rerank 后仍以 digest 寻址入库**——检索可以模糊，**入库与引用必须精确**，这样向量层的召回误差不会污染证据链。chunking 按文档小节、embedding 选型走评测（检索命中率进评测维度）、加'检索来源仅参考'标记与准入隔离。"

## 3.3 Skill（程序性技能）

**一套（项目实现，需补强的第二大盲区）**：
"Skill 是我们的程序性知识资产，全链真实存在：候选（V97 skill_candidate）→策展（SkillCuratorService/SkillCurationController）→发布进 release_manifest 的 skills 冻结允许集→run 期选择（V100 rca_run_skill_binding）。选择是**持久事实**：每 (run, role, configEpoch) 一行，SELECTED 或明确 NONE，insert-if-absent 并发取一——'重启不漂移、发布不追溯'。选择材料全来自服务端可信身份（冻结绑定 roleId/configEpoch/releaseDigest+alertname/service），双维命中 S06、冲突字典序 S07、选择器版本钉 skill-selector.v1。消费面：DEPRECATED 禁新选但不破坏老绑定，RETIRED 紧急撤销阻断后续消费，资产缺席显式 none 加告警不静默换替补。选中后以受控视图（name/assetDigest/body/steps/tools）入信封 skill 槽。与 prompt 的区别：Skill 可独立灰度、有 digest 审计、可紧急撤销——它是'资产化的 prompt 段'。"（锚：SkillSelectionService.java:26-41、ContextAssembler SkillPort:228-240）

**二套（设计题）**：
"自动蒸馏方向：成功调查的取证序列→候选 skill（现在 SkillCandidate 就是这个形态）→策展评审→灰度发布→评测对比。关键治理点：蒸馏物必须过与 prompt 同门槛的评测回归，且要有 RETIRED 紧急撤销——'技能资产的一次性下架能力'比生成能力重要。"

## 3.4 Sandbox（沙箱）

**一套（项目实现+历史）**：
"沙箱在本项目有两层含义。现状：代码取证工具 code.read/code.search 是只读沙箱面——路径 pattern 天然拒绝反斜杠与分隔符、'..' 段由执行器沙箱复判、内容脱敏加溯源块（DirectReadToolCatalog:39-40,195-196）。历史：V6__m4_sandbox 迁移和根 pom 注释证明曾有 sandbox-broker 组件（publisher-app 与 sandbox-broker 已删除，历史在 git）——对应 Holmes 外挂时代的动作执行隔离。现在高危动作的'沙箱'被更狠的东西替代了：**默认 dry-run 铁律**——真执行要解锁注册表三元匹配，未解锁时连执行通道都不存在（04 篇）。"
**二套（设计题）**：
"真执行的动作沙箱设计题：容器级（gVisor/Firecracker 微 VM+只读 rootfs+cap-drop-all+非 root——正好对应我们 deploy/policy 的 P-01~P-07 rego 族）、网络级（egress 白名单）、时间级（硬 deadline+幂等快照回滚点）。我的立场：先把 dry-run+审批+对账做到可靠，执行沙箱是它之后的能力增强。"

## 3.5 K8s

**二套（基础+迁移设计）**：
"现状如实说：单机 docker-compose，没有 K8s。但架构是'K8s-ready'的：worker 是无状态循环（状态全在 PG）、领取是 SKIP LOCKED 多实例安全、租约回收自愈、心跳可中断——上 K8s 的改造清单就四项：nonce 防重放换共享存储（02 篇登记的债）、会话外部化或粘性、CAS 文件仓换对象存储（13 篇预留）、本地 CAS 卷改 PVC/对象存储。K8s 基础题照常准备（Deployment/HPA/PDB/liveness-readiness 探针对应我们的 gatus+selfcheck）。"（锚：24 篇、02 篇登记债）

## 3.6 流式协议

**一套（项目实现）**：
"系统有两处流式：观测侧 SSE——EventSource 换票开流（30 秒单次票），事件按 per-run seq 游标断点续传，票即能力凭证（03 篇）；模型侧**刻意非流式**——决策协议要求完整 JSON，token 流式对结构化决策无意义，且'一次 complete 至多一次真实 HTTP'（I34）的账本纪律在流式下会更复杂。"（锚：SseStreamService、SpringAiRouteClient）
**二套（设计题）**：
"如果要做模型流式：推理型场景（诊断会话 v2 自由问答）适合流式输出+前端增量渲染；决策循环不适合——我们需要完整 JSON 才能解析裁决。折中方案是'流式传输+整体校验'：token 流给 UI 看进度，完整体做解析。协议上 SSE 已有 seq 游标基础，WebSocket 不必要（单向推送 SSE 足够且过代理友好）。"

## 3.7 Java/JVM 基础

**一套（项目用法）**：
"项目里 JVM 相关的实点：Java 21 虚拟线程跑四个常驻循环（`Thread.ofVirtual()`——阻塞 DB/HTTP 不占 OS 线程）；常量时间比较防时序侧信道（MessageDigest.isEqual）；ConcurrentHashMap 做nonce/票/回环计数的并发原语；虚拟线程命名可观测（rca-worker-xxx）。虚拟线程的已知风险我答得出 pinning（synchronized 长块内不卸载）——我们的循环体无长 synchronized。"（锚：RcaWorker:477、HmacFilter、09 篇）
**二套（基础知识，需另行准备）**：
"JVM 基础题清单（项目外）：G1/ZGC 选型与容器内存（-XX:MaxRAMPercentage 与 P-06 memory-limit rego 联动）、GC 日志与调优思路、JMM 可见性（volatile/final/ConcurrentHashMap 语义）、虚拟线程原理（carrier 线程/pinning/结构化并发）、类加载与元空间。这些是通用八股，与项目解耦准备。"【二套为通用知识，非项目事实】
