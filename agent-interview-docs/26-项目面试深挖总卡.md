# 一、BFS 广度主线（L0~L10 十层讲述框架）

**L0 一句话定位**
"一套交易系统线上告警的自动根因分析系统：告警进来，一个受控的多智能体去查指标、日志、变更，产出带证据链的根因报告，自动通知和开处置单——用自研 Java Harness 治理大模型，不是套框架。"

**L1 业务背景与痛点**
"交易告警原来靠人查：半夜被告警叫醒，从'哪个服务'开始人肉翻监控翻日志，MTTR 全看人醒不醒得来；告警风暴时人根本看不过来。固定脚本能做的（查固定指标套模板）又查不出真根因——因为下一步查什么取决于上一步看到了什么。"

**L2 目标、指标、约束**
"目标就三个：根因找得准（评测有冻结公式）、结论可信（证据链+裁决）、过程可控（预算/步数/审批）。硬约束：交易系统不能等、不能瞎重启、不能烧钱无上限。"

**L3 为什么用 Agent**
"穷举了流程：接入、聚合、分类、调度、发布全是确定性代码——分类器甚至明文写着不接 LLM。只有'下一步查什么'这一段真正依赖中间证据，才给模型，而且用大量确定性代码把它关在有界循环里。"

**L4 系统架构**
"六模块：控制面主应用加交易靶场加评测演练面加通知值班适配。主链路：告警 webhook→收件箱→投影聚合成事故和调查任务→Worker 双租约领取→确定性 Supervisor 落任务图→主智能体有界循环（三选一决策）→工具七步闸取证或委派确定性专家→冻结证据→黑板裁决组报告→四道栅栏收尾→赢家 CAS 发布。"

**L5 我的个人贡献**
"机制层的主体工作：有界主循环与检查点提交围栏、委派协议与裁决、工具七步闸、审批链、评测六维——每个机制在仓库里有文件行号可指认（25 篇对抗表）；骨架（AM1 状态机与收尾算法）是系列起点，我精读内化并如实区分（OWNER 诚实律）。"

**L6 测试**
"三层：单测加集成（Testcontainers）；评测面——order-arena 靶场 13 类交易语义故障注入，GT 与注入同事务封存，三维冻结公式纯函数评分加六维镜头，红队诱饵取反；演练面——相位机管理注入到恢复全生命周期。"

**L7 上线**
"灰度分三种对象：引擎灰度走 Canary 分桶（Holmes 到 NATIVE 五步替代）；优化灰度走三臂对照（压缩默认关）；能力灰度走 dry-run 铁律（真执行要解锁注册表）。Prompt 走工作台配置 Bundle。"

**L8 监控**
"三面留痕：状态行（现在）、账本（动作）、事件哈希链（顺序）；决策溯源八字段；指标封闭标签禁 UUID；排障五步串链——从 incident ID 到验链五分钟内讲清一次调查。"

**L9 结果**
"机制结果可讲：证据单字节篡改可检出、崩溃任意点 O(1) 续走、同签名失败两次熔断、R3 永远双人。运营数字（命中率/延迟/成本）【未确认——面试引结构引机制，数字说'以评测面最新跑批为准'】。"

**L10 复盘与边界**
"最大的边界：单机 PG 部署、语义级注入靠纵深、自研的知识门槛。最大的收获：把概率组件关进确定性系统的整套方法论——诚实中间态、接口窄化、对峙即人工。"

# 二、三版本项目介绍（全部口语化，可直接背）

## 30 秒版

"我做的是交易告警的自动根因分析系统。告警一进来，系统聚合成事故、自动开一次调查——调查内核是个有界的多智能体：主智能体每步只能三选一，查证据、委派专项、或者收口出结论；委派由确定性 Supervisor 裁决，工具调用过七道安全闸，所有进度落数据库检查点，崩了任意一步都能原样续走。结论要过代码准入才能变报告，发布按事故代际抢唯一赢家。整个系统十万行 Java，模型接口只占千分之八——我们自研 Harness 治理大模型，换模型零代码改动，靠评测回归保质量。"

## 2 分钟版

"项目背景是交易系统告警的人工排查太慢，固定脚本又查不出真根因——因为排查的下一步取决于上一步的观察，这个分支结构穷举不完。

系统的主线是：Alertmanager 告警打到 webhook，先过验签、尺寸、注入扫描这些入口闸，原样落收件箱就回 202；后台消费把告警聚合成事故，铸出调查任务。Worker 用槽位加任务双租约领取，执行时心跳续租。调查内核是有界的智能体循环：主智能体无状态单步驱动，状态全在数据库检查点——每步读检查点、确定性装配一封有界信封、守卫下调一次模型，输出必须是纯 JSON 三选一：调工具、委派、或者收口。工具调用过七步闸——白名单、策略二次鉴权、Schema 硬拒绝、动作摘要、风险分诊、硬超时、结果上限；只读工具直接执行，高危工具零执行只记意图转审批。委派由确定性 Supervisor 裁决，上限两批，同一个信息缺口全局只裁一次；子任务是固定查询专家，不调模型。模型要收口，结论要过代码准入：引用越界剥离、没有双源支持的根因自动降级成假设。停止也不靠模型自觉——步数耗尽、独白回环、同签名失败两次，全部走零模型调用的确定性收口。

可靠性上是双循环恢复：快回收扫过期租约，慢看门狗按十一类决策处理停滞。质量上是评测面：交易靶场注入十三类已知根因的故障，冻结公式纯函数评分，红队诱饵防作弊。整个控制面十万行 Java，模型触网代码 836 行——千分之八。"

## 5 分钟版

在 2 分钟版基础上，按面试官表情挑三段展开（每段 1 分钟）：
1. **并发与恢复**（09/14 篇）：四道栅栏收尾、双租约回收、看门狗十一类决策、LIVE_BUT_STUCK 活但卡死检测；
2. **安全与审批**（04/23 篇）：Guardian 三值、Hardline 先于一切、Grant 一次性四元绑定、默认 dry-run 铁律、注入注入三态；
3. **评测与治理**（20/21 篇）：GT 同事务封存、UNRESOLVED 不进准确率分母的激励设计、红队取反、HOLDOUT 隔离题。

# 三、高频题全集（第二十部分 36 题逐题口语化）

> 格式：**Q**｜考什么｜答（30 秒内）｜↑追问预备

## A. 为什么 Agent（3 题）

**Q1 为什么需要 Agent，不是 Workflow？**
考：架构边界。答："我们穷举过流程：接入、聚合、分类、调度、发布全是确定性代码，分类器注释明写首期不接 LLM。只有调查这一段，下一步查什么取决于上一步看到什么——日志静默就改查变更，发现下游错就追下游——这个分支穷举不完。所以判据是'输入空间能否穷举'：能穷举的全代码化，不能的才给模型，还用步数、白名单、准入把它关在有界循环里。"↑"举例"→DOOM_LOOP 反馈原文"日志静默改查 change.diff"就是活例子。

**Q2 Agent Loop 怎么实现？**
考：实现深度。答："无状态单步驱动：每步读检查点、确定性装配一封有界信封、守卫下调一次模型、剥掉 markdown 围栏后严格解析——必须恰好一个分支的纯 JSON，tool_call、delegate、final 三选一。执行完用四元围栏加 revision 条件写推进检查点。runner 本身零跨步状态，崩了重驱动从检查点原样续走，恢复和正常执行是同一条代码路。"↑"为什么不用内存循环"→崩溃零损失加多实例接管。

**Q3 怎么保证 Agent 不死循环？**
考：终止思维。答："三层互补加一个绝对上限：工具层 DoomLoopGuard——同一查询签名连续零进展就熔断那个签名；轮次层 RoleLoopGuard——连续三步不碰工具就是独白，硬停；预算加步数是绝对天花板。四条终止线——步数耗尽、独白硬停、同签名失败两次、委派批耗尽——全部走零模型调用的确定性收口，以未决加缺口清单诚实结束。"↑"为什么独白算循环"→不发起取证的步对调查零贡献。

## B. 委派与多智能体（5 题）

**Q4 什么时候直接调工具，什么时候委派？**
考：委派实质。答："委派的实质是借专家的工具白名单，不是借推理。信封里有委派余量，模型确需专业能力才提；但 question 只进审计台账不进执行面——专家按铸造时冻结的时间窗和绑定引用做固定查询。判据说白了：主任务自己的 16 个只读工具够用就直查，不够（比如要专项日志聚合）才委派。"↑"question 模型写了给谁看"→只给审计，防注入进执行面。

**Q5 Multi-Agent 为什么比单 Agent 好？增加了哪些复杂性？**
考：诚实辩证。答："先纠正：我们是'一个会推理的 Agent 加一群不推理的执行器'——子智能体不调模型。好处是单点的：大体积原始取证不进主上下文，委派产证据行回喂摘要。代价也是确定的：上下文分裂、等待窗、裁决回执复判三套机制。最关键的结构是委派树深度恒为一——PRIMARY 不接子任务，这是类型保证不是参数限制。"↑"为什么不自由协作"→上下文分裂加成本失控，收益没被证明。

**Q6 Supervisor 到底做什么？**
考：名词辨析。答："它是确定性总指挥，一行模型调用都没有。三组入口全幂等：编译落图、图收敛推进、委派裁决和唤醒。固定链是编译、并行调查、归并、至多一个验证、组装、验证、发布。核心纪律是模型无调度权——模型可以提案可以委派，但任何任务图的生命周期事件都是固定算法。"↑"图死锁怎么办"→REQUIRED 前置死了后继确定性收敛 SKIPPED，被剪的链也能收敛。

**Q7 异步子任务怎么保证不丢？**
考：恢复语义。答："三层：子任务行在 PG（铸造和裁决同事务）；执行走同一套双租约回收——崩了租约过期重领；回执用确定性 messageId，恢复重驱等于重投，按键恰一次合并。子任务失败不自动重试——死亡也是终态，主 Agent 醒来看缺口清单自己决定改道还是认账。"↑"为什么不自动重试"→重试决策归有全局视野的主 Agent。

## C. 可靠性与并发（6 题）

**Q8 Worker 挂了怎么办？**
考：恢复全链。答："分两段。快回收：下一拍扫到租约过期，四条件原子回收成 RETRY_WAIT，别的 worker 重领，租约 epoch 加一拒旧提交。慢看门狗：REPORTING 阶段死的、材料齐的铸唯一恢复任务只组装不重查；材料不齐的告警交人工不猜。worker 自己活但卡死也有检测——心跳在续但有效进展滞后，判活但卡死。"↑"旧 worker 复活"→四道栅栏第一道就是提交权栅栏，0 行一行不写。

**Q9 Checkpoint 为什么不能单独完成崩溃恢复？**
考：四概念辨析（必背）。答："检查点只回答'从哪继续'。谁有权继续靠租约加 epoch 栅栏——没有它两个执行者同时续。重做有没有副作用靠幂等——幂等键加动作摘要，没有它续出双份。这次失败要不要再试靠重试语义——退避加次数上限，没有它一崩就死或者无限烧。四个机制缺一不可，合起来才叫崩溃恢复。"↑"举一个只有检查点的事故"→两个 worker 从同一检查点同时续，双倍费用双份报告。

**Q10 重复任务怎么办？**
考：幂等分层。答："分层拦：事件层去重键——重复告警只累加计数不重铸 run；run 层活跃唯一索引——同事故同时只一个活跃调查；领取层 SKIP LOCKED——行在领取语句提交时就离开可见集；账本层幂等键——重复调用落不了第二行账。入口不判重是刻意的，判重放投影和下游——每层只管自己那一段。"↑"为什么入口不判重"→收发室只管登记，判重是投影的职责，职责分离。

**Q11 状态并发更新怎么办？**
考：并发原语。答："全系统没有 Lost Update，靠五身份分型加条件写：租约 epoch 管执行所有权，检查点 revision 管提交修订，configEpoch 管运行配置，decisionSeq 管业务决策序，callSeq 管调用序——五个计数器语义分型不可互代。所有写入都带身份谓词，影响行数为零就是诚实放弃：竞争性失败绝不重试覆盖。"↑"怎么证明没有漏网"→按写入点穷举，唯一写口模式加架构测试。

**Q12 高并发会先坏哪里？**
考：容量推演。答："确定顺序：先模型网关——配额吃紧触发冷却和熔断；然后槽位——默认两个调查并发，任务排队走 SLA 排序，重要的先查；再是 PG 写入；最后才是观测层。系统对风暴的表态是少查慢查不是查询风暴：排队、软背压、Defer，被挤掉的事故有显式的等待原因，backlog 回落自动补铸。"↑"槽为什么才 2"→调查是分钟级重操作，并发闸保守，扩容加槽加实例机制现成。

## D. 工具与上下文（5 题）

**Q13 工具超时怎么办？工具结果为空怎么办？**
考：工具语义。答："超时：硬 deadline 取工具超时和任务硬期限的小者，到点 cancel 掉，迟到结果直接作废不补旧快照——错误归模型可见族回喂计步。空结果：NO_DATA，是观察不是证据，上层纪律是'无故障不制造证据'——判断留给有完整上下文的下一步。"↑"迟到的结果丢了不心疼吗"→证据权威来源是账本不是某次 HTTP 响应，丢一次可以重查，错误时间差的证据混进去查不出来。

**Q14 Tool Schema 怎么约束参数？**
考：schema 即权限。答："三重身份：给模型是接口说明书，带中文用途描述和调用约束；给校验是权限法典——required 缺失拒、未声明字段硬拒、类型 maxLength pattern 全查，缺省额外属性直接归一成 false；给身份是 digest 的一部分——schemaHash 焊进动作摘要，升级工具旧授权自动失效。顺序纪律是先校验成功再算摘要，反过来裁字段会撞 digest。"↑"为什么未声明字段硬拒"→静默裁字段会让两个不同请求算出同一个摘要，破坏幂等身份。

**Q15 结构化 JSON 怎么保证？**
考：输出协议。答："四道：协议后缀是 runner 硬契约随信封下发——不依赖 prompt 记得；解析只剥 markdown 围栏不掏任意文本——容忍面越宽注入面越大；解析即校验——恰好一个分支、未声明字段显式拒绝；解析失败计步重驱，把'严格按协议输出'当修正指引喂回去。真窗实证过：没有协议描述时模型全程自然语言，八步全解析失败耗尽——所以协议是硬契约不是请求。"↑"模型就是不给 JSON"→步数耗尽走确定性收口，不等它。

**Q16 上下文越来越大怎么办？**
考：长度治理。答："我们根本没有累积对话——每步输入是从账本确定性重建的信封。治理三刀：裁剪，证据最多二十条时间倒序，超的进省略集但引用资格不丢；压缩，独立服务默认关，开要三臂对照证明收益，且摘要协议明令不得为压缩比丢反证；卸载，大内容永远在库，信封只有摘要和引用。还有个纪律叫装配零写入——记忆候选要等模型真执行了才落库。"↑"模型记得之前想过什么吗"→推理就是决策本身，落在轨迹和检查点里，比自由文本思考可审计。

## E. 安全与审批（4 题）

**Q17 权限怎么设计？**
考：权限全链。答："七层纵深：入口验签加尺寸闸；认证是人走会话机器走五条 bearer 线；授权是 deny-by-default 路径矩阵，最后一条 anyRequest 全拒；工具三层闸——智能体白名单、网关策略二次鉴权、风险四级；高危操作零执行只记意图转审批；数据层证据摘要锁内容；部署层 OPA 策略一票否决特权容器。每层 fail-closed，新功能忘配闸是不可用不是裸奔。"↑"最薄一层"→登录无限速，已登记待补。

**Q18 Prompt Injection 怎么防？**
考：注入纵深。答："先承认：字面清单拦字面注入，语义级绕不完——所以重点是压终点损失。告警进门前扫描隔离，命中'ignore previous'这类特征直接进隔离区人工复核，根本不进上下文。就算进去了，模型输出要过结构裁决、白名单、Schema；高危动作是零执行转审批；目标资源以权威解析为准，告警标签零授权效力——伪造服务名过不了解析。攻击的最好结局是一条被拒的审批记录。"↑"和 SQL 注入区别"→语法注入治通道，语义注入治后果。

**Q19 为什么高风险操作需要人工审批？**
考：权限单调。答："因为审批链上层有个确定性 Guardian，但它有权限单调律：R3 高危永远转人工，Guardian 无升级放行权——自动系统的权力只能向下覆盖。批了也是一次性授权，绑定动作摘要、代际、快照哈希、策略版本四元组，换代即作废。执行还要过五步同事务、资源锁、发件箱。而且现在生产默认全链干跑，真执行要解锁注册表显式放行。"↑"误判了怎么办"→Guardian 判不了就 UNCERTAIN 转人工，绝不猜 SAFE。

**Q20 Prompt Injection 之外，模型自己幻觉乱来怎么防？**
考：模型约束软硬。答："幻觉的每条出路都有闸：乱调工具——白名单加 Schema；参数乱填——校验拒了带原因回喂；结论乱下——准入面引用越界剥离、无双源支持自动降级成假设；目标乱指——权威解析器只认 canonical 身份，告警标签零授权效力；同参数反复试——熔断签名。模型的最坏产出就是一条被拒的决策加一步消耗。"↑"哪条闸最容易被低估"→准入的语义规则——全量日志计数不能当错误证据，这类'语法对语义错'只有评测能逼出来。

## F. 评测（7 题）

**Q21 Agent 评测和 LLM 评测有什么区别？**
考：评测观。答："LLM 评测考模型能力，Agent 评测考'模型加脚手架'这个系统的行为——同样的模型，闸门不同结果天差地别。所以我们评的是整链：工具调用序列、委派协作、上下文漂移、安全拦截、最终根因命中。方法上可判定的用纯函数——根因命中是类型化三元组等值，明文拒绝 LLM 裁判；开放面才用裁判，裁判自己带校准样本和位置偏差检查。"↑"为什么拒绝 LLM 裁判"→可判定事实引入裁判等于引入方差和作弊面。

**Q22 为什么不能只看最终报告？**
考：过程价值。答："有实证：模型把数据源标签填进症状码槽位，语法完全合法，报告看起来正常——评测一对标准答案，命中为零、误报九十九、漏报六十，结构性恒 miss。还有更隐蔽的：乱查二十次碰中一次的报告和精准取证的报告，最终报告可能一样——过程维的重复调用计数把它们分开。六维镜头刻意不聚合成单一分，就是为了保留这些诊断角度。"↑"哪些维度"→结果、过程、工具、成本、断言裁决、安全。

**Q23 故障注入怎么设计？**
考：出题系统。答："靶场是交易模拟器，十三类业务语义故障——掉单、支付悬挂、重复扣款、库存超卖、对账不平。激活是个带校验链的 API，最关键是标准答案和注入同事务绑定，摘要封存——答案先于答卷锁死。生效靠数据库权威总开关，业务路径探针命中才故障，数据库异常一律按无故障。清理三条路：TTL 清场、恢复相位、开关账本清扫。注入结果三态诚实：没做成、做成了、不知道——不知道必进恢复路径。还留了个 F18 金额错算做隔离题，调优跑批不进，防过拟合。"↑"怎么防止注入失控"→TTL 加前缀靶向加故障恢复，还有一句铁律：数据库异常等于无故障。

**Q24 根因命中率怎么定义？**
考：指标精度。答："三个冻结指标：覆盖率——给出可判定根因的场景占比；条件准确率——根因正确的场景占可判定的比例；端到端命中率——根因正确占全部。精髓在拒答的处理：谨慎拒答算未覆盖但不进准确率分母，单独报合理拒答率——这样指标不会激励智能体乱猜，'诚实说不知道'是被计分的合法策略。四类判定分开：可判定、拒答、结构不合格、超时缺席——各自不同分母不混。"↑"Agent 会不会学会永远拒答"→覆盖率掉零，四个数一起看无法单刷。

**Q25 重复/错误工具调用怎么统计？**
考：观测口径。答："调用遥测三计数：逻辑调用、物理调用、是否带来新证据内容。判重靠两道：动作摘要——同工具同版本同参数同窗口算同一语义查询；载荷摘要——换措辞拿到同一份材料不算新进展。复用不重打数据源，摘要落账本。评测的过程维再做一遍等价调用判重——工具名加参数摘要。逻辑调用量减物理调用量就是省下的钱，物理减新证据就是无效功。"↑"复用会不会过期"→摘要钉了时间窗，run 内窗口冻结不存在过期；跨 run 新摘要。

**Q26 如何做回归？**
考：质量资产化。答："四层：SMOKE 面板快速回归子集每次改动跑；难度分层的全量跑批按里程碑；红队案例常驻防劫持退化；坏 case 准入成回归资产——生产或者评测发现的结构性错误，经准入变成永久案例。所有改动过对比：同数据集新旧两版跑分对照，自动记录。上线由私有靶场集做主质量门。"↑"回归挂了怎么办"→准入阈值加人工复核，坏结论不许上线，可以带未决清单灰度观察。

**Q27 如何灰度 Agent 新策略？如果模型换了怎么证明没退化？**
考：灰度与回归双问。答："灰度分三种对象：引擎替换走金丝雀分桶加对比观测，Holmes 到自研引擎就是五步替代的完整案例；优化开关走三臂对照——关、确定性、消费，证明收益才放量，压缩和增强都是这么治的；Prompt 走工作台配置包，run 铸造时冻结版本。模型换了证明没退化：代码零改动——模型接口就 836 行——直接跑评测面，同数据集同公式对齐跑分，红队和难度分层全过才算。接口窄是可替换性的根。"↑"评测结论可信吗"→私有靶场是主质量门，评测恢复未核验的不冒充已验证。

## G. 架构与 Harness（5 题）

**Q28 Session 怎么隔离？**
考：概念纠偏。答："先纠偏：这个系统没有聊天 Session——会话是对话式 Agent 的概念。我们的隔离单位是调查：run 加任务加检查点，物理隔离靠数据库行加唯一键——同事故同时一个活跃调查，检查点按任务主键一行。跨调查不共享任何可变状态，能共享的只有事实：证据不跨 run，历史判例走只读检索工具。问 Session 隔离我就会先讲这个概念替换。"↑"多轮对话呢"→没有多轮对话，每步信封重建，这是可复现性的根。

**Q29 Agent Harness 是什么？Eval Harness 是什么？区别？**
考：概念定义权。答："Agent Harness 是把模型运行成可靠 Agent 的全部控制代码——循环、工具闸、状态、恢复、预算、权限，我们自研，十万行里占九成三。Eval Harness 是质量基建——案例库、批跑、评分、对比、发布门。同仓不同库身份：评测面独立授权。一句话分界：Agent Harness 让单次调查可信，Eval Harness 让一类调查的质量可信。占比我算过：模型触网代码 836 行千分之八，模型侧宽口径 6.7%——93% 以上是 Harness，方法论可复核。"↑"为什么不用框架"→框架替代冰山尖，事务语义的冰山体它给不了。

**Q30 整个项目最大的技术难点是什么？**
考：全局提炼。答："有界自主的工程化：把概率组件放进确定性系统，还要求崩溃可恢复、并发安全、成本有界、行为可审计。最难三个点：检查点提交围栏——五层防护保证任意一步崩溃原样续走，这是全部恢复语义的根；错误两族加三层重试的边界——每个失败归到正确处置层，错一层就是事故；把上面一切做成可评测——每个机制对应评测维度，行为变化可量化。模型本身不是难点，它是被治理的对象。"↑"哪个最难"→围栏。锁序、四元身份、条件写、动作幂等、审计槽，少一层就出末写胜出。

**Q31 哪个设计是你自己做的？哪些是框架已有能力？**
考：OWNER 诚实。答："没有 Agent 框架——十五项 Harness 能力全部是仓库内代码，每篇有文件行号可指认。外部的只有 Spring Boot、Spring AI 客户端、Postgres、Flyway 这些基础设施。我的主体工作在机制演进层：有界循环、委派协议、围栏、审批链、六维评测。骨架是系列起点，我精读过可以说清语义，但初版提交不是我——ownership 我按语义定义权画边界，编造是最速死的死法。"↑"举个例子"→比如收尾四道栅栏是骨架起点，检查点提交围栏是演进层主体。

**Q32 哪个方案如果重新做会改？**
考：REDO。答："九项工程性欠账在清单上，说三个最想改的：一是五身份分型类型化——现在靠注释和评审防混用，我会做成编译期类型；二是真实 token 统计闭环——现在是字符近似，预算和成本治理都需要校准模型；三是登录限速——安全面最薄的一层。十个骨架不动：PG 并发底座、检查点五层防护、无状态单步循环、委派深度恒一、高危零执行审批链、三面留痕、纯函数评分公式、GT 同事务封存、诚实中间态、模型接口窄化。"↑"为什么不现在改"→都是欠账清单在册项，随里程碑还，不动摇正确性骨架。

## H. 运行细节（4 题）

**Q33 上下文（信封）里都有什么？模型上下文越来越大会怎样？**
（与 Q16 合并答，此处补充信封清单）"十八个键：告警、目标、预算、证据窗、子任务回执、人工材料、工作记忆、轨迹、已验证摘要、工具白名单加中文描述的 Schema、合法引用集、上一步错误反馈。全部有界：证据二十条轨迹八步记忆十槽。越来越大这个问题在我们这被结构消解了——没有累积，只有重建。"↑"工作记忆是什么"→假设、已排除、缺口、反证四槽，宿主确定性重建，模型不写。

**Q34 重复唤醒怎么办？**
考：幂等细节。答："唤醒是幂等 CAS：等子任务的相位下，每次驱动先复判——当前轮子任务没全终态就返回继续等，全终态才原子翻回就绪态，可任意次重入。子任务死亡也算终态——失败不阻塞唤醒，失败事实随回执缺口清单给主 Agent。没有'重复唤醒导致重复推进'的通道——相位翻转是条件写。"↑"谁触发唤醒"→驱动循环每拍，不是事件推送——轮询加幂等比事件加去重简单可靠。

**Q35 数据库失败/Redis 失败怎么办？**
考：依赖故障。答："数据库失败分层：接入侧收件箱退避重试加 Alertmanager 五零三整组重发；调查侧领取事务失败整拍放弃，收尾失败任务留租约由回收接管——一切状态在库，数据库回来即续走，零系统级损失。Redis 失败这题不存在——我们没有 Redis，全系统只有 Postgres、本地内容寻址仓和进程内可丢缓存。"↑"为什么敢不用 Redis"→并发原语全是 PG 内生的，账本优先模式不需要PubSub。

**Q36 状态更新失败/结果回收失败怎么办？**
考：0 行语义。答："状态更新失败先分两类：竞争性失败——条件写零行说明有别人合法地做了，诚实放弃一行不写只留审计；环境性失败——数据库抖动，事务回滚交给上层重试路径。结果回收失败——比如工具调用结果回写不上了——账本终态单向 CAS 保证不覆盖，悬挂行由回收面诚实标 UNKNOWN，之后看门狗分诊。核心是那句：零行等于诚实放弃，绝不末写胜出。"↑"放弃的任务谁管"→租约过期回收面接管，全程有指标计数。

9. 篡改是"可检出"不是"不可改"（22/18 篇）。
10. 评测三维是纯函数，LLM 裁判只在开放面且被治理（20 篇）。
11. 工具回放存在——冻结载荷重放+账本比对（20 篇）。
12. 审计判负/deny-by-default/不回落——fail-closed 是全系统默认方向（03 篇）。

# 七、5 句话总结（全系列收官）

1. **业务**：交易告警的自动根因分析——把"半夜人肉排查"变成"带证据链的自动诊断文书"。
