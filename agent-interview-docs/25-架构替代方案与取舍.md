# 25-架构替代方案与取舍

> 本系列第二十六篇，架构思辨收官。把全系列散落的十一个重大架构决策收拢成正面对抗：**每个决策列出真实的替代方案、"为什么不"的代码级理由、当前边界、以及 REDO 立场**——面试官问"为什么不用 X"时，这里每一条都是可背的弹药。
> 标注约定同前：【代码事实】/【合理推断】/【设计扩展】/【未确认】。

# 本层要解决的问题

一句话：**证明这套架构不是"没想到别的方案"，而是"每个替代方案都因具体约束被否决"——十一个决策×十一个被否决的替代品，每个否决都有代码锚。**

# 先看一个交易告警

> 面试官最爱问的五个"为什么不用"：
> "为什么不用 LangChain？"——因为核心机制全是 PG 事务语义（槽+任务同事务、检查点 revision CAS、账本 PENDING 先行），框架的内存编排装不下（17 篇）。
> "为什么不用消息队列调度？"——因为任务领取需要"SLA 排序+活跃 run 栅栏+task_key 过滤+槽位原子绑定"四条件单语句，MQ 都做不到，PG 一条 UPDATE 全做了（09 篇）。
> "为什么不用 Multi-Agent 自由协作？"——因为委派树深度恒 1 是**类型结构**保证的（PRIMARY 不接子任务），自由协作换来上下文分裂和成本失控，换不来根因命中率（07 篇）。
> "为什么不用框架的 function calling？"——因为协议即围栏：PROTOCOL_SUFFIX 让解析容忍面被刻意收窄（"不提取任意文本中的 JSON 片段——容忍面越宽注入面越大"，05 篇）。
> "为什么不用事件溯源做恢复？"——因为恢复要 O(1)：读一行检查点+账本判悬挂，重放几十步大 JSON 又贵又不可信（13 篇）。

# 如果没有这一层会怎样

没有"为什么不用 X"的正面回答，架构答辩会退化成"我们觉得这样好"——本篇的任务是把全部感觉替换成约束推导。

# 代码是怎么做的

## 0. 先给我一句话

架构取舍的总原则只有一句：**凡是正确性相关的（状态/并发/恢复/权限）全部自研并压进 PG 与状态机；凡是质量相关的（prompt/策略/模型）全部做成可灰度的配置资产——确定性的自研，概率的才外包给模型。**

## 1. 业务上为什么需要这一层

面试与真实演进都需要"决策的可辩护性"：每个替代方案的否决理由必须随代码可追溯——否则半年后没人记得为什么这么建，重构就会盲目。

## 4. 真实代码入口（三个最容易被追问的决策，深挖版）

**决策 #2 的深挖：Multi-Agent 为什么不自由协作（第七部分明确警告"不要看到多个 Agent 名字就自主协作"）**【代码事实】：
- 结构层：`RoleRuntimeKind` 只有两个值（BOUNDED_LLM/DETERMINISTIC_SINGLE_TOOL）；裁决时"主 Agent 不是可委派专家（PRIMARY 只出决策，不接子任务）"（Supervisor:341-342）——**委派深度=1 不靠配置靠类型**；
- 账本层：uq(run,gap) "信息缺口只裁一次"；
- 语义层：question 不进执行面（07 篇）——自由协作的"对话"在协议里没有通道；
- 成本层：委派批 2×2+RUN_TASK_CAP（≤8 任务）；
- 收益层诚实评估：自由协作的收益（复杂分解/并行探索）在 RCA 场景未被证明必要，而成本（上下文分裂/无限递归/账目混乱）是确定的。

**决策 #3 的深挖：为什么 PG 能扛"队列+状态+账本+锁"四职**【代码事实】：
- 队列：`FOR UPDATE SKIP LOCKED` + 公平 ORDER BY（09 篇 CLAIM_SQL）；
- 状态：条件写 CAS 全家（epoch/revision/ON CONFLICT）；
- 账本：append-only+唯一键+哈希链；
- 锁：行锁+统一锁序（防 AB-BA 有具名设计记录）；
- 反面承认：PG 方言绑定（SKIP LOCKED/部分唯一索引/ON CONFLICT 换库即重写）；单写点吞吐上限——"调查频率分钟级"是让这个取舍成立的前提（24 篇）。

**决策 #7 的深挖：引擎替代（HolmesGPT→NATIVE）的演进纪律**【代码事实】：
- 双轨期：CanaryRouter 分桶（V25）+engine comparison 观测（V32）+"engine 影子工作"（V34）；
- 退场不是删除：HOLMES 行留读面（"M6-07 影子抽样入队钩子已随 Holmes 退场拆除（V34 面保留为对照期历史读面）"，Orchestrator:347）；`RcaEngine` 枚举保留（但铸造点拒绝 HOLMES——"第二引擎已退场，不铸 run"）；
- 诚实边界：枚举注释仍写"HOLMES=主路径"——**文档性注释落后于代码现实**（00 篇排雷点），面试按铸造点代码说。

## 5. 核心对象：取舍判断的四个通用判据（从十一个决策中提炼）

1. **正确性自研，质量外包**：状态/并发/恢复/权限自研进 PG；prompt/策略/模型选择做成配置资产（灰度+评测）。判据：这东西错了会出事故吗？会→自研+状态机。
2. **接口窄则替换易**：模型接口压缩到一个决策 JSON+一封信封（17 篇试金石：换模型零代码）。
3. **不确定即诚实**：对峙即人工/UNKNOWN/UNRESOLVED/RECOVERY 交人——三个字节的枚举换掉整套"假装智能"。
4. **机制先于流量灰度**：dry-run 铁律（能力灰度）+Canary（引擎灰度）+三臂对照（优化灰度）——三种灰度对象不同：能力/引擎/优化。

## 6. 一条真实调用链（"如果重来一次"的推演——假设换成 LangGraph 实现同等功能）

```
需要：槽+任务同事务领取（PG 条件写）——LangGraph 无此原语→自研
需要：检查点 revision CAS+四元围栏——LangGraph checkpoint 是序列化快照，
     无 owner/epoch/configEpoch 身份语义→自研围栏层
需要：账本 PENDING 先行+错误两族+预算六维——框架 callback 难以强制
     "不记账不触网"→自研守卫层
需要：委派裁决五拒绝码+深度恒 1——框架的图要手工退化成星型→自研 Supervisor
结论：框架能给的（图编排/内存/重试装饰）恰是本系统最薄的部分（模型侧 6.7%）；
     框架给不了的（事务语义/身份分型/结构纪律）恰是 93% 的核心
→ 自研决策在定量上成立：框架替代的只是冰山尖，代价是冰山体不可控
```

## 7. 状态机

架构决策没有状态机，但有一个"决策的演进状态"值得记录【代码事实】：Holmes→NATIVE 的替代走了完整灰度（Canary 分桶→对比观测→投影拒绝→钩子拆除→枚举留名）——**替代一个引擎用了五个迁移版本（V25/V32/V34/V35/M6-07），没有一步跳**。这本身就是取舍纪律的展示：替代是过程不是开关。

## 8. 正常业务流程（决策复审的节奏——架构不是一次性的）

每个决策的复审触发器【设计扩展】：模型换代（协议遵循度漂移→评测数据触发）；业务量级变（PG 单写点是否到顶→24 篇边界）；团队规模变（自研 Harness 的知识门槛）；事故复盘（负面清单漏项）。**十一个决策里多数的复审触发器是"外部条件变化"而非"技术时尚"**——这是取舍稳定的来源。

## 10. 并发问题

架构取舍的共同底座（10 篇）：十一个决策里有七个（#1/#3/#5/#6/#8/#10/#11）的正确性依赖 PG 并发原语——**并发模型是这栋楼的地基，其他十个决策都是在它上面装修**。这也是为什么"换掉 PG"在所有替代方案里被否决得最彻底。

## 11. 崩溃恢复

#8（检查点 vs 事件溯源）是恢复语义的架构决策；#6（单体）让"finishTask 十表同事务"成为可能——**架构决策的恢复影响：拆得越碎，恢复事务越难原子**。反证：notify-app 拆出去后，它的恢复靠 outbox at-least-once——拆出去的每个组件都要重新发明一套恢复语义，这就是不轻易拆的理由。

## 12. 安全

架构与安全：#3（PG 一切状态）让审计面完整（哈希链/账本不需要跨系统对齐）；#6（单体）让路径矩阵一条链管完；#2（深度恒 1）让权限面可枚举。**安全边界（23 篇七层）的简洁性直接受益于架构的克制。**

## 13. Agent Harness

本篇是 17 篇的续篇：17 篇证明"Harness 是主体"，本篇证明"Harness 为什么长这样"——十一个决策就是它的施工图审查记录。

## 14. 可观测性

决策的演进全部有迁移版本与事件留痕（V25→M6-07 的引擎替代五步）——**架构决策本身被审计**（这是 18 篇精神在元层面的应用）。

## 15. 性能和成本

每个取舍的性能账已在对应篇目：#3 的 PG 吞吐（10/24）、#5 的轮询延迟（09）、#11 的评测成本（20）。本篇补一句总账：**93% Harness 的运维成本（理解/演进/排障）是这套架构最大的持续支出——它的回报是模型迭代零重构**（17 篇）。

## 16. 设计取舍（本篇即主题——REDO 总清单）

**全系统 REDO 立场汇总**（各篇 REDO 的收拢，按"会改/不会改"二分）：

会改（工程性）：
1. 五身份空间类型化（编译期防混用）

## 17. 面试背诵卡

【30 秒主答】
"这套架构有十一个重大取舍，我用三个例子说明决策方式。第一，自研 Harness 而不用框架：因为核心机制全是 PG 事务语义——槽和任务同事务领取、检查点 revision CAS、账本先行——框架的内存编排装不下，而框架能给的图编排恰恰是模型侧那 6.7% 的薄层。第二，状态全放 PG 不用 Redis 和 MQ：任务领取要 SLA 排序加活跃 run 栅栏加槽位原子绑定，一条条件 UPDATE 全做了，引入 MQ 反而把事务边界打碎。第三，恢复用检查点当前态不用事件溯源：恢复要 O(1) 读一行，重放几十步大 JSON 又贵又不可信，审计由账本加哈希链补。总原则一句：正确性相关全部自研压进 PG 和状态机，质量相关全部做成可灰度配置资产。REDO 时会改的是工程性欠账，骨架一百次都保留。"

## 18. 这一层哪些话不能说

1. ❌ "我们的架构是业界最佳实践" → ✅ 每个决策都是"在特定约束下的最优"，约束变了结论会变（复审触发器第 8 节）。
2. ❌ "我们评估过所有替代方案" → ✅ 评估过的是与本业务相关的替代方案；框架生态演进快，评估有时效。
3. ❌ "自研就是先进" → ✅ 自研是约束推导的结果不是偏好——约束消失（业务量/团队/框架成熟度变化）时决策应复审。
4. ❌ 引用具体框架版本/性能对比数据【未做 benchmark——不要编】。
5. ❌ "HOLMES 从未存在过" → ✅ 演进史要讲：双轨灰度五步替代是亮点不是污点。
6. 迁移版本与钩子拆除的完整时序【V25/V32/V34/V35/M6-07 锚定，细节以迁移代码为准】。

# 面试官追问卡

**Q1：你说"正确性自研"——难道框架做的东西就没有正确性需求？**
考什么：论证的精确性。
30 秒答："有，区别在于正确性的**定义权**。框架的重试/checkpoint 也有正确性语义，但那是框架定义的语义（如 LangGraph checkpoint 是序列化快照），我需要的语义是'owner+epoch+configEpoch+revision 四元围栏下的推进'——这种定制语义要么等框架支持，要么在框架上叠一层与框架语义打架的补丁。自研的定义是'语义定义权在自己手里'——不是框架不能做，是它做的不是我要求的那个正确性。"
继续追问 1："等框架支持不行吗？"——答："框架演进方向由社区多数需求决定，'PG 事务语义的四元围栏'大概率不是主流需求——把系统正确性押注在自己不是主要用户的社区的路线图上，才是真正的风险。"

**Q2：单体 control-app 是不是违背微服务潮流？什么时候该拆？**
考什么：拆分时机的判断。
30 秒答："潮流不是拆分理由，故障域和事务边界才是。现在的拆分已经做了故障域切分：通知（外部依赖抖动）、值班适配、靶场（评测隔离）都独立进程/模块——它们是'失败会传染'的边界。剩余的告警域内部不该拆：finishTask 十表同事务拆开=恢复语义全碎（25 篇 #6）。该拆的信号：告警域内部出现独立的伸缩需求（比如解析洪峰）、或独立发布节奏的真实冲突——目前都没有证据。拆分的正确姿势是先拆故障域，再谈服务化。"
继续追问 1："eval 为什么不拆成独立服务？"——答："评了半截：库身份已分（eval_app），worker 独立循环已具备——差的是进程隔离。当前评测流量小，同进程省运维；跑批规模上来后 eval_app 拆出是低风险动作（写面已隔离）。"

**Q3："不确定即诚实"会不会让系统显得不智能？老板问"为什么 30% 的报告是 PARTIAL"？**
考什么：诚实策略的业务辩护。
30 秒答："PARTIAL 的含义是'有确认根因但证据不全'——它比 30% 份'看起来 CONFIRMED 实则单源臆测'的报告有价值得多，因为前者告诉值班者可以信到什么程度。业务辩护三步：一是分级报告让响应动作可分级（CONFIRMED 立即处置/PARTIAL 带保留/UNRESOLVED 转人工）；二是 PARTIAL 率是证据基建的改进指针（缺哪个源的数据一目了然）；三是对比数据说话——竞品或旧方案如果 100% CONFIRMED，先问它的评测对照面在哪。不诚实的智能是负资产。"
继续追问 1："怎么降低 PARTIAL 率？"——答："两条正路：扩证据源（工具目录演进）和提升取证效率（预算内多走步）——都不是改报告措辞。"

**Q4：十一个决策里，哪一个是你会最先推翻的？**
考什么：自我批判的勇气。
30 秒答："#10 的周边——Spring AI 单路由直调的模型接入层。理由：它是十一个决策里唯一'被动跟随框架'的（I34 关重试/原始错误捕获都是对抗框架默认行为的补丁），而模型接入协议（尤其推理模型的 reasoning token、structured output 原生支持）正在快速演进。我会把这一层换成更薄的自己写 HTTP 客户端（错误分类和账本已经是自己的了，框架只贡献了序列化）——但这是'最小的那个决策'，动摇不了地基。让我最先捍卫的相反是 #3：谁想引入 MQ 先回答领取四条件怎么表达。"
继续追问 1："团队里有人强烈要求上框架怎么办？"——答："用第 6 节的推演和 17 篇的数字（93%/6.7%）谈：框架能替代的是薄层，代价是厚层失去定义权。再要求做一次 spike：用框架实现'槽+任务同事务+四元围栏'三个原语——spike 的结论会比争论有效。"

**Q5：这十一个决策，哪些是"你做的"，哪些是"继承的"？**
考什么：ownership 的精度（第十九部分 OWNER 维度）。
30 秒答："按 git 史实分层：AM1~AM5 的骨架（状态机/投影/Worker/收尾算法）是系列起点，我精读并内化了它；R7 系列（有界主循环/委派协议/检查点围栏）、CL/PB/PC 系列（提交围栏/变更链/审批链）、EN/MC/ME 系列（工具目录/MCP/回执/六维评测）是演进层的主体工作——每个机制在本系列都有文件行号可指认。诚实回答的结构：'机制设计可指认到 commit，基础设施（PG/Spring/框架客户端）是公开件，模型能力是外部件'——ownership 的边界画在'语义定义权'上。"
继续追问 1："如果面试官深挖一个你没写过的模块？"——答："12 篇立场复用：如实说'这是系列起点骨架，我精读过它的契约与测试，可以说清语义，但初版 commit 不是我'——编造 ownership 是面试最速死的死法。"

# 这层不要乱说什么

1. 不要说"我们的选择是唯一的正确"——每个决策都绑定约束，约束变则结论可复审。
2. 不要贬低被否决的方案——LangGraph/MQ/事件溯源各有适用域，否决理由是"不匹配本约束"。
3. 不要编造未做过的 benchmark/对比数据。
4. 不要把"自研"讲成"不用开源"——Spring Boot/Spring AI/PG/Flyway 都是开源件；自研的是 Harness 语义层。
5. 不要回避架构的历史包袱（双路由共存/枚举注释过时/138 迁移考古成本）——24 篇风格：诚实边界是设计的一部分。
6. 各决策的具体演进 commit 归属【按 git 史实回答，本篇锚定的是机制而非人】。

# 5 句话总结

1. **为什么需要**：架构答辩与真实演进都要求"决策可辩护"——否决理由必须随代码可追溯。
2. **核心机制**：十一决策对抗表+四判据（正确性自研/接口窄/不确定即诚实/机制先于流量）+九改十不改的 REDO 清单。
3. **上下游协作**：地基是 10 篇并发原语，墙是 12 篇状态机，装修是 17 篇 Harness——本篇是施工图审查记录。
4. **最大风险**：约束漂移后决策未复审（框架生态/业务量/模型能力都在变）。
5. **最大取舍**：用"每个决策写下可追溯的否决理由"换"半年后重构不盲目、面试答辩不背稿"。
