## 2. FUP-01：关闭新建没有覆盖全部执行入口（P1）

### 证据与触发条件

- [DrillWorker.java:126](E:/kimiCode/control-app/src/main/java/com/objwww/pr/control/drill/application/DrillWorker.java:126) 每拍仍 claimNext，再经过模板预检到 [197 行](E:/kimiCode/control-app/src/main/java/com/objwww/pr/control/drill/application/DrillWorker.java:197) `injection.inject(current)`；worker 未接收 `app.drill.launch-enabled`。
- [EvalRunnerConfig.java:495](E:/kimiCode/control-app/src/main/java/com/objwww/pr/control/eval/application/EvalRunnerConfig.java:495) 仍装配真实复合注入端口及 worker；服务 DTO 的 ready=false 不会修改 catalog 内原始模板。
- [EvalRunnerMain.java:47](E:/kimiCode/control-app/src/main/java/com/objwww/pr/control/eval/application/EvalRunnerMain.java:47) 只有字符串恰为 `worker` 才进入命令 worker；其他任意字符串都进入 `runOnce()`，在 64 行直接 `runner.runBatch()`，不经过 EvalLaunchGate。

离线输出：

```text
CLOSE-BACKLOG apiLaunchEnabled=false injectionPortCalls=1
CLOSE-CLI mode=once directRunBatch=true (stopped at fake port)
CLOSE-CLI mode=workre directRunBatch=true (stopped at fake port)
```

演练触发条件是关闭前已受理 QUEUED，或崩溃 PRECHECK 经孤儿清扫重排队；CLI 触发条件是部署设置 once 或模式值误拼。这不是证明普通 HTTP 用户能绕过当前 409，也不证明 195 正存在这些排队任务。

### 怎么改

1. 将现有能力配置收成可复用的执行政策对象；DrillJobService、DrillWorker 与 CompositeDrillInjection 使用同一个来源。能力响应增加 policyVersion/配置指纹，便于核对 API 和 worker 是否一致。
2. DrillWorker 领取后、进入 INJECTING 前复验。确定未触及外部效果的 PRECHECK 可以按现有状态机落 FAILED + `LAUNCH_DISABLED`；记录拒绝事件，避免永远重排队。不得把 INJECTING/UNKNOWN 当作“无副作用失败”释放占用。
3. 在最靠近副作用的注入端口再检查一次，阻断绕过 worker 的应用调用。对于运行时可热更新开关，要明确检查与开始操作的边界；若配置仅启动时加载，应如实标记需要重启，不宣称即时急停。
4. EvalRunnerMain 将 mode 改为枚举或显式 switch：只允许 worker/once，未知值启动失败；once 调同一 EvalLaunchGate 或在闭面期直接禁止。不要再默认落到一次性执行。
5. API 与 worker 分进程时分别核对有效配置/镜像指纹。部署脚本的验收应覆盖旧队列、once、误配置路径，不能只测 HTTP create。

不建议靠“把模板再写一遍 false”解决根因，也不建议停掉整个恢复线程来阻断新注入。

## 3. FUP-02：评测对比能对未完成/缺失证据落档 PASS（P1）

### 证据

[EvalCompareService.java:255](E:/kimiCode/control-app/src/main/java/com/objwww/pr/control/eval/application/EvalCompareService.java:255) 已读取包含 state 的 CompareRunMeta，但 compute 没有用 state 判定结论；[298 行](E:/kimiCode/control-app/src/main/java/com/objwww/pr/control/eval/application/EvalCompareService.java:298) 传给 gate 的只有 comparable、扫描截断、配对数、退化数和统计量。

[EvalCompare.java:177](E:/kimiCode/control-app/src/main/java/com/objwww/pr/control/eval/application/EvalCompare.java:177) 只排除两侧 digest 都存在且冲突的行；缺 digest 的行仍进入统计，仅标 UNVERIFIED。未配对行有列表和计数，但不会阻断 gate。

本次直接调用真实 `EvalCompareService.record()`，得到并验证仓储 insert：

| 候选状态 | 基线/候选案例数 | 其他条件 | 实际结论 |
|---|---:|---|---|
| RUNNING | 5 / 5 | 5 个独立簇，命中相同 | PASS，并可落档 |
| FAILED | 5 / 5 | 同上 | PASS，并可落档 |
| SUCCEEDED | 50 / 5 | 45 个仅基线案例 | PASS，并可落档 |
| SUCCEEDED | 5 / 5 | 双侧案例 digest 全缺 | PASS，并可落档 |

[EvalCompareView.vue:147](E:/kimiCode/alert-web/src/views/EvalCompareView.vue:147) 直接展示后端门结论，PASS 是绿色标签。页面同时显示状态/未配对计数不能消除“质量门通过”的歧义。

**边界：这是对比工作台的质量门与落档问题；本次没有发现/证明该 PASS 会直接触发自动发布。不要把它与另一个 QualityGate 的 ELIGIBLE 判定混为一谈。** 对未完成数据作探索性比较可以保留，但应明确为暂态分析。

### 怎么改

1. 复用 EvalCompare 纯函数层，加 `EvidenceReadiness` 输入，而不是前端自己补门。区分“能展示差异”和“能产生最终结论”。
2. 最小修复：RUNNING/PENDING 等未完成状态只能出 INCONCLUSIVE + `RUN_NOT_FINAL`；FAILED/CANCELLED 等不完整终态不能因局部命中率好就成为最终 PASS。允许保存诊断快照，但保存同样的非最终结论。
3. 按冻结计划的 `(caseVersionId 或稳定 scenarioId, roundNo)` 集合核算 expected/completed/paired/verified，输出缺失数、身份未验证数、覆盖率。过渡期至少用双侧键并集检测单侧缺失；不能仅靠并集证明完整，因为两侧一起漏同一案例时并集也缺。
4. 默认最终门要求计划全部完成、应配对案例全部配对、关键案例没有缺失。若将来允许部分覆盖，必须冻结阈值与关键场景策略，阈值按计划集合算，不能只以幸存 paired 为分母。
5. UNVERIFIED 可以展示差异，但不应充当输入身份已核验。已有历史数据缺字段时明确降级；逐案例 identity 应优先在执行时冻结，避免依赖读时多义的 dataset version 字符串匹配。未知值相等不代表证据充分。
6. 沿用已有簇级 bootstrap、最小簇数与扫描截断保护，不重写统计引擎。门规则变更将 `eval-compare-gate-v1` 升版，保存新规则的 readiness/阈值/计划摘要；旧快照保留原始结论和规则版本，页面标“历史规则”，不要静默改旧审计记录。
7. EvalCompareView 给出“暂态分析/结果不完整/身份未核验”徽章、明确分母，并能跳到缺失案例。后端禁止最终 PASS，前端只映射机器码。

## 4. FUP-03：新注入关闭后，遗留恢复仍会走 SAFE-03 旧协议（P1，已知问题的可达性补充）

[DrillWorker.java:127](E:/kimiCode/control-app/src/main/java/com/objwww/pr/control/drill/application/DrillWorker.java:127) 每拍先执行 flagdSweeper；[FlagdRestoreSweeper.java:43](E:/kimiCode/control-app/src/main/java/com/objwww/pr/control/drill/application/FlagdRestoreSweeper.java:43) 取超过截止时间的 OPEN/UNKNOWN 台账并调用 FlagdConditionalRestore。它不依赖新作业 create。

因此，只要历史恢复台账存在可恢复行，原 SAFE-03 的“读后无条件写回”风险仍有调用路径。此次是源码调用链确认；没有读取 195 当前恢复台账，不声称 e03 一定对应 OPEN/UNKNOWN 行，也不把 CONFLICT 当作仍会自动重试的状态。

### 怎么改

1. BUGLOG 的结论调整为“新请求已阻断；旧队列、CLI 与遗留恢复需分别确认”，删除未附条件的“缺口不可达”。
2. 继续完成既有 SAFE-03：持久化激活意图、owner/activationId、条件写、持久化修订号。自建 sidecar 的恢复操作在一次锁/事务内完成“校验 expected owner + revision + applied value → 写 restoreTarget → 推进 revision → 持久化回执”。任一不匹配都不写。
3. 单纯先 GET 后 POST 仍有竞态；内容 hash 只能表示内容，不能识别 A→B→A 的改写历史。sidecar 若整体重写 JSON，要覆盖跨不同 flag 的并发写；多进程/多副本要由所有写入者共享序列化机制，进程内锁不足以覆盖这些部署方式。
4. 台账 close 的数据库 CAS 不能替代外部副作用的 CAS。先完成外部条件恢复，再按回执关账；超时结果 UNKNOWN 必须能用同一 operationId 查询，不重新猜测现场。
5. 恢复功能和新注入能力分开控制。应继续允许已经证明安全的条件恢复；若旧 sidecar 不支持该契约，保留占用和待人工核验原因，提供只读核验材料。不能无条件恢复，也不能一刀切丢掉恢复责任。
6. 对 195 的下一次验收增加只读台账清单、年龄、owner/代次完整性、运行 worker 与 sidecar 指纹。真实恢复与释放 e03 仍按现场核验流程执行，绝不以删作业行替代恢复证据。

## 6. FUP-05：监控页面的诚实展示已改善，采集与恢复告警尚未闭环（P2；开放真实执行前应完成）

已做好的部分：MonitorView 按区块显示失败、缓存更新时间与未知样本；执行器表明确是租约活动推导，不冒充独立心跳。无需重复改这些已修项。

当前仓库 [prometheus.yml:8](E:/kimiCode/deploy/alert/prometheus/prometheus.yml:8) 仅配置 otel-collector:9464 与 order-arena；[MetricsWhitelistService.java:55](E:/kimiCode/control-app/src/main/java/com/objwww/pr/control/ops/application/MetricsWhitelistService.java:55) 的主机/Alertmanager/控制面吞吐指标缺对应采集接线，代码注释也承认未采集。已检查的指标白名单、AlertMetrics 与规则中，没有形成针对评测排队积压、flagd 恢复责任超期的完整告警链。

这属于仓库交付缺口；不能据此断言远端没有额外手工 scrape 配置。应先核对现场配置与仓库是否漂移。

### 怎么改

1. 对齐有效的 exporter/collector 配置及服务名后，补主机、Alertmanager、控制面指标抓取；对只读监控用户仍走现有白名单查询，不开放任意 PromQL。
2. 从数据库状态聚合恢复责任与任务积压，不仅依赖 worker 自报。worker 死亡时，自报 gauge 可能停留在旧值；导出采集成功时间，查询失败不能发布成零。
3. 建议的最小观测集：launch_enabled（区分 API/worker）、pending_count、oldest_pending_age、recovery_obligation_count（状态枚举）、oldest_unresolved_recovery_age、worker_last_success、数据采集成功时间。名称为方案建议，尚未实现。
4. 标签只允许有限的 env/执行器类型/state；runId、drillId、token、任意异常消息不进指标标签。具体作业通过受鉴权详情链接排查。
5. 规则区分“当前业务故障”“故障已停止但恢复证据未完成”“数据源失联”。RECOVERY_FAILED/CONFLICT 对应可操作告警；期限采用业务配置，不能拍脑袋固定统一秒数。新注入关闭时，合理的排队告警可抑制，但恢复责任告警不应被抑制。
6. MonitorView 增加恢复责任卡片：未核验数量、最长等待、数据时间、跳转明细。DrillDetailView 同时显示真实相位、停止请求状态与核验状态，OBSERVING + stopRequested 不能仅凭已受理就显示已经进入 RECOVERING。
7. 完成 Prometheus 规则测试及通知接收端验收：规则产生告警只是半程，还要用隔离测试接收器验证路由、分组和恢复通知。不要向实际人员发送测试消息冒充本地验证。

## 9. 下一轮怎么收口，避免无限优化

**包 A：当前受限交付的必要收口。** 完成 FUP-01 全入口拒绝、FUP-02 完整性门、FUP-04 同源预检，修正 BUGLOG 可达性声明；完成对应单测/浏览器负例。没有真实注入也可以完成。

**包 B：恢复安全与最小运维链。** 完成既有 SAFE-03 条件写、遗留责任核验，以及 FUP-05 最小采集/告警。对已有恢复责任同样有价值，不必等到重新开放新注入才处理。

**包 C：完整执行能力重开。** 完成已立案的共享占用、每次运行身份、停止/恢复/核验、续租与 fencing，再在可用隔离靶场跑正常、停止、超时、进程崩溃、响应丢失与并发负例；最后兑现 BA-141/RV09。不要提前翻转 launch-enabled。

生产验收应写成“允许哪些能力 + 哪些验收证据”，而不是“所有优化点都消失”。包 A 完成可支撑更严格的受限读面交付；完整在线评测与故障注入仍以包 B/C 的恢复安全和真实链路证据为准。主题美化、额外图表、引入新平台都不属于本轮必要门槛。
