|---|---|---|

1. **先关住不真实的能力。** 在 EvalCommandService 入队前校验本环境支持的 mode 和可配置字段；EvalLaunchExecutor 领取后复验。E/B 未实现隔离执行器时拒绝请求；前端从同一能力数据禁用模式并解释原因。不能只禁前端，旧客户端也要被拒绝。不支持动态版本时，页面仅展示实际部署版本，后端拒绝不同的自报版本。非空但不能执行的限额拒绝，不默默忽略。固定并发 1 可以作为明确的支持范围，不能让用户填写更高值后仍显示已生效。

完整版本绑定：在受理时解析不可变配置快照，持久化 requestedConfig 与 effectiveConfig、数据集内容摘要、模型/provider、prompt 内容摘要、工具与评分器版本；worker 按快照执行。允许默认值，但默认值必须在受理或明确的解析阶段解析并留证，不能运行完后用环境名称补标签。旧评测记录保留原样，对无法核对有效配置的历史记录标记“执行配置未验证”，不能改名伪装成新契约结果。

**PAGE-07：修复演练详情轮询和路由生命周期**

位置：[pollTick](E:/kimiCode/alert-web/src/views/DrillDetailView.vue:363)、[loadDetail](E:/kimiCode/alert-web/src/views/DrillDetailView.vue:373)、[挂载启动](E:/kimiCode/alert-web/src/views/DrillDetailView.vue:432)、[未按身份 key 的 RouterView](E:/kimiCode/alert-web/src/layouts/AppShell.vue:70)。

首屏立即启动 5 秒 interval，而请求最长可等待 15 秒。第一次 tick 时仍 loading，会进入 `detailState !== 'ok'` 分支并永久 stopPoll；随后请求成功不会重新启动。首屏失败后手动重试成功也可能停留在静态页面。正在恢复的演练因此可能长期显示旧状态。

同一组件内没有 watch drillId；通过路由从 A 切 B 时旧详情/事件不重置，轮询却读取新的 route.params，可能出现旧数据与新请求混合。详情与事件还共用一个 connIssue，任一路成功会清掉另一路的失败提示。

修改方法：按 drillId 建立本页生命周期；路由改变取消旧请求、清空事件/cursor/展开状态、递增 generation，再拉新详情。首轮详情成功且非终态后启动轮询；初始加载中跳过，不当作终态。手动重试成功也恢复轮询。采用“本轮请求完成后再安排下一轮”的有界 timeout，或在 interval 上加 in-flight 锁，避免慢请求叠加。隐藏时暂停，重新可见时立即刷新；卸载和身份切换取消请求。

详情和事件分别保存失败状态、最后成功时间；页头错误由二者合成。终态后停止周期刷新，但保留事件加载更多及明确的剩余游标；最后一页事件不应因为详情先终态而被描述为已全部加载。将 `@click="loadDetail"` 改成显式 `@click="loadDetail(false)"`，避免 MouseEvent 被当作 silent=true。

保留已实现的正确语义：停止 202 仅为受理，RECOVERING 不是已恢复，只有后端核验结果能驱动 CLOSED。RECOVERY_FAILED 应显示具体失败原因、环境仍占用及现有运维指引；不能在 UI 强行改成终态或释放锁。

**PAGE-08：监控各数据源独立表达失败、新鲜度与未知**

位置：[趋势与 worker 加载](E:/kimiCode/alert-web/src/views/MonitorView.vue:223)、[主机新鲜度](E:/kimiCode/alert-web/src/views/MonitorView.vue:282)、[图表有数据判断](E:/kimiCode/alert-web/src/views/MonitorView.vue:79)、[MetricsWhitelistService](E:/kimiCode/control-app/src/main/java/com/objwww/pr/control/ops/application/MetricsWhitelistService.java:53)。

确认的问题：有历史数据后，趋势和 worker 刷新失败保持 ok，仅 worker 的时间文字仍在；摘要刷新成功不代表其他区块新鲜。主机图用所有实例里最新点判断整图是否陈旧，一台停更、一台正常时，停更实例不会被标出。后端剔除 NaN/Inf 后仍保留空 series，前端只检查 series.length，结果是空白图而非“无有效样本”。

修改方法：每块维护 data、lastSuccessAt、lastError、loading；保留旧图时明确显示“刷新失败，当前为缓存数据”。新鲜度和失败是两个维度，不能只看顶栏 generatedAt。按序列显示最近有效点与 stale/unknown，任一实例过期时给出部分数据陈旧提示。图表渲染条件使用至少一个有效点；全空时显示“所选窗口无有效样本”，不要据此断言未部署 node_exporter。NaN、缺失与零值必须区分。

有界轮询防止上一次慢请求覆盖较新的窗口；现有 30 秒刷新频率无需为此更换实时传输协议。Worker 当前是按租约活动推导，页面已经明确说明，不要求为上线另造心跳平台。

磁盘口径另列 P2：当前查询对同一 instance 的各文件系统容量求和，再计算总使用率。小的数据库分区几乎满、大的数据分区空闲时，总体比例仍很低。若此图用于排障，应展示 instance + mountpoint 的使用率，或明确“容量加权总使用率”并另列最满分区。保留白名单查询，不让前端提交任意 PromQL；修改查询时同步 seriesName，不能同主机多个 mountpoint 都使用相同名字。最小验收样本：10 GB 分区占用 9.9 GB、990 GB 分区占用 0，不能用总占用 0.99% 掩盖该分区 99%。

**PAGE-09：历史对比身份与落档结果不能依赖当前列表/选择**

位置：[loadRuns/validateQuery](E:/kimiCode/alert-web/src/views/EvalCompareView.vue:422)、同文件 saveComparison、annotate。

当前只加载最近 50 条，validateQuery 将不在列表中的 query ID 清空。有效的老基线因此被当成链接失效。已有比较读取使用 cmpSeq 防乱序，这部分有效；但是 saveComparison 等待期间若选择改变，返回的旧 gateRecord 会合到新的 cmp 中。annotate 发起后若候选变动，成功跳转也读取新的 candidateId。

修改方法：列表仅供选择，不充当对象存在性判据。对 URL 指定但不在当前页的 ID，单独查详情并补入选项，只有真实 404/403 才显示相应状态；增加远程搜索或游标加载，而不是把 50 改成一个更大的固定数字。落档与标注请求捕获 baseline/candidate/caseId 及 generation，返回结果只更新对应实验对。另一种局部做法是提交期间锁定选择，但仍应捕获 ID，防浏览器路由改变。已发成功的落档可以通知其真实对象，不把记录挂到当前新对象上。

**PAGE-10：把“已受理、等待执行”做成完整状态**

位置：[新建页跳转](E:/kimiCode/alert-web/src/views/EvalNewView.vue:224)、[详情加载](E:/kimiCode/alert-web/src/views/EvalRunDetailView.vue:561)、[取消先查 run](E:/kimiCode/control-app/src/main/java/com/objwww/pr/control/eval/application/EvalCommandService.java:96)。

新建 202 返回预定 runId，run 行要等 worker 领取才创建。页面成功消息让用户接受“短暂 404 后手动刷新”；详情没有自动轮询跟踪执行阶段。已有取消服务又先查 run，因此该等待窗口里的取消返回不存在。队列延迟或 worker 不可用时，这个状态不一定短暂。

修改方案：复用已有持久化 eval_run_command，补充受理状态投影，使 run 详情可表达 ACCEPTED/PENDING/CLAIMED 以及尚无案例；或提供同等权限过滤的命令读取接口供详情过渡使用。不要为消除 404 在多个位置提前随意插 run，破坏 worker 稳定身份和幂等语义。前端只对已确认受理的对象展示等待和有界刷新；任意不存在 ID 仍应给出 404，不能全部无限重试。

非终态按 3～5 秒或现有约定频率轮询摘要/阶段；案例、用量和证据可降低频率或手动更新。终态、隐藏和卸载停轮询。排队取消应能针对已受理命令落取消意图，并保证 worker 在首次外部副作用前检查；如果本轮不支持排队取消，页面必须明确状态并禁用操作，但完整评测控制面验收仍应补齐这一能力。

3. **固定提交进行发布验收。** 后端与前端自动检查通过；在授权隔离环境按 PRT-02/07/30/45 验证预检、注入、停止、恢复、互斥与失败路径。保留本次 run/drill 与部署身份。BA-141、RV09 等既有外部验收义务按发布范围分别裁定，不以页面修复替代。

满足发布范围的 P1 全部关闭、P2 修复或明确限制、真实操作链路验收通过后，这轮即可结束，进入灰度和常规缺陷维护。首包进一步压缩、WebSocket、更多图表、重做工作流引擎、全新 worker 心跳平台不作为本轮上线条件。

如果选择暂时关闭不成熟的 E/B、动态配置和未执行的限额，只能宣布“受限范围可验收”；如果要宣布全部评测模式和故障演练控制面生产可用，必须完成相应实际执行及恢复验收。这两种完成标准应提前固定，不能以同一个“全部优化完成”概括。
