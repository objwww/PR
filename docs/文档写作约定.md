# 项目讲解与面试文档写作约定

本约定记录用户对后续项目文档的偏好：采用中文大白话和连贯段落，让句子有因果衔接，避免用大量孤立短句或专业名词代替解释。以真实告警业务为起点，按“遇到一个小问题、提出解决办法、说明办法带来的新问题、继续解决”的顺序展开，不随意换成无关业务例子。

先读当前源码，再核对文档和测试，区分代码已有能力、设计推理、历史试验、本次实测与尚未完成的方案。默认值不冒充实测值，超时不冒充服务承诺，存在一个组件不冒充业务链路已经接通。个人贡献只按真实参与说明，不把文档写作包装成业务代码已经亲自实现。

对有调用先后、状态变化、并发竞争或依赖关系的模块，在相关章节嵌入 Mermaid 图，再紧接一段解释图里的关键关系、失败分支与边界。时序图用于调用链，状态图用于允许的迁移，流程图用于分支；不要把所有情况塞进一张大图，也不为单步事实和重复工具接口机械增加图。相似工具可按域共用一张图，每个工具仍保留自身参数、结果和约束说明。

技术说明必须落到面试官能追问的程度，尤其检查线程池、并发、队列、锁、延迟、限流、取消、重试、幂等、事务、崩溃恢复及一致性。每个机制说明保护什么、源码如何实现、在哪个范围内有效、存在什么缺口，以及为何当前没有增加消息队列、缓存或其他设施。

扩展思路沿调用链逐层说明，特别区分工具目录规模与实际调用流量；覆盖登记、权限、检索、描述加载、校验、执行、结果、恢复与观测，不把待实现方案写成现有能力。大型扩展只需明确方向和触发条件，不编造容量与性能承诺。

文档末尾保留面试卡片，每张用连贯段落给出可讲述的回答，并补充继续追问时的事实边界。具体工具文档还应包含 id、version、描述、schema、返回值、错误码、幂等性、副作用、成本、延迟、SLA、权限、租户、依赖和示例；没有实现或没有测量的项目要明确写出，不能留给读者猜。
