## 第一部分：五项裁定落地

### §1 Outbox 保持八态；漂移建模为 `publication_resource`

Outbox 状态机维持 `PENDING/IN_FLIGHT/RECONCILING/RETRY_WAIT/CONFIRMED/SUPERSEDED/FAILED_TERMINAL/MANUAL` 八态，**DRIFTED 不进入 Outbox**。

理由：Outbox 八态回答"这次发布尝试进行到哪了"（命令视角、历史事实）；漂移是"远端对象现在还在不在"（资源视角、现在时）。命令 CONFIRMED 后历史不可变，远端对象的存续另建表跟踪。

**`publication_resource` 规则**：

1. T3 事务 B（标 CONFIRMED）同事务插入 resource 行（create 类命令产生新行；update 类命令引用已有行）；
2. 写入权归 Publisher（Drift Reconciler 为"Control 发起、Publisher 执行"），Control 只读；
3. 漂移修复 = 新 Outbox 命令（新 operation_id），原命令保持 CONFIRMED，resource 行记录 `state=DRIFTED → REPAIRED` 与 `repaired_by_operation_id`；
4. 不可逆外部副作用（删评论、关 PR）修复档位为"仅告警 + 人工"，不自动收敛（证据：Flux suspend / K8s finalizer 惯例，见证据清单 C-3）。

```sql
create table publication_resource (
    id                        uuid primary key,
    resource_type             varchar(32) not null,
    created_by_operation_id   uuid not null references outbox_command(operation_id),
    pr_subject_id             uuid not null references pr_subject(id),
    remote_id                 text not null,
    remote_url                text,
    marker                    text,
    state                     varchar(24) not null default 'ACTIVE',
    drift_detected_at         timestamptz,
    repaired_by_operation_id  uuid references outbox_command(operation_id),
    created_at                timestamptz not null,
    updated_at                timestamptz not null,

    constraint ck_pub_resource_type
        check (resource_type in (
            'CHECK_RUN','PR_COMMENT','REVIEW','REVIEW_COMMENT',
            'FIX_BRANCH','CHILD_PR'
        )),
    constraint ck_pub_resource_state
        check (state in ('ACTIVE','DRIFTED','REPAIRED','RETIRED')),
    constraint uq_pub_resource unique (resource_type, remote_id)
);
```

`RETIRED` 用于"终结旧世代自身对象"类命令正常关闭的旧对象（如旧 Check 标 cancelled）。

### §2 Patch 状态机：加 `VERIFICATION_FAILED` + `failure_class`

- `ck_patch_state` 增加 `'VERIFICATION_FAILED'`，状态机 `VERIFYING → VERIFIED | VERIFICATION_FAILED`；
- 新增列 `failure_class varchar(24)`（`TESTS_FAILED | INFRA | TIMEOUT`，仅 VERIFICATION_FAILED 时非空）；
- `TESTS_FAILED`：终态，修复必须新提案（新 digest 天然新身份）；
- `INFRA/TIMEOUT`：允许 `VERIFICATION_FAILED → VERIFYING` 回流转（新建 verification Step/Attempt，受 max_attempts 约束），耗尽后停在失败态等人工；**不存在任何自动路径通往 VERIFIED**（安全步骤 fail-closed）。

不拆双终态的理由：门禁判断（AFT-08 查 `state = VERIFIED`）必须保持单点，分类用列表达。

### §3 Fence = `revision_id + publication_epoch`

**冻结规则**：

1. `pr_subject` 加 `publication_epoch bigint not null default 0`；
2. T1 中 `current_revision_id`/`current_policy_version` 变更与 `publication_epoch + 1` **同事务**提交；
3. `outbox_command` 加 `publication_epoch bigint not null`，插入时在同一行锁下与 `aggregate_sequence` 一起从 `pr_subject` 取出——命令不可能带过期 epoch 被铸造；
4. Publisher fence：`command.publication_epoch = subject.publication_epoch`，不等则 supersede（走 v2.1 修订三路径）；
5. **分类型 fence 保留**（F9）：`outbox_command` 加 `fence_mode` 列——`CURRENT_EPOCH`（影响当前修订结论的写，过 epoch 栅栏）/ `OWNED_GENERATION`（终结旧世代自身对象的写，绑定所属旧 epoch，放行）；
6. **epoch > 当前值 ≠ fence**：视为读取陈旧，可重试（证据：KIP-320 `UNKNOWN_LEADER_EPOCH` 双错误码设计，证据清单 C-1）。

**明确拒绝的替代方案**（有据）：Kafka 调研建议"epoch 仅在写者身份变更时递增，revision 另做乐观并发号"。不采纳——Kafka fence 的是僵尸写者存活，我们 fence 的是**结论时效**；revision 变化废掉在途旧结论写命令是 F9 的设计目标，不是误伤。

### §4 Digest 约束条件化

```sql
constraint ck_patch_verified_digest
    check (
        state <> 'VERIFIED'
        or (verified_patch_digest is not null
            and verified_patch_digest = patch_digest)
    )
```

替换原 `ck_patch_digest_consistency`。理由：无条件 CHECK 会把"验证对象 ≠ 提案对象"这一换包事故挡在库外，丢失取证事实；条件 CHECK 既允许记录失配（状态停在 VERIFICATION_FAILED），又守住"VERIFIED 必须同一对象"的不变量。AFT-08 的完整判定仍在 FencedPublicationExecutor，DB 约束只是第二道防线（B25）。

### §5 新增最小 `review_finding` 与 `artifact` 表

```sql
create table review_finding (
    id                    uuid primary key,
    review_run_id         uuid not null references review_run(id),
    pr_revision_id        uuid not null references pr_revision(id),
    fingerprint           char(64) not null,  -- head_sha/file/range/rule/message_hash
    rule_id               text not null,
    severity              varchar(16) not null,
    file_path             text not null,
    line_start            integer,
    line_end              integer,
    body_artifact_digest  char(64),
    state                 varchar(24) not null default 'PENDING',
    created_at            timestamptz not null,

    constraint uq_finding_per_run unique (review_run_id, fingerprint),
    constraint ck_finding_state
        check (state in ('PENDING','PUBLISHED','SUPERSEDED','WAIVED'))
);

create table artifact (
    digest          char(64) primary key,
    artifact_type   varchar(32) not null,
    size_bytes      bigint not null,
    storage_path    text not null,
    created_at      timestamptz not null
);
```

MVP 批量 Review 时 finding 与 `PUBLISH_REVIEW` 命令是 N:1，finding 表只登记不逐条驱动发布；`fingerprint` 为 M5 行级评论幂等预留挂载点（冻结文档 §5.4）。artifact 表只做登记，GC/retention 策略另行 ADR，不在本稿膨胀。

## 第二部分：开源证据驱动的十条修正

> 每条括号内为证据清单索引。完整出处 URL 见《OSS-证据清单-v1.md》。

**E1. fence/lease 比对必须落在存储端、与状态推进同事务原子完成。**
禁止 worker 内存自检后再写。外部 GitHub 写无法被本地 CAS 保护，顺序固定为：本地事务（校验 epoch + sequence → 原子 claim）→ 外部写 → 结果回账本 → 不确定由 Reconciler 收敛。（证据 A-5/C-4：Kleppmann fencing token 红线、K8s resourceVersion 409、HBase/GC 停顿事故）

**E2. 补 sequence 跳号检测。**
Publisher 领命令时同事务校验 `aggregate_sequence = last_applied + 1`；跳号 = 致命，触发对账而非静默跳过。`last_applied_sequence` 为 `pr_subject` 持久字段，不得存内存；outbox 清理不得破坏序列可推导性。（证据 C-2：KIP-98 `OutOfOrderSequenceException` 语义）

**E3. 依赖判定终态归类表（替代含糊的"视命令而定"）。**

| 前置终态 \ 模式 | REQUIRE_CONFIRMED | REQUIRE_TERMINAL | OPTIONAL |
|---|---|---|---|
| CONFIRMED | 放行 | 放行 | 放行 |
| SUPERSEDED | 级联 supersede（v2.1 修订二先行） | 级联 supersede | **不级联**，可放行 |
| FAILED_TERMINAL | 本命令 → SUPERSEDED（前置不可达，终态取消） | 放行 | 放行 |
| MANUAL | 等待人工判定 | 等待人工判定 | 等待人工判定 |

推论：v2.1 修订二的级联规则修正为**尊重 dependency_mode**——`OPTIONAL` 依赖不被级联 supersede。（证据 D-4：Airflow trigger_rule 的 skip 语义踩坑史、Argo `.Omitted` 操作数）

**E4. 防"空转成功"。**
三 hash 同一性门校验**等集且非空**：`verified_hashes == approved_hashes == published_hashes`，不允许空集合通过，不允许仅包含关系。（证据 D-5：Atlantis #6529 的 0/0 apply 空转成功事故）

**E5. 安全门禁 fail-closed 显式冻结。**
Publisher 二次校验依赖的数据源不可读时，禁止放行。反面先例：Binary Authorization 在 BinAuthz 服务不可达时官方 fail-open（pod 照常部署）。（证据 D-2）

**E6. Token 策略措辞修正。**
D2 的"按操作现铸"改为："铸造时收窄 repo + permission scope（GitHub 官方支持），同 scope token 在 TTL 内允许缓存复用"。理由：每次现铸消耗 API 速率限额，GitHub 官方最佳实践明确建议缓存至过期。（证据 D-3）

**E7. 沙箱 egress 网络策略补齐。**
Job Container 默认 deny 全部出站，仅白名单放行（如依赖仓库镜像源）。注意两个坑：allow 规则永远优先于 deny；被拦截的 TCP 连接从沙箱内看可能"假成功"（防火墙先 accept 再判定），探测逻辑不得依赖连接失败信号。（证据 B-3：E2B 网络文档）

**E8. 审批失效自包含。**
"revision 或 patch 变化 → 审批失效"的判定全部在账本会话内完成，**不依赖** GitHub 的 "Dismiss stale approvals" 等外部配置（漏配即裸奔）。（证据 D-1：Atlantis #1508 教训）

**E9. 回放确定性约束 + 版本兼容机制。**
- 录制回放/Projection 重建：副作用永不重跑，只读历史结果；重执行 = 新 Run（冻结文档已有，现补出处）；
- prompt/模型/工具 schema 变更等价于 Temporal 的 workflow 代码变更——每次变更必须过"历史账本回放兼容性测试"，否则回放功能在第一次升级后失效；
- `review_run` 加 `root_run_id uuid references review_run(id)`，与 `parent_run_id` 组成双字段 lineage（链首 + 直接父代）；
- 隔离重执行的锚点只允许落在"步骤完成事件"边界上，不允许账本中间任意位置切开。（证据 A-1/A-2/A-8：Temporal Reset、GetVersion、Replayer、first/original_execution_run_id）

**E10. 账本噪声控制。**
attempt 的 start 不全量进 `execution_event`（重试链路会淹没账本）；attempt 计数存 projection/mutable 字段按需查询，账本只记终态结果事件与关键事实。（证据 A-3：Temporal 刻意让 `ActivityTaskStarted` 在终态前不入历史）

## 第五部分：v2.3 增量（M1 编码期两项产品行为变更，评审对账驱动）

> 性质：不改变 v2.2 冻结的表结构与状态机，属于已冻结机制的参数化收紧。两条均已在 M1 编码中实现并测试。

### §6 Outbox payload 增加 `installation_id`，Executor 触网前预检

- **变更**：`outbox_command.payload_json` 新增必填字段 `installation_id`，由 Control 在铸造命令时从 `pr_subject.github_installation_id` 写入（T2 内）。`FencedPublicationExecutor` 在 T3-A fence 判定 PROCEED 之后、首次触网之前比对 `payload.installation_id` 与本进程配置的 `publisher.github.installation-id`：错配 → 命令直接 `FAILED_TERMINAL("INSTALLATION_MISMATCH")` + `SAFETY_REJECTED` 事件，**零触网**。
- **原因**：安装体重铸/错挂是 Publisher 唯一无法靠 revision fence 发现的越权写场景（fence 管世代，不管"写到谁的仓库"）。二次授权由"PR 归属 installation 白名单"（§D2 措辞）落地为可强制执行的字段比对。
- **边界**：预检只在发布路径（execute）；reconcile/sanityRead 探测路径不预检（读不造成越权写）。repo 维度白名单未做，记为已知残余（installation 已收敛到单安装体，风险可接受）。

### §7 Finding 锚定唯一性（INC-30）

- **变更**：FindingMapper 两级匹配（精确子串 → 行级 trim）均要求唯一命中；多重命中 → 该 Finding 丢弃并计 dropped，不猜第一处。
- **原因**：ADR-014/E9"锚点受限"的实现层兑现——歧义定位的静默猜测会污染行号事实。
