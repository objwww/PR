**三、逐项怎么修改**

**RV01：先封住通知预览的 HTML 输出边界。**

位置：[DutyChatView.vue:204](E:/kimiCode/alert-web/src/views/DutyChatView.vue:204)，危险输出挂点在同文件第 52 行 `v-html="renderMd(item.msg.body)"`。

当前 `escapeHtml` 只转义 `& < >`；链接匹配允许 URL 中有 `"`，随后把匹配内容拼进 `href="$2"`。本次只使用无网络、无数据读取的标记输入，生成结果含一个真正的 `onmouseover` 属性。存储输入来源包括 DutyQueryController 的通知回写/手动测试入口，以及告警标签拼出的正文；它们存在鉴权，但“允许提交正文”不应等于“允许在其他查看者浏览器执行脚本”。本次未运行完整浏览器/数据库链路，生产可利用程度还与部署 CSP 和可写身份有关。

推荐的最小修法：保留现有有限 Markdown 外观，在 `renderMd` 的最终输出、进入 `v-html` 之前，用成熟 HTML sanitizer 做最后一道严格白名单净化。借鉴 DOMPurify，只允许当前实际需要的 `a/b/br/div/span` 等标签、`href/target/rel/class` 属性；URL 仅允许 http/https，拒绝事件、style、SVG、MathML。净化之后不得再做字符串替换。增加依赖是为安全解析，不是为增加 Markdown 功能。

如果愿意把当前子集改成 Vue 文本/VNode 渲染，也可彻底移除 `v-html`：文本作为 text node，链接用 Vue `:href` 且单独校验协议，不拼 HTML。不要一边自写 HTML tokenizer 一边再扩大 Markdown 支持。

仅给 `escapeHtml` 增加双引号转义可以封住本次样例，但原有 `<font color="...">` 的识别正则也要同步修改；后续粗体/链接正则还会处理已经生成的 HTML，不能只凭一个样例绿就认为所有组合安全。

验收：T01～T04。优先级高于拆包和样式调整。

**RV02：把“引用存在、载荷可查、定位成立、作用可授予”分开判断。**

位置：[PrimaryClaimAdmission.java:175](E:/kimiCode/control-app/src/main/java/com/objwww/pr/control/alert/application/agent/PrimaryClaimAdmission.java:175)，`verdictFor`；同文件第 263 行 `Integer.parseInt(segment)`；消费面 [ContextAssembler.java:803](E:/kimiCode/control-app/src/main/java/com/objwww/pr/control/alert/application/agent/ContextAssembler.java:803)。

当前具体行为：

- ref 已在 `validRefs`，但仓库读回为空时，模型提议的 SUPPORTS 保留。
- locator 查不到时，只清空 locator，SUPPORTS 和 ROOT_CAUSE 仍可保留。
- 数组节点下 locator 段为 `2147483648` 时，`Integer.parseInt` 抛出 NumberFormatException。它是模型输出错误，不能让正常的业务准入过程失控。
- REFUTES 不经过与 SUPPORTS 对称的内容限制。`EXCLUSION` 下游资格也不能只由非空 refs 和任意 REFUTES 条目决定。

修改顺序：

1. 保留现有 validRefs 白名单，继续拒绝越界引用；不要删除它另造准入入口。
2. UUID 证据读回缺失、跨 Run、载荷不可解析，均返回 CONTEXT + 明确 reason，或拒绝当前 Claim。已有 PostgresEvidenceRepository 在读时调用 `EvidenceEnvelope.verify` 校验摘要，不重复声称这里完全没有完整性校验。
3. 非 UUID 的合法 artifact 应有明确可验证的 artifact 类型处理；如果仅能证明引用身份而不能证明内容支持，就保留上下文资格，不能因为“不是证据表 UUID”而自动授予 SUPPORTS。
4. locator 是可选的：未提供 locator 可以按工具专属规则验证；提供但定位失败则不能继续沿用该引用的 SUPPORTS/REFUTES。数组下标加长度/数值边界，捕获 NumberFormatException 并返回“定位失败”。例如 `try { ...parseInt... } catch (NumberFormatException e) { return false; }`，同时限制路径长度/段数。错误应只影响当前引用。
5. SUPPORTS/REFUTES 都要检查窗口、服务范围、generation/snapshot 和工具结果类型。先利用现有 EvidenceEnvelope 元信息和冻结时间窗；确实缺指标类型再扩结果元数据。不依靠自然语言字符串相似度证明因果。
6. `_total` 规则只覆盖部分累计指标；histogram `_count`、无 `__name__` 的表达式结果应由算子/类型标记判定。`rate/increase` 的时间窗也要与调查窗绑定。ERROR 数量可以支持“出现错误”，不自动证明“新版本导致错误”。
7. `ContextAssembler` 与 Claim projector 只消费准入产物；EXCLUSION 的 REFUTES 必须对应此 Claim 的有效 ref。历史 `[EX]` 前缀可兼容清理，但不能成为永久免检凭证。

迁移注意：旧结果中原来被错误授予 ROOT_CAUSE 的行不要静默改写历史，应标出旧准入策略版本或通过明确的重评流程生成新结果。新规则会增加 HYPOTHESIS/未决比例，这是纠正证据资格后的预期，不应为保住“根因命中率”放宽准入。

验收：T05～T11。

**RV03：在执行体退出时回收在飞事实。**

位置：[ToolGateway.java:151](E:/kimiCode/control-app/src/main/java/com/objwww/pr/control/alert/application/tool/ToolGateway.java:151)、[InFlightToolCancels.java:27](E:/kimiCode/control-app/src/main/java/com/objwww/pr/control/alert/application/tool/InFlightToolCancels.java:27)。

当前等待线程在 `future.get` 因 cancel 返回后，finally 立即 unregister；Java 的 `cancel(true)` 只请求中断，不能证明执行体已经退出。本次探针让执行体短暂忽略中断，结果 `reported_inflight=0`、`actual_executor_exited=false`，最后主动释放并回收线程。

最小设计沿用现有 ToolGateway 和有界执行池，增加每次调用的执行句柄，而不是新增任务平台：

| 句柄状态 | 谁推进 | 在飞计数是否保留 |
|---|---|---|
| QUEUED | 入池前注册 | 保留，或单列 queued 计数 |
| RUNNING | 执行包装器 CAS 开始 | 保留 |
| STOP_REQUESTED | 取消动作标记，同时请求中断 | 仍保留 RUNNING 事实 |
| CANCELLED_BEFORE_START | 取消与开始 CAS 竞争获胜，证明执行体不会启动 | 回收 |
| EXITED | 实际执行包装器 finally | 回收 |

`STOP_REQUESTED` 最好作为独立标记，与 QUEUED/RUNNING/EXITED 正交。入池拒绝也必须走回收路径。调用方 finally 只结束“等待”，不释放仍在执行的句柄；`FutureTask.done()` 在取消时也可早于 callable 退出，不能把它当执行退出回调。

注册/删除使用同一个按 Run 的原子 `compute` 操作，避免 `computeIfAbsent→add` 与 `empty→remove` 交错把新成员加到已移除的 Set。取消时标记与获得待取消句柄应有一致的 Run 状态；不要在持锁时执行慢 I/O。

`stopCancelled` 当前无回收路径。终态且注册/排队/执行全部结束后回收取消墓碑，新的动作仍通过持久 Run 终态检查拒绝。不能简单加五分钟 TTL 然后允许旧 Run 再注册。

单进程在飞数仍须明确标注作用域。跨实例依靠持久终态检查、deadline、执行器自己的超时/关闭资源，不能靠本机 Map 宣称全系统静默。对外部系统实际工作是否结束也只能按协议确认，本地线程退出不是远端完成证明。

验收：T12～T16。不要用 Thread.stop 或随意回收 UNKNOWN 预算规避问题。

另有两个需真 PG 交错测试的静态问题：

- `submit` 先读未命中再 INSERT；唯一冲突在事务内部 catch，然后立即 SELECT。在没有 savepoint 的 PostgreSQL 事务中，唯一冲突使事务进入失败状态，后续 SELECT 不能作为正常恢复路径。现有 IT 验证的是串行重复提交，没有验证这个双事务并发分支。建议仓储使用 `INSERT ... ON CONFLICT (message_id) DO NOTHING`，返回是否插入，再在 READ COMMITTED 下另条查询读取胜者；或者让失败事务完全回滚后在事务外重读。不要在 catch 中 `orElse(receipt)` 返回一条未持久化的“既成回执”。
- 回执事务仅 `runs.findById` 读取活跃状态，取消可能在其检查后提交、回执随后仍记 ACCEPTED。复用已有 `findByIdForUpdate` 或在统一短事务收尾中采用既有锁序，明确线性化点；若回执先提交、取消后提交，回执不算迟到。不要未经锁序审查机械加锁导致死锁。

这两个点尚未用真实 PG 并发重现，报告将其列为代码风险，不写成线上已发生。验收：T17～T22。

**RV05：通知错误落账用 Jackson 序列化，reason 保持固定码。**

位置：[FencedNotifyExecutor.java:124](E:/kimiCode/notify-app/src/main/java/com/objwww/pr/notify/domain/service/FencedNotifyExecutor.java:124)、同文件第 153 行。

当前 `errorJson` 自己拼 JSON；detail 只替换斜杠和双引号，不处理换行，reason 完全未转义。`retry` 又把上游 errmsg 同时传成 reason/detail。一个合法响应 `errcode≠0` 且 errmsg 含引号或换行，就能让生成的 last_error 不是合法 JSON。

后果链：PostgresNotifyOutboxStore 的 `cast(:lastError as jsonb)` 拒绝更新→claimer 捕获异常→行留 CLAIMED→租约回收后重试→尝试数未能落库推进。它比“错误信息显示难看”严重，会破坏重试预算和退出机制。本次用实际执行器和 JSON parser 复现非法字符串，没有执行真实 PG CAST。

最小修改示意（沿用项目已有 Jackson，不加库）：

```java
private static String errorJson(String reason, String detail) {
    var value = JSON.createObjectNode();
    value.put("reason", reason);       // 固定枚举码，如 channel_retryable
    value.put("error", detail == null ? "" : detail);
    return value.toString();
}
```

将 retry 参数分为 reasonCode 和 detail：如 `channel_retryable` + `business_code_123: ...`；不要把自由文本作为枚举原因，也不要把原始含敏感信息的异常无限制写库。现有 snippet/脱敏能力可复用。

**RV06：在统一发送执行器处理 null 渠道。**

**RV07：最长通知期限放到真实发送之前，时间在对应事件发生时取。**

位置：[FencedNotifyExecutor.java:64](E:/kimiCode/notify-app/src/main/java/com/objwww/pr/notify/domain/service/FencedNotifyExecutor.java:64)。

当前年龄检查只在 retry 分支，48 小时前的通知仍可在 24 小时上限配置下发送并落 SENT。本次已复现。它没有保证“最长通知期限”，只保证“遇到本次失败后不再安排重试”。

在 execute 开头（至少在 channel.send 前）判 `now >= createdAt + maxAge` 就 DEAD，零触网；retry 时保留二次期限检查，避免一次长耗时发送跨越边界后再安排旧消息。`markSent` 使用发送确认后的 `clock.get()`，当前发送前取得的 now 只能叫 startedAt，不能准确充当 sentAt。若产品允许“积压多久都可首发”，则必须把配置和文档改成明确的重试期限，而不是继续称最长通知年龄。
