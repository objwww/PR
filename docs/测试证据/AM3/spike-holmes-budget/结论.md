## 一、问题①：能否在每次真实模型调用前硬拦预算？

### 判定：holmes 原生【不能按 token/成本硬拦】（BEST_EFFORT）；LiteLLM proxy 层【能硬拦】

**1) holmes 原生无预算参数 —— 全量源码扫描 0 命中。**
对部署包 195 个 `holmes/**/*.py` 以 `max_budget|budget_duration|BudgetConfig|max_cost|
cost_track` 等词表全文扫描：预算类参数零命中（`源码审计.md §0`）。holmes 只有
用量记录（`core/llm_usage.py`、`core/tool_calling_llm.py:1226-1241` 记账不拦截）。

**2) 原生仅有的两个上限（均为 BEST_EFFORT，但都是"调用前"生效的真拦截）：**

- **`max_steps`（LLM 调用次数上限）——实测确认为硬拦**。
  依据：`core/tool_calling_llm.py:1154` `while i < max_steps:`（每次迭代恰一次
  completion 调用，`:1216`）；达上限抛
  `tool_calling_llm.py:1533-1535` `Too many LLM calls - exceeded max_steps: {i}/{max_steps}`；
  默认 100（`config.py:103`），CLI `--max-steps` 可覆盖（`main.py:107`）。
  实验（Exp2，echo 假端点驱动无限工具调用循环）：`--max-steps 1/2/4` 三档，
  echo 端实测收到的调用次数恰为 **1 / 2 / 4**，holmes 全部以
  `Exception: Too many LLM calls - exceeded max_steps: 1/1、2/2、4/4` 终止
  （`evidence/exp2_*`）。
- **`max_tokens`（单次调用输出上限）——实测精确生效**。
  依据：`core/llm.py:708-717` "An explicit max_tokens / max_completion_tokens in
  model args wins"；注入路径：`model_list.yaml` 条目任意额外键直通
  `litellm.completion()` kwargs（`ModelEntry extra="allow"` `core/llm.py:211-213` →
  `config.py:788-821` → `core/llm.py:763-778`）。
  实验（Exp1/Exp3）：不注入时请求体 `max_tokens=64000`（holmes 默认输出预留）；
  model_list 写 `max_tokens: 64` → 请求体精确出现 `"max_tokens": 64`
  （`evidence/exp1_echo_req_plain.log`、`evidence/exp3_echo_req_capped.log`）。
- **BEST_EFFORT 的含义**：`max_steps × (context_window + max_tokens)` 给出一次
  调查的确定性 token 上界，但无法表达"本次调查最多花 X token / ¥Y"这类精确预算。

**3) 真正的调用前预算硬拦应放在 LiteLLM proxy 层 —— Exp5 实证【能硬拦】。**

- **实验形态**：proxy = 官方镜像 `litellm/litellm:1.89.0`（与 holmes 客户端同版本，
  经 195 已配镜像加速从 docker.io 拉取）+ postgres 16-alpine（SpendLogs/虚拟 key 台账）；
  上游即 195 `.env` 的真实兼容端点；holmes 的 model_list `base_url` 指向 proxy、
  `api_key` 用 per-run 虚拟 key（`key_alias=spike-run-holmes`，`max_budget=0.0001`，
  proxy 侧按 token 钉死单价使预算确定性触发）。
- **e2e 先通**：holmes 经 proxy 正常完成一次调用并返回 "AI: PING"，exit=0
  （`evidence/exp5_holmes_via_proxy.log`）；该次调用真实计费 **$0.002933**
  （prompt 5864 tok，SpendLogs 原文）。
- **超限后下一跳 = 调用前拒绝（硬拦成立）**：同 key 再请求 → **HTTP 429、0.017s**
  （真实调用 0.595s，快 ~35 倍 = 请求未出 proxy），body
  `{"error":{"message":"Budget has been exceeded! Current cost: 0.002933, Max budget: 0.0001","type":"budget_exceeded","code":"429"}}`
  （`evidence/exp5_budget_reject_status.txt`、`exp5_budget_reject_1.json`；两轮独立复跑同结果）。
- **拒绝点在 proxy auth 层（先于任何模型调用）**：proxy ERROR 日志给出栈
  `user_api_key_auth → _virtual_key_max_budget_check`（`litellm/proxy/auth/auth_checks.py:3547`
  抛 `BudgetExceededError`，`evidence/exp5_proxy_budget_lines.log`）；访问日志
  `POST /chat/completions → 429`（`exp5_proxy_access_log.txt`）；被拒调用在 SpendLogs
  只落一行 `status=failure`、spend=0、tokens=0 的记录（`exp5_spendlogs.txt` RECORD 1）
  —— 上游模型零流量、零计费。
- **超额状态持久化**：spend 异步 flush 后 key 台账 `spike-run-holmes spend=0.002933 >
  max_budget=0.0001`（`exp5_key_state_after_flush.txt`；拒绝瞬间的在途判定读的是内存
  缓存，即时生效）。
- **坑位记录（M3-24 运维手册直接可用）**：① holmes 镜像内 pip 装 `litellm[proxy]`
  起不来（缺 Prisma node binaries，take-1，本文件头部已记）——**用官方镜像
  `litellm/litellm` 经 daocloud/腾讯/dockerproxy 加速可正常拉取**；② 195（CentOS 7
  内核 3.10）上 `postgres:16-alpine` 首次 initdb 写文件报 EPERM（musl 调
  `fchmodat2`，老内核未知，docker 默认 seccomp 对未知系统调用回 EPERM 且 musl 不回退）
  —— spike 容器加 `--security-opt seccomp=unconfined` 解决（一次性容器/独立网络/
  不发布端口；生产 pg 数据目录已初始化则不受影响）。

### 附带实测：预算校准基线

holmes 空载（一次最简单调用、仅 internet 工具集 8 个工具）的真实 prompt 开销：
**3 次同一固定 prompt 实测完全一致 `prompt_tokens=4545 / completion_tokens=1 /
total_tokens=4546`**（Exp4，真实端点（195 `.env` `AGENT_MODEL_ID=qwen-plus`，
非生产 compose 的 deepseek-v3，提示词底座与模型无关），`evidence/exp4_holmes_real_1..3.log`）。
→ AM3 预算模型应按"每调用 ~4.5k token 底座 + 工具结果增长"校准；调用次数 × 底座
即可由 `--max-steps`/model_list `max_tokens` 折算成粗预算。
（同批捕获到 holmes 告警：model_list 未配 `input_cost_per_token/output_cost_per_token`
时 holmes 侧成本记 0 —— AM3 落码需补。）

## 二、问题②：能否透传自定义 metadata（run_id/attempt_id）供 LiteLLM spend log 对账？

### 判定：【能透传】，通道为 HTTP 头（EXTRA_HEADERS）与请求体（model_list `extra_body`）双通道；但均为**实例级静态注入**，且请求头不落 SpendLogs

**1) HTTP 头通道 —— 实测到达端点。**
`EXTRA_HEADERS` env（JSON）→ `core/llm.py:676-677`
`self.args.setdefault("extra_headers", json.loads(EXTRA_HEADERS))` → 每次调用的
HTTP 头。实验（Exp1）：holmes 向假端点发出的每个请求都带有注入的
`X-Run-Id: run-20260905-spike`、`X-Attempt-Id: attempt-1`、
`x-litellm-metadata: {"run_id":"run-20260905-spike","attempt":1}`
（`evidence/exp1_echo_req_plain.log` 截获原文）。

**2) 请求体通道 —— 实测到达，且正中 LiteLLM SpendLogs 白名单字段。**
`model_list.yaml` 条目写
`extra_body: {litellm_metadata: {spend_logs_metadata: {run_id: ..., attempt_id: ...}}}`
→ 请求体原文出现
`"litellm_metadata": {"spend_logs_metadata": {"run_id": "run-FROM-HOLMES-XBODY", "attempt_id": "a1"}}`
（exp_c1 实验，`evidence/expc1_reqs.jsonl`）。而 litellm proxy 的 SpendLogs
metadata 白名单恰好含 `spend_logs_metadata`（"special param to log k,v pairs to
spendlogs for a call"，`litellm/proxy/_types.py:3596-3621`），proxy 从请求体的
`litellm_metadata`/`metadata` 字段提取（`litellm/litellm_core_utils/core_helpers.py:177-186`）。

**3) 走不通的通道（负证据，避免 AM3 踩坑）：**
- 直接 kwargs `user=` / `metadata=` / `litellm_metadata=`（不经 extra_body）：
  litellm 1.89.0 客户端在 openai 兼容路由上一律**不放进请求体**（微实验 K1：
  body 仅 `[max_tokens, messages, model]`；源码：三者只进客户端本地
  `litellm_params`，`litellm/main.py:1601-1618`）。
- HTTP server 形态无 per-request 注入点：`/api/chat` 的 `meta` 字段只进 holmes
  自家用量事件（`core/usage_recorder.py:147`），passthrough headers 只给工具集
  （`/app/server.py:504-529`），均不进 LLM 调用 → **注入粒度 = holmes 实例
  （容器）启动时的 env/model_list，不能按单次调查 API 请求变化**。

**4) SpendLogs 实际落库对账 —— Exp5 实证（proxy=官方镜像 1.89.0，`evidence/exp5_spendlogs.txt` 三行全景）：**

| 行 | 来源 | key_alias | spend | tokens(in/out) | metadata.spend_logs_metadata | 结论 |
|---|---|---|---|---|---|---|
| 1 | 超预算被拒调用 | spike-run-holmes | 0 | 0/0 | null | `status=failure` + `error_class=BudgetExceededError`——硬拦调用零计费、不污染账本 |
| 2 | **holmes 经 proxy**（model_list `extra_body` 注入） | spike-run-holmes | 0.002933 | 5864/1 | `{"run_id":"run-HOLMES-001","attempt_id":"a1"}` | **端到端：holmes 侧注入直达 SpendLogs** |
| 3 | curl 直连（body `metadata.spend_logs_metadata` + 头 `X-Run-Id: run-HEADER-002`） | spike-run-meta | 2.1e-05 | 10/16 | `{"run_id":"run-BODY-002","attempt_id":"a1"}` | body 通道落库 ✓；**`run-HEADER-002` 全表无踪——请求头不落库（负证据成立）** |

- 每行 metadata 同时自带 `user_api_key_alias` 与 `user_api_key`（sha256 hash，非明文）
  → **run 级（key 级）对账零成本**，key 台账（`LiteLLM_VerificationToken`）另按
  `key_alias` 聚合 spend（`exp5_key_state_after_flush.txt`）。
- 版本差异注记：1.89.0 的 SpendLogs **没有独立 `api_key_alias` 列**（alias 在
  metadata JSON 内；表结构 dump 见 `exp5_spendlogs_schema.txt`）——AM3 查询/报表
  按 metadata JSON 取，或升级 litellm（新版才有独立列）。

## 三、对 AM3 M3-26 的落地建议（不改 holmes 源码）

1. **预算硬拦**：eval-runner 每个 run 生成一个 LiteLLM proxy 虚拟 key
   （`key_alias=run_id`，`max_budget=单 run 预算`），holmes 容器的
   model_list `base_url` 指向 proxy、`api_key` 用该 key —— 超限在模型调用前
   被拒（Exp5：HTTP 429 / 0.017s，auth 层 `BudgetExceededError`，上游零流量），
   同时天然按 key_alias 对账。holmes 原生 `--max-steps` + model_list `max_tokens`
   继续作为第二道粗闸（防单 run 失控）。
2. **对账**：
   - key 级（run 级）：SpendLogs 自带 `api_key_alias` —— 零成本；
   - attempt 级：model_list `extra_body.litellm_metadata.spend_logs_metadata`
     注入（per-instance 静态；eval-runner 按 run 起容器时天然 per-run），
     或 proxy 侧加自定义回调把 `X-Run-Id` 头转写进 spend log（holmes 侧头通道
     已验证可用）。
3. **成本记账补丁**：model_list 条目应补 `input_cost_per_token/output_cost_per_token`
   —— 否则 holmes 侧 cost 全记 0（Exp4 实际捕获到该告警）。
4. **预算基线**：按 ~4.5k token/调用底座（Exp4）× max_steps 估算单 run 上界。

## 200 字结论摘要

holmesgpt 0.40.0 原生**无** token/成本预算硬拦（源码全量扫描零命中），仅有
`--max-steps`（调用次数，实测 1/2/4 档精确硬拦并报 "Too many LLM calls"）与
model_list `max_tokens`（单调用输出上限，实测 64 精确生效）两个 BEST_EFFORT 上限。
精确硬拦在 LiteLLM proxy 层用 per-run 虚拟 key `max_budget` 实现——Exp5 官方镜像
1.89.0 实证：holmes 经 proxy e2e 正常、计费 $0.0029 后同 key 下一跳 HTTP 429/16ms
auth 层拒绝（上游零流量、SpendLogs 仅留 failure 行）。透传**可行**：EXTRA_HEADERS
（HTTP 头）与 model_list `extra_body.litellm_metadata.spend_logs_metadata`（请求体）
双通道实测到达端点，后者正中 proxy SpendLogs 白名单并已实证落库（含 holmes e2e）；
请求头实测不落库；`user/metadata` 直传 kwargs 与 `/api/chat` per-request 数据均进不了
LLM 请求。空载基线 ~4.5k token/调用（4545，三次实测零方差）。holmes 零改码。
