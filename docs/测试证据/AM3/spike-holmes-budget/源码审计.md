> 审计对象：`holmesgpt-am1` 容器实际部署的包（`/usr/local/lib/python3.12/site-packages/holmes/`，
> 2026-09-05 以 tar 流方式只读导出，195 容器未写入）。版本：holmesgpt **0.40.0** /
> litellm **1.89.0** / openai **2.54.0** / fastapi 0.136.3 / uvicorn 0.40.0。
> 镜像 `local/holmesgpt:am1-http`（构建自 `deploy/alert/holmesgpt/Dockerfile`，
> `pip install holmesgpt==0.40.0` + vendor server.py）。
> 引用格式 `文件:行号` 均指向包内 `holmes/` 或 `litellm/` 实际源码。

## 0. 全量扫描结论

对 195 个 `holmes/**/*.py` 全文正则扫描（脚本 `_audit_holmes.py`，词表含
`max_budget|budget_duration|BudgetConfig|max_cost|spend|cost_track|max_tokens|max_steps|
extra_headers|extra_body|metadata|callbacks` 等）：

- **0 处**命中 `max_budget` / `budget_duration` / `BudgetConfig` / 成本上限类配置
  → holmes **原生没有按 token 金额/成本的预算拦截**。
- 命中的预算相关机制只有两类：**调用次数上限（max_steps）** 与 **单次调用输出 token 上限（max_tokens）**，见下。

## 1. 预算侧：两个原生上限（粗粒度，BEST_EFFORT）

### 1.1 max_steps —— 一次调查的 LLM 调用次数硬上限（真拦截，在调用前判定）

- `config.py:103`：`max_steps: int = 100`（默认 100，CLI `--max-steps` 可覆盖，
  `main.py:107` 定义选项，`main.py:210/301/…` 透传）。
- `core/tool_calling_llm.py:1154`：`while i < max_steps:` —— 每次迭代恰对应一次
  `litellm.completion` 调用（`:1216` `full_response = self.llm.completion(...)`）。
- `core/tool_calling_llm.py:1161`：`tools = None if i == max_steps else tools`
  —— 最后一次调用强制剥离工具，逼模型收敛输出。
- `core/tool_calling_llm.py:1533-1535`：
  ```python
  raise Exception(
      f"Too many LLM calls - exceeded max_steps: {i}/{self.max_steps}"
  )
  ```
  —— 达上限后循环退出并抛异常，调查终止（对 CLI/HTTP 调用方表现为报错）。
- **性质**：调用次数硬拦。因每次调用的输入被 context window 约束、输出被 max_tokens
  约束（见 1.2），`max_steps × (context + max_tokens)` 构成一次调查 token 消耗的
  确定性上界，但**不是精确预算**，也不是按金额。

### 1.2 max_tokens —— 单次调用输出上限，model args 显式值优先（每次调用都生效）

- `core/llm.py:703-717`（`completion()` 内，原文注释）：
  ```python
  # Always send an explicit output-token limit: ...
  # An explicit max_tokens / max_completion_tokens in model args wins;
  if self.args.get("max_tokens", ...) is None:
      self.args.pop("max_tokens", None)
  ...
  if "max_completion_tokens" not in self.args:
      self.args.setdefault("max_tokens", self.get_maximum_output_token())
  ```
- 默认输出预留：`core/llm.py:787-794` `max(64000, context_window*12%)`，再被
  litellm `model_cost` 的 `max_output_tokens` 收紧（`:805-810`）；
  环境变量 `OVERRIDE_MAX_OUTPUT_TOKEN` 可整体覆盖（`core/llm.py:54`、`:796-800`）。
- model args 的注入路径（谁给 `self.args` 赋值）：
  - `config.py:788-821` `_get_llm()`：`model_entry.model_dump(exclude_none=True)`
    整体作为 `args` 传入 `DefaultLLM`；`ModelEntry` 定义为 `extra="allow"`
    （`core/llm.py:211-213`）→ **model_list.yaml 条目上的任意额外键都会成为
    `litellm.completion()` 的 kwargs**（`core/llm.py:763-778` `**self.args`）。
  - 即：`model_list.yaml` 写 `max_tokens: 64` → 每次调用输出被截到 64（Exp3 实证）。

### 1.3 token 用量统计（只记账，不拦截）

- `core/llm_usage.py:100/121/139-140`：`max_completion_tokens_per_call` 等为统计字段。
- `core/tool_calling_llm.py:1226-1241`：每次迭代 `RequestStats.from_response` 累计
  cost/token，`cost_logger.debug` 输出 —— **是记录，不是闸门**。

## 2. metadata 透传侧

### 2.1 唯一现成通道：EXTRA_HEADERS（env，进程级静态）

- `common/env_vars.py:73`：`EXTRA_HEADERS = os.environ.get("EXTRA_HEADERS", "")`
- `core/llm.py:676-677`：
  ```python
  if EXTRA_HEADERS:
      self.args.setdefault("extra_headers", json.loads(EXTRA_HEADERS))
  ```
- `extra_headers` 进入 `litellm.completion(**self.args)`（`core/llm.py:763-778`）
  → litellm 客户端将其转为**发往端点的 HTTP 头**（Exp1 实证到达）。
- 也可写在 model_list 条目里（`extra_headers: {...}`，同 1.2 的 kwargs 直通路径）。

### 2.2 HTTP server 形态（am1-http 实际部署形态）没有 per-request 通道

- `/app/server.py:504-529` `extract_passthrough_headers()`：把调用方 HTTP 头收进
  `request_context`，但它只下传给**工具集**（`:708-716`/`:754-759` 传给
  `call/call_stream` 的 `request_context`），**不进入 LLM completion 参数**。
- `ChatRequest`（`core/models.py:321-341`）里最接近的是 `meta`
  （`core/models.py:264-270`："Forward-compatibility metadata bag. FE-supplied
  opaque dict"），其唯一消费点是 holmes 自家用量事件：
  `core/usage_recorder.py:147` `merged_meta = dict(chat_request.meta or {})`
  → 只进 Supabase `HolmesUsageEvents`，**不进 LLM 请求**。
- `server.py:148-150` 的 `X-Braintrust-Experiment` 头仅影响 tracing 实验路由。
- **结论**：server 形态下，`run_id/attempt_id` 无法按请求注入 LLM 调用；EXTRA_HEADERS
  / model_list 都是**进程启动时固定**的 → 粒度 = 每个 holmes 实例（容器）。

### 2.3 litellm 客户端不会把 metadata 放进请求体（负证据，源码）

- litellm 客户端 `main.py:1601-1602`（get_litellm_params 调用）与 `:1618`
  `litellm_metadata=kwargs.get("litellm_metadata")` —— `metadata`/`litellm_metadata`
  只被打包进 **litellm_params（客户端本地日志上下文）**，
  不进入发往端点的请求体 `optional_params`。
- `litellm/llms/openai/` 全目录检索：`litellm_metadata` 仅在 guardrail/realtime
  内部处理器出现，chat/completions 出站路径无写入。
- 因此：即使 holmes 侧能传 `metadata` kwarg（model_list extra 直通），到端点的
  **请求体里也不会有它**（Exp1 实证）。

### 2.4 LiteLLM proxy 侧对账白名单（1.89.0）

- SpendLogs 落库 metadata 白名单 `litellm/proxy/_types.py:3596-3621`
  `class SpendLogsMetadata`：包含
  `user_api_key / user_api_key_alias / user_api_key_team_id / user_api_key_org_id /
   spend_logs_metadata("special param to log k,v pairs to spendlogs for a call") /
   requester_ip_address / ...`
- 提取函数 `litellm/litellm_core_utils/core_helpers.py:177-186`
  `get_litellm_metadata_from_kwargs`：取请求体 kwargs 的 `litellm_metadata`（新）
  或 `metadata`（旧）字段 —— 即 **proxy 从请求体读 metadata，请求头不进 SpendLogs**
  （无 `x-litellm-metadata` 头处理，包内 grep 0 命中）。
- 组装：`litellm/proxy/spend_tracking/spend_tracking_utils.py:68-131/327`
  `_get_spend_logs_metadata` 按 `SpendLogsMetadata` 字段过滤后写入。
- **Exp5 实测校准（官方镜像 1.89.0）**：SpendLogs 表无独立 `api_key_alias` 列
  （alias 与 `spend_logs_metadata` 都在行 `metadata` JSON 内，见
  `evidence/exp5_spendlogs_schema.txt`/`exp5_spendlogs.txt`）；请求头实测不落库
  （`X-Run-Id: run-HEADER-002` 全表无踪）；超预算被拒的调用落一行
  `status=failure`/spend=0 的记录。

## 3. 由此推出的 AM3 路线（供主会话决策）

1. **硬拦预算**：holmes 原生仅 `max_steps`（次数）+ `max_tokens`（单调用输出），
   属 BEST_EFFORT；**精确的"每次调用前"预算拦截应放在 LiteLLM proxy 层**：
   每个调查 run 生成一个虚拟 key（`key_alias=run_id`，`max_budget=预算`），
   proxy 在每次请求前比对已记账 spend，超限直接拒绝（Exp5 实证：HTTP 429、
   0.017s，proxy auth 层 `_virtual_key_max_budget_check` 抛 BudgetExceededError，
   上游模型零流量），holmes 侧只需把 `base_url` 指向 proxy、`api_key`
   换成 run 级虚拟 key —— 全部经 model_list.yaml/环境注入，**holmes 零改码**。
2. **对账**：per-run 虚拟 key 的 spend 行自带 `key_alias`/`user_api_key` →
   天然按 run 聚合；`metadata.spend_logs_metadata`（请求体）可携带
   `run_id/attempt_id` 落 SpendLogs —— 但 holmes 客户端进不了请求体（2.3），
   因此该字段只能由 proxy 之前的调用方（curl/eval-runner 直连 proxy 时）使用；
   若必须让 holmes 的每次 LLM 调用带 run_id，只有两条路：
   a) **每 run 一个 holmes 实例**（EXTRA_HEADERS/model_list 注入 run 级静态值，
      eval-runner 本来就是按 run 起容器的形态）；或
   b) proxy 端加自定义回调/中间件，从 holmes 透传的 HTTP 头
      （EXTRA_HEADERS，2.1）读取 `X-Run-Id` 并写入 `spend_logs_metadata`（需少量
      proxy 侧 Python，不改 holmes）。
3. 请求头本身**不会**出现在 SpendLogs（2.4 + Exp5 负证据）。
