# P4 百炼模型结构化输出稳定性实验——结论

> 任务来源：`docs/告警-并行任务-七项备料.md` 任务 P4（AM3 EvidencePackage v2 备料）。
> 执行日期：2026-09-05。执行方式：直连百炼专属实例 DashScope 兼容端点（`.../compatible-mode/v1`，BA-02 的 `/v1` 后缀已带），复刻生产 BA-14 修复前/修复后两种输出契约做 A/B/C 对照。

## 1. 实验设计

- **对象**：`deepseek-v3`（生产现役，BA-14 当事模型）+ `qwen-max`、`qwen-plus`（qwen 系对照；qwen-plus 为 `.env` 默认模型，BA-02 曾记录其不可用——本实验实测已恢复可调）。
- **协议**：同一 RCA prompt（S1 paymentFailure 场景：发布后收单渠道超时，3 条告警事件 + 已核实指标摘要，文风复刻 `HolmesInvestigationExecutor.buildAsk`，含注入框定语与环境框定语）× 每模型每臂 20 次，并发 4。
- **三臂**（唯一变量 = 输出契约载体）：
  - **A 文字硬指令**（BA-14 修复模式）：ask 文末附生产逐字硬指令段（"最终回答必须是纯 JSON 对象…七个顶层键清单"），不带 `response_format`；
  - **B strict json_schema**（BA-14 修复前生产配置）：ask 仅软引用 "response_format 给定的 json_schema"，请求带 `HolmesInvestigationExecutor.RESPONSE_FORMAT` 原样 strict schema；
  - **C json_object**：带 `{"type":"json_object"}`，无 schema、无硬指令。
- **采样**：不设 `temperature`（端点默认）与 `max_tokens`；180/180 调用 HTTP 200、`finish_reason=stop`（无截断）、零传输失败。总消耗 235,489 tokens（prompt 123,340 / completion 112,149）。
- **判定链**：机械复刻 `EvidencePackageValidator.parseAnalysis`——整包 `JSON.parse` → 失败取 ```json 围栏内容 → **围栏非法即拒（不回退花括号）** → 无围栏取首 `{` 到末 `}` 片段；提取成功后按 v1 七键（`schema_version=1`、`summary/root_cause/impact/remediation` 非空字符串、`evidence[]`、`references[{artifact_ref}]`）做存在+类型校验。
- **密钥纪律**：`AGENT_MODEL_API_KEY` 仅从仓库根 `.env` 载入进程内存，任何输出/日志/落盘不含密钥；证据目录已做零落盘扫描（见 §5）。

## 3. 发现

**发现一：BA-14 复现且加深——`response_format` 对该端点是"无操作"。**
deepseek-v3 三臂 60/60 全部以 ```json 围栏包裹输出，含 strict json_schema 臂与 json_object 臂。json_object 按 OpenAI 兼容契约要求消息体本身就是裸 JSON，该端点照样返回围栏——即 response_format 两档（json_schema/json_object）对输出形态的约束力实测为 **0**，连"保证合法 JSON"这一最弱承诺都不兑现。api 层参数不构成任何可依赖的契约（与 BA-14 结论一致，本次给出 n=60 定量版）。附带观测：B/C 臂平均延迟显著更高（deepseek-v3：A 7.6s vs B 13.2s vs C 16.0s），response_format 只增加开销不增加约束。

**发现二：七键 schema 契约只有"文字硬指令"这一条通路能到达模型行为层。**
无硬指令的 B/C 臂，deepseek-v3 与 qwen-max 一律返回自创的 incident 报告键（`incident_id`/`status`/嵌套 `root_cause{}` 等），schema 完整率 0%——schema 本身写在请求里也无人看。唯一例外是 qwen-plus B 臂本批 20/20 守约，属模型个体偶然行为，不构成可依赖机制（同端点不同模型行为分裂本身就是风险）。A 臂（硬指令）下三家 schema 完整率 100%/100%/80%，证明硬指令是唯一把字段清单传达到输出行为的载体。

**发现三："文字硬指令 + 容错提取"的实际兜住率 = deepseek-v3 100% / qwen-max 100% / qwen-plus 80%。**
- deepseek-v3 的围栏提取是**常态路径**而非兜底：100% 响应都走 `fence` 分支，且 20/20 提取后 schema 全过——BA-14 双层设防对生产现役模型完全兜住。
- qwen-max 硬指令臂 100% 直出纯 JSON，零提取。
- qwen-plus 硬指令臂 4/20（20%）失败，机理单一且已精确定位：`references` 数组**最后一个条目**写成 `{ "dashboard://payment-svc-release-impact-v2.3.1" }`——丢了 `artifact_ref` 键名的裸值简写，属**语法级损坏**（`Expecting ':' delimiter`）。它不是"包裹"，围栏/花括号两类提取在原理上都救不了，生产链判 `REJECTED_MALFORMED`。该损坏形态与 `HolmesInvestigationExecutor` 对结构失败不重试的既有决策（重试同形状概率高）一致，但注意它违反"同形状"直觉——模型对同一 prompt 的 20 次输出里 16 次合法 4 次损坏，是**随机**翻车而非稳定违约，重试一次的期望收益为正（若主会话愿意为 qwen-plus 开重试，属路线性变更，留裁定）。

## 4. 对 AM3 EvidencePackage v2 的输入建议（路线性，主会话裁定）

1. **双层设防（硬指令 + 有界提取）必须保留，且设计上应假设 response_format 不存在**——它是零约束、纯开销的参数。若 AM3 保留透传（如 Holmes 链路原样），对账与验证不得依赖其生效。
2. **围栏提取按"常态路径"做容量/延迟预算**：deepseek-v3 场景 100% 走提取分支，其耗时与失败语义（fence_invalid 即拒、不回退）已实测无回退需求——本次 20/20 围栏内容均合法。
3. **qwen-plus 若入候选池**：~20% 语法级损坏在 §6.4 评分口径下以 `REJECTED_MALFORMED` 计 0 分入总场景分母，评分器无需改动即可消化，但 coverage/accuracy 会系统性承压；相对地 qwen-max 与 deepseek-v3 在硬指令臂都是 100% 兜住。**结论排序（硬指令臂兜住率）：deepseek-v3 = qwen-max (100%) > qwen-plus (80%)**。
4. **提取层不要试图修复语法级损坏**（丢键名、裸值简写等）——维持"提取只是恢复被包裹的合法包，不是放宽标准"的既有纪律；本次 4 例损坏即使宽松提取也拿不到合规包，证明该纪律没有代价。
5. EvidencePackage **v2 类型化 schema**（`root_cause{component,fault_type,reason_code}` + `claims[]`）键位更多更复杂，本次 v1 七键在硬指令臂的 80~100% 完整率是 v2 完整率的**上界估计**，v2 落码时应预期更高拒绝率并在评测报告里单列结构失败。

## 结论摘要（约 200 字）

BA-14 定量复现并加深：deepseek-v3 对该百炼兼容端点的 response_format 三态实测零约束（60/60 围栏包裹，连 json_object 契约都违反），且 B/C 臂纯增延迟。七键 schema 契约唯一有效载体是文字硬指令：硬指令臂兜住率 deepseek-v3 100%、qwen-max 100%、qwen-plus 80%。qwen-plus 的 4 例失败为 references 末条目丢键名的语法级损坏，提取层原理上不可救，生产判 REJECTED_MALFORMED。建议：双层设防保留并假设 response_format 不存在；围栏提取按常态路径对待；qwen-plus 入池将系统性压 coverage，候选排序 deepseek-v3 = qwen-max > qwen-plus；v2 类型化 schema 键位更繁，完整率应按低于本实验上界预期。共 180 调用 235,489 tokens，证据齐落 raw/ 可复算。
