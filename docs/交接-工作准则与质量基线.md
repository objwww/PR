# 交接工作准则与质量基线（给下一位接手者）

> 版本 v1.3 ｜ 2026-08-31 ｜ 适用于所有接手本项目工作的 agent/会话
> 本文不是流程条文（流程见《测试交接规范.md》），是**态度与判断标准**。
> 条文告诉你做什么，本文告诉你做到什么程度才算"做完"。

## 一、用户定下的工作态度（原话精神，逐条可溯源）

1. **不盲从，证据先行**。任何人给你的批判性意见、任何文档里的论断——包括本项目
   已有的方案文档——都不可直接采信。拿不准的论断，去高星成熟开源项目里找证据
   （看它的设计思想与编程思维，不是抄代码），用证据链证明它对不对，再决定采纳、
   修正后采纳还是驳回。站在巨人肩膀上找适合自己的方案，**不闭门造车**。
2. **不信任任何二手结论，包括你自己的**。文档说的"已通过"、别人汇报的"已完成"、
   上一轮的"全绿"，都只是线索。验收的唯一标准是：你亲自复跑、亲自查库、
   亲自看日志，结果与声称一致。
3. **mock 绿 ≠ 真实绿，stub 绿 ≠ 真实绿，本机绿 ≠ 部署绿**。本项目的缺陷史
   （INC-19/22/24/26/27）反复证明：每一层替身都有自己的盲区。能用真实环境
   验证的，绝不止步于替身验证。
4. **bug 是资产，不是耻辱**。遇到 bug 当场记录：现象、前因后果、根因（追到"为什么
   写代码时会这么以为"那一层）、解决方案、预防措施。记 BUGLOG 不是走形式，
   下一个同类 bug 的修复时间取决于你这次记得多清楚。
5. **分层清晰，不为炫技而炫技**。能三行直白代码解决的不要抽象；设计要可扩展、
   可靠，但扩展性来自正确的边界（聚合、端口、状态机），不来自提前堆机制。
6. **里程碑是硬门禁**。当前里程碑未开发完、未验证、未部署成功、未获用户明确
   书面确认，绝不进入下一阶段；发现后续阶段的依赖，只记录指出，不提前实现。

## 二、质量基线（每件事做到这个程度才算完）

- **"完成"的定义**：代码写完 ≠ 完成。完成 = 代码 + 测试绿 + 部署验证过 +
  证据落盘 + 文档（PROGRESS/BUGLOG）更新。缺任何一项，如实说"没完成"。
- **验证要可复现**：你报的每一个 PASS，别人拿你的命令原样跑必须得到同样结果。
  凭印象报"应该是绿的"等于撒谎。
- **断点续做是你的义务**：每完成一项立即更新 `docs/PROGRESS.md`（干了什么、
  证据在哪、下一步是什么），让上下文清空后的下一个人（可能是你自己）能
  无缝接手。交接质量按"对方零上下文能否接手"衡量。
- **异常要追到底**：测试红了、日志有 ERROR、计数对不上——不许"再跑一遍看看"。
  先定位根因再行动；修复必须带回归测试，否则同族 bug 会第三次出现。

## 三、执行期的硬规范（测试/验证任务）

引自《测试交接规范.md》，此处重申四条铁律：

1. **只执行与取证，不修复**——产品代码、测试代码、断言、配置、数据，一律不碰
   （用例自带的故障注入除外，且注入后必须复原）。
2. **不跳测**——每个用例 PASS / FAIL / BLOCKED 三态必居其一；BLOCKED 写明阻塞
   原因后继续跑后面的，不允许"前面挂了就停"。
3. **不造临时脚本污染**——必要助手只放 `deploy/test-tmp/`，用完删除并登记；
   服务器禁碰区（117 整机、195 的 mall_R 目录、/opt/backups）绝对不碰。
4. **故障卡六要素缺一不可**——现象 / 复现步骤（命令可复制直接跑）/ 退出码与
   输出 / 环境快照（容器状态 + 涉事数据库行）/ 时间线 / 初步猜想（可选，必须
   标注"猜想"）。你取证的质量 = 主会话修复的速度。

## 四、判断力场景（条文覆盖不到时怎么办）

- **断言失败但疑似"设计内行为"**：不许自行裁决为 PASS。记 FAIL，故障卡里写清
  "疑似设计内"及依据，交主会话裁定。（先例：INC-23/27 中"RECONCILING 重发"
  "LWW 拦陈旧事件"确属设计内，但那是主会话核对代码后的结论，不是执行者的豁免权。）
- **环境疑似坏了**（容器起不来、端口不通、库连不上）：记 BLOCKED + 环境快照，
  不要试图"顺手修好"。修好环境的诱惑是测试污染的最大来源。
- **发现交接文档本身错了**（命令跑不通、预期数字对不上）：记 BLOCKED，指出文档
  哪一条与事实不符——文档错误本身就是要回流修复的缺陷。
- **拿不准要不要做某个破坏性操作**：不做。问。破坏性操作的默认答案永远是"先确认"。

## 五、开发与部署流水线（本地唯一编辑现场）

```text
本地（E:\KimiCode）                195 服务器
─────────────                ──────────────
1. 写/改代码（唯一编辑点）
2. mvn test 全 reactor 绿
   （本机无 docker，IT 跳过）
3. tar/scp 同步源码 ──────►  4. maven 容器打包
                             5. mvn verify 挂 docker.sock 真跑 IT ← 硬门禁
                             6. 重建镜像 + force-recreate + 启动自检
                             7. DP 门禁（stub）→ 真实联调（需用户批准）
8. PROGRESS/BUGLOG 记账
9. push GitHub（每次当场经用户确认）
```

三条推论（均有 INC 实录背书）：

1. **绝不在服务器上改代码**——195 只做构建/运行/验证；现场改不回写仓库，
   下一次全量同步必冲掉（INC-25：compose 公网绑定被 tar 同步冲掉 → 投递 502）。
2. **本地绿不够，195 真跑 IT 才是部署门禁**——本机无 docker，IT 全跳过；
   INC-22/26/27 全是"本机全绿"掩盖的缺陷。不经 195 `mvn verify` 绿不部署。
3. **配置漂移零容忍**——服务器侧任何改动（.env/compose/密钥挂载）当天回写
   本地仓库或 .env 模板；单一事实源 = 本地工作区，最终 = GitHub。

## 六、里程碑工作法（方案先行 + 双人工门禁）

每个里程碑严格按六道工序走，**顺序不可颠倒、不可跳步、不可跨阶段并行**
（完整强制版见 `.kimi-code/skills/milestone-workflow/SKILL.md`，此处是交接摘要）：

```text
工序1 任务拆解+技术方案（12 节结构缺一不可）
  → 工序2 【G1 方案门】用户明确确认前，禁止写任何实现代码
  → 工序3 最小模块编码（只做当前阶段范围，越级需求记入"压力点"不实现）
  → 工序4 部署验证（195 起栈 + 自检 + 冒烟）
  → 工序5 测试验证（完整矩阵全绿；委托执行时走《测试交接规范》）
  → 工序6 【G2 阶段门】用户明确说"可进入下一阶段"，才允许开始下一阶段工序1
```

要点：

1. **方案不是形式**。十二节结构（核心问题/任务拆解/类设计+时序图/实现方式/
   数据流图/边界与不变量/设计原因+开源证据/压力点/事故记录/技术债分析/
   测试设计/DoD）每一节都对应一次真实评审踩过的坑。没方案就编码 = 返工。
2. **两个人工门禁是用户的权力，不是流程装饰**。G1 不过不写码，G2 不过不进
   下一阶段。"我以为方案没问题"不构成开工依据。
3. **越级开发的处置**：发现后续阶段的依赖/需求，只准写入方案 §8"问题与
   压力点"移交，**不准顺手实现**。
4. **测试执行 agent 只参与工序 5**，且按交接文档执行；工序 1/2/3/4/6 与它无关，
   它也无权要求修改方案——方案缺陷作为 BLOCKED 回流即可。

## 七、技术方案写作标准（工序 1 的质量门）

方案的读者是"零上下文的下一个会话"。判断标准只有一条：**仅凭方案就能动手编码，
全程不需要反问作者"这个类放哪层、这个字段叫什么、这个异常往哪抛"。**

### 写到什么程度

1. **可执行**：类清单落到 DDD 具体层、职责一行说清、**明确写出"不做什么"**；
   事务边界画到哪张表哪几行；状态机列出全部合法迁移而不是只画主干。
2. **每个决策有依据，三选一**：开源先例（证据入 `docs/OSS-证据清单`，引用前
   逐句核对原文，不许凭印象转述）/ 冻结文档条款编号 / 本项目 INC 实录。
   三者皆无的决策，写明"无先例，系本项目自研判断，风险是 X"。
3. **每个"不做"有触发条件**：压力点清单里每条写"什么信号出现时重新评估"——
   这是下一里程碑的输入，不是免责声明。
4. **图必须能渲染**：mermaid 画完后过一遍语法校验（本项目教训：subgraph 里
   不用节点形状语法、标签一律加引号）；时序图必须覆盖崩溃/重试/乱序路径，
   只画 happy path 的时序图等于没画。
5. **诚实清单**：边界条件里显式列出"本方案承认的残余风险"。藏起来的风险
   会在联调时变成 INC；写出来的风险才是设计。

### 调研先行（方案起草与评审反馈处置的强制前置工序，2026-08-31 用户订立）

任何技术方案（含修订）和任何外来评审反馈，**先批判、再调研、后落笔**。五步，顺序不得颠倒：

1. **先学 agent 同类**：调研优秀开源 agent 项目（LangGraph/OpenHands/SWE-agent 等），
   学它们的编程思维与设计巧思（checkpoint、打断恢复、护栏、事件溯源、预算……）；
2. **再学技术本体**：调研所涉技术的代表性开源项目、高质量文档与官网，既学优秀思想，
   更挖**存在的坑**（官方 issue、默认值的坑、版本差异）——一手资料为准，禁止二手转述；
3. **适配性判断**：每条巧思必须回答"适不适合我们项目、为什么/为什么不"。
   本项目定位锚点：**harness 优先——把模型放进可靠的工程环境里消除它的不确定性**；
   单人维护、单实例、Postgres 全家桶、可靠性优先于功能丰富。与此冲突的巧思，
   再优秀也不引入，写明拒绝理由；
4. **引入代价推演**：凡采纳的设计，必须写出"它带来了什么新问题/弊端、怎么解、
   有没有现成方案"——解不了或代价过大的，退回第 3 步重新裁定；
5. **回头看旧账**：顺带调研既有里程碑（M0/M1/M2…）相关技术有没有该修的优化；
   有则登记（压力点/INC/下阶段输入），**是否当期修由用户裁定**，不擅自扩范围。

调研结论入 `docs/OSS-证据清单`（附 URL 与核对日期）；调研推翻的在役假设当场登记 BUGLOG
（先例：INC-42——Spring AI 默认 10 次隐藏重试在役三个里程碑未被发现）。

### 评审处置留痕

评审意见（用户或二审）逐条处置：**采纳 / 修正后采纳（写明修了什么）/
驳回（写明证据）**，处置记录进方案修订章节。不盲从——批判性意见也要先验证
再采纳（INC 教训：错误的"正确意见"采纳了同样是 bug）。

## 八、测试用例设计标准（全面性的定义）

"全面"不是数量多，是**每个失效模式都有至少一条用例守着**。按六层防线组织，
每层防一类事故：

| 层 | 防什么 | 要求 |
|---|---|---|
| L0 静态架构（ArchUnit） | 分层腐化、权限越界 | 红绿验证留证（先证断言能红） |
| L1 单元 | 纯函数/状态机逻辑错误 | 状态迁移表反射穷举，不抽样 |
| L2 组件规则（Testcontainers PG） | SQL/约束/权限/并发领取 | 真实 PG，禁止 H2 替身 |
| L3 业务场景闭环 | 多对象协作的正确性 | 覆盖乱序/重投/并发双源/崩溃窗口 |
| L4 边界异常 | 依赖故障时的行为 | 每类外部失败（404/403/429/5xx/超时）各一条 |
| L5/L6 + DP 部署门 | 用户视角验收、整栈故障注入 | 在 195 真栈跑；崩溃注入用 SIGKILL 不用优雅停 |

每条用例四要素缺一不可：**场景（含注入方式）、预期断言（可机器检查）、
取证要求（查哪张表哪个字段）、回指条款（不变量编号/冻结项/方案小节）**。

覆盖面自查清单（任何里程碑的方案送审前逐项过）：

- 正常路径之外：重试耗尽了吗？幂等重放了吗？并发抢同一份资源了吗？
- 崩溃窗口枚举了吗（事务提交前/提交后/回写前，每个窗口一条）？
- 乱序与迟到（旧事件晚到、晚到结果覆盖新状态）防住了吗？
- 安全面：签名伪造、payload 污染、权限越界、密钥泄漏进日志，各有断言吗？
- 成本面：draft/重复事件的"零模型调用、零 API 调用"有计数断言吗？
- 替身盲区标注了吗：本机跑不了的（无 docker）必须写明"195 跑"；
  stub 不能表达的（权限语义、probe 列表）必须写明"真实模式验"或"已知局限"。

## 九、服务器与背景

开工前必读 `docs/测试交接-背景与服务器现状.md`（当前 v1.1）。它告诉你：
项目是什么、进度到哪、195 服务器四容器栈的现状与模式、密钥在哪（不许打印外泄）、
禁碰区、出问题的自查顺序。**它过期或与现实不符时，按第四节"文档错了"处理。**
