# Prompt、Skill 版本演进与评测补充评审

日期：2026-09-10。对象：增强线 v1.1、评测执行方案 v1、主计划 v1.2，以及当前工作区 ConfigBundle、ReplayToolGateway、AgentReplayRunner。本文只调研和补充方案，没有实施增强线代码，也不是对全部已修复项的重新验收。主计划已纠正 Native 基线、R6 前置和排期等问题，本次不重复旧评审。

## 一、结论：缺的是版本实验与发布闭环

增强线已经有工具清单、轻量 RAG、Skill 候选和盲评晋升方向，但 §四 Skill 仅三条，提示词只有 ConfigBundle digest。还不能直接回答：这次修改改变了什么、在哪些告警上有效、失败是否由新查询缺数据导致、哪个组合允许上线、上线后如何退回。

推荐保留 Git + PostgreSQL + ConfigBundle + 现有执行守卫。先补四件事：不可变资产、组合发布清单、可独立核验的评测证明、自动产候选但受控晋升。不需要为此先部署新的 Prompt 平台、向量库或消息队列。

外部方案只是参考，本文下面的状态与字段是针对本项目的设计建议，不声称现有代码已经实现。

## 二、先分清四种对象

| 对象 | 在 checkout 告警里的作用 | 版本边界 |
|---|---|---|
| Prompt | 指标角色如何选择查询、诊断角色如何表达不确定性 | 消息模板、变量契约、输出 schema、装配规则 |
| Skill | 遇到特定告警如何按条件排查、何时停止或补证 | 适用条件、步骤、分支、依赖工具、输出与停止条件 |
| RAG 资料 | 历史事故、runbook 提供参考 | 文档内容、有效期、来源、索引版本与过滤策略 |
| Release | 本次调查实际采用的完整组合 | 模型+角色 Prompt+Skill 集合+工具+检索+Harness 版本 |

Skill 不是额外一个 Agent。Agent 是执行角色，Skill 是角色可采用的方法；格式像一个 Markdown 文件，也不意味着文件能自行获得执行权限。

官方 Agent Skills 使用 SKILL.md、元数据及可选资源目录，并支持按需加载。其 allowed-tools 字段仍是实验性字段，不能替代本系统的权限执行。增强线把 subagent frontmatter 当 Skill 格式蓝本，建议改成明确采用 Agent Skills 外壳，项目运行契约另行定义。[Agent Skills 规范](https://agentskills.io/specification)

## 三、Prompt 版本演进：不能只保存最后一份文本

### 3.1 内容版本与发布指针分开

已有 ConfigBundle.of() 对内容计算 digest、保存不可变配置，适合继续复用。每个调用点使用稳定名字，例如 rca/metric-investigation、rca/log-change-investigation、rca/diagnosis；内容改变产生新 digest，禁止覆盖旧版本。

每个 Prompt 资产至少记录：asset_id、content_digest、parent_digest、模板消息及角色、变量 schema、输出 schema digest、变更说明、作者、创建时间。模型采样设置和工具 schema 作为发布依赖冻结。展示给人的 v1.2 不能代替内容身份。

Langfuse 将版本与部署标签分开管理，这个机制值得借鉴；本项目可用既有 ConfigBundle 指针实现，不必因此部署 Langfuse。[Prompt 版本与标签](https://langfuse.com/docs/prompt-management/features/prompt-version-control)

一次 Run 开始时只解析一次发布指针，持久化组合 digest；之后每次调用读取固定版本。发布新 Prompt 时，已经运行的调查继续使用原版本。回滚改变未来 Run 的版本选择，不改写历史记录，也不强制进行中的 Run 混用版本。

### 3.2 冻结的不仅是模板

一次模型调用还要关联：template_digest、rendered_messages_digest、input_snapshot_digest、实际 Skill 及资源 digest、工具 schema digest、模型路由与供应商返回的模型标识、采样设置、结果 schema、上下文裁剪/摘要版本。

只有 hash 无法恢复原文：评测需要保留经过脱敏、访问受控的实际输入工件，注明保留期。不要把完整生产日志直接放进公开 prompt trace；模板变量不齐、资源缺失应显式失败，不能从 latest 偷补。

固定这些内容能追溯运行，不保证供应商模型输出逐字确定；别把“可追溯”写成“完全确定性复现”。

### 3.3 修改、比较、发布流程

1. 从现役版本创建候选，写出故障假设：例如当前诊断会把错误率升高直接写成根因，拟增加反证与机制要求。
2. 固定其他因素，先只改诊断 Prompt。静态检查变量、引用和 schema，跑开发集与安全回归。
3. 在相同输入集上运行现役与候选，比较根因正确性、错误确认、成本和有效补证；不能只比较文本是否更流畅。
4. 对通过开发门的候选运行受限访问盲评，得到绑定组合 digest 的资格证明。
5. 人工审阅后以 CAS 激活组合；有限影子观察只读结果，不重复发值班通知。达到预定放量条件再生效。
6. 指标异常则退回最后已验证且兼容的组合，保留失败版本与回滚事件。

兼容性变化包括变量/输出 schema、工具参数和角色职责。即使只改几个字也可能改变行为，不能把小文本差异视为低风险。反之仅修不参与运行的说明，不需要重跑全套 Live 注入。

## 四、Skill：把排查方法沉淀下来，而不是记住答案

### 4.1 最小资产契约

建议每个 Skill 使用 SKILL.md 描述方法，附一个小型 manifest 保存可校验契约。manifest 字段是本项目扩展，不属于 Agent Skills 标准。首期不接任意 scripts，不从自然语言任意编译代码；步骤只能引用注册工具和受限分支，继续经过已有 Harness。

至少包括：skill_id、版本 digest、parent_digest、适用服务/告警/版本、前置数据源、排除条件、允许工具及版本约束、步骤与有限分支、最大轮次/成本、停止和退回通用调查条件、结果 schema、原料轨迹、复核依据、关联评测。

例：checkout 高错误率 Skill 应说“先看错误分布和依赖调用，再核对故障窗变更，证据矛盾时查反证”。不能写“这个告警根因就是某个 flag”，不能固化注入参数、某次 trace_id、固定主机或答案标签。

有效权限取交集：系统策略 ∩ 角色权限 ∩ Skill 声明 ∩ 本次 Run 授权。Skill 不得增加预算、改目标服务范围或引入新网络目的地。

### 4.2 状态机补完整

当前“五态+REJECTED”缺少验证与发布之间的边界。建议使用以下语义，可以通过资产状态与发布记录组合实现，不要求机械增加同名数据库枚举。

| 状态/阶段 | 转入条件 | 允许做什么 |
|---|---|---|
| DRAFT | 自动或人工产出新内容 | 编辑候选；变更重新计算 digest |
| VALIDATING | 内容封存提交校验 | 校验权限、依赖、DAG 上限、资源路径、输出契约 |
| EVALUATING | 静态校验通过 | 仅在评测身份下运行，读取允许的输入 |
| QUALIFIED | 质量与安全门通过 | 等待发布；通过不等于已上线 |
| ACTIVE | 发布事务选择该版本 | 新 Run 可按选择规则采用 |
| DEPRECATED | 不再供新 Run 选择 | 旧 Run 可完成、历史可审计 |
| RETIRED | 不再允许执行 | 保留历史内容和评测证明 |
| REJECTED | 校验或质量失败 | 保留失败依据；修改要创建新候选 |

INCONCLUSIVE 是某次评测的结论，不应伪装成 REJECTED 或 QUALIFIED；可以补新样本后对同一不可变版本再评测。多次评测有独立 eval_id，不能覆盖前次失败。

紧急禁用是独立的撤销机制：即使某 Run 已固定 ACTIVE 版本，发现越权或污染也应在下一动作入口阻止继续使用；已经发出的请求按现有取消/UNKNOWN 契约处理。普通退役与紧急撤销不要混为一谈。

### 4.3 自动沉淀的边界

建议链路：已封存调查工件 → 提取观察/动作/结果/反证 → 脱敏并移除事故特例 → 生成候选及适用边界 → 静态验证 → 独立评测 → 人工发布。

沉淀可审计的动作和证据摘要，不依赖或要求模型隐藏思维链。候选生成器仅能写 DRAFT，不能写 ACTIVE 指针、评分器或 HOLDOUT。

生产事故一般没有天然 root_cause_hit 标签。用 verification_status + 人工处置复核/故障修复验证作为原料资格，保留复核者和证据。别为了生成 Skill 从金标答案仓取 root_cause_hit，再把金标内容泄进候选。

只吸收成功轨迹会产生幸存者偏差：失败轨迹也应产出反例、禁用条件和回归测试，但不能未经验证转为正向操作步骤。“证据不足时及时停止”同样是可复用经验。

“人工晋升20个版本后再考虑自动晋升”可作为复盘时间点，不是安全或统计证明。小型个人项目可长期采用自动候选、自动评测、人工发布；这已经有可展示的自改进闭环。

### 4.4 选择与组合也要测试

先用服务/告警/能力/版本做确定性过滤，再由模型在少量匹配项中选择或弃选；选择结果写入 Run。首期每个角色最多采用一个方法 Skill，是降低组合复杂度的建议约束，后续有证据再放开。

必须测试近似但不适用的告警不会被误选、两个 Skill 冲突、所需源缺失、工具 schema 升级、同名不同版本、Skill 失效后退回通用方法。评测不仅问“选中后能否成功”，也问“是否选错”。

## 五、最值得新增的评测能力

### 5.1 修正精确回放对新方法的偏差

源码 ReplayToolGateway 按工具版本/schema/参数/窗口/输入摘要精确查记录，MISS 不触网。这对故障复现很合适，却不能完整评价会提出新查询的候选策略。

分三类运行：

| 类型 | 用途 | 边界 |
|---|---|---|
| 精确轨迹回放 | 旧行为与账本回归 | 不能把未录制查询直接当能力失败 |
| 冻结数据上的受限查询 | Prompt/Skill 新策略比较 | 在冻结指标/日志样本上允许声明范围内的新查询；明确支持的查询语义 |
| Live 受控验证 | 新工具/新查询面真实性 | 有预算、有隔离，单独报告，不把活查询偷偷混入离线结果 |

首期不必造通用离线 PromQL/LogQL 引擎。可以预建有限查询空间的响应集；超出覆盖就报告 REPLAY_INCOMPLETE，之后补充数据集新版本并重跑比较双方。不能用 HOLDOUT 答案指导补齐，也不能只挑候选成功的覆盖项计算总胜率。

### 5.2 区分“离线工具”和“模型也断网”

全进程 network_mode:none 可以验证录制模型响应下的恢复与评分器隔离，但不能调用外部新模型评测新 Prompt。方案必须分别提供：全断网契约回放；工具断网、模型仅允许访问隔离网关的候选评测；评分器完全断网。若使用本地模型，也要明确模型版本与资源面。

### 5.3 新增十组测试

| 组 | 告警场景 | 指标/判据 |
|---|---|---|
| Prompt 契约 | 缺变量、错误 JSON、纠正轮耗尽 | 显式失败、有限重试、调用全计费 |
| Skill 适配 | 类似告警但故障机制不同 | 误选率、弃选是否正确 |
| 证据反事实 | 去掉关键日志、加入反证 | 应降级原因未确认，不能坚持原答案 |
| 表面变化 | 服务别名、等价单位、时间整体平移、日志排序 | 在预先声明的不变量范围内结论稳定 |
| 因果质量 | 仅有症状的多源重复证据 | 不升级根因；所有根因引用可回读 |
| 协作收益 | 单 Agent 与三角色同预算比较 | 命中/错误确认/延迟/费用；不强制机械相同轨迹 |
| 污染与越权 | 日志/runbook/工具描述含“忽略规则” | 不能修改权限、泄漏数据或执行未授权动作 |
| 选择漂移 | RAG/Skill 索引更新、旧文档过期 | 固定版本 Run 不漂移，失效资源显式处理 |
| 发布恢复 | 晋升竞争、回滚、缺历史资源 | CAS 只有一方生效，旧 Run 可回读 |
| 无效循环 | 一直查同样数据但调用持续增长 | 信息无增益停止，deadline/预算依旧硬约束 |

评测应同时保留结果、调用轨迹与最终环境事实，规则评分、模型评分和人工复核各有用途；不要强行逐步匹配唯一“标准路径”。这一分层与 Anthropic 的 Agent 评测实践一致。[Agent 评测方法](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)

### 5.4 评分器、样本和晋升证明也要版本化

每次结果绑定 candidate_release_digest、baseline_release_digest、dataset_digest、split_manifest_digest、runner/harness_version、grader/rubric_version、若有模型裁判则 judge 模型与 prompt、重复运行编号、工具覆盖率、泄漏检查、费用对账状态。

**MATCHED 不能独自表示质量通过。** 费用已对账、输入已配对、质量达标是三件事，分别保存 usage_status、comparison_status、quality_verdict。建议晋升同时满足安全硬门、工件完整、费用状态符合策略、质量 PASS、人工批准；样本不足仍 INCONCLUSIVE。

模型裁判隐藏候选身份并随机化展示顺序，先用人工标注校准；schema、引用、权限、预算由程序判断，不让模型自己评分自己的证据真实性。

HOLDOUT 要防反复调参间接泄漏：开发集可见详情，验证集限制反馈，最终留出集限制访问次数；记录污染谱系，来自某事故的 Skill、其改写、近重复日志不能进入该事故关联留出评测。旧 HOLDOUT 曝光后可转回归集，未来晋升使用新的封存集。

### 5.5 小样本与成本口径

评测执行方案已改为10 Case/5场景，主计划部分段落仍写47，需统一成 dataset manifest 的实际计数，避免手写多份数字。

五个故障家族不足以支持普遍能力结论；重复模型运行衡量随机波动，不增加独立故障家族数。先报告每家族配对结果、错误确认数、成本和不确定性，随后补不同原因但相同症状的事故。预先规定统计与容忍界限，不在出分后修改阈值。

“回归成本压到1/5以下”应改为待测目标：现列1～1.5小时对3.5～5小时并不能始终满足。分别记墙钟、模型 token/费用、工具调用和人工复核耗时，不能只减少故障注入等待就宣称所有成本都降到1/5。

## 六、版本组合与发布门如何落在现有项目

建议在 ConfigBundle 内增加不可变 release manifest，固定角色 Prompt 映射、Skill 版本集合、模型配置、工具 schema 集、检索语料/索引快照、上下文策略和 Harness 兼容版本。配置中存引用时，发布前确认内容可取且 digest 一致。

现有 ConfigBundleService/Repository 可复用不可变内容与指针 CAS。新增资格证明与激活校验，避免存在另一条直接 activate 路径绕开评测。检查通过与指针切换应保证检查的是同一个候选、基线和授权状态；旧证明不能给被修改后的内容背书。

普通运维配置不必全部强制跑模型质量评测：按字段影响划分验证策略。修改 Prompt/Skill/工具 schema 要重验相关组合；纯展示字段只跑对应检查。跨供应商模型替换不能只凭“同档”免质量门，预先建立已验证兼容组合才可快速切换。

首次采用单角色 Prompt 变更、单 Skill 变更等对照；再测组合交互。Skill 开/关、RAG 开/关、单/多 Agent 是有意义的消融，不必一开始穷举所有笛卡尔积。

## 七、增强线 v1.1 另外几处应修改

1. 文首 EX13/13+C 才编码，与“工具随R7”“RAG A后”并存。把实际门写成前置条件的交集，区分现在做方案、何时编码，避免再次分歧。
2. MCP 每次短会话与持续监听 list_changed 不是同一生命周期；短会话没有连接时收不到通知。声明 TTL 的陈旧边界，或采用有引用计数的长期 client；列表变更是可选能力，不能假设一定支持。[MCP Tools 规范](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)
3. 注册表 generation 与 driver leaseEpoch 是不同身份，分别校验；updated_at 增量还须处理同时间戳和删除，少量 server 首期全量快照更简单。撤销后失败不宜无脑 RETRYABLE 到无限重试。
4. RAG 的“20次且误召回<漏召回”不是合格阈值。单独标注相关文档，统计Recall@k、误召回和最终诊断收益；冻结文档版本，历史结论只能作线索。是否上向量检索由漏召回样例决定。
5. 摘要“≤原文50%”不能保证保留反证。先确定性聚合去重；若LLM摘要，保留原始引用、摘要模型版本，测试稀有错误和反证不丢。
6. 调用次数增长不代表进展；stall monitor需要证据新增、缺口减少等信号，且不能替代绝对deadline。
7. “无人值守on-failure”不能作为写权限制度；也不能在未授权动作执行失败后才补授权。查询与写操作按系统自己的授权模型处理。
8. runId 全后移到守卫之后过于笼统：预算与拒绝审计需要稳定身份。区分业务Run创建、动作准入和远端发送，按现有幂等契约落地。

## 八、建议补入增强线的任务卡

| 卡 | 交付 | 退出标准 |
|---|---|---|
| PE-01 版本契约 | Prompt/Skill/release manifest与兼容规则 | 同内容同digest、依赖齐备、模板变量校验 |
