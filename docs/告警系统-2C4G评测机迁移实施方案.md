## 一、先给结论：不能搬现有 JAR，必须先把现有评测切成两条管线

当前 `eval` profile 虽然叫 eval-runner，但它并不是纯离线 runner：

- `EvalRunnerConfig` 注入 `DataSource/JdbcClient`，以 `eval_app` 读取 195 的 `rca_run`、`rca_report`、`rca_attempt`、`incident`、`rca_tool_call` 等表。
- 同一个进程访问 Prometheus、flagd admin、order-arena、Chaos Admin 和 LiteLLM。
- `GoldenScenarioRegistry` 从同一份 YAML 同时读取 driver、注入参数、时间参数、`expected_root_cause` 和 `expected_symptom_codes`。
- `SingleCaseScorer` 在同一 JVM 中同时拿到生产观测和 `GoldenCase` 答案，并把答案写进 `eval_case_result.expected_*`。
- `PostgresToolReplayStore` 仍从 195 PostgreSQL 的 `rca_tool_replay` 读取回放内容。

复核注记（2026-09-09，代码逐条核对后补充）：

1. `rca_tool_replay` 的当前读者是生产 `control_app`（`PostgresToolReplayStore` 装配在 `AlertAm4Config` 的 docker profile，V19 只授权 `control_app`），不是 eval 进程；但这不改变结论——回放内容的事实源在 195 PG，HOST2 必须用 `FileToolReplayStore` 替代。
2. “同一时刻最多一个 Live E2E”的跨进程锁当前**不存在**（`EvalBatchRunner` 只有批内串行）；§六 Step 1 的"增加锁"是新建工作项，不是对现状的描述。
3. `application-eval.yml` 全文仅 7 行，唯一生效内容是清空 DataSource/Flyway 自动配置排除；`app.alert.eval.*`（含 litellm.*）全部以 `@Value` 默认值存在于 `EvalRunnerConfig`，收口配置时需同时处理这两处。

所以，把现有镜像放到 HOST2，再配置 195 数据库地址，只是“把 JVM 搬走”，并没有迁走数据依赖、资源负载和答案边界。正确拆分是：

| 路径 | 放在哪里 | 做什么 | 是否允许访问 195 |
|---|---|---|---|
| Live E2E | 195，或从受控运维端触发 | 注入故障、等待真实告警/RCA/恢复、验证全链路 | 允许，但低频、串行、维护窗口 |
| Dataset Packager | 195 上的一次性可信作业或 CI 可信区 | 把生产事实和录制工具响应导出为脱敏冻结输入；把答案单独封装 | 只在打包时允许，凭据不离开 195 |
| Replay Runner | HOST2 | 读取输入包，运行 baseline/RAG/Skill 候选，工具只精确回放 | 禁止访问生产 DB、Prometheus、日志、变更、Chaos Admin |
| Blind Scorer | HOST2 独立容器 | 输出封存后，用秘密答案评分 | 禁止模型、工具和外网；不访问 195 |
| Score Importer | 195 或 CI | 只导入签名后的聚合分数和工件 digest | 不读取答案正文 |

这台机器的定位是“单并发批处理执行器 + 外部探针”，不是新控制中心。它故障时最多延迟评测，不能影响告警接入、Incident 状态、RCA 生产链和 Gatus 探针。

例外与代价（2026-09-09 用户裁定"尽可能迁移"后明确）：若 LiteLLM 按 §三.4 的条件门迁至 127，127 将进入生产模型路径——127 故障会使 RCA 报告生成延迟（入口持久化不依赖模型，Alertmanager 重试不丢告警；Incident 状态机不受影响），此时由第三方 heartbeat 发现 127 失联并通知。接受这一代价换取 195 释放约 430~500MiB 常驻 RSS；不接受则 LiteLLM 留 195，195 减负只剩 eval-runner 一项（约 230~250MiB）。

## 二、目标部署：同一台机器上也要分成不同信任域

```text
195 / 可信打包区
  Live E2E ──读取生产事实──> EvalBundlePackager
                                  ├─ agent-input-bundle ───────┐
                                  └─ scoring-answer-bundle ─┐  │
                                                           │  │
HOST2 / 2C4G                                               │  │
  probe-net: Gatus ──health/readiness──> 195               │  │
       │                                                    │  │
       └────────自己的公网出口────────> 值班接收器           │  │
                                                           │  │
  eval-runner identity <── input volume 只读 <─────────────┘  │
       │                                                     │
       ├─ FileReplayToolStore（无活网 fallback）              │
       ├─ baseline / RAG / Skill candidate                   │
       └─ candidate-output.tmp ──hash+atomic rename──> sealed output
                                                             │
  eval-scorer identity <── answer volume 只读 <──────────────┘
       ├─ sealed output 只读
       ├─ network_mode: none
       └─ score-summary + private case detail

  host systemd + evalctl（编排器，不在容器内持有 Docker socket）
       ├─ 只看 case_id、input/output digest、状态、资源水位
       ├─ 不知道 answer object key/digest
       └─ OUTPUT_SEALED 后才启动 scorer
```

这里的隔离目标是防止 Agent 进程、Prompt、RAG、Skill 生成器或普通运行日志接触答案。它不能防住 HOST2 的 root 管理员：同一物理机的 root 最终可以读所有卷。若威胁模型包含恶意主机管理员，Answer Vault 必须迁到另一账号、另一主机或外部 KMS/对象存储，由远端 scorer 完成评分。第一期至少保证“Agent 运行身份无法读取答案”。

## 三、2C4G 到底能放什么

### 1. 可以放

- Gatus 和探针自身 heartbeat，常驻且优先级最高。
- 一个由 systemd timer/oneshot 调用的 `evalctl`，负责资源门、状态机和 one-shot 容器启动；它运行在宿主机，不把 Docker socket 挂进任何业务容器。
- 单并发 Replay Runner。当前固定 Native 链以确定性 Tool 回放为主，可以在本机运行。
- 与 runner 不并发的 Blind Scorer。
- 少量本地 SQLite/JSONL 状态、输入/输出包和短期归档。
- 模型推理为远端服务时的轻量客户端；必须使用评测专用凭据和费用上限。

### 2. 不能默认放

- 生产 PostgreSQL 副本或新的事实源。
- 完整 order-arena、Prometheus、Alertmanager、OTel Demo、Chaos Admin。
- 本地 7B/14B 大模型推理。
- ~~LiteLLM 1.5 GiB 常驻实例再叠加 2 GiB runner~~（2026-09-09 修订：按用户"尽可能迁移"裁定，LiteLLM 改为**条件迁移项**，见 §三.4；原文不成立的不是资源算术本身——启动峰值约 1013 MiB、稳态 RSS 约 477~501MiB、1536 MiB 上限的事实不变——而是"默认不放"的结论让位给带门试验）。裸的 1.5 GiB 上限 + 2 GiB runner 直接叠加仍然禁止。
- HNSW 大索引构建、批量 embedding、Live E2E 与 Replay 同时运行。
- 多个候选并行跑。第一期并发固定为 1。

### 3. 推荐资源预算

| 部分 | 常驻/按需 | CPU | 内存硬上限 | 说明 |
|---|---|---:|---:|---|
| OS、Docker、WireGuard、页缓存余量 | 常驻 | — | 预留 900～1200 MiB | 不分配给容器 |
| Gatus | 常驻 | 0.20～0.35 | 160～256 MiB | 先测 RSS 和 scheduler lag，再定最终值 |
| heartbeat/notification adapter | 常驻 | 0.05～0.10 | 64～128 MiB | 与 Gatus 同优先级 |
| host `evalctl`/systemd | 按调度短时运行 | 0.05～0.10 | 64～128 MiB | 不加载 Spring 全栈；不常驻 JVM |
| Replay Runner | 按需 | 1.0～1.25 | 1024～1280 MiB | Java heap 初始 `-Xmx768m`，并发 1 |
| Blind Scorer | 按需 | 0.25～0.50 | 384～512 MiB | runner 退出后才启动 |
| transfer/cleanup | 按需 | 0.10 | 128 MiB | 不与 runner 大量解压并发 |

资源不是简单相加：Runner 与 Scorer 必须互斥。常驻面主要是 OS、Gatus 和 heartbeat，约占 1.2～1.6 GiB；Runner 活跃时整机仍要保留约 1 GiB 作为内核、Docker、缓存和瞬时峰值余量。

建议准入门：

- 启动新 runner 前 `MemAvailable >= 1536 MiB`。
- 磁盘使用率 `< 75%`，预计输出后仍 `< 80%`。
- 1 分钟 load average `< 1.2`，连续 3 个窗口超限则不接新作业。
- Gatus 最近调度延迟 `< 15s`，最近一次探测和 heartbeat 均正常。
- 没有正在运行的 scorer、索引构建、Live E2E 或人工诊断任务。
- 运行期间 `MemAvailable < 768 MiB`、探针延迟超过一个检查周期、磁盘达到 85% 时，runner 接收 TERM，输出标记 `INFRA_ABORTED`；超时后才 KILL。

不能把 CPU limit 当资源预留。建议让 Gatus/heartbeat 所在 systemd slice 的 `CPUWeight/IOWeight` 高于 eval slice；runner 即使吃满 1 核，也不应让探针拿不到调度时间。

### 4. LiteLLM 条件迁移的内存算术（"尽可能迁移"裁定后的修订）

目标是把 195 上最大的可回收常驻项 LiteLLM（稳态 RSS 约 477~501MiB）迁到 127，同时不把 2C4G 压垮。算术（单位 MiB，按 §三.3 表）：

```text
常驻面：OS/Docker/WireGuard 900~1200
      + Gatus 160~256 + heartbeat 64~128
      + LiteLLM 1024（上限由 1536 压至 1024）
      + litellm 本地 PG 256
      ≈ 2400~2944
按需面：runner 1024（由 1280 压至 1024，-Xmx 512~640m）或 scorer 384~512
```

常驻面取上限时整机仅剩约 1.1~1.2 GiB 可用，runner 准入门的 `MemAvailable >= 1536 MiB` 会频繁红灯。因此以下条件全部满足才允许 LiteLLM 落 127：

1. **压限实测**：LiteLLM 在 1024MiB 上限下能完成启动（注意 195 实测启动峰值 1013MiB 贴线）且稳态 ≤ 600MiB；启动窗口与 runner/scorer 互斥。若 1024MiB 下重演 OOM-137 循环，本项迁移整体放弃，litellm 留 195。
2. **评测改走 127 litellm**：runner 的模型调用使用 127 litellm 的评测专用虚拟 key（带 max_budget 硬预算），不直连厂商端点；这样计费面统一、195 彻底不持上游 key。
3. **runner 压限**：runner 上限压至 1024MiB 并在与 litellm 共存的满载实测中证明 RSS 不越限、Gatus scheduler lag 不越门。
4. **互斥规则升级**：litellm 重启/Prisma migrate、runner、scorer 三者两两互斥；orchestrator 在 litellm 不健康时拒绝新作业（`INFRA_ABORTED` 语义不变）。
5. **回退门**：上述任一条连续两次验收不达标，litellm 回 195（原服务在观察期内不下线），127 仅保留探针+评测面；195 减负目标相应下调为只释放 eval-runner。

litellm 的本地 PG 是 litellm 自身的记账库，不是事实源也不是评测数据库——§十四"不部署第二个 PostgreSQL"指的是后者，本项是例外，但必须随之承担备份义务（SpendLogs 是费用账本）。

## 四、磁盘、目录和身份设计

第一期不在 2C4G 上增加 PostgreSQL、RabbitMQ、Redis 或 MinIO。单机、单并发、可重跑的批作业，用文件 spool + SQLite 公共状态足够；新增中间件只会增加常驻内存、备份和故障恢复面。

建议至少 60 GiB 系统盘，保留 20% 空闲。若只有 40 GiB，必须缩短本地保留并把封存包转移到外部对象存储。

```text
/srv/alert-eval/
  manifests/             # orchestrator 可读；绝不含 answer ref/digest
  inputs/                # runner 只读
    <dataset_digest>/<case_id>/...
  outputs/               # runner 写；scorer 只读挂载
    <run_id>/.tmp/
    <run_id>/sealed/
  answers/               # 只挂给 scorer；目录名和文件名不含根因
    <dataset_digest>/<opaque_case_id>.answer
  scores/
    public/               # 聚合分和发布门，importer 可读
    private/              # 逐 Case 差异，仅 scorer/受控复核人可读
  state/eval-orchestrator.sqlite
  quarantine/            # digest、签名、schema 或 canary 检查失败的包
  archive/                # 短期归档，按策略外移
```

容器身份建议：

| 身份 | 本地 UID | 可读 | 可写 | 明确拒绝 |
|---|---:|---|---|---|
| host `evalctl` | 11000 | manifests、公共状态、资源指标 | SQLite、作业日志 | answers、候选正文、模型凭据；只被授予启动固定 Compose service 的窄权限 |
| `eval-runner` | 11001 | manifests 的 runner view、inputs | outputs `.tmp`，完成后 seal | answers、scores、195 数据库、Chaos Admin |
| `eval-scorer` | 11002 | answers、sealed outputs | private/public scores | inputs 原文非必需、模型凭据、所有网络 |
| `eval-importer` | 11003 | public scores | 无或已发送标记 | answers、private scores |

Docker 挂载再做一次强制：runner 没有 answers mount；scorer 对 outputs 使用 `:ro`，对 answers 使用 `:ro`；scorer 设置 `network_mode: none`。不要只靠应用内 `if (role == ...)`。

工件写入遵循：写临时目录 → `fsync` → 计算 digest → 写 seal manifest → 原子 rename。Scorer 只认 `sealed/` 和 seal 中的 digest，不读取 `.tmp`。删除或过期清理由 orchestrator 产生待删除清单，运维审计后执行；不能让模型决定文件路径。

## 五、网络设计：Gatus 与评测流量必须是两条路

### 1. Gatus 网络

允许：

- 经 WireGuard 访问 195 上少量 health/readiness/synthetic 入口。
- 从 HOST2 自己公网出口访问值班接收器。
- 访问独立 heartbeat 服务。

拒绝：PostgreSQL、Docker socket、Chaos Admin、完整控制 API、模型管理 API。

### 2. Replay Runner 网络

默认无生产网络。若当前 baseline 完全确定性，直接无外网运行；若后续 RAG/Skill 候选需要远端模型，只允许：

- 指定的模型 API 域名/IP 和 443。
- 必要的输入包下载地址或结果上传地址。
- DNS/NTP 等基础设施最小出口。

必须拒绝 195 的 PostgreSQL、Prometheus、日志、变更、Alertmanager、Chaos Admin 和业务端口。`ReplayToolGateway` 的 MISS 只能返回 `REPLAY_MISS`，不能因为“网络恰好可达”就回落在线查询。

不要把 195 上现有 LiteLLM 当永久依赖，否则 195 故障时评测也停，且模型流量仍占用 195。过渡期可以临时复用，但要标记 `TRANSITIONAL_DEPENDENCY`。终态按 §三.4 的门裁定：门过则评测经 127 litellm 的评测专用虚拟 key 出网（计费面统一）；门不过则使用评测专用模型凭据直连合规端点，litellm 留 195。两种终态都不允许 HOST2 依赖 195 故障域内的模型网关。

### 3. Blind Scorer 网络

`network_mode: none`。答案、候选输出、词典和评分策略全部以只读文件挂载；评分结果写本地 scores 卷。它不需要访问模型，也不应让模型参与裁判。

## 六、代码怎么拆：现有类不能原样复用的地方

### Step 1：冻结旧 `eval` 为 `live-e2e`

当前 `EvalRunnerConfig` 同时装配 DB、故障驱动、轮询、评分和进程退出。先不大改行为，只把语义说清：

- 将现有 profile 从宽泛的 `eval` 收口为 `eval-live-e2e`。
- 保留 `EvalBatchRunner`、`FlagdScenarioDriver`、`ArenaChaosScenarioDriver`、`PrometheusAlertProbe`、`PostgresRcaRunResolver`。
- 只允许在 195 的维护窗口或受控 CI runner 启动。
- 增加锁，保证同一时刻最多一个 Live E2E。
- Live E2E 的结果用来验证生产链路，不作为 HOST2 离线 runner 的运行入口。

这样做的好处是先保住已有验收能力；问题是它仍接触生产和答案，所以不能作为 Skill 自动晋级的最终盲评门。

### Step 2：把 `GoldenCase` 拆成三个不同对象

当前 `GoldenScenarioRegistry` 和 `EvalCaseInput` 把执行输入与期望答案装在一起，是最大结构性问题。建议拆为：

1. `LiveScenarioSpec`：仅可信打包/Live E2E 使用，含 driver、injection、target、timing、恢复判据。
2. `ReplayCaseInputV1`：runner 可读，含 opaque case id、Alert/Incident 快照、可见上下文、replay tool records、config/tool/knowledge/skill digest、预算和 deadline。没有 `expected_*`、fault injection、会泄漏答案的 family/name。
3. `GoldenAnswerV1`：scorer 可读，含 expected root cause、symptom rules、allowed unknown、negative assertions、scoring policy version。

相应地：

- `GoldenScenarioRegistry` 退到 trusted packager/live-e2e，不再成为 Replay Runner bean。
- `EvalCaseInput` 去掉 `GoldenCase golden`，改成不含答案的 `CandidateObservation`。
- `ScenarioEvaluator` 改为纯函数 `score(GoldenAnswerV1, CandidateObservation)`，只在 scorer 模块装配。
- `SingleCaseScorer` 不再直接查 195 的 repositories；改由 `CandidateOutputReader` 读取封存输出，再由 `AnswerVault` 按 case id 取答案。

### Step 3：增加四个文件端口

建议新增：

- `EvalInputBundleReader`：校验 manifest/schema/signature/digest 后读取输入。
- `FileToolReplayStore implements ToolReplayStore`：从输入包的 replay index 精确读取响应。
- `CandidateOutputWriter`：只写 `.tmp`，完成后 seal；封存后拒绝覆盖。
- `AnswerVault`：只有 scorer profile 存在，按 case id 读取答案，不向调用方暴露对象 key。

现有 `AgentReplayRunner + ReplayToolGateway` 值得复用，因为它已经具备 action digest 精确匹配和 MISS 不触活网的正确语义。需要替换的是底层 `PostgresToolReplayStore`，不是重新写一套 Gateway。

### Step 4：新增三个严格互斥的 Spring profile

| Profile | 允许装配 | 明确不能装配 |
|---|---|---|
| `eval-live-e2e` | DataSource、Live drivers、Prometheus probe、旧 scorer | Replay 文件 runner、HOST2 自动晋级 |
| `eval-replay-runner` | File bundle、in-memory/file repository、Replay Gateway、候选执行、output writer | DataSource、Flyway、GoldenAnswer、ScenarioEvaluator、Chaos/Prometheus HTTP client |
| `eval-blind-scorer` | AnswerVault、CandidateOutputReader、ScenarioEvaluator、score writer | Agent、模型 gateway、ToolInvoker、DataSource、所有 HTTP client |

新增 profile 隔离测试不能只断言 bean “存在”，还要断言危险 bean “不存在”。例如 runner context 中 `DataSource`、`GoldenScenarioRegistry`、`SingleCaseScorer`、`ChaosAdminClient` 必须全部缺席；scorer context 中 `ToolInvoker`、模型 client、HTTP client 必须缺席。

### Step 5：构建 HOST2 runner，而不是复用硬编码 docker profile 的入口

当前 `control-app/Dockerfile` 的 ENTRYPOINT 固定 `--spring.profiles.active=docker`。有两种方案：

- 第一阶段：继续使用同一 exec jar，但为 HOST2 增加 `Dockerfile.eval`，入口根据镜像固定为 `eval-replay-runner` 或 `eval-blind-scorer`，并用 profile 测试证明装配隔离。
- 后续若实测 RSS 仍高：抽出 `eval-core` 与轻量 `eval-worker` Maven 模块，去掉 Web、生产持久化和不需要的 Spring 自动配置。

不建议在 Compose 中用随意 command 覆盖同一个生产镜像入口，因为一次误配置就可能在评测机启动 `docker` 生产 profile。

## 七、冻结包怎么从 195 生成并送过去

### 1. Packager 在 195 做什么

Packager 是一次性可信作业，它可以读取必要的生产表和当前 GT，但必须在输出时分流：

1. 锁定 dataset version、case family partition、tool registry、config、knowledge、skill 和模型指纹。
2. 从已封存 Run 读取 Alert/Incident 输入快照、选定上下文和 Tool 调用账本。
3. 按 action digest 导出真实 Tool 响应，形成 replay index；缺少响应的 Case 进入 quarantine，不能让 HOST2 回落活网。
4. 脱敏正文，删除生产凭据、内部 URL、无关个人数据和会暴露 GT 的注入标签。
5. 生成 `agent-input-bundle`，执行禁止字段和值扫描。
6. 从 Golden 数据生成 `scoring-answer-bundle`，放入独立 Vault 路径。
7. 对两个包分别 canonicalize、hash、签名；公开 manifest 只写 input digest，不写 answer ref/digest。
8. 在 Answer Vault 私有索引中写 `case_id -> answer object + answer digest + scoring policy`。

Packager 应使用新的 `eval_packager_ro` 数据库角色，只授权导出所需列；不要把当前权限较宽的 `eval_app` 密码复制到 HOST2。

### 2. 包格式建议

```text
agent-input-bundle/
  bundle.json                 # schema、dataset、opaque case ids、版本 digest
  cases/<case_id>/input.json  # Agent 可见输入
  cases/<case_id>/replay.idx  # action digest -> response file/digest
  cases/<case_id>/responses/*
  policy/tool-registry.json
  SHA256SUMS
  SIGNATURE

scoring-answer-bundle/
  answers/<opaque_case_id>.json
  scoring-policy.json
  synonym-lexicon.yml
  PRIVATE-SHA256SUMS
  PRIVATE-SIGNATURE
```

压缩包也要防 zip-slip、符号链接和解压炸弹：拒绝绝对路径、`..`、符号链接、超文件数、超单文件和超解压总量；先在 quarantine 解包校验，再原子移动到 inputs/answers。

### 3. 传输方式

优先级：

1. 已有企业对象存储：使用两个 bucket/prefix 和两个身份；runner 只有 input GET，scorer 只有 answer GET 与 score PUT。
2. 没有对象存储：通过 WireGuard/SFTP 分别投递到 HOST2 的 inputs 和 answers staging；使用不同 SSH key/受限命令，投递后撤销临时写权限。
3. 人工离线拷贝：仅适合首批验证，也必须核对 digest/签名并留下交接记录。

不要为了单机单并发专门部署 MinIO。等出现多台 runner、远端共享、生命周期管理或本机磁盘成为瓶颈时，再评估外部对象存储。

## 八、HOST2 上一次完整作业如何运行

建议由一个很小的 `evalctl`/orchestrator 串行执行：

```text
RECEIVED
→ VERIFYING_INPUT
→ READY
→ RUNNING
→ OUTPUT_SEALING
→ OUTPUT_SEALED
→ SCORING
→ SCORED
→ PUBLISHED

任意资源/宿主问题 → INFRA_ABORTED
任意 schema/digest/canary 问题 → QUARANTINED
候选本身失败 → CANDIDATE_FAILED（与基础设施失败分开）
```

逐步过程：

1. Orchestrator 验证 Gatus、内存、load、磁盘和当前互斥锁。
2. 校验输入包签名、digest、schema、路径和泄漏 canary；失败直接 quarantine。
3. 创建 run id，把不可变 runner manifest 写入 SQLite；它没有 answer ref。
4. 启动 one-shot `eval-replay-runner`，inputs 只读、outputs 临时目录可写。
5. Runner 对每个 Case 重建冻结上下文，调用既有 Agent/DAG；Tool 只走 `FileToolReplayStore`。
6. 任一 `REPLAY_MISS` 记为 Case 的 `REPLAY_INCOMPLETE`，不能在线补查，也不能偷偷忽略。
7. Runner 写 candidate report、Claims/Evidence refs、action sequence、token/费用/耗时、停止原因和版本指纹。
8. Runner 完成后 fsync、计算 output digest、原子 rename；Orchestrator 用 CAS 迁移到 `OUTPUT_SEALED`。
9. 这时才启动 one-shot scorer。Scorer 只有 answers、sealed outputs 和 scores 三个挂载，且无网络。
10. Scorer 用 case id 在 Vault 内部取答案，输出逐 Case 私有详情与公开聚合门；公开结果不含答案正文。
11. Orchestrator 验证 score digest，把公开 summary 交给 importer；Skill 生命周期只接受签名、dataset sealed、leakage guard 为零的 summary。
12. 到期后先外移封存工件，再清理本地；删除不影响主系统事实。

## 九、Compose 与进程管理建议

不要在第一期引入 Kubernetes。一个专用 Compose 项目加宿主机 systemd timer/oneshot 足够。建议三个 profile：`probe` 常驻，`runner` 与 `scorer` one-shot。`evalctl` 由 systemd 以专用宿主用户执行固定的 Compose 操作；任何容器都不挂载 `/var/run/docker.sock`。

配置要点：

```yaml
services:
  gatus:
    profiles: [probe]
    restart: unless-stopped
    mem_limit: 256m
    cpus: 0.35

  eval-runner:
    profiles: [runner]
    restart: "no"
    mem_limit: 1280m
    cpus: 1.25
    pids_limit: 256
    read_only: true
    cap_drop: [ALL]
    security_opt: [no-new-privileges:true]
    environment:
      JAVA_TOOL_OPTIONS: >-
        -Xms128m -Xmx768m -XX:+ExitOnOutOfMemoryError
    volumes:
      - /srv/alert-eval/manifests:/eval/manifests:ro
      - /srv/alert-eval/inputs:/eval/inputs:ro
      - /srv/alert-eval/outputs:/eval/outputs
      # 明确没有 answers/scores/生产 socket

  eval-scorer:
    profiles: [scorer]
    restart: "no"
    mem_limit: 512m
    cpus: 0.5
    pids_limit: 128
    network_mode: none
    read_only: true
    cap_drop: [ALL]
    security_opt: [no-new-privileges:true]
    volumes:
      - /srv/alert-eval/answers:/eval/answers:ro
      - /srv/alert-eval/outputs:/eval/outputs:ro
      - /srv/alert-eval/scores:/eval/scores
```

这是设计骨架，不应直接复制上线：具体 Compose 版本、磁盘路径、UID/GID、网络和健康检查要在 HOST2 验证。特别注意，Compose 的 `cpus/mem_limit` 是否生效必须用 `docker inspect` 与实际压力验证。

## 十、迁移顺序：按可回滚的小步执行

### M0：冻结当前基线（1～2 天）

- 选 10～20 个可重放 Case，记录当前 `eval` 的 config digest、结果、耗时、RSS、数据库查询量和 Tool replay 命中率。
- 给旧评测入口改名/标记为 `LIVE_E2E_LEGACY`，禁止误称离线。
- 冻结旧流程启动方式和回滚脚本。

退出标准：能重复执行旧批次，且知道它访问了哪些表、HTTP 服务和凭据。

### M1：先在代码内拆输入与答案（3～5 天）

- 新建 `ReplayCaseInputV1`、`GoldenAnswerV1`、`CandidateObservationV1`。
- `ScenarioEvaluator` 改成 scorer-only 纯函数。
- 在测试中加入答案 canary，并断言 runner prompt/context/tool args 全部不含 canary。
- 保持旧 Live E2E 行为不变，通过 adapter 兼容新 scorer 输入。

退出标准：同一 JVM 测试中可以分别构造 runner 与 scorer，runner API 类型上拿不到答案对象。

### M2：做文件化 Packager 与 Replay Runner（4～7 天）

- 新增 Packager、bundle schema、签名/digest 和 quarantine。
- 实现 `FileToolReplayStore`，复用 `ReplayToolGateway`。
- 以 in-memory/file repositories 运行一条完整固定 DAG，输出 sealed bundle。
- `eval-replay-runner` profile 下无 DataSource、无 HTTP Tool、无 scorer bean。

退出标准：拔掉网络后仍能跑完；MISS 显式失败；输出可重复校验。

### M3：做独立 Blind Scorer（3～5 天）

- Scorer 只读答案与 sealed output。
- 输出 public summary 与 private detail 两层结果。
- 加入状态机、输出先封存、评分幂等和重复请求测试。
- 加入“替换答案不改变 runner 输出”的变形测试。

退出标准：scorer 在 `network_mode:none` 下完成评分；runner 容器访问 answers 得到拒绝。

### M4：准备 HOST2（1～2 天）

- 基础 OS、时间同步、磁盘、Docker、WireGuard、最小 SSH 管理面。
- 创建专用 UID/GID 和目录 ACL；安装日志轮转与磁盘清理策略。
- 先上线 Gatus/heartbeat，完成压力下调度延迟基线。
- 防火墙分别验证 probe 和 eval 网络；从 runner 容器探测 195 DB/Chaos/Prometheus 必须失败。

执行面（2026-09-09 已落码）：基座初始化用 `deploy/eval-host2/mig01-run.sh` / `mig01-host2-bootstrap.sh`（含 UID、目录 ACL、slice 权重、WG 骨架、node_exporter 与 PASS/FAIL 验收，证据回收至 `docs/测试证据/HOST2-127/`）；Gatus 上线与六项验收按评审文档 Phase 1 执行。

退出标准：不运行评测时，探针连续 24 小时无异常；权限和网络负测试通过。

### M5：影子迁移（3～7 天）

- Packager 在 195 导出首批输入/答案，分别投递。
- HOST2 只跑 baseline，结果不进入任何 Skill 发布门。
- 对同一组封存 Case 比较旧 scorer 与新 Blind Scorer；差异逐条解释，不能只比总分。
- 连续运行至少 20 个 batch 或达到约定 Case 数，记录 RSS、OOM、CPU steal、磁盘、Gatus scheduler lag。

退出标准：结果差异为零或有已批准解释；无答案泄漏；评测压力下 Gatus 不漏调度。

### M5b：LiteLLM 条件迁移（1～2 天，门控，可与 M5 并行准备）

- 按 §三.4 五条门逐项验收：1024MiB 压限启动实测、runner 共存满载实测、互斥规则进 orchestrator。
- 切换按 `docs/告警系统-演进方案可行性评审与详细改造计划.md` Phase 11 §4 第 4 步执行：127 双跑 → usage 双通道对账 MATCHED → 低峰窗口切 `OPENAI_API_BASE` → 观察 24h → 195 litellm 下线。
- 195 侧 litellm 在观察期内保留下线不删除，作为回退；127 失联路径由第三方 heartbeat 覆盖。

退出标准：对账 MATCHED、24h 模型 p95 无显著劣化、评测满载时 Gatus 调度不越门；任一门不过则 litellm 回 195，本阶段以"放弃迁移"结论关闭而非带病通过。

### M6：切换离线发布门（1～2 天）

- Skill `EVALUATING` 只接受 HOST2 public score summary 的签名与 digest。
- 停止 195 上旧的“离线”定时批次；保留低频 Live E2E。
- HOST2 不配置 `EVAL_DB_PASSWORD`、`CHAOS_ADMIN_TOKEN`、生产 webhook bearer。
- 创建本地-only `eval_packager_ro`，轮换旧 `eval_app` 密码并确认 HOST2 到 5432 被网络拒绝。
- 更新值班手册、失败分类和回滚按钮。

退出标准：一个完整 Skill 候选通过 `VALIDATING → EVALUATING → REVIEW`，其评分链可从签名 summary 追到 sealed output 和 dataset digest，但 Agent 侧无法追到答案对象。

## 十二、必须通过的验收矩阵

### 1. 功能

- 同一 input/config/tool/knowledge/skill digest 可重复运行。
- Replay hit 返回与录制字节一致；MISS 不访问网络。
- baseline/RAG/Skill 三臂使用同一 Case、同一 replay 响应和同一评分策略。
- public summary 可驱动门禁，但不含根因答案和逐 Case 解释。

### 2. 答案隔离

- Runner 容器没有 answers mount、Vault token 或答案字段类型。
- 高熵 canary 在 prompt、RAG chunk、Skill 输入、tool args、trace、日志和 output 中命中为 0。
- 评分前替换测试答案，runner 输出 digest 不变。
- `OUTPUT_SEALED` 前启动 scorer 被状态机拒绝。
- HOLDOUT private detail 不回流 Skill generator。

### 3. 网络

- Runner 到 195:5432、Prometheus、Chaos Admin、业务端口全部失败。
- Scorer DNS、ICMP、HTTP 全部不可用。
- Gatus 仍能访问指定 health 与通知出口。
- 断 WireGuard 不影响 scorer；模型可选路径失败时作业正确标记，不影响探针。

### 4. 资源

- Runner 峰值 RSS 不越 1280 MiB，宿主 `MemAvailable` 不跌破紧急线。
- Runner 满 CPU 时 Gatus scheduler lag 不越约定阈值。
- Runner OOM/kill 后状态为 `INFRA_ABORTED`，没有半封存输出被 scorer 读取。
- 磁盘接近阈值时拒绝新 job，Gatus 日志仍可写。

### 5. 故障恢复

- Runner 中途 kill：重跑产生新 run id，旧 `.tmp` 被隔离清理。
- Scorer 中途 kill：对相同 `output_digest + scoring_policy` 幂等重试。
- HOST2 重启：Gatus先恢复；orchestrator 恢复状态但不自动评分未封存输出。
- 包损坏、签名不符、schema 未知：进入 quarantine，不尝试“尽量解析”。
- 195 不可用：已有离线包仍可完成确定性 replay/scoring；新包生成暂停。

## 十三、回滚方案

迁移失败时只回滚评测，不回滚探针：

1. 停止 HOST2 runner/scorer profile，保留 Gatus/heartbeat。
2. 禁止 Skill 发布门消费 HOST2 新 summary，把门状态恢复为“无可用盲评，禁止晋级”，而不是自动放行。
3. 如确有需要，在 195 手工恢复旧 Live E2E 批次；它必须继续标记为 live，不冒充离线 HOLDOUT。
4. HOST2 已产出的 score summary 不覆盖旧记录；标为 `MIGRATION_SHADOW` 或 `INVALIDATED`。
5. 不需要把任何生产数据从 HOST2 写回 195；回滚不涉及 Incident/RCA 主表恢复。

## 十四、为什么不用 RabbitMQ、Redis、第二个 PostgreSQL

- 并发只有 1，作业可重跑，文件 spool + SQLite 状态能表达所有必要状态；RabbitMQ 的确认、重投、DLQ 和集群维护没有对应收益。
- Redis 不能成为封存工件和发布门的唯一事实源；重启或淘汰不应改变一个 Skill 是否通过评测。
- 第二个 PostgreSQL 会引入迁移、备份、角色、升级和复制问题；HOST2 只需不可变包和少量本地状态，不需要事务数据库服务。例外：若 LiteLLM 按 §三.4 迁至 127，其本地小型 PG 仅承载 litellm 自身记账表（Prisma 自管理），不承载任何告警/评测事实；它随 litellm 迁移一起通过条件门，并必须纳入备份。
- 当未来出现多台 runner、多个并发消费者、远程共享数据集和长期重放时，应优先评估外部对象存储 + 轻量作业队列；有测量证明单机 spool 已成为瓶颈后，再选消息系统。

## 十五、最终推荐的切换口径

“迁移完成”必须同时满足：

1. HOST2 的 Replay Runner 在断开 195 数据面的情况下仍能运行冻结 Case。
2. HOST2 不存在 `EVAL_DB_PASSWORD` 和 `CHAOS_ADMIN_TOKEN`。
3. Agent 输入包没有答案、答案引用、注入机制或泄漏根因的名称。
4. Runner 输出先封存，Blind Scorer 后启动且无网络。
5. Skill 晋级只认签名后的盲评 summary。
6. 满负载评测不影响 Gatus 的探测与通知。
7. Live E2E 仍保留，但被明确标记为生产链路演练，不与离线 HOLDOUT 混为一谈。

做到这七点，才叫“把评测迁到 2C4G”；只把 `eval` profile 的容器启动位置从 195 改到 HOST2，不算迁移。
