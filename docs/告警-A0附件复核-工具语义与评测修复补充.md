## 2. 最关键的修正：引用存在不等于证据支持

附件中的错误 RPC 指标可以支持“特定调用存在失败”，普通 PlaceOrder 日志可以支持“该服务处理过请求”。如果该日志没有相应失败、依赖或关联请求信息，它不能仅因来自 Loki 就成为根因的第二份独立支持证据。

同时，累计失败计数非零不能证明告警窗口内正在失败；需要同窗口增量/速率、标签身份、采样覆盖与重置处理。诊断“下游调用失败”也要与更深层的“为什么失败”分开，不能把症状自动升级为机制根因。

修改 `PrimaryClaimAdmission` 与 `PrimaryFinalClaimProjector`：

1. 在既有 claim 提案中增加每个 evidence_ref 对本断言的作用：SUPPORTS、REFUTES、CONTEXT，以及定位到载荷字段/行区间的引用。LLM 可以提议作用，但不能自己授予最终可信状态。
2. Host 校验引用所属 Run/快照、时间范围、服务/依赖身份、字段是否真实存在。计数断言优先确定性检查：全量日志数不能成为错误数；累计值不能冒充窗口增量。
3. 普通上下文证据不计入支持来源数。多个工具读取同一底层信号应归并来源，不能按 toolId 数量伪造独立性。
4. 明确冲突优先级，保留现有同 claimKey 冲突呈堂能力。无法确认支持关系时降为 UNKNOWN/HYPOTHESIS，报告仍可成功生成，不迫使模型给 ROOT_CAUSE。
5. Projector 消费准入后的判定结果，不再仅从 kind 推出 TRUE、从来源数量推出一致。对语义复杂的结论可调用评审模型辅助，但保存依据与版本；评审模型不是事实裁判，不能绕过确定性限制。
6. 升级投影策略版本；新旧结果在评测中分开，不批量回写旧报告为新策略通过。

“单一权威证据已充分支持某个有限结论”也可能是合理结果。不要机械规定所有根因必须两种来源；应按断言类型定义必要证据，区分已确认的失败位置、候选机制与未决内容。

## 3. 工具链具体怎么改

### 日志聚合

保留 `logs.aggregate` 为通用计数工具，但 schema 和结果必须明确口径。增加可选的受限 severity 参数，默认 ALL；若保留名为 log_error_aggregate 的工具/别名，其契约必须明确过滤 ERROR 及以上或明确选定等级，不能继续表示全量行。

由服务器按已核对的日志源 schema 生成过滤表达式。标签 detected_level、结构化正文 level、自由文本 ERROR 是不同数据面，不可混为一个通用正则。未识别级别标记 UNKNOWN，不自动判为 INFO/健康。

结果至少携带 service、window、filter、count、coverage、truncated。成功空结果可返回 count=0，但必须同时注明日志源覆盖情况：未采集/标签不匹配/没有流量都不能据此证明无故障。源不可用仍是明确错误，不转成 0。

`logs.query` 沿用流式截断修复，返回截断标记和实际覆盖；提示词不得要求“SUCCESS 就代表支持根因”。SUCCESS 仅表示查询执行成功。

### 错误分类

修改 `PrimaryGatewayToolPort`：优先使用类型化 outcome/reason；若短期仍沿用 errorClass 字符串，做封闭枚举解析，未知值走显式 INTERNAL_ERROR，不默认 REMOTE_UNAVAILABLE。

| 类别 | 行为 |
|---|---|
| NO_DATA | 返回空结果语义，允许有界调整查询，不自动重复同参 |
| INVALID_ARGS | 返回脱敏、可纠正的字段错误，消耗纠错步数 |
| 不在本 Run 允许集 | 零触网，返回 TOOL_NOT_ALLOWED 的有界反馈；不扩大权限 |
| 允许集内但没有执行装配 | CONFIGURATION_ERROR；启动或创建 Run 时失败，不能等模型第二步才发现 |
| BUDGET_EXHAUSTED / DOOM_LOOP_TRIPPED | 控制终止/降级，不当网络错误重试 |
| 超时、限流、源不可用 | 按各自策略有界重试，保留原始分类 |
| 取消、失租 | 接入看门狗 v2 的停止传播，不触发模型 fallback |

注册期检查“发布工具目录、schema、执行器、delegate、Run allowlist”一致性。模型可见目录从已验证的当前 Run 工具快照生成，不再用人工同步四处清单来保证一致。

## 4. A0 与动态多 Agent 怎么验收

不要把直查 A0 的“零委派”设置为全局生产策略。测试 profile 可以固定零委派，另设动态路由测试：简单场景主 Agent 直查；证据不足且预算允许才委派；委派拒绝必须能收敛；追加角色不改变旧角色权限。

phase7 拆成两个独立用例：

1. **首次发布**：唯一 incident/正确 generation，验证本次报告赢得发布、publication/outbox 关联及真实接收回执。只看到 outbox 行不等于通知已经送达。
2. **重复调查仲裁**：有意复用 incident，核对精确仲裁键对应的 winner，验证 loser 事件、自己的报告存在、无重复外发。不能仅凭“没有 publication”判为合法 loser。

探针改为 package_json；超时按链路配置推导，等待时输出卡在哪一段，不能简单延长 30 秒掩盖错误。历史失败证据保留，新 runner 另版本执行。

phase5 不再对所有场景强制 TRUE：故障正例检查正确的支持结论；健康负例检查不编造；无数据例检查未决；矛盾例检查冲突保留。v13 含特定 RPC 指标提示，属于已知场景知识，验收应另外使用未参与提示词调整的留出场景。连续调 prompt 直到某一跑过门，只能形成回归样例，不能作为泛化准确率。

预算 8 是否足够应按场景集统计成功率、正确率、调用数和费用分布。单次 4–5 次工具调用收敛不能排除复杂告警、临时源故障或委派路径的预算问题。

## 6. 部署与性能结论的边界

附件中“215/300 MiB 导致 GC 卡顿”“重建后几秒是 DNS 预热”均是可能解释，时序相关不能独立证明原因。内存扩容后五次探针改善可以保留为观察；应补查询延迟分布、CPU 限流、GC、网络/DNS、查询并发证据，不能直接宣布因果已锤死。

执行修改应使用固定构建快照，记录源码版本、镜像摘要、prompt/tool 配置摘要及实际生效值。不从共享 WIP 拼装生产镜像，不用 main 编译绿替代相关回归验证。环境变量必须核对容器实际生效，健康 200 不能证明 allowlist、工具装配与评测契约都正确。

实施顺序：错误分类及日志口径 → Claim 准入/投影 → A0 发布与负例验收 → 固定版本跑留出集。与看门狗 v2 同属闭环收口，但不能用取消传播通过替代本文件的语义正确性验收。
