# ABC 执行方案、R7 多 Agent 与排期联合评审

评审日期：2026-09-09。源码基准：`aedf1ddb03445441a906fb0835212eeef88f102a`，另核对当前工作区方案。评审对象：ABC v1.0、R7 v1.0、主计划 v1.1、四线压缩排期 v1.0、AM7 v1.0。本文给出修改意见，不代替用户批准，也没有实施部署或修改业务代码。未读取用户禁止的三个文档。

## 1. 结论

**保留技术方向，修改执行契约和排期后再作为照做版下发。** PostgreSQL 持久化、共享预算、driver 独占、有界三角色、真实证据、显式 UNKNOWN 都值得保留。问题在于：若照当前顺序做，会先接入模型，后补其依赖的快照、账本和响应限制；恢复与补证的关键状态转换还没有定义；生产验收又混用了几个不相容的口径。

建议分开评审：方向可通过；“全部卡已足够精确”“6～7 周承诺”“现在跑的是 glm-5 RCA 基线”不宜通过。文件行号能帮助定位，但不能替代事务边界、身份、状态转换和异常语义。

## 2. 必须先修改的执行问题

### P1-01：A4 中的核心依赖不能排在真 LLM 之后

位置：ABC 第 18、24、66～83 行；R7 第 61 行；主计划 §8.5。

R7 的 ClaimDeriver 明确依赖 F05 冻结成员读取，但 F05 被放在 A4 后段；A3 要支持崩溃恢复，却把 F16 调用账本修复放在后面。F04/F14 决定调查的配置、输入、时间窗，F17 决定一次真实查询会不会先撑爆内存。这些都是第一条可靠链路的前提。

**改法：拆 A4，不必增加全部工作量。**

| 拆分 | 内容 | 完成门 |
|---|---|---|
| A0 身份与执行契约 | F04/F14 三种 digest、冻结时间窗；持久 attempt/call_seq；预算和结果提交接口 | A1/A3 接线之前定契约 |
| A4a 必要正确性 | F05 快照成员读取、F13 活跃集合、F16 UNKNOWN/调用结果原子落账、F17 有界读取与队列；F06 最小类型门 | 真实 LLM A 门之前 |
| A4b 剩余收口 | F18/F19 入口竞争与背压、F23/F24 身份和延迟准入等剩余工作 | C/D 之前；F23 若影响新身份格式，应在 A0 一次定好 |

A4a 是前移而非再算一遍工期；F06 由 R7c 一个责任人交付，A 线提供存储与快照契约，避免双方各写一套 Claim 转换。

### P1-02：预算接口不是“加一个 reserve 调用”这么简单

源码：`control-app/src/main/java/com/objwww/pr/control/alert/application/RunBudgetGate.java`，当前公开的是 `call(ReservationKey, estimateUnits, remote, usageExtractor)`；`ReservationKey` 包含 run/task/attempt/callSeq/budgetKind。ABC 中 `reserve(runId,costClass)` 应标为拟议接口，不能写得像现有方法。

先确定逻辑动作与物理请求：同一动作读取已完成回执可以复用身份；发生新的物理模型请求，必须可单独追踪和计费，不能用旧 reservation 掩盖第二次费用。多维预算还需要一次准入全部成功，或明确处理部分预留失败的撤销，不能只消费工具次数就称五维预算生效。

R7 loop 的文字顺序先写 LLM 输出、后写工具 ActionGuard，容易漏掉模型动作。改成模型与工具共同经过执行入口，各自校验模型路由或工具权限；每个物理重试仍受共享预算控制。A1 与 R7 只能有一处预算所有者，避免双重扣账。

验收至少包括：工具额度够但 token 不够；两任务争最后预算；预留成功而调用记录写失败；模型返回结果但缺 usage；同动作恢复读取结果不再触网；真正重发另记成本。

### P1-03：“无回执按幂等键重驱”必须删除

位置：ABC 第 61 行。进程可能在供应商完成请求之后、数据库写结果之前崩溃。此时没有回执，并不代表远端没有执行；本地幂等键也不代表供应商承诺去重。

建议持久化以下逻辑状态，可复用现有表，但必须列出实际需要的字段和迁移：

| 动作阶段 | 恢复行为 |
|---|---|
| 尚未取得发送资格 | 新 driver 重新核验预算、租约、取消后决定执行 |
| 已取得发送资格，结果未知 | 标记 UNKNOWN，保留预算占用；按供应商能力查询/对账，不能默认免费重发 |
| 结果已落库、任务未完成 | 从 result_ref 恢复，幂等提交任务，无须再触网 |
| 任务与结果已提交 | 重放读取既有结论 |

网络与数据库之间不存在一个本地事务能消除所有不确定窗口。只读工具如需再查，要约束原始时间窗并留下新的观察记录；模型请求如允许有限重试，要承认可能重复收费并预留新物理请求预算。未来有写工具时，必须另有远端幂等契约。

checkpoint 最少明确：run/round/task/attempt/action_seq、request_digest、reservation_id、dispatch 状态、result_ref、driver_epoch。不要为了“不加表”省略必要持久信息。

### P1-04：二次查 LeaseFence 还不等于结果提交有栅栏

位置：ABC 第 49 行，R7 §四。若先 SELECT 检查租约，再 INSERT 证据，中间可能已被新 driver 接管。旧 worker 仍会写入。

**改法：结果的业务准入、任务状态和事件提交，放在受 owner/epoch/generation/Run 状态保护的同一事务中。** 可通过锁定所有权行后校验并写入实现，或等价的条件写；影响行数为零明确为失去提交权。远端迟到响应可作为审计/对账资料保存，但不得因此进入有效证据快照。

取消也应声明线性化点：取消事务成功后不得取得新的动作发送资格；已获资格或已在飞的请求尽力取消，晚到结果隔离、费用仍对账。不要承诺 HTTP 请求与取消事务之间无法实现的绝对同时性。

源码 `PostgresRcaRunRepository` 暴露 `last_event_seq`，不要直接想当然新增一个不相关 revision。明确 `updateIfRevision` 与现有命令版本的映射及更新事务。

### P1-05：补证不是简单地往终态 DAG 后面加任务

位置：R7 第 68 行。源码 `DeterministicSupervisor.advance()` 在全任务终态时进入 REPORTING。新方案要求诊断结束后再派补证、再诊断，需要修改这个核心终态条件；“不动已测核心”不成立。

推荐明确 round：第 0 轮调查 → 冻结证据集 → 诊断输出 FINAL 或 NEED_EVIDENCE；后者经裁决创建下一轮有界 DAG，完成后生成新快照再诊断。只有没有待处理补证、诊断已最终收敛时才进入 REPORTING。每轮 DAG 无环，跨轮循环有上限，并且总预算不重置。

必须定义：round_id、父补证请求、请求去重键、最大轮数、拒绝补证原因、无信息增益停止、required/optional 失败、等待中的持久唤醒时间。崩溃在补证裁决后不得重复创建子任务。旧快照不可追加成员。

还有一个数据依赖矛盾：主计划说日志 Agent 按指标 Agent 圈定范围查询，R7 图却是两者平行根节点。首期若需要传递范围，就明确指标发现→日志调查的依赖；若两者先独立调查，再由诊断统一补证，也可，但不要在图里隐藏消息依赖。

### P1-06：LLM Findings 不能充当第二份独立现场证据

位置：R7 第 45 行“落 Evidence”。必须区分原始 Observation、模型派生 Findings、最终 Claim。可以共用存储，但要有明确类别、父引用与来源身份；模型复述一份日志，不应被算作第二个来源，两个 Agent 引用同一日志也不是两份因果证据。

ROOT_CAUSE 有“机制文字+引用”只是必要结构条件，不能证明因果正确。应列可程序检查的场景证据条件，保留反证和缺失，并用盲评核验正确性；无法确认就 HYPOTHESIS/UNKNOWN。不要让模型自己填一个类型，就自动晋升为根因。

同时明确 ClaimDeriver 与 RcaDiagnosisAgent：建议诊断 Agent 负责提出 Claim，ClaimDeriver/validator 负责引用与类型准入，避免两个地方分别再调模型生成不同答案。

### P1-07：A/B 验收定义应与交付内容一致

R7 第 76 行 A 门使用“日志 Agent 查询参数改变”作为示例，但第 86～87 行日志角色在 B 才交付。

建议 A 门验证单指标角色：真实 checkout 现场 → 第一次指标观察 → 模型选择第二个受限指标查询 → 真实执行 → 生成有引用的观察/假设报告。允许原因未确认。A 叫“单 Agent 真实模型闭环”，B 才叫“三角色 RCA”。如 A 必须包含日志角色，就相应前移实现并重估工期。

B 的“每角色≥1非固定动作、诊断≥1补证”应成为专门验收场景，不应成为每条生产告警的硬要求。增加三类对照：证据足够时零补证；缺证时有效补证；查不到/预算不足时明确终止。否则系统会为了验收次数浪费调用。

### P1-08：主计划的 glm-5 基线口径自相矛盾

主计划 §8.1 承认 Native 主链零 LLM，§五却要求当前全量跑批作为 glm-5 命中率起点；压缩排期也沿用这个名称。LiteLLM 单独 chat 成功或配置指向 glm-5，不能证明 RCA 运行调用了它。

改为：当前批次按实际执行引擎标注 Native 确定性基线。只有 run→task→attempt→模型请求/供应商回执关联完整，才能标注真实模型臂；连接探针单独归类。若本次运行的部署版本已不同于审计版本，须提交该版本及逐 Run 调用证据再裁定，不能由本地旧源码反推远端绝对没有调用。

“Up 33 分钟、七轮快照、内存正常”只支持当时运行水位，不能推出 RCA 质量或 LLM 在环。记录这些观测有价值，但不要把它们替代智能面证据。

## 3. 工具与产品面的具体修订

### B1：变更事实需要与生效动作同一事务

ABC 第 93 行建议 Controller 成功后写 change_event。源码 `ConfigBundleService.movePointer()` 经 repository.activate 完成激活，若控制器随后写事件失败，会出现配置生效但变更证据缺失。

把配置激活/回滚事实与 pointer CAS 放入同一事务，或事务内写 outbox 再投影 change_event；CAS 败者和幂等重放不能产生新“生效”事件。表可以 append-only，但这并不自动解决采集完整性。

部署脚本记录 deployment_id、目标 digest、实际生效时间、成功/失败/回滚状态。先核对当前实际部署入口，不能只因仓库有 deploy-am4.sh 就只挂这一处。Agent 保持只读。

### B2：保留盘点门，修改预设实现

盘点应追到 checkout 等业务服务的日志源、collector、存储、查询 API，不能只验证 control collector 自己有日志。没有数据时区分 EMPTY、SOURCE_UNAVAILABLE、QUERY_FAILED，禁止 fixture 顶替。

Loki 512MiB 应写成试验资源上限与准入条件，不是容量承诺。官方当前推荐通过 `otlphttp` exporter 向 Loki 原生 OTLP 入口发送日志；方案不宜直接指定旧 `loki exporter`。最终仍要按现有镜像版本验证。参考：[Grafana Loki 官方 OTel 接入文档](https://grafana.com/docs/loki/latest/send-data/otel/)。

PG 全文兜底也要计算采集、索引、保留清理和主库竞争成本；“已有 PG”不代表一定最轻。用实际业务日志样本测试检索效果。优先复用已可查询来源，缺少来源则显式降级。

### C1/C3：身份最小闭环应该先于生产写界面

ABC 第 119 行把手工配发 bearer 放浏览器并自报 X-Operator-Id，后面再做真实认证。AM7 管理面也沿用这一过渡方式。开发联调可临时隔离，但不能作为生产验收状态。

先完成服务端认证主体、读写权限、注销/过期，再开放生产 CRUD。修 Vite 路由无需等待。认证优先沿现有 Spring 栈的成熟机制实现，C3 先选清楚是服务端会话还是标准 token，不要同时模糊写“token 表+HMAC”变成自建协议。actor 从认证上下文生成；机器凭证与浏览器用户身份分离。

### AM7/C4：通知至少还有六处契约要补

1. **事件身份过粗。** source+alertname+startsAt 分钟桶可能合并同一分钟两个不同实例故障。加入资源指纹与稳定 episode 标识，并明确 firing/resolved 的关系；恢复通知不能被故障通知去重掉。
2. **送达不确定。** 超时可能已发送，六态必须说明如何记录 UNKNOWN 结果、是否允许重复以及如何审计；epoch 只能阻止旧 worker 写数据库，不能撤回群消息。不必为形式强加第七态，但不能缺语义。
3. **降级并发。** 多 watcher 扫同一 DEAD 时，需要唯一键和条件推进，避免同时创建多个下一通道投递。退避还要有最长通知期限，不能无限等到失去告警价值。
4. **已读不等于接单。** 全局 READ 不能证明当班人确认处理。若将来做升级，需要 recipient/read receipt 或 ACK 状态，不能直接把列表已读当成处理确认。
5. **快照陈旧不止 60 秒。** 195 离线数小时，127 缓存就可能陈旧数小时。定义 schedule_version、有效区间、首次启动无快照、快照损坏及过期 fallback；建议持久排班规则与本地独立应急通道，不能只依赖未来七天展开结果。
6. **探针自身故障仍有盲区。** 127 上 Gatus 经同机 adapter 报 adapter 故障会形成循环依赖。增加独立心跳接收/死信号检测通道，或明确这部分可用性承诺的限制。Docker 自动重启不是外部死亡检测。

建议把最小外部通知腿从完整排班 CRUD/消息列表拆出：先固定应急通道+业务码校验+持久重试+195 断链演练，后接动态排班。这样 Gatus 不用被产品页面工期阻塞。实际 webhook 地址和主机资源仍需由部署事实确定，本文不代填。

AM7 §3 时序图下补一段说明：195 与 127 两条发送腿的故障边界、回写失败不影响直发、哪些回执只代表机器人接收而非值班员阅读。

## 4. 排期核算与建议顺序

### 4.1 现有数字不能支持 6～7 周承诺

ABC 十卡相加是 **29～46 净开发日**，不是 29～45。每周五个净开发日，执行者自身就占 **5.8～9.2 周**，尚未证明包含全部联调与故障返工。前五卡 12～19 日约 **2.4～3.8 周**，上界不能写 W3 末完成。

四线文档的评测卡 M1-1 至 X-1 逐行相加是 **12.5～19.5 日**，不是文末 11～17 日（需要解释哪些工作已完成或合并抵扣）；再加主会话 R7 12～16 日，为 **24.5～35.5 日**。不能将“主会话”当成不消耗工时的协调角色。

| 人力口径 | 按已列工作量能得出的结论 |
|---|---|
| 一个执行者+一个实际开发的主会话 | 是两条开发线。6～7 周仅可能是偏乐观目标；ABC 上界自身已超过九周，不能保证完成 |
| 总共一名开发者 | ABC+评测明细+R7机械相加为53.5～81.5日，即10.7～16.3个五日工作周；这不是最终估算，仍需去重和补集成，但不能声称单人6～7周 |
| 四条独立开发线 | 原5～6周也须重新验证关键路径与共享文件冲突，人数不能直接除总工时 |

AM7 文档 §10 仍写 3～4 天，主计划原表 4～6、修订表 5～8，应统一。不要再维护多个含义不同的总数。

建议两条实际开发线先以 **8～10 周作为讨论用计划窗口**，而非交付承诺；身份/状态契约、日志盘点完成后，基于剩余工作与实际吞吐重新估算。该窗口仍可能因未知日志面、集成与验收失败增长。若必须更早展示，压缩首个真实模型闭环的范围，不压缩生产正确性门。

### 4.2 修订后的依赖顺序

1. 冻结身份、动作账本、round、快照、模型上下文接口，以及部署/评测版本锚点。
2. A1/A2 接预算与租约，同时完成 A4a 的必要正确性，随后 A3 实现可恢复驱动。
3. R7 模型适配可在隔离测试中与上述工作并行；已有 ModelRouter 直接复用，不再抽取同名类。真实触网验收必须等待执行守护就绪。
4. 交付单指标 Agent 的 A 门。若采用此范围，B1/B2 改为 B 门硬前置，不必阻塞首次看到真实模型决策。
5. B1/B2 完成真实源，R7b/c 完成三角色、补证 round、来源与 Claim 验证，过 B 门。
6. 完成剩余 A4b、并发恢复矩阵，过 C 门。认证最小面与外部通知最小面按资源可并行前移。
7. AM7 完整产品面、真实前端、备份恢复和部署演练收口，过 D 门及质量发布门。

R6 建议分两层：开发验证用最小无泄漏回放契约尽早提供；完整盲评是质量结论与发布晋升的硬前置。主计划 §三“R6 G2 前不得写 R7 实现”与 §8.5“R6 与 A/B 并行、B 后启用”必须选择并改成同一条规则。

### 4.3 只保留一份有效排期

四线版应在文首标记被替代，而不是仅在 ABC 中说作废。主计划需要整体修订，不能只用“智能面以§八为准”留下 §五错误基线、§一 HA/容量强制而压缩版后置等冲突。

明确两个范围：核心生产闭环（有真实智能、持久执行、安全边界、真实通知、恢复演练、可量化 SLO）；后续增强（RAG、Skill、MCP、额外 HA/容量能力）。若暂不交付主库 HA，就声明单主故障后的 RPO/RTO 和恢复方式，不要叫完整高可用。用户不要求百万告警，但仍需选定合理入口速率、并发调查上限和排队时延进行容量验收。

## 5. 每张卡还应增加什么
