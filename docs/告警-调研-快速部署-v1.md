# 告警平台快速部署调研 v1

- 核对日期：**2026-09-03**（所有"最新版本"以此日为准）
- 调研范围：一体化告警/AI RCA 平台核查（A）+ 拼装路径各组件快速部署（B）
- 目标环境：CentOS 7 / 内核 3.10.0 / docker 26.1.4 / 内存 7.5GB（可用约 5.7GB）/ 磁盘余 29GB / 已有 PostgreSQL 16 容器 / 中国大陆网络
- 标注约定：【明示】= 官方文档/源码直接写明；【推断】= 基于一手资料的判断；【未核实】= 未能从一手资料确认

## 结论摘要（约 300 字）

**一体化平台不成立（对本项目目标而言）。** Keep 自身的全自动 AI 关联（AI Correlation）在开源版明确不可用（⛔，仅 Cloud/企业版），开源版只有"AI 工作流步骤"（✅）和实验性的 AI 事件助手/半自动关联；夜莺 v9 开源版虽有内置 AI 助手和告警事件 AI 分析，但它是"告警产生引擎"而非"告警聚合/Incident 平台"，且依赖 MySQL+Redis，与项目 Postgres 惯例冲突。**最短可行路径仍是拼装：OTel Demo（故障注入+指标）→ Prometheus + Alertmanager（告警产生/去重）→ Keep（聚合/Incident/工作流）→ HolmesGPT（AI RCA，可调阿里云百炼 OpenAI 兼容端点）**。最大风险是**镜像拉取**：Keep 和 HolmesGPT 的官方镜像都只发布在 Google Artifact Registry（`us-central1-docker.pkg.dev`），不在 docker.io，国内可达性必须最先实测；备选是第三方镜像同步站或 HolmesGPT 改用 GitHub Release 的 Linux 二进制裸跑。**内存紧张但可行**：OTel Demo 官方 minimal 模式约 3GB + Keep 三容器约 1.2GB + Prometheus/Alertmanager 约 0.5GB + HolmesGPT 官方参考值 2Gi，合计已逼近上限，建议 HolmesGPT 按需 one-shot 运行而非常驻。

## A. 一体化平台核查

### A.1 Keep（keephq/keep）—— 一体化程度核查

Keep 自我定位是"open-source alert management and AIOps platform"。
来源：[Keep 官方文档 - Introduction](https://docs.keephq.dev/overview/introduction)（核对 2026-09-03）

各能力逐项核查（全部来自官方文档，标注开源版可用性）：

| 能力 | 开源版可用？ | 来源 |
|---|---|---|
| 告警接入（60+ provider 含 Alertmanager webhook） | ✅ | [providers 列表](https://docs.keephq.dev/llms.txt)、[prometheus-provider](https://docs.keephq.dev/providers/documentation/prometheus-provider) |
| 去重（Deduplication） | ✅ | [deduplication](https://docs.keephq.dev/overview/deduplication.md)（文档索引列出） |
| 规则关联（Correlation Rules / Topology） | ✅ | [correlation-rules](https://docs.keephq.dev/overview/correlation-rules.md) |
| Incident 管理 | ✅ | [incidents/overview](https://docs.keephq.dev/incidents/overview.md) |
| 工作流自动化 | ✅ | [workflow-automation](https://docs.keephq.dev/overview/workflow-automation.md) |
| **AI Correlation（全自动 AI 聚合）** | **⛔ 开源版不可用** | [ai-correlation](https://docs.keephq.dev/overview/ai-correlation) 原文："Keep Cloud: ✅ / Keep Enterprise On-Premises: ✅ / Keep Open Source: ⛔️"，且模型为 Keep 自研托管的专有模型 |
| AI Semi-Automatic Correlation（手动圈选告警 → AI 建议 Incident） | 开源版 experimental | [ai-semi-automatic-correlation](https://docs.keephq.dev/overview/ai-semi-automatic-correlation.md) 原文："Keep Open Source: (experimental)" |
| AI Incident Assistant（Incident 页内聊天、可问 RCA） | 开源版 experimental | [ai-incident-assistant](https://docs.keephq.dev/overview/ai-incident-assistant.md) 原文："Keep Open Source: (experimental)"；"Users can ask for root cause analysis" |
| AI in Workflows（LLM 作为工作流 step/action：归纳、定级、路由、摘要） | ✅ 开源版可用 | [ai-in-workflows](https://docs.keephq.dev/overview/ai-in-workflows.md) 原文："Keep Open Source: ✅"；"Supported providers include DeepSeek, OpenAI, Anthropic, Grok, Gemini, Ollama, Llama.cpp, vLLM" |

**Keep 的 AI 功能具体形态**【明示】：
- 不是一个内建的"RCA 引擎"，而是三类用法：工作流里调 LLM（开源可用）、Incident 页 AI 助手（实验性）、AI 关联（闭源）。
- 需要自带 LLM key。后端/前端 env：`OPENAI_API_KEY`、`OPENAI_MODEL_NAME`（默认 `gpt-4o-2024-08-06`）、`OPENAI_BASE_URL`（官方注明"useful for LiteLLM proxy"）。
  来源：[Keep deployment/configuration](https://docs.keephq.dev/deployment/configuration)（核对 2026-09-03）
- 另有独立的 LiteLLM provider 和 DeepSeek provider，DeepSeek 本身就是 OpenAI 兼容协议。
  来源：[llms.txt 文档索引](https://docs.keephq.dev/llms.txt)

**能否配阿里云百炼**：百炼提供 OpenAI 兼容端点，base_url 形如 `https://dashscope.aliyuncs.com/compatible-mode/v1`（旧域名仍可用；新 workspace 专属域名 `https://{WorkspaceId}.<region>.maas.aliyuncs.com/compatible-mode/v1`）。
来源：[阿里云 Model Studio - OpenAI compatible](https://www.alibabacloud.com/help/en/model-studio/compatibility-of-openai-with-dashscope)（核对 2026-09-03）
【推断】Keep 侧设 `OPENAI_BASE_URL` + `OPENAI_API_KEY` + `OPENAI_MODEL_NAME=qwen-*` 理论上可通，但**未经实测**，且百炼文档注明 tools（function calling）目前仅 qwen-turbo/plus/max 等部分模型支持、且 tools 不能与 stream 同用——Keep 的 AI 工作流若用 structured output 可能踩坑。

### A.2 Robusta + HolmesGPT 捆绑关系

【明示】Robusta 的 helm chart `values.yaml` 内嵌：
- `enableHolmesGPT: false`（开关）+ `holmes:` 子 chart 配置段；
- `kube-prometheus-stack:` 完整子 chart 段（含 Alertmanager 预配 webhook 指向 robusta-runner、Prometheus 资源 request 2Gi/retention 15d/存储 100Gi）；
- `enablePrometheusStack: false`（开关，"install prometheus, alert-manager, and grafana along with Robusta?"）。

来源：[robusta helm values.yaml](https://raw.githubusercontent.com/robusta-dev/robusta/master/helm/robusta/values.yaml)（核对 2026-09-03）

**纯 docker 形态**：Robusta 本体【明示】仅支持 Kubernetes（chart 注释与官方安装文档均以 K8s 为前提）。**但 HolmesGPT 有独立纯 docker 形态**（官方 docker-compose HTTP server + CLI 容器，见 B.2）——即"Robusta 捆绑"对非 K8s 环境无意义，直接单用 HolmesGPT 即可。

### A.3 夜莺 Nightingale

- 【明示】v9.0.0（2026-07-27 发布）主线是 Nightingale AI：内置 AI 助手（多轮对话、流式）、20+ Skill、"**告警事件的 AI 分析**"、事件流水线里的 **AI 总结节点**；LLM 集中配置"支持 OpenAI 兼容协议、Claude、Gemini 三类接口"，私有化模型兼容 OpenAI 协议即可接入。
- 【明示】AI 助手依赖 Redis 5.0+（Redis Streams）；不配置大模型时功能照常。
- 【明示】部署形态：v8 起可用 sqlite+miniredis 单二进制一键拉起（仅个人测试）；生产依赖 MySQL+Redis；镜像/compose 官方有提供。
- 定位：多数据源**告警引擎**（对接 Prometheus/VM/ES 等数据源，在夜莺里配规则产生告警），不是 Alertmanager 下游的聚合/Incident 平台。

来源：[夜莺 v9 正式版发布（官方博客）](https://flashcat.cloud/blog/nightingale-release-v9/)、[夜莺 v8 beta1（官方博客）](https://www.oschina.net/news/326038/nightingale-release-v8-beta1)（核对 2026-09-03）

【推断】对本项目的适配性：夜莺可以替换"Prometheus+Alertmanager+Keep"里的前两环并自带事件管道和 AI 分析，但 (a) 依赖 MySQL+Redis，与项目 Postgres 惯例冲突；(b) 它是告警产生方而非聚合方，交易域告警 RCA 作品集的"聚合去重 → RCA"叙事不完整；(c) AI 事件分析是否开源版全量可用需实测（v9 发布文未区分开源/企业版边界，【未核实】）。

### A.4 SigNoz

【明示】Docker Compose 部署前提："At least 4GB of memory allocated to Docker"；组件含 ClickHouse、clickhouse-keeper、PostgreSQL（metastore）、signoz-otel-collector、signoz。
来源：[SigNoz Docker 安装文档](https://signoz.io/docs/install/docker/)（核对 2026-09-03）

【推断】SigNoz 是 APM/可观测平台（带告警），无开源 AI RCA 能力；4GB 起步 + ClickHouse 栈对 5.7GB 可用内存的机器代价过高，且与"告警聚合+RCA"目标链路不匹配。过筛排除。

### A.5 Grafana（OnCall / IRM / LLM 插件）

- 【明示】**Grafana OnCall OSS 已于 2026-03-24 归档（仓库只读）**，2025-03-11 起即 maintenance mode，官方建议迁移到 Grafana Cloud IRM（SaaS）。
  来源：[Grafana OnCall 官方文档归档公告](https://grafana.com/docs/oncall/latest/set-up/open-source/)（核对 2026-09-03）
- 【推断】Grafana 本体 + Alerting 可做告警产生与简单分组，但 Incident 管理（OSS）已死；LLM 相关插件（grafana-llm-app 等）主要面向 Grafana Cloud / Assistant，自托管开源路径没有等价于 HolmesGPT 的 RCA agent。过筛排除。

### A.6 Alerta / Zabbix（快速过筛）

- Alerta：【明示】官方 docker 镜像 `alerta/alerta-web` + Postgres，compose 一键起，去重/关联靠插件机制；无任何 AI 能力。
  来源：[alerta/docker-alerta](https://github.com/alerta/docker-alerta)、[Alerta 官方 docker 教程](https://docs.alerta.io/gettingstarted/tutorial-10-docker.html)（核对 2026-09-03）
- Zabbix：重量级监控套件，官方有 docker 镜像仓库 [zabbix/zabbix-docker](https://github.com/zabbix/zabbix-docker)（【未核实】细节），无 AI RCA，与本项目链路不匹配。过筛排除。

### A.7 A 部分结论

- **没有单一开源 compose 能全覆盖"接入 + 聚合 + Incident + AI RCA"**。最接近的 Keep 把最关键的 AI Correlation 放在闭源；夜莺 v9 覆盖"产生+AI 分析"但不是聚合/Incident 定位。
- 选一体化（Keep 单平台 + 其开源 AI 工作流）比"Alertmanager+Keep+HolmesGPT"少 1 个组件（HolmesGPT），但妥协是：RCA 能力降级为"工作流里调一次 LLM 做摘要"或实验性聊天助手，**没有 HolmesGPT 那样的多轮工具调用 agent 调查**（HolmesGPT 会自主执行 PromQL 查询、拉日志、看拓扑再给结论——见 B.2 的 38+ toolset 与 max_steps 机制）。
- **后续替换为自研 Java RCA 的可行性**：拼装路径反而更有利——Keep 与 HolmesGPT 之间是 HTTP 调用关系（Keep 工作流的 http provider → HolmesGPT `/api/chat`），RCA 环节天然是一个可替换的独立服务边界；若用 Keep 内建 AI 工作流，替换时要把 LLM 调用逻辑从 Keep workflow YAML 里拆出来，边界反而模糊。【推断】

## B. 拼装路径各组件

### B.1 Keep

**最新版本**：v0.54.2（2026-07-13 发布）。
来源：[GitHub Releases API](https://api.github.com/repos/keephq/keep/releases/latest)（核对 2026-09-03）

#### 【最快路径】

【明示】官方一键脚本（[deployment/docker](https://docs.keephq.dev/deployment/docker)）：

```bash
curl https://raw.githubusercontent.com/keephq/keep/main/start.sh | sh
```

实际等价于下载 `docker-compose.yml` + `docker-compose.common.yml` 后 `docker compose up -d`。共 3 个容器【明示】（[docker-compose.yml](https://raw.githubusercontent.com/keephq/keep/main/docker-compose.yml) / [docker-compose.common.yml](https://raw.githubusercontent.com/keephq/keep/main/docker-compose.common.yml)，核对 2026-09-03）：

| 容器 | 镜像 | 说明 |
|---|---|---|
| keep-backend | `us-central1-docker.pkg.dev/keephq/keep/keep-api` | FastAPI，端口 8080 |
| keep-frontend | `us-central1-docker.pkg.dev/keephq/keep/keep-ui` | NextJS，端口 3000 |
| keep-websocket-server | `quay.io/soketi/soketi:1.4-16-debian` | Pusher 协议实时推送，端口 6001 |

默认 env：`AUTH_TYPE=NO_AUTH`、`SECRET_MANAGER_TYPE=FILE`、`DATABASE_CONNECTION_STRING=sqlite:////state/db.sqlite3?check_same_thread=False`（即 **SQLite 开箱即用**，数据落 `./state` 卷）。

#### 【配置样板要点】

- **数据库**：`DATABASE_CONNECTION_STRING` 接受任意 SQLAlchemy 连接串【明示】（[configuration 文档](https://docs.keephq.dev/deployment/configuration)："Valid SQLAlchemy connection string"）；`pyproject.toml` 依赖含 `psycopg`/`psycopg2-binary`/`pymysql`【明示】（[pyproject.toml](https://raw.githubusercontent.com/keephq/keep/main/pyproject.toml)）。【推断】指向已有 PG 16 容器：`DATABASE_CONNECTION_STRING=postgresql+psycopg2://keep:***@<pg容器名>:5432/keepdb`（需先建库；`SKIP_DB_CREATION=true` 可跳过自动建库/迁移【明示】）。
- **Redis 非必需**：`REDIS` 默认 `false`【明示】；ARQ 为依赖（`arq = "0.26.3"`，见 pyproject），但官方 compose 主路径不带 Redis 容器，仅 `docker-compose-with-arq.yml` 变体带（用于 AI 后台任务）。【推断】demo 规模不开 ARQ/Redis 即可跑通接入+聚合+工作流。
- **接收 Alertmanager 告警**【明示】（[prometheus-provider](https://docs.keephq.dev/providers/documentation/prometheus-provider)）：Alertmanager 配置 webhook 指向 `KEEP_BACKEND_URL/alerts/event/prometheus`，basic auth 用户名固定 `api_key`、密码为 Keep API key：

```yaml
receivers:
- name: "keep"
  webhook_configs:
  - url: 'http://keep-backend:8080/alerts/event/prometheus'
    send_resolved: true
    http_config:
      basic_auth:
        username: api_key
        password: <KEEP_API_KEY>
```

- **公网安全**：`AUTH_TYPE` 支持 `DB`（账号密码登录，配 `KEEP_JWT_SECRET`，可选 `KEEP_DEFAULT_USERNAME/PASSWORD`）【明示】；另有 `KEEP_USE_LIMITER`/`KEEP_LIMIT_CONCURRENCY` 速率限制。【推断】公网机器至少开 DB 认证 + 防火墙只放必要端口。

#### 【坑与注意】

- **镜像在 Google Artifact Registry（`us-central1-docker.pkg.dev`），不在 docker.io**【明示】。国内直连大概率失败，需实测；已有第三方同步案例（如华为云 SWR 同步仓库中存在 `keep-ui`，见 [kubesre/docker-registry-mirrors#4123](https://github.com/kubesre/docker-registry-mirrors/issues/4123)，非官方、时效性不保证）。
- 默认 compose 把 3000/8080/6001 直接绑到宿主机——公网机器需改成 `127.0.0.1:` 前缀或前置反代。【推断】
- 官方未给资源占用数据【未核实】。【推断】FastAPI 后端约 300–600MB、NextJS 前端约 300–500MB、soketi 约 50–100MB。
- 官方默认 compose 会在 backend 里读 `$OPENAI_API_KEY`（shell 未设置则为空，不影响启动）。

### B.2 HolmesGPT

**最新版本**：0.40.0（2026-08-25 发布；仓库已从 robusta-dev/holmesgpt 迁至 HolmesGPT/holmesgpt，CNCF Sandbox）。
来源：[GitHub Releases API](https://api.github.com/repos/HolmesGPT/holmesgpt/releases/latest)、[HolmesGPT/holmesgpt](https://github.com/HolmesGPT/holmesgpt)（核对 2026-09-03）

#### 【最快路径】两种形态【明示】

**one-shot CLI（容器）**（[CLI 安装文档](https://holmesgpt.dev/dev/installation/cli-installation/)）：

```bash
docker run -it --net=host \
  -e OPENAI_API_KEY="your-api-key" \
  -v ~/.holmes:/root/.holmes \
  us-central1-docker.pkg.dev/genuine-flight-317411/devel/holmes \
  ask "what Prometheus alerts are currently firing and why?"
```

**HTTP server（官方 docker-compose，无需 K8s）**（[HTTP Server (Docker)](https://holmesgpt.dev/latest/installation/docker-compose-installation/) + [仓库 docker-compose.yaml](https://raw.githubusercontent.com/HolmesGPT/holmesgpt/master/docker-compose.yaml)）：

- 单容器，镜像同上（GAR），端口绑 `127.0.0.1:5050`，healthcheck `/healthz`；
- 挂载 `~/.holmes`（配置）；
- 核心 API 为 `POST /api/chat`。

#### 【配置样板要点】

- **OpenAI 兼容端点**【明示】（[OpenAI-Compatible 文档](https://holmesgpt.dev/dev/ai-providers/openai-compatible/)）：
  - `OPENAI_API_BASE` = 端点 URL；`OPENAI_API_KEY` = key（无鉴权端点也要填占位符如 `none`）；模型写法 `openai/<model-name>`。
  - **模型必须支持 function calling**（官方原文警告：不支持的模型"may produce incorrect results"）。
  - 【推断】接阿里云百炼：`OPENAI_API_BASE=https://dashscope.aliyuncs.com/compatible-mode/v1`，`--model="openai/qwen-plus"`（百炼 tools 支持 qwen-turbo/plus/max 等，见 A.1 来源）。
- **Prometheus toolset**【明示】（[prometheus toolset 文档](https://holmesgpt.dev/dev/data-sources/builtin-toolsets/prometheus/)）：`~/.holmes/config.yaml`：

```yaml
toolsets:
  prometheus/metrics:
    enabled: true
    subtype: prometheus
    config:
      prometheus_url: http://<prometheus>:9090
```

  提供 `list_prometheus_rules`、`execute_prometheus_instant_query`、`execute_prometheus_range_query` 等工具。

#### 【坑与注意】

- **镜像同样在 GAR（`us-central1-docker.pkg.dev/genuine-flight-317411/devel/holmes`）**【明示】，国内拉取风险与 Keep 相同。**备选**：GitHub Release 提供 `holmes-linux-amd64-0.40.0.zip`（约 150MB 独立二进制）【明示】，或 `pipx install holmesgpt`【明示】——可完全绕开容器镜像问题。
- 官方 helm chart 默认资源 `requests: 100m/2048Mi, limits: 2048Mi`【明示】（[helm/holmes/values.yaml](https://raw.githubusercontent.com/HolmesGPT/holmesgpt/master/helm/holmes/values.yaml)）——**官方参考值就是 2Gi**，对 5.7GB 可用内存偏重。【推断】docker-compose 无 limit，实际空闲远低于 2Gi，峰值取决于调查轮次；建议 demo 时按需运行而非常驻，或加 `--memory` 限制观察。
- HTTP server 模式官方定位是"供二次集成用"（接 Keep 工作流正合适）。

### B.3 Prometheus + Alertmanager

【明示】镜像名：`prom/prometheus`（docker.io）、`prom/alertmanager`（docker.io）——均在 docker.io，国内加速可解。Keep 自带的 compose 里也用了 `prom/prometheus:latest`（见 B.1 compose 源码）。

最小 compose 样板（【推断】，基于官方镜像惯例）：

```yaml
services:
  prometheus:
    image: prom/prometheus:v3.13.1   # OTel Demo 3.0.0 配套版本
    volumes:
      - ./prometheus.yml:/etc/prometheus/prometheus.yml
      - ./alert-rules.yml:/etc/prometheus/alert-rules.yml
    ports: ["127.0.0.1:9090:9090"]
  alertmanager:
    image: prom/alertmanager:latest   # 版本号未核实，建议锁定
    volumes:
      - ./alertmanager.yml:/etc/alertmanager/alertmanager.yml
    ports: ["127.0.0.1:9093:9093"]
```

`prometheus.yml` 中 `alerting.alertmanagers` 指向 alertmanager；`alertmanager.yml` 的 receiver 用 B.1 的 Keep webhook 样板。
Alertmanager 自身去重/分组参数【明示】（Keep provider 文档样例）：`group_by` / `group_wait` / `group_interval` / `repeat_interval` / `send_resolved: true`。

### B.4 OpenTelemetry Demo

### B.5 Pumba

- 仓库已迁移至 **alexei-led/pumba**（原 gaia-pipeline/pumba 已 404）【明示】。
- **最新版本 1.2.1（2026-08-23）**，提供 `pumba_linux_amd64` 单二进制（约 28MB）；官方定位"Chaos testing, network emulation, and stress testing tool for Docker, containerd, and Podman containers"。
  来源：[Releases API](https://api.github.com/repos/alexei-led/pumba/releases/latest)、[alexei-led/pumba](https://github.com/alexei-led/pumba)（核对 2026-09-03）
- docker 26 兼容性【推断】：项目活跃维护（1.2.x 系列 2026 年发布），未发现官方声明的 docker 26 不兼容；其网络故障（netem）依赖容器内 tc 工具与 `NET_ADMIN` 能力，CentOS 7 内核 3.10 支持 netem。
- 【推断】若只用 OTel Demo 的 feature flag 注入应用层故障，Pumba 可选；它适合补"容器 kill/网络延迟"类基础设施故障。

### B.6 兼容性（linux/amd64 + 内核 3.10）

- 【明示】以上所有镜像均提供 linux/amd64 manifest（各仓库 release/compose 默认面向 amd64）。
- 内核 3.10：未检索到任何上述项目官方声明的最低内核版本要求【未核实】。【推断】docker 26.1.4 自带的 seccomp profile 已覆盖新 syscall（早年 Alpine 镜像 faccessat2 被旧 docker 拦截的问题不适用），主流 Go/Rust/Node/Python 镜像自带 libc，内核 3.10 下一般可运行。
- **Redis 官方镜像**：官方未声明内核要求【未核实】。【推断】redis:7 容器在 CentOS 7 + docker 26 上无已知系统性问题（Keep 默认不需要 Redis；夜莺 AI 需要 Redis 5.0+——若上夜莺路径才相关）。
- 已知真正会踩内核的组件：OTel Demo **profiling 模式**（eBPF profiler `ghcr.io/open-telemetry/opentelemetry-collector-releases/opentelemetry-collector-ebpf-profiler`）对内核版本要求高，内核 3.10 不要用 profiling 模式【推断，eBPF CO-RE 一般需 4.x+】。

## C. 总装顺序建议 + 内存预算

### C.1 总装顺序（按一票否决风险优先）

1. **镜像拉取实测（最高优先，一票否决）**：在目标服务器实测 `us-central1-docker.pkg.dev`（Keep、HolmesGPT）、`ghcr.io`（OTel Demo、flagd）、`quay.io`（soketi、prometheus、jaeger）的直连可达性。任一不通立刻定备选：第三方同步镜像站 / `docker pull` 代理 / HolmesGPT 改用 GitHub Release 二进制裸跑 / OTel Demo 镜像走代理预拉后 `docker save/load`。
2. **LLM 端点连通性（一票否决）**：`curl https://dashscope.aliyuncs.com/compatible-mode/v1/models -H "Authorization: Bearer $KEY"`，并实测一次带 tools 的 chat completion（HolmesGPT 强依赖 function calling）。
3. Keep 三容器（SQLite 起步，跑通后再切 PG 16）。
4. Prometheus + Alertmanager + 自写告警规则 → webhook 进 Keep（验证指纹去重/Incident 聚合）。
5. OTel Demo minimal（或 minimal-no-o11y，Prometheus 用自己的），flagd 开 `paymentFailure` 之类故障触发告警。
6. HolmesGPT：先用 one-shot CLI 验证 RCA 质量，再决定是否常驻 HTTP server 接 Keep 工作流。
7. 安全收尾：所有端口绑 `127.0.0.1` + 反代/防火墙，Keep 开 `AUTH_TYPE=DB`。

### C.2 内存预算表

可用内存约 **5.7GB**（7.5GB 总量，已有一个 PG 16 容器在跑）。

| 组件 | 预估内存 | 依据 |
|---|---|---|
| 已有 PostgreSQL 16 | 200–500MB | 【推断】 |
| Keep backend + frontend + soketi | 约 0.9–1.6GB | 【推断】官方无数据 |
| Prometheus + Alertmanager | 0.3–0.6GB | 【推断】demo 量级 |
| OTel Demo minimal 模式 | **~3GB** | 【明示】官方文档 |
| HolmesGPT 常驻 | **官方参考 2Gi** | 【明示】helm values；docker 无 limit 时【推断】空闲约 0.5–1GB、调查时上涨 |
| **合计（HolmesGPT 常驻）** | **约 6.7–8.2GB，超了** | — |

**明确结论：HolmesGPT 常驻 + OTel Demo minimal 全开 = 超内存。** 取舍方案（按推荐排序）：

- **方案 1（推荐）**：HolmesGPT 不常驻——demo 讲解到 RCA 环节时一次性 `docker run --rm`（或裸跑二进制）执行 `holmes ask`，用完即释放。常驻合计压到约 4.5–6.0GB，可行。
- **方案 2**：OTel Demo 用 `minimal-no-o11y`（去掉其自带 Grafana/Jaeger/OpenSearch，约再省 1GB【推断】），观测面全走自己的 Prometheus + Keep。
- **方案 3**：砍 Keep frontend（纯 API 操作）或砍 soketi（关实时推送）——能省 0.3–0.5GB 但损害作品集演示效果，不建议。
- 磁盘：OTel Demo 官方要求 14GB，加 Keep/HolmesGPT/Prometheus 镜像约再 3–5GB【推断】，29GB 余量勉强够，跑完即清理。
