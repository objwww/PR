# 告警 Agent v1.2：评测与安全反馈核查纪要 v1

> 日期：2026-09-04  
> 对象：`docs/架构设计-告警Agent-v1.2.md` 及本轮外部评审反馈  
> 结论：**吸收可验证的合理项，改写与现有边界冲突的部分，明确拒绝不适用的炫技项。**  
> 原则：先核对当前代码和官方资料，再决定是否进入架构；不因为项目“高星”或术语高级就改变已冻结的 Docker Compose + PostgreSQL 控制面。

---

## 1. 一句话结论

这轮反馈最有价值的不是再增加组件，而是补齐四个此前表达不够硬的边界：

1. 评测安全必须同时看 **正常任务 Utility** 和 **攻击是否得逞 Security**；
2. Replay 的工具返回必须精确匹配，无法匹配就承认 `REPLAY_MISS`；
3. Holmes 已经能暴露 tool-call 和 token 元数据，Java Adapter 应保存，但 Holmes 不能拥有最终授权；
4. RCA 系统的自告警必须走独立通道，不能指望故障中的 RCA 系统给自己诊断。

真正值得直接引入的是：2C4G 上的 Inspect AI 评测 Runner、Promptfoo 离线红队、Gatus 外部探针；OPA 只在未来 Action Runner 真正进入 R2/R3 时引入。AIOpsLab、NeMo Guardrails、AgentDojo 主要借结构；gVisor/Kubernetes 不进入本项目。

## 2. 先看当前代码，而不是只看目标图

### 2.1 当前 Holmes 客户端保存了什么

代码证据：

- `control-app/src/main/java/com/objwww/pr/control/infrastructure/holmes/HolmesClient.java:62-64` 的 `HolmesChatResult` 只有 `body`、`promptTokens`、`completionTokens`、`totalTokens`、`usageMissing`；
- `HolmesClient.java:109-111` 只从 `metadata.usage` 提取 aggregate usage；
- `control-app/src/main/java/com/objwww/pr/control/infrastructure/holmes/HolmesInvestigationExecutor.java:179-201` 对最终 body 做 EvidencePackage 验证并落总 Token，但没有把 tool-call 拆成内部审计记录；
- `HolmesInvestigationExecutor.java:246-264` 已明确把 labels/annotations 框定为不可信数据，并用 `response_format.strict=true`，说明入口不是完全裸奔。

因此反馈中“扩展 HolmesClient 保存 tool_call 元数据”是**真实差距**；但“当前完全没有 Prompt Injection 防线”不成立，准确说法是：已有上下文框定和输出 Schema，尚缺预 tokenization 归一化、间接注入回归、ToolCall 级审计和更完整的输出安全验证。

### 2.2 当前没有使用 ThreadPoolBulkhead

v1.2 的正式设计是：

- PostgreSQL 持久任务承担排队；
- Scheduler 以 lease + slot 控制并发；
- Java 虚拟线程/普通线程只负责等待；
- 外部调用期间不持有数据库事务。

所以外部意见要求补 `ThreadPoolBulkhead.maxQueueCapacity=50`，并不是当前实现缺陷，而是把另一种并发模型套到了本项目。若将来只用 `SemaphoreBulkhead` 包本地调用，应该 `maxWaitDuration=0`，饱和后回到持久任务，而不是再叠一层内存队列。

## 4. ConfigBundle：为什么不能“INSERT-only 但回滚时 UPDATE 旧行”

### 4.1 原意见的自相矛盾

`INSERT-only` 的意思是历史事实不允许改。若回滚时执行：

```sql
UPDATE config_bundle SET valid_until = NULL WHERE version = :old;
```

旧 bundle 就被重新解释成“从过去一直有效到现在”，历史事实被改写。更麻烦的是并发发布：两个人同时回滚/发布时，可能出现多行 `valid_until IS NULL`，查询“当前配置”不再唯一。

### 4.2 本项目采用的模型

```text
config_bundle            不可变内容
config_activation_event  不可变发布/回滚历史
config_active_pointer    唯一当前指针，pointer_version 做 CAS
```

伪代码：

```text
publish(targetVersion, observedPointerVersion):
    begin short transaction
    bundle = SELECT ... WHERE config_version = targetVersion
    assert digestValid(bundle)
    assert qualityGatePassed(bundle)

    updated = UPDATE config_active_pointer
              SET active_config_version = targetVersion,
                  pointer_version = pointer_version + 1
              WHERE singleton_key = true
                AND pointer_version = observedPointerVersion

    if updated != 1:
        rollback; return CONFLICT

    INSERT config_activation_event(... targetVersion ...)
    commit
```

这样回滚只是“新事件指向旧 bundle”，旧内容没有被修改，谁、何时、为什么回滚都可审计。

## 5. PostgreSQL 队列：采纳护栏，但不制造恐慌数字

### 5.1 “超过 100 QPS 就会耗尽连接池”没有通用依据

连接是否耗尽取决于事务时长、索引、批量大小、连接池、轮询频率和外调是否占连接，不存在一个跨系统通用的 100 QPS 分界。PostgreSQL 官方明确说明 `SKIP LOCKED` 可用于多个消费者访问 queue-like table；同一文档也说明它只跳过行锁，仍会获得普通表级锁。

### 5.2 真正要防的四件事

1. claim 查询全表扫描；
2. 抢到任务后带着事务去调 LLM；
3. Worker 占光连接导致入口不能持久化；
4. SQL/锁等待没有上限。

所以 v1.2 增加入口 4 + Worker 8 两个隔离池、1/2 秒连接获取上限、2 秒 statement timeout、250ms lock timeout、5 秒 idle-in-transaction timeout、claim batch≤10 和部分索引。数值是**初始配置**，不是行业真理，AM4 必须用 EXPLAIN 与压力测试校准。

### 5.3 为什么入口应该返回 503

在尚未提交 Atomic Intake 前，没有任何持久事实证明告警已受理。返回 202 或 200 会让 Alertmanager 误以为已交付，造成静默丢告警；返回 503 才能让上游按其重试语义重新投递。

## 6. 为什么不新增 60 秒“结论缓存”

外部建议的 Key 包含 Pod 名：

```text
tenant + alert_name + pod_name + metric_name
```

如果 1000 个 Pod 同时告警，恰好生成 1000 个 Key，根本不能压成 1 个；如果拿掉 Pod，又可能把不同故障实例错误合并。TTL 到期时还可能同时重新触发一批 LLM。

现有模型已经更完整：

```text
Alertmanager group       上游按告警语义聚合
alert fingerprint        单 alert 幂等
incident_key             因果域归并，禁止包含接收时间戳
incident generation      区分同一 Incident 的不同 episode
snapshot/config digest   决定是否可复用调查结果
```

因此不建第二套缓存一致性。只有同一 generation、同一 EvidenceSnapshot、同一 ConfigBundle 才能复用同一 Run；其他 alert 只是 Incident member，不自动继承一个可能过期的最终根因。

## 7. F1：为什么 Weighted-F1 不能按样本量自动接管

scikit-learn 官方定义：

- macro：逐类 F1 的不加权平均；
- weighted：按每类 support 加权；
- micro：全局累计 TP/FP/FN。

官方没有“小于 30 不算、30～100 必须 weighted”的规则。Weighted-F1 的“稳定”来自多数类权重大，这对 RCA 反而可能危险：100 个 CPU 类全对、2 个跨租户/支付状态错误全错，weighted 仍可能很好看。

本项目的口径是：

```text
始终：逐类 TP/FP/FN/support + UNRESOLVED + coverage
AM3 5×2：只作为冒烟，不做自动发布
扩大后：per-class + macro 主看少数故障类
辅助：micro/weighted 看总体流量表现
发布：关键类最小 support + 配对差异/置信区间
```

这不是拒绝 F1，而是拒绝让一个汇总数字掩盖样本结构。

## 8. Prompt Injection：入口必须防，但入口模型不是安全边界

OWASP AISVS 1.0 C2.1 的控制清单确实包含：tokenization/embedding 前归一化、编码/表示 smuggling 防护、非信任输入筛查、超长拒绝、指令层级等要求。因此这部分反馈成立，v1.2 已补齐阶段：

```text
Input Rail
  → Retrieval Rail
  → Execution Rail
  → Output Rail
  → Audit
```

通俗解释：入口保安可以识别明显危险物，但不能保证每一种新型伪装都识别出来。真正的保险柜是：Agent 没有密钥；工具是白名单；参数受 Schema 和 scope 限制；写动作由独立身份执行；报告必须有 Evidence/Receipt。

因此：

- `attack_success_count == 0` 是每一版必须达成的测试结果；
- 不能写成“系统 100% 不会被 Prompt Injection 攻破”；
- 还要单独看 false refusal，防止安全层把正常告警也全部拒绝。

## 9. OTel：反馈中的“没有工具语义”已经过时

截至本文日期，OpenTelemetry GenAI registry 已列出：

- `gen_ai.operation.name=execute_tool`；
- `gen_ai.tool.call.id`；
- `gen_ai.tool.name/type`；
- tool call arguments/result 等属性。

但它们仍属于 Development，且官方明确警告 messages、arguments、result 可能含敏感信息。

因此正确结论是：

> 可以映射 OTel 的 execute_tool 语义，但不能让数据库审计契约跟着实验性字段漂移，更不能默认把日志正文、参数和工具结果塞进 span。

内部 `rca_tool_call` 永远保存版本化状态、digest、CAS ref 和 policy verdict；OTel 只是观测投影。

## 10. Token：为什么“token_counter 精确”仍需分来源

提供商返回的 `usage`、本地 tokenizer、提供商 CountTokens API、Holmes 角色拆分、最终账单解决的是不同问题：

| 来源 | 用途 | 局限 |
|---|---|---|
| preflight tokenizer/count API | 发送前预算围栏 | provider 不支持时可能 fallback；工具/图片/缓存口径可能不同 |
| provider response usage | 调用后总量 | 字段可能缺失，细分类别因 provider 而异 |
| Holmes `metadata.tokens` | system/user/tool 等角色分析 | 属引擎计算，不等于 provider 账单 |
| 价格表/账单 | 成本对账 | 可能滞后，单位/版本必须固定 |

LiteLLM 官方生态也存在 provider counter fallback 和 provider usage 细分字段稀疏的情况，所以不能用一个 `exact_tokens` 字段覆盖全部历史。v1.2 改成四类字段并保存 `usage_source/tokenizer_version/pricing_version`。

## 11. RCA-Bench、RCAEval、AIOpsLab：都用，但用法不同

### 11.1 RCA-100 / RCA-Bench

阿里云 STAROps 文档披露的 RCA-100 当前有 103 个用例、28 个故障类型，并提供 cause/propagation/impact 结构和图距离评分思路。它是真实可参考的 Agentic Ops 评测资产。

但其样本与实体模型明显偏云原生/ACK/Kubernetes，不能替代订单域的幂等、状态回跳、对账差异等 ground truth。采用方式是做 dataset adapter，验证 Native/Holmes 在外部集上的可迁移性。

### 11.2 RCAEval

RCAEval 提供 735 个 failure cases，覆盖 Online Boutique、Sock Shop、Train Ticket，并包含 metrics/logs/traces 与注入时间。它适合静态算法/回放对照。

它的全量压缩包和解压后数据对 2C4G 不友好，正式方案只下载选定 suite/case 的 Parquet 小子集；不把外部数据全量常驻评测机。

### 11.3 AIOpsLab

AIOpsLab 的 `Application + Task + Fault + Workload + Evaluator` 很适合定义动态 Case，也记录 Session trace。但官方安装和运行依赖 Helm/Kubernetes/kind。本项目明确不使用 K8s，所以只采用 Problem 组合方法，不部署其环境编排器。

## 12. Holmes：元数据值得用，审批不能外包

Holmes 官方 HTTP API 已证实：

- 非流式响应含 `tool_calls`；
- SSE `start_tool_calling` 有 tool name/id；
- `tool_calling_result` 有 call id、name、params、data/error/status；
- token metadata 区分 provider `usage` 与 Holmes 的角色拆分；
- `enable_tool_approval=true` 可暂停并等待 tool_decisions。

这支持扩展 Java Adapter。但要纠正两点：

1. 当前官方文档列出的结果状态是 `success/error/approval_required`，反馈声称可直接映射 `NO_DATA` 等枚举缺少当前 HTTP 契约证据；内部必须容忍未知状态。
2. `enable_tool_approval` 是 Holmes 内部工具安全机制。我们的生产审批还要绑定 tenant、generation、policy revision、action digest、单次消费和 Tool Receipt，不能由 Holmes 会话状态替代。

此外，Holmes SSE 暴露 `ai_message.reasoning` 不代表我们应该保存它。v1.2 已冻结“不保存 Thought”，只保存可验证的 ToolCall/Evidence/Claim。

## 13. Replay：为什么宁可 MISS，也不能“差不多匹配”

候选 Agent 可能把 Prometheus 时间窗从 5 分钟改成 30 分钟，也可能换 tenant/scope。若回放器只按 tool name 找历史结果，就会把从未真正查询过的数据冒充为候选 Agent 的 Observation，评测结果失真。

```text
exact key = tool + version + canonical args + scope
          + incident time range + snapshot digest
```

找不到就返回 `REPLAY_MISS`。这会降低 replay coverage，但它诚实地暴露“候选策略产生了新查询”，比给一份错误 Mock 更有价值。候选新行为应进入后续 Live E2E，而不是在静态回放里被伪造验证。

## 14. 开源评测和安全组件的最终组合

### 14.1 直接采用

#### Inspect AI：2C4G 的评测执行器

采用原因：它已经有 Dataset/Solver/Scorer、限制、可恢复日志、重评分和 Docker Compose sandbox。我们的 Solver 只需调用已有 HTTP API：

```text
submit alert → poll run → fetch report/events/tool calls → score
```

不采用它作为生产工作流或生产审批。Inspect 官方明确：bridged agent 的 approval 只说明“允许传给 Agent”，不等于工具执行；自动 approval 还可能不显示。因此生产必须保留自己的 Receipt。

#### Promptfoo：离线红队生成

采用 `Plugin × Strategy`，覆盖间接注入、跨租户、越权工具、Secret 泄露，再用 base64、Unicode、嵌套 JSON、多轮等变换扩充。它只攻击测试入口，不接管生产 Guard。

#### Gatus：独立黑盒探针

Gatus 是轻量 Go 服务，可用 Docker 运行，支持 HTTP/TCP/DNS 检查和 PagerDuty/Slack/Twilio 等独立通知。放在 2C4G，探测 195 并直接通知值班，恰好补足“主监控或 control-app 挂了就无法自救”的缺口。

### 14.2 借结构，不直接部署

- AgentDojo：借 Utility/Security 分开评分；其 workspace 等任务不是 RCA 真题。
- NeMo Guardrails：借 Input/Retrieval/Execution/Output Rail 位置；LLM rail 不是授权系统。
- AIOpsLab：借动态 Problem 生命周期；拒绝其 K8s/Helm runtime。
- Presidio：借 Recognizer Registry/Analyzer/Anonymizer 契约；先按需批量验证中文与 Secret，不做唯一门禁。

### 14.3 条件采用

- OPA：只有 AM5 决定启用 Action Runner/R2/R3 才加入。OPA 负责 default-deny policy decision、Bundle revision 和 Decision Log；审批、单次授权消费和执行回执仍由控制面负责。OPA 宕机时写操作 fail-closed。

### 14.4 明确拒绝

- gVisor/Kubernetes：与“不要 K8s”的项目边界直接冲突，且会带入新的节点、网络和镜像运维面。
- OpenInference 双栈：OTel 已是现有标准，再加一套语义只会造成重复 span 和字段映射。
- NeMo/Presidio/OPA 全部立即常驻：2C4G 是隔离评测机，不是无限资源平台；组件必须按阶段和真实需求进入。

## 15. 自监控：为什么黑名单方案不够

原建议是入口判断：

```text
source == RCA_SYSTEM_INFRA
or alert_name contains Harness/Agent-
```

这只能做二次保险，不能做主防线：

- source/alert_name 来自载荷，可能被误配或伪造；
- 服务改名后规则失效；
- control-app 已经挂掉时，入口过滤器根本执行不了；
- “静默审计”意味着真正故障可能没人收到。

正式设计：

1. Prometheus 规则写入受控 `monitoring_scope=rca_control_plane`；
2. Alertmanager routing tree 优先匹配该 scope，`continue:false`，直接发独立值班 receiver；
3. 业务告警才进入 RCA webhook；
4. 入口对受信 route/身份再做一次拒绝递归检查；
5. 2C4G Gatus 独立探测 195，并周期发 canary 验证端到端链路，失败直接通知值班，不经过 RCA。

Prometheus 官方的 meta-monitoring 建议同样强调：不仅要监控 Prometheus/Alertmanager，还应使用外部黑盒端到端测试，以覆盖内部监控完全失效时的盲区。
