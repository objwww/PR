## 结论与范围

当前系统已经有告警调查的执行骨架：主Agent循环、工具取证、按需委派、检查点恢复、模型输入捕获、报告发布和通知outbox。不能再称其“没有Agent”或沿用9月11日“没有ContextAssembler/Skill服务”的判断。

但目前不能认定整个Agent达到生产级闭环。代码中仍有影响取证质量、版本一致性与故障恢复的缺口；LLM压缩和Skill自进化也没有形成完整消费/自动触发闭环。执行流程能结束、报告能生成，与根因判断可靠是两项验收。

审查基线：HEAD `cddc86f582b7cf60576430ac1d6a5cd4aa8f9da0`，`BoundedLlmRoleRunner.java`已有未提交修改（本轮未改），结论针对本地工作区，不代表195的实际镜像。未读取用户禁止的三份文档。没有部署、注入故障或访问生产凭据。本次属于重点调用链审查，不是全仓每行安全审计。

验证：实际执行7个测试类82例，0失败、0错误、0跳过。日志见[定向测试记录](agent-audit-20260913-targeted-tests.log)。测试类为ContextAssemblerTest 17、ContextCompactionServiceTest 15、R7RoleRunnerTest 17、RunConfigSwitchServiceTest 18、R7PrimaryModeExecutorTest 8、SkillCuratorServiceTest 4、SkillSelectionServiceTest 3。本轮没有跑真实PG竞争、真实模型、浏览器或195端到端，因此下面并发时序不冒充已复现事故。

## 一、优先处理的发现

### A13-01 / P1：日志入库了，但关键日志正文在通用摘要中被丢弃

代码链：`infrastructure/tool/LogQueryExecutor.java:34`规定响应为`status + data.result[{ts,service,line}]`；`alert/application/agent/SingleToolEvidenceAgent.java:217–236`将该payload保存为证据；`PrimaryGatewayToolPort.java:invoke`向主Runner返回证据ID；`ContextAssembler.java:590–636`只拼顶层标量，遇到嵌套对象/数组只输出省略计数。

因此对于该标准日志响应，摘要只会表达类似`status=success; (+1 struct fields)`，不包含`data.result`中的错误行。标记truncated诚实，但不能代替实际观察。主Agent这条直查路径不能靠一个合法UUID理解错误原因。Prometheus等相同嵌套响应也应一起检查，不能只修日志Prompt。

修改建议：按已注册evidenceType提供最小确定性投影，日志抽取时间、服务、错误摘要和代表行，指标抽取标签、数值和时间；保留总行数、频次、截断和来源。对有用但超长部分提供受控回读。未知形状有界降级，不静默空串。原文为数组/标量时当前appendTopLevel也会直接返回false形成空摘要，应覆盖。

验收：使用真实LogQueryExecutor响应形状，错误码只放在嵌套line；捕获下一次完整模型请求，必须含错误码或可用回读信息。不能继续仅用顶层`{"line":"错误"}`假件证明MC01通过。再做真实模型定位对照。

### A13-02 / P1：Skill的Run版本固定仅是进程内缓存

`release/application/SkillSelectionService.java:27–30,57–99`用512项LinkedHashMap保存Run→SkillView；selectFresh从当前ACTIVE候选重选。重启会清空，超过容量会淘汰；构造参数accessOrder=false，实际还是插入顺序淘汰而非注释所称LRU。

触发：Run R选择v1→发布v2→worker重启或R被淘汰→R再次组装上下文。同一Run可重新选版本，或从原先none变为有Skill，没有显式安全切换事件。select方法“检查缓存/查询/写缓存”也分两次同步，并发首次选择遇到发布可各自返回不同视图。

修改建议：复用Run/configEpoch持久化身份，在准入或首次选择时原子记录skill digest（包括明确NONE）。读取该绑定，进程缓存只加速；新选择限定在冻结release允许集内。热切沿现有命令和安全点协议，不以重新装配代替切换。紧急撤权另走即时资格检查。

验收：v1选择后发布v2并重启，R仍v1；512以上Run后R仍不漂移；首次选择与发布竞争只有一个持久绑定；旧Run绑定NONE也不随重启改变。

### A13-03 / P1：检查点写入缺少数据库提交围栏

`infrastructure/persistence/PostgresPrimaryCheckpointRepository.java:38–78`的ON CONFLICT无条件覆盖phase、decision_seq、steps、memory、final；`BoundedLlmRoleRunner.java:173,274,299,357`等直接调用upsert。`NativeInvestigationExecutor.java:630–682`在runner返回后按state推进DONE/DEAD。`RcaActionGuard.java:64`起的租约检查在模型调用前进行，不能自动保护模型返回后的检查点写入。

危险时序：旧worker已过准入并等待外部结果→失租→新worker接管推进→旧worker恢复并写旧检查点。无条件写入本身是已确认的代码缺口；完整双worker竞争事故本轮未执行复现。外围已有心跳、回收和最终报告generation保护，不能据此断言全部恢复都坏了；同样也不能用外围保护证明此写入原子安全。

修改建议：检查点提交接口携带expected owner/leaseEpoch/revision，数据库事务内锁定/校验任务资格并条件更新检查点；提交失败必须中止本次驱动，不再进入FINAL/DONE。读后Java判断仍有TOCTOU窗口。对任务收尾采用同一围栏契约。

验收：真实PG双worker屏障，A停在返回后提交前，B接管提交，释放A；A更新影响行数0，B记忆和FINAL不变。覆盖step、delegate、final、lastError四个写点，扩现有恢复测试。

### A13-04 / P2，启用摘要消费前升级为阻断：工作记忆没有跨轮累计语义

`ContextAssembler.java:353–391`每次从检查点与当前回执重建，再append新记忆；`receiptsOf:399–410`只查当前round。counter_evidence_refs/open_gaps由当前轮重建，未合并上一记忆。hypotheses来自finalClaims，ruled_out却来自委派REJECTED裁决。

两个不同问题：上一轮反证可能仍在原始库中，却从下一轮记忆槽消失；“因预算/重复gap被拒绝委派”也不等于“该根因假设已被证据排除”。当前命名会让模型误读控制决策。

修改建议：控制拒绝放delegation_rejections；业务假设必须带支持/反证和状态。按上一已提交记忆+本轮新证据做有界更新，明确何时关闭gap。持久化只是保存，不会自动获得累计推理能力。

验收：round0得到反证，round1没有新反证且原文超过20条展示窗，旧反证仍可达；预算拒绝不进入业务ruled_out。保留真实来源，不让摘要变成新证据。

## 二、尚未形成完整闭环的能力

### A13-05：LLM压缩目前属于候选生成实验

`ContextCompactionService.java:44–47`明确“只生成不消费”；`BoundedLlmRoleRunner.java:159–164`先maybeCompact，随后仍发送原assembly.prompt。默认关闭是合理的，不能宣传为已减少后续模型上下文；enabled=true在当前路径只增加调用成本。

启用消费前还需修：requiredRefs只取binding.inputRefs与finalClaims，遗漏工作记忆反证；提交复验只比较decisionSeq/source（约240行），没有把owner/epoch及写入做成原子条件提交；次数与ordinal取自成功摘要行数，失败候选不计次数，不能代表最大物理压缩尝试数。其余Run预算仍可能限制总成本，但“maxPerRun”不能解释为全部尝试上限。

保持默认关闭；若近期调查轨迹很短，可以先不引入LLM摘要消费。确有长轨迹收益后再接摘要+未覆盖增量的输入组装、原子提交、全尝试计数和三组质量/成本对照。不要只证明表里有摘要行。

### A13-06：Skill服务存在，但自动提炼入口和LLM经验归纳未闭合

本次搜索生产Java代码中`curate(`与`Curation(`只找到`SkillCuratorService`自身定义；PersistenceConfig有Bean注册，未发现完成事件、作业或Controller调用它。此结论范围是当前生产Java源码，不能排除未检查的外部手动操作。

该服务79行后的实现按SUCCEEDED、证据等校验后，用证据类型集合和固定文案组成body，再调用candidate.propose；这属于确定性模板提炼，不是LLM总结排查思路。声明humanReviewed由调用方提供，未来暴露入口时必须绑定认证身份和可审计复核记录，不能直接信任请求boolean。

建议：先确定产品口径是“人工发起生成候选”还是“调查完成后异步建议”；以run+来源digest幂等触发，候选记录实际步骤、参数范围、失败经验和反例。要LLM归纳就复用受控模型网关并独立计费。候选隔离评测、人工发布保持，不给调查Agent自行发布权限。无需为了演示自进化增加一个常驻Agent。

## 三、完整链判断

| 环节 | 当前判断 | 不能据此宣称什么 |
|---|---|---|
| 主Agent直接调查、按需委派 | 实现存在，相关定向测试通过 | 不等于复杂告警的角色选择质量已验证 |
| 工具执行→证据→下一次推理 | 路径存在，但嵌套摘要有明确内容丢失 | 不能用“工具SUCCESS”代替模型看懂证据 |
| 重启恢复与预算/权限 | 已有机制和测试；提交围栏仍需补验证/实现 | 单次硬杀PASS不能覆盖失租后迟到写 |
| 工作记忆 | 有持久化，跨轮业务语义存在缺口 | 落库不是长期记忆正确性的证明 |
| 报告与通知 | RcaRunOrchestrator发布赢家分支调用ReportCompletedNotifier并生成outbox；通知明确候选标记 | 本轮未验证通知实际投递；SUCCEEDED不代表故障恢复或根因已语义验证 |
| Prompt/运行配置热更新 | 已有安全点服务，18例相关定向测试通过 | 不能覆盖仅内存保存的Skill选择与未消费摘要 |
| 上下文LLM压缩 | 候选生成已实现，消费未闭合 | 不能称实际降token/成本 |
| Skill自进化 | 候选、选择服务存在，模板提炼无生产调用点证据 | 不能称自动学习→评测→上线→收益回归已闭合 |

调查闭环的合理终点可以是“有证据的候选根因或诚实未决，通知送达并可人工跟进”，不必自动修改生产环境。业务处置闭环还要记录认领、处置、恢复和复盘；本轮没有验证该全链。自进化闭环另需候选来源、独立评测、发布、回滚和效果反馈，不能与调查终态混为一谈。

## 四、业界依据与取舍

[Anthropic上下文工程](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)将上下文选材、压缩和结构化记忆用于长任务管理。本项目应先保证有信息价值的证据进入模型，再做压缩；这是结合本地嵌套响应缺陷的工程判断，不是要求照搬其框架。

[LangGraph持久化文档](https://docs.langchain.com/oss/python/langgraph/persistence)区分检查点与已完成任务写入的恢复。本项目已有Postgres机制，可以继续使用，重点是补提交一致性与可重复恢复，无须迁移框架才能完成。

[Anthropic工具设计实践](https://www.anthropic.com/engineering/writing-tools-for-agents)强调返回信息对Agent是否有用及迭代评测。针对本系统，真实工具响应→完整模型输入捕获→真实模型判断的测试，比增加Agent数量更优先。

## 五、执行优先级与发布判断

先修A13-01证据投影、A13-02 Skill持久绑定和A13-03检查点围栏；再补A13-04跨轮记忆语义。摘要保持关闭，Skill明确标注当前是候选能力。每项复用既有MC/RG测试矩阵，不重建框架、不额外引入MQ。

上线依据应是当前精确构建的：嵌套证据入模通过、真实PG迟到提交拒绝、Skill重启不漂移、一次隔离环境告警→有引用报告/未决→测试通知→resolved全链证据。若要宣传自进化，另给候选→盲评→授权发布→新Run消费→回滚的独立证据。

本轮结论：**具备可继续完善的Agent调查系统，尚不能签署“生产级完整闭环”验收。** 主要欠缺不是Agent数量，而是证据消费、运行身份稳定、迟到写保护和能力端到端接线。82例绿证明现有测试断言通过，不反证上述未覆盖问题。
