### 写请求三件套（缺任一是 403）

1. **CSRF 引导**（operator 写面保留 CSRF，bearer 不豁免）：
   ```sh
   CJ=/tmp/t-cookies.txt; rm -f $CJ
   curl -s -o /dev/null -c $CJ http://127.0.0.1:8080/api/auth/csrf
   XSRF=$(awk '$6=="XSRF-TOKEN"{print $7}' $CJ)
   # 之后每个 POST 都带：-b $CJ -H "X-XSRF-TOKEN: $XSRF"
   ```
2. bearer 头：`Authorization: Bearer $BEARER`。
3. **stop 的 body 是 `{"idempotencyKey": "..."}`**——不是 stopKey（冒烟踩过，400 报错信息会写「idempotencyKey 必填」）。

### ssh 操作纪律（已踩过的坑）

- 嵌套引号/heredoc 经 ssh 必炸——一律本地写脚本 → scp → 远端执行。
- 远端脚本里 `curl` 连接拒绝（exit 7）与 `grep -c` 零命中（exit 1）会让 `set -e` 静默中止——健康轮询一律 `|| true`。
- SQL：本地写 .sql → scp → `docker cp` 进 deploy-postgres-1 → `docker exec ... psql -f`。
- `/opt/build/pr/deploy/.env` 是真实文件（47 行、600），**严禁 ln -sfn / rm -rf 同步**。
- stderr 的 openssh 警告噪音用 `grep -vE "post-quantum|may be unable|decrypt later|openssh.com"` 过滤。

## 四、故障注入与复原 / 已知边界（如实登记，测试时不得当成新缺陷）

1. **停止语义（设计，非缺陷）**：stop 受理只置 stop 两列+STOP_REQUESTED 事件（「受理≠恢复完成」）。
   OBSERVING 相位的 stop 不即时生效——作业保持占位直到 `claimed_at + totalEstimateSeconds`
   （S1 模板 = 60+600+1500+2100+120=4380s ≈ 73 分钟）由截止扫描器推进 RECOVERING→RECOVERY_FAILED；
   flagd 旗标由 FlagdRestoreSweeper 在台账 `deadline_at` 后恢复。**测 T12/T14 时不要误判为"停止没生效"**。
2. **RECOVERY_FAILED 占位处置（T12 核心）**：占位会阻塞同靶场下一场（409 ENV_OCCUPANCY，DU15 设计）。
   人工核验关单路径：先确认 flagd 旗标已回 baseline（GET /flags/paymentFailure 应为 off）、
   台账行已收口，再按 DrillController 的终态处置面关单（若 409/无端点则如实登记缺口）。
3. **DR-06 关联回填的既有边界**（冒烟实测命中，设计文档已声明「不猜不凑」）：
   - 关联判据 = `incident.first_seen_at ∈ [OBSERVING 进入时刻, +max_firing_wait_seconds]`；
   - **同 incident_key 复燃不换行**（first_seen_at 停留在 09-04）→ 本场 drill 的关联恒 null；
   - 复验 T10 尾段需要**干净前提**：换一个从未产生过 incident 的症状身份，或先人工结清既有
     checkout incident（49ea2bf5）再跑一场新 drill（需等占位释放或换 S2/换靶场）。
4. **路由姿态**：当前活跃配置包 canary.percent=0 → 一切 incident 路由 BUCKETED_HOLMES →
   fail-closed WAITING_CAPABILITY、**不铸任何 RCA run**（HOLMES 已物理退场）。
   若 T10 尾段要验到 related_run_id，需用户裁定放行姿态（白名单该 incident 或 percent>0）——
   **执行者无权自行改绑**，先向用户请示。
5. **本批已修复的三个环境雷**（验证已修复即可，勿重复立案）：
   - flagd-admin-am3 镜像陈旧（09-06 构建，无 GET /flags/{flag} 读面）→ 已重建（server.py 142 行）；
   - alertmanager-am0 的 `/etc/alertmanager/secrets/webhook-bearer` 宿主侧丢失致 webhook 断送
     3.2h（08:54→12:09 UTC）→ 已重建文件（65534:65534 / 400，与 control-app 侧哈希对拍 MATCH）；
   - `deploy/alert/.env` live 树缺失（litellm 等 3 键）→ 已从 09-07 备份树恢复（17 行，600）。
6. **已知瑕疵（惰性面，登记不阻塞）**：eval-runner-drill-e03 的 LITELLM_MASTER_KEY 实为 2 字符
   （从 compose yml 解析姿势不对）——drill 不调 litellm 不受影响；若 drill 触发的 RCA 走不通模型先想它。
   真值在已恢复的 `deploy/alert/.env`。
