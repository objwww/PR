# 架构冻结文档 v2.1 修订草案（评审用，未生效）

> **性质**：对 v2 冻结基线的局部修订提案，走 ADR 变更流程。
> **范围**：仅修补 Outbox 状态机的三处漏洞（DRIFTED 缺失、SUPERSEDED 级联未定义、supersede 执行路径与 AFT-06 冲突）。
> **不涉及**：revision fence TOCTOU 窗口、Artifact 只读挂载措辞等其余评审项（另行记录，不阻塞本草案）。
> **影响条目**：§5.2 状态表、B13、B14、ADR-005、ADR-006、AFT-06 措辞确认。

---

## 修订一：DRIFTED 纳入状态机（八态 → 九态）

### 问题

v2 §5.2 冻结了八态，但 `CONFIRMED` 行写明"对象后来消失→Reconciler 标 `DRIFTED`"——`DRIFTED` 是事实上的第九态，却未定义其语义、入口和出口，导致表 DDL 的 `CHECK` 约束与状态机代码无从冻结。

### 修订内容

§5.2 状态表追加一行：

| 状态 | 含义 | 允许的下一步 |
|---|---|---|
| `DRIFTED` | 已 `CONFIRMED` 的远端对象后来被删除或篡改，本地记录与远端事实漂移 | 终态。修复动作以**新的 Outbox 命令**表达，本命令不再迁移 |

配套规则（并入 B13）：

1. **入口唯一**：`DRIFTED` 只能从 `CONFIRMED` 进入，只能由 Drift Reconciler 标定。`IN_FLIGHT`/`RECONCILING` 中的"远端查不到"走原有的 `RETRY_WAIT`/`MANUAL` 路径，**不是**漂移。
2. **历史不可变**：命令进入 `DRIFTED` 后不再迁移。需要修复时（如 Check 被人工删除后按策略重建），由 Drift Reconciler **签发新命令**（新 `operation_id`，`depends_on` 为空，`revision_id` 按当前世代重新计算），原命令保留漂移事实供审计。
3. **与告警策略的关系**：评论类资源默认只告警不自动补发（v2 §10 已定），此时 `DRIFTED` 即最终状态 + 一条告警事件；Check 类资源按策略可触发上述新命令。
4. `DRIFTED` 与 `SUPERSEDED` 的区分：`SUPERSEDED` = 从未产生外部副作用；`DRIFTED` = 副作用曾确认存在、后来消失。二者审计含义不同，不得合并。

**B13 措辞修订**："Outbox 使用 `PENDING/IN_FLIGHT/RECONCILING/RETRY_WAIT/CONFIRMED/SUPERSEDED/FAILED_TERMINAL/MANUAL` 状态" → 追加 "`DRIFTED`（仅自 `CONFIRMED` 进入的漂移终态）"。

## 修订二：SUPERSEDED 级联规则（新增，并入 B14）

### 问题

v2 §5.3 定义了 `depends_on` 因果依赖（"前置结果没终结时不能执行"），但未定义前置命令**被取消**时后继命令的命运。典型场景：revision 失效 → `PublishFinding-A`（PENDING）被标 `SUPERSEDED` → 依赖它的 `CompleteReviewCheck` 若无规则，会出现"Finding 一条未发、Check 却 completed"的孤儿结论。

### 修订内容

**级联规则**：

1. 命令 C 进入 `SUPERSEDED` 时，所有满足以下条件的命令级联标 `SUPERSEDED`：
   - `depends_on` 包含 C 的 `operation_id`；
   - 当前状态为 `PENDING` 或 `RETRY_WAIT`（即**尚未产生不确定外部结果**）。
2. 级联递归传播：被级联 supersede 的命令同样触发规则 1。
3. **孤儿防护优先**：处于 `IN_FLIGHT`/`RECONCILING` 的命令**不级联**，继续走对账路径（v2 §5.1 的边界不变）。
4. **`FAILED_TERMINAL` 不级联**：前置失败不取消后继。后继命令照常进入领取流程，由自身的 revision fence 与业务校验决定命运（例如 Check 以 `completed` + 警告结论收尾，符合"terminal ≠ 全成功"的既有语义）。
5. 级联在**同一事务**内完成：标 C 为 `SUPERSEDED` 与级联更新后继命令是原子的，避免"父已取消、子被领取"的竞态。

**B14 措辞修订**：追加"命令 `SUPERSEDED` 时，其未进入外部尝试的下游依赖在同一事务内级联 `SUPERSEDED`；`FAILED_TERMINAL` 不级联"。

## 修订三：supersede 执行路径收口到 Publisher（消解与 AFT-06 的张力）

### 问题

AFT-06 冻结"只有 Publisher 能 UPDATE outbox 状态"（DB 层：Control 角色可 INSERT、不可 UPDATE）。但 revision 失效由 **Control 侧 PR State Reconciler** 发现，v2 §5.2"revision 失效可→`SUPERSEDED`"读起来像 Control 直接改状态——两条冻结项在执行路径上冲突。

### 修订内容

明确唯一合法路径，职责拆分如下：

1. **Control 侧只记录事实，不动 Outbox**。PR State Reconciler 发现 revision 失效后：更新 `run_projection`（旧 Run 标 superseded）、追加 `execution_event`（`RevisionInvalidated`，含旧 `revision_id` 与新世代快照）。**不 UPDATE `outbox_command`**。
2. **Publisher 是唯一 supersede 执行者**，两个时机：
   - **领取时预检**：`FencedPublicationExecutor` 第 3 步（check revision）判定失效 → 同事务内将该命令标 `SUPERSEDED` 并执行修订二的级联，随后领取下一条。
   - **周期兜底扫描**：Publisher 定时对 `PENDING`/`RETRY_WAIT` 命令按 `aggregate_key` 批量做 fence 预检，覆盖"该 PR 再无新命令、无人触发领取时预检"的场景，防止失效命令长期滞留。
3. **fence 判定依据**：Publisher 以账本分区内当前活跃 `revision_id`（来自 projection 的只读副本或 Control 的只读视图）为准；不因此引入 Control → Publisher 的新调用（保持"写协作只经 Outbox"不变）。
4. `RETRY_WAIT → PENDING` 的到期迁移前同样先过 fence：已失效则直接 `SUPERSEDED`，不再回到待领取队列。

**AFT-06 不变**：Control 角色依旧只有 INSERT 权限；本修订只是把"谁来标 supersede"从含糊收口到 Publisher，DB 权限测试无需放宽。

**§5.2 `PENDING` 行措辞修订**："revision 失效可→`SUPERSEDED`" → "Publisher 领取预检/兜底扫描判定 revision 失效→`SUPERSEDED`（Control 从不直接 UPDATE）"。

## 迁移成本

- 表 DDL：`outbox_command.status` 的 `CHECK` 约束加 `DRIFTED`（M0 尚未建表，零迁移成本——**这是现在修的最佳时机**）。
- 代码：Publisher 领取路径增加 fence 预检 + 级联更新（同事务），均为 M0 范围内的新增逻辑，无返工。
