## 审查甲

### 一、技术方案本身的阻塞问题

#### P0-1：两个 G1 决策尚未裁定

同机 Docker 只是容器隔离，不能继续宣称满足冻结的"不可信执行物理边界"。冻结基线明确要求
不可信代码位于独立 2c4g 执行域。[冻结文档 §4 部署拓扑]

建议裁定：

- 同机形态仅作为开发/演示过渡；
- DoD 中不得写"F1-C 物理边界已兑现"，只能写"容器级降级边界已验证"；
- 第二台机器到位后，双机+mTLS 才关闭 F1-C；
- 只读工具可留 Control，但必须限制为 SnapshotTree API、字面搜索、CPU/输出预算，
  禁止任意正则和本地文件系统访问。

#### P0-2：`sandbox_job` 与 `tool_call` 循环外键导致首条数据无法插入

当前设计：

- `sandbox_job.tool_call_id NOT NULL` 并引用 `tool_call`；
- SANDBOX 类型 `tool_call` 又要求 `sandbox_job_id NOT NULL` 并引用 `sandbox_job`。

两个 FK 都是即时约束，先插任何一方都会失败。文档所说"tool_call 先建、之后回填 job"又被
SANDBOX 必须有 job 的 CHECK 阻断。

建议只保留一个引用方向，或者使用明确的延迟约束；同时增加一对一和 lineage 一致性约束。

#### P0-3：`SKIP LOCKED` 不能保证全局并发 1

N 个 PENDING 任务、两个并发 claim：

- Broker A 锁第一个；
- Broker B 会跳过它并领取第二个。

因此 CT-64 要求"LEASED 始终 ≤1"在当前 SQL 模型下不可能成立。

需要数据库全局信号量，例如：

- 单行 admission/semaphore 表；
- advisory lock；
- 或对常量表达式建立 `WHERE state='LEASED'` 的部分唯一索引。

Broker 单线程只能作为第二道保险，不能作为全局事实源。

#### P0-4：租约配置自身矛盾，默认配置无法启动

方案要求 `lease > job timeout + 余量`，但默认值 `lease=120s`、`job timeout=600s`，按启动校验
会直接拒绝启动。而且有心跳续租时，租约不需要大于整个作业超时。正确关系应围绕心跳故障检测，
例如：`heartbeat interval × 安全倍数 < lease`；`job timeout` 独立控制作业总寿命。

#### P0-5：当前文件系统设计无法实际编译

冻结架构要求"只读源码 lower layer + 临时可写 overlay"，因为编译测试需要写 `target/`、
`build/` 和缓存。当前方案却同时设置 `/src` 只读、rootfs 只读、仅 `/tmp`、`/out` 为 tmpfs。
普通 `mvn test`、`gradle test` 无法在 `/src` 生成构建产物。

必须增加明确的可写 workspace 方案，例如：`/src` 保持只读；启动时复制到受限 tmpfs `/workspace`；
在 `/workspace` 执行；`/out` 只保存允许回传的报告。

#### P0-6：Broker 容器内路径不能直接作为兄弟容器宿主 bind 路径

Docker daemon 解析 bind source 时使用的是宿主机路径，不是 Broker 容器内部路径。方案说物化目录
可以位于 Broker 容器 tmpfs，然后直接 `new Bind(snapshotDir, /src)`——dockerd 无法看到 Broker
内部 tmpfs 路径。

必须冻结一种真实可行方案：Broker 专属宿主 bind 目录；或 Docker named volume；并明确 Job 只可见
某个 job/epoch 子目录。还需要验证符号链接、路径规范化及 TOCTOU。

#### P0-7：`/out` 结果没有取回通道

方案把 `/out` 设为 Job 私有 tmpfs，但生命周期只有 `wait → logs → remove`，没有 Docker
archive/copy API、共享只写输出卷、或其他 Broker 读取 `/out` 的方式。容器删除后测试报告和结果
文件将直接消失。必须补完整的结果提取路径，并在 remove 前完成 digest 和大小校验。

#### P0-8：Broker 崩溃后，Job 容器不会因"超时"自动死亡

`awaitCompletion(timeout)` 是 Broker 侧等待逻辑。Broker 进程死亡后：兄弟 Job 容器仍由 dockerd
运行；没有 Broker 执行 kill；容器内部也没有自杀 watchdog。文档所称"容器由超时兜底死亡"不成立。

需要：容器内部 PID 1 超时包装器；job/epoch/owner 标签；Broker 启动时先清扫过期容器，再允许
claim；Control 不得在旧容器清理事实不确定时立即重领。

#### P0-9：工具循环跨 attempt 重跑必撞唯一约束

`tool_call` 唯一键是 `UNIQUE(run_step_id, call_seq)`，但方案明确说工具循环不做 checkpoint，
崩溃后整个循环按新 attempt 重跑。新 attempt 再次产生 `call_seq=1` 就会撞旧行。并且表缺少
`attempt_id`，也不能兑现文档声称的 `run → attempt → step → tool_call`。

需要增加 `attempt_id` 或 `tool_loop_id`，唯一键至少包含 attempt 边界。

#### P0-10：CAS 文件写与 PG 事务不能"原子提交"

CAS 是本地文件系统，PostgreSQL 事务无法同时提交 CAS 文件。方案所称"原子写 Observation(CAS) +
tool_call 终态 + sandbox_job 终态"属于过度承诺。

应沿用 M2 诚实事务模型：

1. CAS 先 `putIfAbsent`；
2. PG 单事务登记 artifact 并推进 job/tool_call；
3. CAS 成功、PG 失败允许留下孤儿文件；
4. 禁止 PG 提交后引用不存在的 CAS 对象。

#### P0-11：`control_app` 拥有 `sandbox_job` 整行 UPDATE 权限

方案强调 image、command、资源限制在创建时定死，但授权矩阵给了 control 整行 UPDATE。这允许
运行期修改 image、command、snapshot digest、network policy、资源上限、lineage。

必须改为列级 UPDATE，并用 trigger 或约束禁止 JobSpec 身份字段在 INSERT 后变化。

#### P1 问题

还应修正：

- `image_ref` 没有 DDL CHECK，但 CT-53 声称浮动 tag 会被数据库拒绝。
- `command/input_digests/allowed_digests` 只是 JSONB，没有数组、元素类型和非空校验。
- schema 允许 `EGRESS_WHITELIST`，但 MVP 没有实现，可能出现"数据库允许、执行器不支持"。
- 心跳 HTTP 暂时失败与服务端明确返回"租约已丢失"没有区分；前者不应立即 kill。
- claim 响应没有 `lease_until/server_now`，Control 不可达时 Broker 无法安全判断本地自杀时间。
- grant 的 Range、并发消费、字节预留和中断请求如何计费没有定义。
- 非零测试退出是业务 observation；digest 损坏、grant 越权、隔离失效则是安全/基础设施故障，
  不能全部喂给模型继续决策。
- Docker 日志可能无限灌满内存或宿主磁盘，必须流式限额，不应先完整读取再截断。
- 安全剖面还需明确 `Privileged=false`、零 devices、零 host PID/IPC/UTS、零端口、
  零 docker.sock、日志驱动大小限制。
- 原始 fork bomb 脚本不应出现在可误执行的测试脚本中，应用受控小程序验证 PidsLimit。
- `env | sort` 会在密钥错误注入时主动把密钥打印进日志；探测只能输出变量名/哈希比较结果，
  不能输出值。
- M4 同时做 Sandbox 基础设施和 ReviewAgentLoop 多轮化，风险面过大；建议拆为 M4-A 执行面、
  M4-B 工具循环接线两个门。

### 二、现有测试中必须先修的用例

- CT-64 在当前实现模型下不可能通过，必须先增加 DB 全局并发闸。
- EX-60 使用"FAILED 或保持 LEASED"二选一，违反文档自己的确定性断言纪律。
- EX-71 使用"heartbeat 恢复或租约回收"，同样是不确定断言，应拆成两个场景。
- E2E-79 要求 Broker 崩溃后容器自动清扫，但当前没有自杀 watchdog/清扫握手协议。
- E2E-73 不能打印完整 env，否则测试本身可能成为泄密通道。
- E2E-76 不能把裸 fork bomb 作为可复制命令，必须使用仅在确认 cgroup/容器身份后执行的受控探针。

## 审查乙

**结论：v1.0 建议退回修订，暂不通过 G1，编码门保持关闭。**

整体方向可行：Broker 独立进程、Job 零凭证、grant 传输、租约 fencing、工具账本、network none
都符合目标。但当前存在若干"实现后必然跑不通"或"测试无法证明承诺"的阻断问题。至少完成下面
P0 项并形成 v1.1 后，才适合重新送 G1。

### 一、两个 G1 决策点建议

#### 决策点一：部署形态

建议裁定为：**同机形态仅作为 M4a 降级验证模式，不得宣称完成生产级 F1-C；真实不可信 PR 的
执行门仍要求专用 Sandbox 主机 + mTLS。**

原因：Job 和 control 共享宿主内核，容器逃逸后就是可信域失守；Broker 挂载 docker.sock 实际上
拥有接近宿主 root 的控制能力（Docker 官方明确把 daemon/socket 访问视为 root 级安全面）；
195 只有 7.5GB 内存，当前 Job 默认 2.5GB，再加 PG、control、publisher、Broker、Docker page
cache，资源预算尚未证明成立。

| 模式 | 可执行内容 | 能否声称 F1-C 完成 |
|---|---|---|
| M4a 同机降级模式 | 合成仓库、内部可信测试仓库、故障注入 | 否 |
| M4b 双机正式模式 | 任意外部 PR、不可信 fork PR | 是，且需 mTLS |

如果用户坚持同机直接执行公开不可信 PR，应记录为风险接受，而不是把它写成"已经实现物理边界"。

#### 决策点二：只读工具落点

建议选择：**list/search/read 留在 control 的 SnapshotTree；build/test/command 必须进入
Sandbox。** 但要补四条硬边界：

1. 只允许字节级 list/read/search，不启用语言服务器、编译器、模板引擎、宏展开或仓库自带解析器。
2. 不跟随 symlink/hardlink。
3. 路径先做 Unicode 规范化，再拒绝绝对路径、反斜杠、NUL、`..` 和编码后的 traversal。
4. 文件内容始终按不可信文本处理，不能参与 SQL、shell、镜像名、命令模板拼装。

并同步修改冻结文档，否则方案通过后仍存在"实现与冻结要求不一致"的审计争议。

### 二、P0 阻断问题

#### P0-1：默认租约配置自相矛盾

当前默认 lease 120 秒、job timeout 600 秒、启动校验 `lease > job timeout + 余量`——默认配置
必然拒绝启动。且该不等式本身不合理：租约通过 heartbeat 持续续期，没必要长于整个 Job。

建议改为：`heartbeat_interval <= lease_seconds / 3`；
`heartbeat_timeout + retry_jitter + kill_margin < lease_seconds`；
`job_timeout_seconds` 独立于 `lease_seconds`。

心跳失败也不能一律立即杀容器，应区分：

- HTTP 409/410、epoch 不匹配：确认租约失效，立即 kill。
- 单次网络超时/5xx：重试，但必须在本地估算的租约安全截止时间前 kill。
- 连续失败直至 `lease_until - safety_margin`：kill 并停止上报。

#### P0-2：I47"全局并发 1"没有被数据库保证

SKIP LOCKED 只能避免两个 Broker 领取同一行，不能阻止它们分别领取两个 PENDING Job。CT-64 按
当前 SQL 不成立。

建议新增唯一容量槽：

```sql
CREATE TABLE sandbox_capacity_slot (
    slot_no       int PRIMARY KEY CHECK (slot_no = 1),
    job_id        uuid UNIQUE REFERENCES sandbox_job(id),
    lease_epoch   bigint,
    lease_until   timestamptz
);
```

claim 时在同一短事务中：SELECT slot FOR UPDATE SKIP LOCKED → 领取一个 PENDING Job → 更新
LEASED → slot 绑定该 Job → 提交。终态、取消、租约回收时释放 slot。仅靠"Broker 进程里只有一个
Poller"不能作为数据库不变量。

#### P0-3：Broker 容器内路径不能直接作为 Job 的宿主 bind 路径

Docker bind mount 的源路径由 Docker daemon 所在宿主机解释，而不是由发起调用的 Broker 容器解释。
建议采用明确的双路径配置：Broker 容器路径 `/sandbox-staging` ↔ 宿主真实路径
`/var/lib/pr-sandbox/staging`；Broker 写 `/sandbox-staging/{jobId}/{epoch}/snapshot`，传给
dockerd 的是宿主路径。并增加：规范化后必须仍位于固定根目录；禁止 Job ID、epoch 参与未经校验的
字符串拼接；staging 根目录必须是 Broker 唯一额外宿主挂载；不得把 Broker 容器的普通 overlay
路径传给 dockerd。

#### P0-4：只读 `/src` 无法直接执行 Maven/Gradle 测试

`mvn test`、Gradle、npm 需要写 `target/`、`build/`、`.gradle/`、`.m2/`、临时编译文件。建议改
为固定可信 wrapper：`/src` 只读源快照、`/work` 有容量上限的 tmpfs 或专用临时卷、`/out` 有容量
上限的结果区。wrapper 固定执行：安全复制 `/src`→`/work/src`；cd `/work/src`；HOME=/work/home；
Maven/Gradle 缓存到镜像内只读缓存或 `/work/cache`；执行注册表允许的固定命令；将允许输出复制到
`/out`。禁止模型直接提供 wrapper、working directory、entrypoint 或 shell 字符串。

#### P0-5：没有定义如何从 `/out` 取回结果

`/out` 如果是 Job 私有 tmpfs，Broker 不能直接从自己的文件系统读取。推荐 Docker archive 流式
提取：Job 停止后、remove 前 Broker 调 Docker archive/copy API 获取 `/out`；设置最大响应字节数；
将 archive 当作不可信输入；校验路径、文件类型、文件数、单文件大小和总大小；上传 CAS；最后
remove。需要特别防止：结果 tar 的 `../`、绝对路径、symlink/hardlink、device/FIFO、超大稀疏
文件、超文件数、压缩/展开炸弹、`/out` 中指向 `/src` 或宿主路径的链接。

#### P0-6：Broker 同时"解析不可信数据"和"持有 docker.sock"

这是当前最危险的组合：恶意 archive/结果 → Broker 解析器 → Broker 被攻陷 → docker.sock →
整个宿主机。建议：

1. Broker 下载的 source 必须是 control 根据 SnapshotTree 重新生成的规范化归档，不得直接传
   GitHub 原始 tarball。
2. 规范化归档不包含 symlink、hardlink、device、FIFO。
3. Job 输出 archive 优先由 control 做深度解析；Broker 只做字节上限、digest 和流式转发。
4. 如果 Broker 必须解析输出，输出提取器必须复用安全防线，并单独增加恶意结果样本集。
5. 同机模式下把这个风险升级为 G2 明示风险，而不是普通技术债。

#### P0-7：CAS 与 PostgreSQL 不可能组成"同一事务"

方案多处写"observation 入 CAS 登记 + tool_call 终态 + sandbox_job 终态同一事务"。CAS 是文件
系统，不能和 PostgreSQL 原子提交。建议改为明确的两阶段：上传临时对象 → 完整接收并计算 digest
→ CAS putIfAbsent → 数据库事务（register artifact + 更新 tool_call + 更新 sandbox_job +
revoke grant）→ 提交。可保证"DB 不得引用不存在的 CAS 对象"；不能保证"绝无孤儿对象"。

#### P0-8：DDL 存在循环引用与状态约束错误

1. 双向 FK 冗余：`sandbox_job.tool_call_id` 与 `tool_call.sandbox_job_id` 可能互相不一致并造成
   插入顺序复杂。建议只保留 `sandbox_job.tool_call_id uuid NOT NULL UNIQUE REFERENCES
   tool_call(id)`，反向查询。
2. REJECTED 的 finished_at 约束错误：REJECTED 是终态，应要求 finished_at IS NOT NULL 且
   reject_reason 必填。
3. CHECK 不能证明状态迁移合法：仓储必须限定状态更新（UPDATE ... WHERE state=:expected AND
   lease_epoch=:epoch，0 行=冲突）。

#### P0-9：观测链缺少 attempt

文档承诺 `run → attempt → step → tool_call`，但 `tool_call` 和 `sandbox_job` 都没有
`attempt_id`。Step attempt 重启后 `UNIQUE(run_step_id, call_seq)` 会撞旧 attempt 的序号。
建议 `attempt_id uuid NOT NULL REFERENCES ...` + `UNIQUE (attempt_id, call_seq)`；以下表均需
追溯 attempt：tool_call、sandbox_job、必要时 execution_event payload、model call ledger 与
tool round 的关联字段。

#### P0-10：claim 响应丢失后，grant 永久不可恢复

token 明文只返回一次，DB 只存 hash。窗口：DB 成功 claim 并生成 grant → HTTP 响应在到达 Broker
前断开 → Broker 没拿到 token → Job 已 LEASED → 原 token 无法从 hash 恢复，只能等 120 秒租约
过期。建议支持同 worker、同 job、同 epoch 的幂等补领：Broker 再次 claim/recover → Control 撤销
旧 grant → 重新签发新 token → epoch 不变 → 旧 token 即刻失效。不要把 token 明文存库。

#### P0-11：上传 grant 的 digest scope 与 JSON 契约冲突

I40 要求 grant 绑定 digest scope，但 `ResultUploadGrant.allowed_digests=[]` 又被定义为"任意本
Job 结果"——这不是 digest 白名单。建议明确区分：

| Grant | 约束 |
|---|---|
| ArtifactReadGrant | 已知 digest 白名单 |
| ResultUploadGrant | job + worker + epoch + artifact type + 单对象大小 + 总字节 + 次数 |
| 上传请求 | 客户端声明 digest、type、size；服务端流式重算 digest |

上传完成时必须再次验证 epoch（上传开始时有效、途中租约易主、旧 Broker 上传完成并推进终态的
竞态）。允许未登记 CAS 孤儿，但不得接受旧 epoch 的 DB 终态。

#### P0-12：Broker 崩溃后无法保证"零重复容器"

E2E-79 目前要求 Broker SIGKILL 后零重复副作用，但 Broker 死后无法 kill 它已创建的 Job 容器；
Recovery 重新入队后可能启动第二个容器，而旧容器仍在跑。需要新增宿主级 orphan reaper：每个 Job
容器打固定 labels（pr.sandbox.managed=true / job-id / lease-epoch / worker-id）；Recovery 重新
入队前根据 label 查询旧容器，仍运行则先 kill/remove，确认不存在旧容器后才能释放 capacity
slot、重新 PENDING；无法确认时进入 RECOVERY_BLOCKED 或保持 LEASED，不得直接重复执行。

#### P0-13：重试语义没有区分"业务失败"和"基础设施失败"

| 结果 | 是否自动重跑 |
|---|---|
| 测试失败、编译失败、非零 exit | 否，失败即数据 |
| OOM/PID 限制 | 默认否，除非策略明确 |
| Job timeout | 默认否 |
| digest 不匹配、恶意 tar | 否，安全拒绝 |
| Broker 在 create 前崩溃 | 可以 |
| Broker 在容器执行中崩溃 | 清理旧容器后可以，计入 infra attempt |
| control API 短暂不可用 | 不立即重跑容器，先恢复 heartbeat/上报 |
| dockerd 不可达 | 可延迟重试，但必须有上限 |

建议增加 `failure_class = BUSINESS | POLICY | SECURITY | INFRASTRUCTURE` + `retryable boolean`，
避免测试失败被自动执行两次。

#### P0-14：资源、日志和镜像启动契约不足

- 内存：只设置 Memory 不代表禁止 swap；要禁止 swap 应设置 MemorySwap=Memory（Docker 官方
  resource constraints 文档）。
- 日志：恶意 PR 可无限刷 stdout 使宿主 Docker 日志占满磁盘。需要每 Job 日志 driver 明确
  max-size/max-file；Broker 读取日志流式字节上限；超限标记 log_truncated=true；不允许先把全部
  日志读入 Java heap。
- ENTRYPOINT：`withCmd(argv)` 只覆盖 CMD；镜像若有 ENTRYPOINT，传入命令会成为其参数。必须镜像
  digest 精确允许、固定可信 wrapper、明确覆盖或校验 ENTRYPOINT、T00 inspect 镜像的
  Entrypoint/Cmd/User/WorkingDir、Job 运行期不得拉镜像。
