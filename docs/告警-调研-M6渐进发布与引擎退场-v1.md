## 1. Argo Rollouts（argoproj/argo-rollouts，~3k★）

### 机制（源码/文档级）

**Canary 步骤推进**。`strategy.canary.steps` 是用户自定义的步骤列表，控制器逐步执行，
每步评估通过后才推进。核心步型（[官方文档 features/canary](https://argoproj.github.io/argo-rollouts/features/canary/)）：

- `setWeight: N`：把 N% 流量切到 canary。无 traffic router 时只能按副本数近似
  （10 副本 41% → 4/6 拆分，四舍五入取 delta 最小），想要精确比例必须接流量管理层。
- `pause: {duration: 1h}` / `pause: {}`：定时暂停或无限期暂停（等 `kubectl argo rollouts promote` 人工放行）。
- `setCanaryScale`：解耦"流量权重"与"canary 副本数"，文档明确给出用例 3：
  "scale the canary up to 100%, in order to facilitate **traffic shadowing**"——即官方承认
  canary 机制可复用为影子流量载体。
- `analysis` 步（inline）：阻塞式分析，成败决定继续/中止；或 `canary.analysis`（background）
  后台常驻分析，可用 `startingStep` 延迟到某个权重台阶才启动。

**AnalysisRun 指标门**（[官方文档 features/analysis](https://argoproj.github.io/argo-rollouts/features/analysis/)）：

- 每个 metric 定义 `interval`（测量间隔）、`count`（测量次数，0=跑到 Rollout 结束）、
  `successCondition` / `failureCondition`（表达式，如 `result[0] >= 0.95`）。
- `failureLimit: 3`：容忍 3 次失败测量后整个 AnalysisRun 判 Failed。
- `consecutiveSuccessLimit`（v1.8+）：要求连续 N 次成功测量才算 Successful；
  两者可组合（"最多失败 3 次的前提下连续成功 4 次"）。
- **三段式结论**：Successful / Failed / **Inconclusive**。Inconclusive（条件未命中任何一侧、
  或 metrics 无判定条件）→ Rollout 暂停在当前步，等人工判断。这是 Argo 对"拿不准"的官方答案：
  不猜，停下来等人。
- `dryRun` 指标：只测量不影响结论——"先观察再启用门"的正式机制。
- `measurementRetention`：默认只留最近 10 次测量，可调。
- 对 NaN / Infinity / 空数组有明确的条件写法约定（`isNaN(result) || ...`、`default(result, 0)`）。

**自动回滚与 abort 语义**。后台分析 Failed → Rollout **abort**：canary 权重立即归 0、
流量全回 stable，Rollout 状态 `Degraded`（analysis 文档原话："The failed analysis causes the
Rollout to abort, setting the canary weight back to zero"）。回滚快的原因是：
**使用 traffic router 时 stable ReplicaSet 默认全程保持 100% 副本**，abort 只是改路由权重，
零启动延迟。省资源的替代项 `dynamicStableScale: true` 会让 stable 随权重下调缩容，代价是
abort 回切要等扩容，可用 `abortScaleDownDelaySeconds` 缓冲。BlueGreen 策略另有
`postPromotionAnalysis`：切流后分析失败则流量切回旧 stable，旧 ReplicaSet 按
`scaleDownDelaySeconds`（默认 30s）延迟缩容——即"回退制品保留窗口"。

**它如何定义"不劣化"门**：注意 Argo 的默认范式是**绝对阈值门**（`result[0] >= 0.95` 判断
canary 自身指标），不是与对照组的统计比较；与对照组平行比较要靠自己起 `Experiment`
（baseline + canary 两个 ReplicaSet 并行 + AnalysisTemplate）来实现。

### 优缺点

- 优：声明式步骤、abort 语义清晰（权重归 0 + Degraded + stable 全程在线 = 秒级回切）、
  Inconclusive 三段式与 dryRun 是"渐进信任门"的成熟设计、失败容忍数/连续成功数语义精确。
- 缺：强绑 K8s + metrics provider（Prometheus 等）；绝对阈值需手工调，无统计学判定；
  步骤列表是静态 YAML，无法表达"连续 N 个窗口达标才升档"之外的复杂状态机。

### 对本项目

- **借鉴**：三段式结论（成功/失败/拿不准→人工）、failureLimit + consecutiveSuccessLimit 组合语义、
  dryRun 先行观察、"回退快 = 旧引擎全程在线，abort 只是改路由"（本项目 Run 级 engine 路由天然满足，
  abort = 把 Native 权重写回 0，Holmes 从未离场）。
- **不适配**：不能引入本体（无 K8s）；setWeight 的副本数近似语义与本项目无关（本项目是
  Run 级确定性分桶，不是流量比例近似）。

## 2. Flagger（fluxcd/flagger，~5k★）

### 机制（源码级）

Canary CRD 的 `analysis` 段（[官方文档 usage/how-it-works](https://docs.flagger.app/usage/how-it-works)）：
`interval`（检查节奏）、`threshold`（失败检查次数上限，到达即回滚）、`maxWeight`/`stepWeight`
（线性步进）、`stepWeights[]`（自定义台阶）、`iterations`（A/B 与蓝绿用）、`metrics[]` 带
`thresholdRange{min,max}`、`webhooks[]`（confirm-rollout / pre-rollout / rollout /
confirm-traffic-increase / **confirm-promotion** / rollback / post-rollout——人工门也是 webhook）。

核心控制器 `pkg/controller/scheduler.go`
（[源码](https://github.com/fluxcd/flagger/blob/main/pkg/controller/scheduler.go)）的
`advanceCanary` 每 interval 触发一次，机制要点：

- **主备模型**：Flagger 为目标 Deployment 生成 `<name>-primary` 副本作为 stable；
  canary 是目标本身。Promote = 把 canary 的 spec 拷回 primary（`canaryController.Promote`），
  再把流量逐步切回 primary（`runPromotionTrafficShift`，`stepWeightPromotion` 控制回切坡度）。
- **失败计数回滚**：`runAnalysis`（内置 request-success-rate / request-duration 检查 +
  MetricTemplate 自定义指标 + rollout webhooks）失败 → `FailedChecks+1`；
  `FailedChecks >= threshold` → `rollback()`：路由 `SetRoutes(100, 0)`、canary `ScaleToZero`、
  Phase=Failed。回滚与 Argo 同构：改路由 + 杀 canary，primary 始终在。
- **分析中检测到新版本**：`hasCanaryRevisionChanged` → 流量归 0、FailedChecks/Iterations 清零、
  分析重启（防止"分析中途换被测对象"的脏数据）。
- **Promoting 期 primary 不健康**：`handleFailedPromotion`——此时 canary 是唯一健康副本，
  反而把流量全切给 canary 并标 Failed（而不是切回不健康的 primary）。边界情形处理值得注意。
- **Mirror 模式**：`analysis.mirror: true` 时先把流量镜像到 canary（响应仍由 primary 返回），
  跑一轮分析后再开始真实切流——Flagger 内置的 shadow 阶段（scheduler.go `runCanary` 中
  mirror 分支）。

### 与 Argo 的异同

| 维度 | Argo Rollouts | Flagger |
|---|---|---|
| 推进方式 | 用户自定义 steps 列表（任意权重/暂停/分析编排） | 固定引擎：stepWeight 线性步进或 iterations |
| 判定 | CEL 表达式 successCondition/failureCondition + failureLimit/consecutiveSuccessLimit | thresholdRange{min,max} + failedChecks 计数 ≥ threshold |
| 对照实验 | Experiment CRD（baseline vs canary 平行） | 无；A/B 按 header 匹配 |
| Shadow | setCanaryScale 100% + 自家 tee | 内置 `mirror` 布尔 |
| 人工门 | pause:{} + promote 命令 | confirm-* webhooks |
| 回滚 | abort：权重归 0，stable 全程在 | rollback：SetRoutes(100,0)+ScaleToZero |

### 对本项目

- **借鉴**：`mirror` 先行（先影子后真切）的两段式节奏；webhook 式多级人工门
  （confirm-rollout / confirm-traffic-increase / confirm-promotion 可映射为 M6 各档位的放行审批）；
  "分析期间被测对象变更则计数清零重来"的纪律（对应本项目：切流期间引擎/config digest 变了，
  当前档位证据作废——`engineDigest` 已在 EvaluationRecordV1 里，可门）。
- **不适配**：线性 stepWeight 固定节奏推进——引擎切换的质量判定不该按墙钟/固定次数自动升档，
  必须门控；本体依赖 K8s + service mesh，不可引入。

## 3. Kayenta（spinnaker/kayenta，1.3k★，Netflix 自动 Canary 分析）

> 仓库已于 2025-12 归档并迁入 spinnaker/spinnaker monorepo，但仍在发版
> （Maven `io.spinnaker.kayenta:kayenta-judge:2025.3.0`）。以下源码引用自归档仓库 master，
> 文件路径在 monorepo 中保持同名。

### 机制（源码级）

**三集群拓扑**（[Netflix 官方博客](https://netflixtechblog.com/automated-canary-analysis-at-netflix-with-kayenta-3260bc7acc69)）：
production（旧版，多数流量）+ **baseline**（与 production 同代码同配置、新建、~3 实例）
+ **canary**（新代码、~3 实例），baseline 与 canary 各吃一小份相同流量。为什么另起 baseline
而不直接对比 production："comparing a newly created canary cluster to a long-lived production
cluster could produce unreliable results. Creating a brand new baseline cluster ensures that the
metrics produced are free of any effects caused by long-running processes."——新鲜对照组消除
长跑进程污染。

**Judge 流程四段**（博客 + `kayenta-judge/src/main/scala/com/netflix/kayenta/judge/NetflixACAJudge.scala`
[源码](https://github.com/spinnaker/kayenta/blob/master/kayenta-judge/src/main/scala/com/netflix/kayenta/judge/NetflixACAJudge.scala)）：

1. **Data Validation**：baseline 或 canary 任一侧无数据 → 标 `NODATA`，跳过该指标。
2. **Data Cleaning**：`nanStrategy`（Remove/Replace，error 类指标 NaN→0）、
   `outlierStrategy`（IQR 检测器剔除离群点，默认 factor 3.0）。
3. **Metric Comparison**：Mann-Whitney U 检验。`NetflixACAJudge.scala` 中实际参数
   `new MannWhitneyClassifier(tolerance = 0.25, confLevel = 0.98, ...)`。判定逻辑在
   `classifiers/metric/MannWhitneyClassifier.scala`
   （[源码](https://github.com/spinnaker/kayenta/blob/master/kayenta-judge/src/main/scala/com/netflix/kayenta/judge/classifiers/metric/MannWhitneyClassifier.scala)）：
   - 计算置信区间（Hodges–Lehmann 估计 ± tolerance×|estimate| 为容忍带）；
   - canary 置信下界 > 上容忍界 且 effect size（默认 meanRatio）≥ allowedIncrease → 判 **High**；
     对称判 **Low**；否则 **Pass**；
   - `direction`（increase/decrease/either）限定只盯哪个方向——"不劣化"门就是
     direction=decrease 的指标（如错误率升了算 High 失败）与 increase 的指标组合。
4. **Score Computation**：`scorers/ScoringHelper.scala`
   （[源码](https://github.com/spinnaker/kayenta/blob/master/kayenta-judge/src/main/scala/com/netflix/kayenta/judge/scorers/ScoringHelper.scala)）——
   按 `groupWeights` 对指标组加权求和（WeightedSumScorer），再用
   `ThresholdScoreClassifier(pass, marginal)` 划档：≥pass 通过，marginal~pass 之间边缘
   （可配人工介入），<marginal 失败。博客口径："score = Pass 指标占比"（9/10 Pass → 90 分），
   刻意选简单易懂的评分。

**critical / non-critical 指标分类**（`NetflixACAJudge.classifyMetric` 从
`analysisConfigurations.canary` 读取）：

- `critical: true`：该指标判 High/Low 且越过 `criticalIncrease/criticalDecrease` 效果量阈值时，
  `MetricClassification.critical=true`——critical 指标失败直接否决整个 canary（一票否决），
  不进加权平均稀释。
- `mustHaveData: true` + 非 critical：无数据时判 `NodataFailMetric`（非否决性失败）；
  critical+无数据 → 否决。
- `muted: true`：ScoringHelper 直接 `filter(!_.isMuted)`——观察但不记分（= Argo 的 dryRun）。

**小样本/退化数据处理**（MannWhitneyClassifier.scala 源码事实清单）：

- 任一侧数据为空 → NODATA 路径，不进统计检验；
- 两侧排序后完全相等 → 直接 Pass（"data are identical"）；
- 合并后只有一个唯一值 → Pass（常量指标不比）；
- 两侧都是退化分布（各自只有 1 个不同值）→ **加高斯噪声**（幅度 = 值×1e-5）再做检验
  （"In the case of the degenerate distribution, Gaussian noise is added"）；
- effect size 算不出（NaN）→ 效果量比较被忽略，只看置信区间；
- **没有最小样本数门槛**——靠置信区间宽度自然表达不确定性（样本少 → 区间宽 → 难越界）。
  实践上千吗尼时长建议 ≥1 小时、每侧 ~3 实例（博客）。

### 优缺点

- 优：统计判定免手调阈值（"removed much of the complexity of setting proper thresholds"）；
  critical 一票否决 + 组加权记分两层结构清晰；muted/dryRun 机制；判定输入输出全归档，
  新 judge 可对历史数据重放实验。
- 缺：重（Scala 服务 + Redis 依赖）；repo 已归档（维护活跃度风险）；Mann-Whitney 需要
  双侧各有一定量的同分布时序点，对小样本 Run 级质量判定是杀鸡用牛刀且样本量不够时
  区分度差。

### 对本项目

- **借鉴（重点）**：**critical vs scored 双层指标分类**——预算硬门、安全门、schema 合法性 =
  critical（一票否决，不进平均）；六维质量分 = 加权记分（对照 ScoringHelper 的
  groupWeights + pass/marginal 阈值）。**muted 机制** = 新指标先观察一个里程碑再转正。
  **新鲜对照组**思想 → 对照期让 Holmes 与 Native 跑同一批告警输入，而不是拿 Native 对比
  "Holmes 的历史基线"（历史基线混杂了配置漂移）。
- **不适配**：不引入 Kayenta 本体；不照搬 Mann-Whitney——本项目每个档位的 Run 样本量
  （尤其 1% 档）远不够 rank-sum 检验的功效，用"阈值 + 连续 N 窗口 + Inconclusive 人工"
  更诚实（见 §10）。

## 4. OpenFeature / flagd（open-feature/flagd，fractional rollout）

### 机制（源码级）

fractional evaluation 的确定性分桶契约在
`core/pkg/evaluator/fractional.go`
（[源码](https://github.com/open-feature/flagd/blob/main/core/pkg/evaluator/fractional.go)，
本次调研读取全文 213 行）：

- **分桶键**：`bucketBy` 默认 = `flagKey + targetingKey`（无分隔符直接拼接）；
  可用 rules 里第一个字符串参数自定义 bucketBy 属性。无 targetingKey 且未给 bucketBy →
  返回 nil（不分桶、不给随机变体）。
- **哈希**：`murmur3.StringSum32`（twmb/murmur3，x86_32，seed=0）。
- **无模偏映射**（`distributeValue`）：`bucket = (uint64(hashValue) * uint64(totalWeight)) >> 32`，
  把 u32 哈希乘到 64 位再取高 32 位 → [0, totalWeight)。低位乘法取高位，避免 naive modulo
  在 totalWeight 不整除 2^32 时对高位桶的可测偏好。
- **变体落桶**：按声明顺序累积权重，`bucket < rangeEnd` 即中。**权重必须为整数**，总和 ≤ 2^31-1；
  负权重 clamp 到 0（注释说明：rollout 计算可能产生负权重，容忍而非报错）。
- **黏性**：同 flagKey+targetingKey+权重分布 → 恒定同桶，纯函数无随机源。
  单调性推论：只增加某前缀变体的权重，已落该变体的 key 不会掉出（bucket < oldEnd ⊂
  bucket < newEnd）——**放量只进不出**，这是渐进切流不抖动用户的关键性质；但调整非前缀
  变体或重排顺序会破坏该性质。

### 本项目现状对照

`control-app/src/main/java/com/objwww/pr/control/release/domain/service/CanaryBucketer.java`
已是该公式的同构 Java 实现（murmur3_x86_32 seed=0 + `(hash_u32 * totalWeight) >>> 32`，
javadoc 明确标注 "fractional.go:196-207 同构"），并加了两条自有纪律：
归一化键 `groupId + ":" + id`（trim + Locale.ROOT 小写，**注意与 flagd 的拼接键口径不同**，
跨实现对拍只在同口径下成立——已有参考向量测试对拍独立 mmh3 实现）；
**缺 stickiness key = 拒绝放量**（IAE，上层转 NO_STICKINESS_KEY 落 HOLMES 主路径）。
后者比 flagd 更严：flagd 缺 targetingKey 返回 nil 由调用方兜底，本项目直接拒绝并回主路径——
M6 应保持这个"宁缺毋滥"语义。

### 优缺点与适配

- 优：契约极小（一个公式 + 一个键口径），可无依赖自实现；确定性 + 放量单调性是
  1%→10%→50% 台阶的正确性基石。
- 缺/风险：键口径是**全局约定**（改归一化规则=全员重分桶），本项目已要求"改动任一项必须升
  ALGORITHM 版本并评审"——M6 方案文档应重申；权重取整意味着 1% 档 totalWeight=100 即可，
  无需浮点权重。

## 5. GitHub Scientist（github/scientist，~7k★）

### 机制（README + 官方博客级）

关键路径重构的"对照实验"模式（[README](https://github.com/github/scientist)
+ 官方博客 [Scientist: Measure Twice, Cut Once](https://github.blog/developer-skills/application-development/scientist/)）：

- `use { }` = control（旧），`try { }` = candidate（新）；`experiment.run` **永远返回 control 的值**，
  candidate 只是被观察。
- 执行序**随机化**（消除顺序效应）；记录两侧 wall/cpu time；`compare` 自定义等价判定
  （默认 `==`）；`compare_errors` 自定义异常等价（同类同 message 视为一致）。
- `ignore { }`：**已知差异白名单**——"early stages 中某些 mismatch 原因已知但未修，ignore 掉
  不污染指标"。ignore 只在值不匹配时才被调用。
- `run_if` / `enabled?`（如 `rand(100) < percent_enabled`）：实验自身的灰度 ramp。
- `publish(result)`：结果（matched/ignored/mismatched + 两侧值 + context + 执行序）发布到
  statsd/Graphite 计时、Redis 存 mismatch payload（GitHub 自用 `ltrim 0 1000` 封顶 1000 条）。
- 异常语义：candidate 异常被吞掉只记录；control 异常重抛（它是真实返回值）；
  `raise_on_mismatches` 仅供测试套件。
- **结束纪律**（博客"Finishing an experiment"）：收敛后禁用实验、删 control、只留 candidate；
  若有 ignore 块则"行为保证有差异"，必须先清 ignore 再下线；**写侧双写要保留到新行为
  上线后很久**（"keep any write-side duplication in place until well after the new behavior
  has been in production, in case you need to roll back"）。
- 大前提（README "Designing an experiment"）：**Scientist 只适用于无副作用代码**
  （candidate 不可写共享状态）；官方建议写路径双系统同时写、读路径用 science 验证，
  并配 reconciliation 脚本核对两库数据。
- 校准技巧：先跑一个 try 和 use 都调 control 的空实验，量化系统性假不匹配底噪
  （≈ Diffy 的 noise band 思想）。

### 优缺点

- 优：把"并行对照期"工程化为库级原语；ignore-with-reason、mismatch payload + context 落库、
  实验自身可 ramp、空实验测底噪——全是可直接抄的模式。
- 缺：Ruby 库（有 Java 移植 rawls238/Scientist4J 但本项目不必引）；同请求内顺序双跑 =
  延迟与成本 ×2；`==` 比对默认假定确定性输出。

### 对本项目

- **借鉴（重点）**：新旧引擎并行对照期按 Scientist 模式组织——control=Holmes（返回值为准）、
  candidate=Native（只观察）；**`ignore` 白名单 = 已知差异清单**（Native 与 Holmes 判定口径的
  已确认合理差异，逐条登记原因）；**mismatch 落库带 context**（Run id、输入摘要、两侧结论、
  digest 集）供回归分析；**空转校准**：先用 Holmes 双跑量化自身不一致底噪（LLM 非确定性
  场景下这步不可省）。
- **不适配（重要）**：不能同请求同步双跑——LLM 引擎调用有预算硬门
  （`ModelStepBudgetGuard`），双跑 = token 预算 ×2 直接撞门，且端到端延迟翻倍。
  应改为**异步离线对照**（同输入事后重放 candidate，或 1% 真实流量分桶后事后比对），
  即"Scientist 的数据模型 + Diffy/回放的执行模型"。另外 LLM 输出非确定，`compare` 必须是
  语义级（结论类别/关键字段一致），不能是文本 `==`。

## 6. Diffy（twitter-archive/diffy，~4.3k★，已归档；活 fork：opendiffy/diffy）

### 机制

影子流量三路比对（[README](https://github.com/twitter-archive/diffy)）：

- Diffy 作为代理把每个请求**组播到三个实例**：candidate（新代码）、primary（旧=已知好）、
  **secondary（与 primary 同代码的另一个实例）**。
- 比对两件事：candidate vs primary 的**原始差异**；primary vs secondary 的**非确定性噪声**。
- **噪声消除**："If these measurements are roughly the same, then Diffy determines that there is
  nothing wrong"——候选-基线差异率 ≈ 基线-基线差异率时，差异归因于系统内在非确定性而非回归。
  两次基准比对把"系统本身就不稳定"从"新代码引入的劣化"中扣掉。
- 前提假设（README 原话）：两个实现对"足够大且多样的请求集"返回"相似"响应即可视为等价。
- 安全默认：POST/PUT/DELETE 默认忽略（`-allowHttpSideEffects` 才放行）——副作用请求不进影子。

### 优缺点

- 优：噪声消除思想直击非确定性系统的对照痛点；零侵入（代理层组播，业务无感知）。
- 缺：Twitter 已归档（"built on our outdated tech stack"）；假定请求/响应式服务与可镜像流量；
  三路 = 3 倍被测资源；响应 diff 假定输出可文本比对。

### 对本项目

- **借鉴（思想级，重点）**：M6 的"不劣化"门应定义为 **Native-vs-Holmes 差异率 −
  Holmes-vs-Holmes 自差异率 ≤ 容忍带**，而不是 Native 差异率的绝对值。落地形态不是三路代理，
  而是**离线回放三桶**：同一批历史告警输入 × {Holmes 重放 A、Holmes 重放 B、Native}，
  A/B 差出噪声带，Native 超出噪声带的部分才算真回归。这与 §5 Scientist 的"空实验测底噪"
  是同一思想的两处独立来源，可信度高。
- **不适配**：不引本体（归档、Scala/Finagle 栈、需代理层）；本项目是 Run 级异步管线而非
  请求/响应服务，没有可组播的流量入口；2C4G + LLM 预算下在线三路（3× token）不可行，
  离线回放也应对输入集做抽样而非全量。

## 7. Strangler Fig 模式（旧系统退场）

### 机制

- **原始文献**：Martin Fowler bliki [StranglerFigApplication](https://martinfowler.com/bliki/StranglerFigApplication.html)
  （2004 年原名 "Strangler Application"，后改名强调绞杀榕植物学隐喻）。核心论点：
  "know what the old system does, build a new system that does exactly the same" 的**整体替换
  计划"goes down in flames most of the time"**；应渐进现代化——识别 **seams（缝隙）**、
  小步替换、接受"transitional architecture（过渡架构）"的临时成本（"the reduced risk and
  earlier value from the gradual approach outweigh its costs"）。Cartwright/Horn/Lewis 四活动：
  明确目标 → 拆小 → 交付小块 → 组织持续化。
- **Azure 官方页**（[Strangler fig pattern](https://learn.microsoft.com/en-us/azure/architecture/patterns/strangler-fig)）：
  - 阶段划分：引入 façade（代理/路由层）拦截请求 → 初始大部分路由到旧系统 → 逐功能增量
    切到新系统 → 旧系统无依赖后**退役** → 最后移除 façade。
  - 关键考量：新旧系统**共享数据存储要能同时访问**；façade 不得成为单点/瓶颈；跨系统
    依赖用 Anti-corruption Layer 隔离；**"把移除旧对象当作每个领域的刻意最终步骤，仅在新系统
    验证通过后才删"**。
  - 数据库示例三阶段（新服务仍读写旧库 → 引入独立库 + ETL 初始装载 + CDC 同步 + 一致性
    校验 → 切换主权并删旧表），并明确：**阶段 2 与阶段 3 早期可回滚；删除旧表/同步进程后
    回滚只能"重建对象+重放数据"，成本与风险剧增**。
  - 不适用情形：请求无法被拦截；改不了旧系统源码；**小系统整体替换更简单时不要用**；
    需要快速完全下线旧系统时不要用。

### 优缺点

- 优：退场风险后置且每步可回退；façade 单一切流点使回滚=改路由。
- 缺：过渡期双系统维护成本；façade 本身要治理；长迁移期组织纪律要求高（Fowler 第四活动）。

### 对本项目

- **借鉴**：本项目的 seam 已经是现成的——`rca_run.engine` 字段 + `CanaryRouter` 就是 façade，
  无需另建。Holmes 退场严格按"刻意最终步骤"处理：**Primary 切到 Native 后，Holmes 容器、
  镜像 tag、路由回切能力（一键权重归 0）至少保留一个 soak 期**；删除 Holmes 代码路径/依赖
  （"旧表删除"对应物）放到 soak 通过后的独立里程碑，且删除前先导出依赖扫描清单
  （谁在 import Holmes 适配器、哪些配置项引用它）。共享 PG 单库 = Azure 页"共享数据存储
  同时访问"场景，schema 变更（如删 HOLMES 专属列）必须排在最后。
- **不适配**：Azure 页明说"小系统整体替换更简单时不要绞杀"——本项目引擎替换虽是小系统，
  但替换的是**质量判定逻辑**（错判代价高）而非 CRUD，故仍适用渐进路线；只是 façade
  复杂度应保持极简（一个分桶函数 + 一个枚举字段），不引入代理组件。

## 8. Google SRE Workbook 的 canary 章节（第 16 章 Canarying Releases）

> 注：canary 的系统论述在 **SRE Workbook** 而非 SRE Book 第一册
> （[官方在线版 sre.google/workbook/canarying-releases](https://sre.google/workbook/canarying-releases/)）。

### 官方建议要点

- **定义**：canarying = "partial and **time-limited** deployment of a change and its evaluation"，
  本质是 A/B 测试过程。
- **错误预算账**：5% canary 跑 20% 错误率 = 全局 1% 错误——"impact on the budget is directly
  proportional to the amount of traffic exposed"。切流比例 × 故障率 = 代价，这是档位设计的
  第一性公式。
- **规模与时长**：canary 要"sizeable and last long enough to be representative"；只收几个请求就
  结束的 canary 没有信号价值；处理速率越高，达到代表性样本所需时间越短。**时长必须与发布
  频率匹配**（日发则不能 canary 一周）；**强烈建议同一时刻只跑一个 canary**
  （并行 canary 信号互相污染）。
- **时段**：性能缺陷通常只在重负载下显现，off-peak 部署可能触发不了性能类缺陷。
- **指标选择**：从 SLI 出发选"对用户可感知问题归因最强"的少数指标（"perhaps no more than
  a dozen"）；CPU/内存这类资源指标噪声大、易使 canary 流程被操作员无视（"can result in the
  canary process being disabled or ignored"）；404 等 4xx 需排除或用黑盒监控隔离用户侧怪异。
- **可归因性**：指标变化必须可归因于被测变更而非外部因素；canary 与 control 共享基础设施
  时（本项目 = 同机同库！）要警惕互相污染，**同时要保留 SLO 类绝对度量**防"A/B 一起烂"。
- **警惕 before/after 对比**（"canary deployment in time-space"）：时间是指标变化的最大噪声源
  （周一发版 vs 周末流量）；应同时段分人群对比。
- **监控口径**：整体监控会把 5%×20% 摊平成 1% 看不见——**必须按人群细分**（canary vs
  control 分开看，图 16-4 的 per-version 分解）；**指标聚合窗口 ≤ canary 时长**，否则
  1 小时窗口评估 30 分钟 canary 必然脏数据。
- **非交互系统**（与本项目最相关的一节）：canary 时长至少覆盖**单个工作单元的处理时长**；
  多级管线要保证同一工作单元始终由同一侧（canary 或 control）的 worker 池处理，否则信号
  混杂；指标含"处理质量"这类完全应用特定的维度。
- **teeing/影子流量**：官方承认可行但警告——有状态系统中流量副本会在看似独立的部署间
  引入意外影响（如共享缓存使命中率虚高）。

### 对本项目

- **借鉴**：① 代价公式 = 档位比例 × 故障率，1% 档的意义是把"Native 全错"的代价压到 1%；
  ② 一次一档；③ **按 engine 细分指标**——`rca_run.engine` 字段就是现成的人群标签，
  所有切流期看板必须 split by engine，绝不看合账；④ **档位时长按"Run 数"而非墙钟**
  （本项目是长耗时非交互管线，SRE 原话"duration at minimum spans the duration of a single
  work unit"——一档至少攒够 N 个代表性 Run）；⑤ 保留绝对度量（预算消耗、总失败率）
  防双侧同步劣化；⑥ 同机同库的共享失效域要在报告里明示（Native 拖垮 DB 会连累 Holmes
  侧指标，归因时排除）。
- **不适配**：Google 的"每日多发的快速 canary"节奏不适用——本项目引擎切换是一次性
  里程碑事件，档位之间应是长 soak + 人工门，不追求自动化快节奏。

## 9. LLM/Agent 系统的引擎切换实践

> 公开一手资料中，"agent 引擎灰度切换"没有类似 Kayenta 那样的命名系统；事实标准是
> **离线实验门 + 在线无参照评估 + 反馈闭环**的组合。以下全部取自官方文档。

### LangSmith（LangChain 官方）

[Evaluation concepts 官方文档](https://docs.langchain.com/langsmith/evaluation-concepts)：

- **Offline evaluation**（部署前）：跑在 **dataset/example**（输入 + 参照输出）上，用途包括
  Benchmarking（多版本对比选优）、Regression testing（**确保新版本不劣化**——这就是
  "不劣化"门的官方措辞）、Backtesting（历史数据回测新版本）。一次评估产出一个
  **experiment**，多个 experiment 在同 dataset 上**并排对比**（prompt/模型/配置变体）。
- **Online evaluation**（生产监控）：跑在 **runs/threads**（真实流量 trace，**无参照输出**），
  评估器只能是 reference-free 技术（安全/格式/质量启发式/reference-free LLM-as-judge）；
  配置含 **sampling rate、filters、spend limits**（按 project 粒度）。
- **生命周期闭环**（文档原话）："Online evaluations surface issues that become offline test
  cases, offline evaluations validate fixes, and online evaluations confirm production
  improvements."——线上发现的问题回流成离线测试集，离线验证修复，线上确认改进。
- **Pairwise 评估器**：两版本输出做成对比较，"当直接打分困难但比较两个输出容易时"——
  摘要任务里"选信息量更大的那份"比"给每份打绝对分"容易。这正是引擎切换的判定形态。
- **Evaluation vs Testing**："Testing asserts correctness; evaluation measures performance...
  Evaluation metrics can be converted into tests. For example, regression tests can assert that
  **new versions must outperform baseline versions** on relevant metrics."——评估指标可固化为发布门。
- 数据集建设：先手工 5–20 个金标样例；生产中把负反馈/异常 run 转为 dataset 条目。

### Langfuse（开源 LLMOps，可自托管）

- [Evaluation 官方文档](https://langfuse.com/docs/evaluation/overview)：实验（experiments）跑在
  dataset 上比较 prompts/models/configurations 变更，LLM-as-a-judge + 人工标注 + 自定义
  确定性评分三路并存。
- [官方博客 LLM Evaluation 最佳实践](https://langfuse.com/blog/2025-11-12-evals)："standard
  pattern is to run **two experiments on the same dataset and compare them side by side** in the
  UI, where per-item outputs and scores"——同数据集双实验逐项并排是事实标准操作。
- [Golden dataset 工程指南](https://langfuse.com/resources/engineering/golden-dataset-evaluation)：
  金标测试集从生产 trace 中持续构建并保持新鲜，prompt/版本间用 experiments 对比。

### 对本项目

- **借鉴（重点，直接映射 M6 三段）**：
  1. **Offline 门（升档前置）**：维护 RCA 金标数据集（历史告警 + Holmes 参照结论），
     每个档位升级前跑 Native experiment，与 Holmes experiment **side-by-side 逐项对比**
     （Langfuse 范式）；判定用 **pairwise**（"Native 结论是否不劣于 Holmes 结论"）而非绝对分
     （LangSmith pairwise 论据：成对比较比绝对打分可靠）。
  2. **Online 门（切流期）**：生产流量无参照输出，只能 reference-free——格式/schema 合法、
     预算合规、工具调用轨迹合理、安全门过；配 **sampling rate + spend limits**
     （LangSmith 概念，恰好适配预算硬门：在线评估自己也耗 token，必须限额）。
  3. **闭环**：切流期发现的 Native 问题 Run → 回流金标数据集 → 修复后离线验证 →
     线上确认（LangSmith 生命周期原话闭环）。
- **不适配**：LangSmith 是 SaaS、Langfuse 自托管也要一整个栈——2C4G 不引平台，只抄
  数据模型（dataset/experiment/并排对比/采样在线评估）落到现有 PG + eval 域
  （`EvaluationRecordV1` 已有 dataset/config/engine digest 集，天然就是 experiment 记录）。

## 10. 综合建议：M6 切流门设计应抄什么 / 不该抄什么

### 应抄（按优先级）

1. **分桶契约继续用 flagd 公式**（§4）：已同构实现且有对拍测试，保持"缺 stickiness key
   拒绝放量"的从严语义与 ALGORITHM 版本纪律。1%→10%→50% 用 totalWeight=100 整数权重，
   靠前缀单调性保证放量只进不出。
2. **三段式档位结论**（§1 Argo）：每档评估 = Success（升档）/ Failed（权重归 0 回 Holmes，
   abort 语义）/ **Inconclusive（停档等人工）**。"拿不准就停"比任何自动统计都适合小样本。
3. **critical 一票否决 + scored 加权两层**（§3 Kayenta）：预算硬门、安全门、schema 合法性
   进 critical；六维质量分与效率指标进 scored。muted/dryRun 机制给新指标一个观察期。
4. **噪声带判定**（§6 Diffy + §5 Scientist 空实验双源印证）："不劣化"=
   Native-vs-Holmes 差异 − Holmes 自差异 ≤ 容忍带。先做 Holmes 双跑校准底噪再定阈值。
5. **对照期 = Scientist 数据模型 + 异步执行**（§5）：Holmes 结论为准返回值，Native 只观察；
   ignore 白名单登记已知合理差异；mismatch 带 context 落库。**绝不同请求同步双跑**（预算门）。
6. **离线金标门 + 在线采样无参照评估 + 回流闭环**（§9 LangSmith/Langfuse 三段式）：
   升档前 offline 并排对比；切流期 online 按 sampling rate + spend limit 跑 reference-free 检查；
   问题 Run 回流金标集。
7. **按 engine 细分一切看板 + 保留绝对度量**（§8 SRE）：split by `rca_run.engine`；
   档位时长按代表性 Run 数而非墙钟；一次一档；防双侧同步劣化。
8. **退场是刻意最终步骤**（§7 Strangler Fig + §5 Scientist 收尾纪律）：Primary=Native 后
   Holmes 镜像/代码路径/回切开关保留整个 soak 期；清 Holmes 依赖先做 import/配置依赖扫描，
   删除独立成里程碑；ignore 白名单清零后才能下线对照机制。

### 不该抄

1. **不引任何本体**：Argo/Flagger/Kayenta 全要 K8s（无）；Diffy 已归档且要代理层；
   LangSmith/Langfuse 是整栈平台（2C4G）。全部只抄机制与数据模型。
2. **不抄 Mann-Whitney 统计栈**（§3）：1%/10% 档样本量撑不起检验功效，且 Run 级质量分
   非同分布时序点。用"阈值 + 连续 N 窗口 + Inconclusive 人工"替代——诚实且可解释。
3. **不做在线三路/双跑影子**（§5/§6）：token 预算 ×2~×3 直接撞预算硬门；影子用**离线回放
   抽样**实现。
4. **不抄固定节奏自动升档**（§2 Flagger stepWeight、§1 Argo pause duration）：引擎切换的
   升档条件应是"证据达标"（Run 数 + 门通过），不是"时间到了"；墙钟只做下限保护。
5. **不做 before/after 时间对比**（§8 SRE 明确警告）：拿 Native 现在的指标对比 Holmes
   上周的指标会被时间噪声污染；对照必须同时段、同输入分布。
6. **不让指标数膨胀**（§8 "no more than a dozen" + 噪声指标会被无视的警告）：切流门指标
   控制在个位数，全部对用户可感知问题可归因。

## 11. v1.1 独立复核：原调研能采纳什么、必须修正什么

本节不是重复罗列项目，而是把官方一手材料与当前仓库实现对拍后的任务级裁定。结论：原 E-20 的方向（稳定分桶、三段式 verdict、只读异步对照、刻意退场）可用，但直接落到 v1.0 数据模型会留下证据污染与并发恢复缺口。

| 主题 | 一手证据与仓库事实 | AM6 裁定 |
|---|---|---|
| 测试流量 vs 晋升证据 | [Google SRE Canarying Releases](https://sre.google/workbook/canarying-releases/) 明确说明实际生产流量能暴露人工测试遗漏，并要求 canary/control 有代表性；[Argo Analysis](https://argoproj.github.io/argo-rollouts/features/analysis/) 的 dry-run metric 不影响 rollout | `evidence_class=LIVE_CANARY/DRILL/REPLAY` 入 V30；E2E/故障注入恒为 DRILL，只证机制，不可“注入足量告警”刷出可晋升 PASS |
| 相对不劣不足以证明健康 | Google SRE 同章指出 A/B 可能同时退化，须保留绝对度量 | 每窗同时保存 contemporaneous Holmes control 与 absolute SLO；禁止 Native 本周对 Holmes 上周的 before/after 对比 |
| 窗口与候选身份 | Argo 在新 revision 上重新分析；本项目 percent、prompt/model/tool/capability 的变化来源并不相同 | 增 `rollout_id/candidate_digest/rollout_policy_digest/capability_digest`；任何行为候选或能力变化作废窗口，不跨 revision 拼样本；percent 变化不伪装成新 candidate |
| 分桶 | [flagd fractional.go](https://github.com/open-feature/flagd/blob/main/core/pkg/evaluator/fractional.go) 使用 murmur3 与乘法映射高位的无模偏桶位 | 保持 M5 `CanaryBucketer` 与缺 key 拒绝策略，不换算法；分桶正确性不能替代窗口代表性，样本仍按 incident/stickiness 聚类 |
| 三段式裁决 | Argo 的 Successful/Failed/Inconclusive 可继续/中止/暂停；[Kayenta canary config](https://github.com/spinnaker/kayenta/blob/master/docs/canary-config.md) 有 critical/must-have-data 等结构 | 采纳 PASS/FAIL/INCONCLUSIVE 和 critical/scored；INCONCLUSIVE 只能延长/回退，人工无权把缺样本改判 PASS；K、最小独立 incident 与墙钟下限须 spike 后版本化冻结 |
| 影子对照 | [GitHub Scientist](https://github.com/github/scientist/blob/main/README.md) 提供 control/candidate、mismatch context、ignore 与 control-vs-control 校准，也明确适合只读实验且 candidate timeout 不被保护 | 采纳实验数据模型，不照抄请求内并行；M6-05 用 PG 持久 work+租约+预算+恰一次结果，拒绝生产一次性 runner |
| 自动动作边界 | 架构 FUT-12 允许安全/运行故障回 Holmes，但禁止语义 disagreement 自动回退；v1.0 INV-AM6-4 又把全部回退写成人工，存在冲突 | 晋升/恢复放量始终人工；安全/运行可自动 STOP 新 admission 或 V32 run fallback；语义 disagreement 只入人工案件 |
| fallback 幂等与单发 | 当前方案只写 `fallback_of` 事件；现有 V9 publication/outbox 的唯一键按 report/channel，不限制同 incident/generation 的 Native 与 Holmes 各发一份 | V32 增加 `source_native_run_id` 唯一 fallback 栅栏与 incident+generation publication winner；深度≤1、独立预算、并发/重启测试 |
| 现有索引回归 | V12 `uq_rca_run_active_incident` 明确含 `REPORTING`；V25 重建为 `(incident_id,engine)` 时谓词只剩 `QUEUED/RUNNING` | 登记 BA-40；禁止改写 V25，V30 补回 `REPORTING`，真 PG 并发契约测试 |
| 退场 | [Azure Strangler Fig](https://learn.microsoft.com/en-us/azure/architecture/patterns/strangler-fig) 要求依赖迁移完成后再 retire，并指出完全移除后恢复/回滚风险显著增加 | M6-06 增 drain barrier；删除前是即时 bundle 回切，M6-07 删除后只能制品恢复，必须单列 RTO/RPO/审批/保留期，不能继续称“一键回退” |

### 明确不采纳/不引入

- 不引 Argo/Flagger/Kayenta/LangSmith/Langfuse 本体；当前 Compose+2C4G 不匹配，只吸收数据模型和控制纪律。
- 不把“默认 50 run + 72h”当统计结论；没有本项目到达率、相关性与分层分布实测前，它只是待验证假设。
- 不新增 `nativeReady` 热开关；部署 capability 是探测事实，发布比例的唯一事实源仍是 ConfigBundle。
- 不做自动语义晋升、不以 LLM 自评报告替代真实业务结案、不用测试租户填充生产样本。
