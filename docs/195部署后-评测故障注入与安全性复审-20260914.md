**SAFE-03：把 flagd 注入—台账—条件恢复做成可追踪的完整写入协议**

位置：[FlagdScenarioDriver.java:77](E:/kimiCode/control-app/src/main/java/com/objwww/pr/control/eval/application/FlagdScenarioDriver.java:77)、[FlagdConditionalRestore.java:34](E:/kimiCode/control-app/src/main/java/com/objwww/pr/control/drill/application/FlagdConditionalRestore.java:34)、[flagd-admin/server.py:29](E:/kimiCode/deploy/alert/flagd-admin/server.py:29)、[台账查询](E:/kimiCode/control-app/src/main/java/com/objwww/pr/control/infrastructure/persistence/PostgresFlagdRestoreLedger.java:67)。

这组问题应一起修，单改一个函数不够：

1. **先改现场，后记恢复台账。** 当前 activate 先 `setDefaultVariant`，再读写后状态、最后 recordActivation。写入已成功但数据库落账失败，或者写入成功后进程退出，清扫器找不到本次恢复记录。离线探针确实捕获“先完成 flag 写入，再因台账异常退出”的顺序。
2. **原值读取失败仍允许注入。** before=null 后照常写入；restoreTarget 后续用模板 baseline 兜底。模板默认值不一定是现场原值，不能把“不知道原值”解释成“可恢复到模板值”。
3. **客户端读后写不是原子条件恢复。** attempt 先 GET 校验 generation，再发只含 flag/variant 的 POST；两者之间其他操作者可修改。假件复现他者更新发生在读取后，恢复仍覆盖其值并返回 RESTORED。台账 close 的数据库 CAS 只能保护台账状态，不能使之前的外部写原子化。
4. **generation 实际是内容哈希。** 相同内容重写不变；A→B→A 回到旧哈希。Python 探针对实际 read_flag 已复现，不能据此声称检测所有同值重写。
5. **不同 flag 并发写也会丢更新。** ThreadingHTTPServer 的两个请求各自加载完整 JSON，然后分别原子 replace；原子替换防半文件，不防读改写覆盖。探针让两次真实 set_default_variant 都完成，最终只有一个 flag 的更新留下。
6. **回执归属太弱。** 恢复查询按 flag 取最新记录再筛 scenarioId，没有绑定具体 evalRunId/drillId/activationId；共享资源或重复轮次下可能取得另一批记录。SAFE-02 修复能缩小窗口，但恢复身份本身也应精确。

建议沿现有台账和侧车修改，不更换故障平台：

- 使用稳定 operationId：从 evalRunId/drillId + scenarioId + round + flag 派生，同请求重试不变。先保存并提交 PREPARED 意图，含已核验原值、原版本、拟写入值、资源归属、恢复截止；没有意图落库成功，禁止远端写。
- 原值、版本或恢复通路无法确认时，注入前明确拒绝。对于已经进入 UNKNOWN 的历史记录，继续保留待核验，不能迁移时伪造原值。
- 侧车增加受控条件写契约 `{operationId, flag, expectedGeneration, variant}`。在同一个锁内重读、比对、改写、更新版本并原子替换。当前单进程 ThreadingHTTPServer 可用一把文件级锁保护所有 flag 的读改写；若允许其他进程直接写同文件，必须统一写入口或使用跨进程锁，不能把仅线程锁宣称为跨进程保护。
- generation 用持久化版本标识，和本次 flag 内容在同一受控文档中提交。例如在已验证兼容的 flag metadata 中保存递增 revision/操作身份；flagd 官方定义支持 [metadata](https://flagd.dev/reference/flag-definitions/)。应先用部署的具体 flagd 版本验证 schema 与热加载，不直接把版本字段塞进未知位置。部署回滚不得重置版本或回退操作身份，旧版本回退要触发重新核验。
- 服务端原子返回 previous、applied、before/afterGeneration 和 operationId，替代写后再 GET 猜本次代际。条件不满足返回冲突，零写入。
- 成功后持久化 APPLIED 回执；响应/落账未知时按稳定 operationId 查询并对账，不盲重写。回执字段需新增受控更新列或只增回执记录；按仓库下一个可用迁移编号实现，不能伪装成本批无需迁移。
- 恢复使用相同条件写协议，明确绑定原 activationId 与预期写入版本。版本缺失属于 UNKNOWN，不自动退化成任意值相等就可覆盖。
- `DrillInjectionFailures` 不应仅凭通用 IllegalStateException/4xx 判断“肯定没发出请求”；前置拒绝使用明确类型，已尝试写入后的错误统一按是否有确定回执分类。现有 PostgreSQL 异常类型与测试假件类型应分别覆盖，不能推断所有台账失败都属于相同异常类。

这项修改的最终目标是：任何远端写入都有可恢复的前置身份；任何恢复写入都由资源端原子确认所有权；任何错误都不能使应用声称现场已恢复。

**SAFE-05：评测执行结束与现场恢复结论要分别完整**

位置：[EvalBatchRunner.java:268](E:/kimiCode/control-app/src/main/java/com/objwww/pr/control/eval/application/EvalBatchRunner.java:268)、[deactivate:317](E:/kimiCode/control-app/src/main/java/com/objwww/pr/control/eval/application/EvalBatchRunner.java:317)、[finalizeSucceeded:334](E:/kimiCode/control-app/src/main/java/com/objwww/pr/control/eval/application/EvalBatchRunner.java:334)。

两条离线执行结果：

- ArenaChaosScenarioDriver.ActivationException 已携带“现场已激活”的 receipt，EvalBatchRunner 却按普通 activate_failed 捕获并返回，没有调用 deactivate。drill 的 Arena 适配器已识别这种异常，eval 调用方没有接同一语义。
- deactivate 抛异常后，仅日志记录并关闭本批后续案例门；run 仍可被 finalizeSucceeded 收尾为 SUCCEEDED，恢复字段停在启动时的 PENDING。正常成功路径也缺少把 L recovery_state 回填 VERIFIED 的收尾。

SUCCEEDED 可以表示批处理完成，不必等于根因正确；问题在于恢复的独立事实没有完成记录，不能让使用者或后续调度从运行终态推断环境可用。当前代码还会在 deactivate 抛异常时漏掉结构化 RECOVERY failure 样本。

修改方法：将“是否已产生副作用、是否有激活回执、恢复状态”贯穿 runRound。对携带回执的 ActivationException 先接管回执，再执行恢复与核验；未知注入结果按意图台账对账。把激活后预热/等待也纳入统一清理范围，不能只保护评分段。业务失败、取消、中断均禁止后续流量，并进入同一恢复路径。

最终分别持久化 executionState、qualityOutcome、recoveryState。只要恢复未证实成功，就不能释放 SAFE-02 的占用或把结果当作完整演练证明；可采用执行 FAILED + recovery FAILED/UNKNOWN，或保留批处理终态但将恢复分面明确终结，标准必须在 API/页面/质量门统一。恢复失败必须有结构化原因与案例身份，不能只输出日志。

已有告警 resolved 只能作为恢复的一部分：不应仅因告警不 firing，就把仍在激活的 chaos 会话或归属冲突的 flag 判为 VERIFIED。

**SAFE-06：连续两次评测的 Arena 场景身份可能重复**

位置：[EvalRunnerConfig.java:216](E:/kimiCode/control-app/src/main/java/com/objwww/pr/control/eval/application/EvalRunnerConfig.java:216)、[effectiveScenarioId](E:/kimiCode/control-app/src/main/java/com/objwww/pr/control/eval/application/ArenaChaosScenarioDriver.java:66)。

Arena 驱动是共享 bean，runTag 来自环境 `app.alert.eval.run-tag`；场景实例 ID 由 runTag + 模板 ID + round 组成，不含本次 evalRunId。进程不重启而启动第二个实验时，会派生与前一批相同的实例 ID。驱动注释自己也要求“逐批唯一 run-tag”，但现有常驻命令路径没有逐批替换。管理面永存唯一约束可能拒绝第二次激活，也会削弱关联与证据隔离。

修改方法：在每条 LAUNCH 的执行范围内用预定 evalRunId 派生短、安全且稳定的 runTag，例如 run UUID 的 32 位 hex。创建该次 Arena 驱动与该次 RCA resolver，二者用同一标签；同一命令恢复/重试不变，不同实验必不同。可复用 [ArenaChaosDrillInjection 的作业身份模式](E:/kimiCode/control-app/src/main/java/com/objwww/pr/control/drill/application/ArenaChaosDrillInjection.java:49)。不要修改共享 bean 的可变 runTag，也不要只改注入 ID 而漏掉读取/关联 ID。

这项是代码追踪发现，本轮没有在 195 执行两次真实 L 来验证冲突。

**SAFE-07：REJECTED 终态与慢请求需要补入受理详情测试**

位置：[EvalRunDetailView.vue:550](E:/kimiCode/alert-web/src/views/EvalRunDetailView.vue:550)、[受理详情展示](E:/kimiCode/alert-web/src/views/EvalRunDetailView.vue:350)。

worker 能将不支持的旧命令标成 REJECTED，但详情只对 FAILED/DONE 停止等待轮询；REJECTED 仍显示“等待执行”。此外，3 秒 interval 每次 loadRun 都 abort 上一次请求，若响应持续超过 3 秒，可能反复取消而无法得到状态。这个是 PAGE-10 新闭环的剩余边界，不否定已验证的 PENDING→建行成功路径。

修改方法：共享命令终态集合 DONE/FAILED/REJECTED；明确展示拒绝与原因，不显示“等待领取”。DONE 但无 run 应显示结果异常，不宣称仍在排队。采用上次请求完成后再调度下一次的 timeout，或加 in-flight guard；切路由、卸载时才取消过期请求。受理状态和运行状态用一致的刷新生命周期，避免 run 建行后即完全停止进度跟踪。

**SAFE-08：claimed_at 超龄不是 worker 已死亡**

位置：[PostgresEvalRunCommandRepository.java:148](E:/kimiCode/control-app/src/main/java/com/objwww/pr/control/infrastructure/persistence/PostgresEvalRunCommandRepository.java:148)、[EvalRunWorker.sweepOrphanedClaims](E:/kimiCode/control-app/src/main/java/com/objwww/pr/control/eval/application/EvalRunWorker.java:120)。

孤儿查询仅判断 CLAIMED + claimed_at 早于阈值；执行中不续租，默认阈值 900 秒。长评测可正常超过这个时间。另一 worker 或重叠部署的新进程启动清扫时，可能将仍运行的 run 标为 worker_lost。finish/requeue 也缺少 owner/lease generation 条件。SKIP LOCKED 保证同一命令瞬时领取，不代表任务整个执行期的租约有效。

本轮未复现多进程现场竞争，当前按部署限制标 P2：继续单实例且避免新旧 worker 重叠；不要只把 staleClaimSeconds 调大当根治。要支持扩容/滚动升级时，增加租约到期与续租、ownerId + fencing token，并在领取、续租、收尾、重排队和副作用入口统一校验。无法确认旧执行者退出时保留恢复义务与资源占用，不能直接新开同资源任务。

**安全边界的另一个已知限制**

[PlatformUserDetailsService](E:/kimiCode/control-app/src/main/java/com/objwww/pr/control/infrastructure/auth/PlatformUserDetailsService.java:17) 明确写明：停用/改密只阻止新登录，已发会话不吊销。对能发起故障的 OPERATOR，这意味着“禁用账号”暂不等于“立即撤销操作能力”。若发布要求紧急撤权，应在敏感写入口核对账号有效状态/授权版本，或使用现有 Spring Session/会话注册机制吊销；本轮不要求为只读试用先接一套 SSO，也不将该已有声明伪装成新发现的匿名越权。
