## 1. 结论

**不能确认所有优化已经闭环。仍有已知产品缺口和验收范围错配；不建议继续增加新架构。**应先完成下面六项：子任务结构化回执、真实执行退出计数、Claim 证据准入、通知出口验收、BA-141 根因定位、台账按实际覆盖范围收口。

这些主要是之前 U04～U08、OR-06/07 的剩余内容，不是重新扩出一批需求。已修复的项不重报：`ruled_out` 已退出 REJECTED 裁决供数，并对父版旧内容增加过滤；看门狗已分页；取消命令事务和锁序已调整；工具分类与日志 severity 已加入；B2 验证器 v2 已能报告非空 witness 不足，而不是强行 PASS。

验证证据：

- [定向测试日志](post-optimization-review-tests.log)：实际执行 47 项，0 失败/错误/跳过。指定了 ContextAssembler、ToolGateway、WorkingMemory、PrimaryClaimAdmission、SingleToolRoleRunner 相关测试选择器，具体实际类以日志为准；允许未匹配选择器，不将选择器数量当覆盖数。
- [取消生命周期离线复现](post-optimization-inflight-repro.txt)：`reported_inflight=0`，但 `actual_executor_exited=false`。
- [复现源码](review-tools/InFlightExitAudit.java)：使用当前 InFlightToolCancels，复现 ToolGateway 相同的 get/cancel/finally-unregister 顺序，底层执行体有意忽略中断；实验结束主动释放并回收线程。不是生产 HTTP 实测，也没有修改应用实现。
- BUGLOG BA-141/142 仍开放。BA-143/144 是测试执行器修复，不能等同于所有被测产品能力已通过。

## 2. 按优先级排列的发现

### R1 / P1：成功回执仍不能生产反证与业务缺口

位置：`control-app/src/main/java/com/objwww/pr/control/infrastructure/nativeexec/NativeInvestigationExecutor.java:606`，`submitDelegationReceipt`。

成功路径仍把 evidenceIds 转成 `evidence:<id>` findings，`missing=List.of()`，Submission 的 counterRefs 明确传 `List.of()`。`SingleToolRoleRunner.java:46` 的 handler 只收到 CallContext 与起止时间，不读取委派任务的调查描述。

因此 BA-142 的核心仍在：已经有任务派发/回执接收的结构，**但这条成功回执生产路径没有表达“查到了什么反证、还缺什么”的能力**。这不能通过更强 prompt 或增加重试解决。也不能把这个结论泛化为仓库所有未来角色都没有推理能力，它针对当前这条兼容角色路径。

修法：

1. 在已有 RoleDriveResult/角色结果协议中增加结构化 findings、supportRefs、counterRefs、missingInformation；版本化，保留旧确定性角色兼容。
2. 角色输入传入绑定的委派目标、允许证据范围和预算；适用角色可用 LLM 判断，确定性角色也必须诚实表达能力边界。不能把确定性查表角色统一伪装成 LLM 专家。
3. ReceiptService 校验 Run/task/round/configEpoch 和引用成员，接收的是已准入结果，不能让模型自报有效反证。
4. 原有 submitDelegationReceipt 不再机械填空；持久化失败要有可重试/可恢复事实，不能仅日志后丢掉回执。
5. 使用非空反证 witness 跑“主查→委派→子结论→回执→下一模型输入”。结构通过与语义通过分列。

验收：成功子任务能提交至少一条真实反证并在后轮入模；越界/迟到回执拒绝；子任务确实无反证时仍允许空，不能为测试伪造。

### R2 / P1：取消后 in-flight=0 仍可能是虚假的静默

位置：`alert/application/tool/ToolGateway.java:163–191`；`InFlightToolCancels.java:32–88`。

get 因 cancel 抛出后，调用方 finally 立即 unregister。底层执行器不响应中断时仍在工作，注册表却为零。本轮已离线复现。此前 BA-139 修复的是“注册前取消丢通知”，修复有效，但不是“真正执行退出”的证明。

另有两个静态风险：stopCancelled 只增加无回收；register 的 computeIfAbsent/add 与 unregister 的 empty/remove 不作为同一原子成员操作，存在注册到已从 Map 移除集合的交错。后者本轮未做确定性竞态复现，不能声称线上已发生。

修法：执行句柄区分 QUEUED/RUNNING/EXITED 与 stopRequested；执行体 finally 才记 EXITED。排队阶段取消通过 CAS 收为 CANCELLED_BEFORE_START。调用方返回只表示等待结束，不删除尚在执行的生命周期事实。成员增删用按 Run 原子操作，终态且无执行/注册中动作后再回收取消墓碑；回收后仍以持久 Run 状态防新动作。

把 task cleanup 指标和 execution exit 指标分开。slot 与预算按实际占用/UNKNOWN 对账，不因为列表显示取消就全部释放。跨实例的停止还要靠持久探针与期限，单实例计数明确标注作用域。

验收：忽略中断、排队取消、register/unregister 并发、取消后长期资源回落、另一实例取消五案。对应已有 U05/U06、WC-T20/21、N22～28，无需新平台。

### R3 / P1：Claim 的“作用提议”仍可能未经验证成为支持/反证

位置：`alert/application/agent/PrimaryClaimAdmission.java:175–202`；`ContextAssembler.java:803–819`。

当前 verdictFor 在证据行无法读回时，不主动降级模型提议的角色；locator 无法解析时只清空 locator，角色可能仍为 SUPPORTS。REFUTES 也需要同等级的真实性核验，否则排除槽虽然不再接收控制拒绝，仍可能接收没有充分依据的业务排除。`isEvidenceBackedExclusion` 只检查 refs 非空、存在 REFUTES 项，本身没有证明该 REFUTES 与有效 ref 一一对应。

这里存在 validRefs 上游保护，不能说任意外来引用都会通过；具体风险是“允许集合内但载荷缺失/失效、无效定位、作用关系不充分”这些后续校验条件未闭合。

修法：证据载荷不可验证、定位失败、服务/窗口/快照不匹配时，SUPPORTS 和 REFUTES 均不得授予；明确 CONTEXT/拒绝原因。业务排除只消费完整验证结果，不能单靠 `[EX]` 文本前缀长期代表资格。前缀可作历史清理兼容标记，但后续应绑定 claim/evidence 身份与策略版本。

计数器判断仍需覆盖 histogram `_count` 等类型，不能只判断 `_total`。采用工具结果元数据中的类型/窗口/算子；累计非零不代表当前告警窗内增长。不要让任意 JSON 字段存在就自动证明自然语言因果。

验收：缺载荷、无效定位、REFUTES 引用错配、过期反证、累计计数/窗口增量、上下文日志冒充第二支持源。对应原 AS06～08、N31～34。

### R4 / P1（验收）：RR27/28 被入口测试替代，通知出口仍未证明

位置：`docs/测试证据/R7/runs/rr2528-20260913/执行记录-rr2528-20260913.md`。

该记录明确说明零 Run 铸造、纯 incident/alert_event 层断言。RR27 使用同 Webhook 载荷重投验证事件去重；RR28 使用迟到 firing 验证不复活。这两部分有价值，但原 RR27 要测“通知接收端已产生效果，响应丢失后 outbox 重试”，原 RR28 要测“通知渠道失败恢复与触发/恢复消息交付”。**入口幂等与出口交付不是同一个接口，也不是同一个事务边界。**

这不是已证明通知产品有 bug，而是目标环境验收覆盖缺口。不能沿用“RR27/28 全量通过”的总状态。

修法：保存当前结果为 RR25 的入口/episode 子用例；通知出口用可控接收器先落幂等效果再断响应，记录真实 HTTP 请求、outbox attempt 和接收器 effectId。同一通知的重试幂等键保持不变。第二案关闭测试渠道再恢复，分别记录 firing/resolved 的逻辑身份和业务顺序策略，验证旧消息不冒充新告警。

必须先有真正的 report→publication→notify_outbox 驱动；零 Run 铸造的场景不能完成这个出口门。

### R5 / P1（已登记待定责）：BA-141 仍不能用诚实未决报告关单

BUGLOG 记载 LLM 路由主任务 attempts=0 即 DEAD，随后 native 兜底、Run=SUCCEEDED。现有资料支持异常现象，不能支持“某个 sweep 竞态就是根因”的确定结论。本轮未复现，不猜原因。

修法先加可定位证据：所有主任务 DEAD/FAILED_TERMINAL 迁移统一记录 taskId、from/to、reason、writer、owner/epoch、checkpoint phase、route/runtimeKind。围栏拒绝与实际迁移区分，事件与迁移尽量同事务。围绕任务创建、driver 领取、恢复 triage、runner 解析和 sweep 无进展建立确定性交错测试。

产品读面分开 requestedEngine、executedEngine、fallbackReason、diagnosisStatus。Run 的工作完成状态可以保留，但主任务未执行/降级必须可见，不能让用户以为 LLM 根因调查成功。

验收：零 attempt DEAD 必有迁移原因；指定 LLM 路由要么真实调用、要么明确拒绝/降级；可恢复流程不被提前收尾。先定位 BA-141，再决定最小代码修补范围。

### R6 / P2（证据治理）：整卡 VERIFIED_TARGET 仍掩盖明确未验子项

最新 OR-06 记录保留 RR23 fail 族与 Clock 的 NOT_VERIFIED；CL-06 非空跨轮仍是待生产面增强；CL-08 最小消费未通过效果门；Skill LLM_CURATE 仍为条件未交付；部分页面/长稳/供应链台账仍未验证。不能从“批次执行完成”推导“所有能力完成”。同时台账可能落后于新 Drill 等实现，不能反过来单凭旧 UNVERIFIED 判没有代码。

修法：每卡分 `implementation / deterministicTests / targetE2E / semanticCoverage / enabled`。明确证明范围而不是只给总徽章。相关代码变化后用构建摘要限定旧证据资格；历史证据保留。缺某模型密钥可阻断该供应商专属试验，不应阻断确定性慢源/TLS/取消测试。

## 4. 最小剩余执行包

1. **正确性包**：R1 回执结构化、R2 执行退出、R3 证据准入。使用原 U/N/AS 编号补实现与回归，不创建平行大方案。
2. **定责包**：BA-141 定向取证和交错复现；未定位前保留开放状态，不靠更多模糊日志或扩大重试掩盖。
3. **验收包**：补真实通知出口 RR27/28、RR23 故障分类确定性路径，修正台账覆盖范围。
4. **条件项**：摘要替换、自生成 Skill、进一步并行/RAG 升级按收益与启用门安排。当前未启用就不视为线上缺陷；不要为宣称“全部做完”仓促打开。

不建议此时新增消息中间件、再拆更多 Agent、增加更复杂自治框架。当前最大收益来自保证现有角色能产出有用结论、取消能真实回收、测试验证的就是承诺的接口。

本轮结论是“仍有明确剩余项，范围可控”，不是“又要从头重做”。产品级闭环需上述正确性与验收补齐后再声明；47 项单元测试通过不能抵消已经复现的生命周期缺口。
