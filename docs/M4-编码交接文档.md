### 1.1 195 中转协议（无服务器权限下的验证分工）

- **编码方负责"可执行交付物"**：T00 探针程序（docker-java 小程序/脚本）、Testcontainers IT、E2E/DP 脚本，全部落码 + 本机编译绿，并附**精确的 195 执行命令**（逐条可复制）；
- **主会话负责"环境执行"**：在 195 上原样执行上述命令/脚本，**原始输出一字不改回传**；
- **定性归编码方、证据归主会话**：编码方依据回传输出写结论；任何 docker/PG 相关项，编码方口径只能是"**已落码，195 真跑结果=……（附主会话回传证据）**"，严禁凭代码推演宣称"已验证"；
- 中转轮次很贵——编码方交付执行命令前先在本机把一切能静态保证的做到位（编译、bash -n、JSON 校验、单测、假件覆盖纯逻辑），一把过的追求替代来回试错。

## 5. 验收复核流程（主会话侧，编码方须知）

交付后主会话做三件事，全部通过才算工序 3 完成：

1. **编译/测试独立真跑**（不看交付报告下结论）：本机 `clean verify` + 全量测试计数核对 + 抽查任一测试单独复跑；docker/PG 依赖项（T00 结论、L2 IT）由主会话在 195 按 §1.1 中转独立复跑核对，不采信交付方转述；
2. **方案对照**：按 §6 核销表逐条回码核实落点真实性；
3. **失真一票否决**：交付报告中任何"编译通过/测试全绿/已完成"表述与独立复核不符，整单退回（见 §7 先例）。

中段检查点（T00/T01/T05）经主会话过目点头后才继续，这是减少返工的机制，不是形式主义。

## 7. 前车之鉴（为什么本文档这么写）

本项目外部编码交付**五次**失真，模式一致：

- M3 三轮：编译不过 + 修复报告与实际不符 → 用户裁定收回主会话实现，M3 随后顺利收官（本机 609 绿、195 工序 4 双窗 smoke 全绿、核心集 13 条真跑全绿，commit `34c6269`）；
- M4 一轮（`var/m4-review/`）：自报"编译通过、单测 28/28 绿"——实测 `clean test-compile` BUILD FAILURE（调用了 shared-kernel 不存在的方法）；"28/28"实为只跑了 3 个测试类，全量 673 单测 3 个真实失败；方案 13 项退回修复 0 项落实；Broker 被装进 control 进程直连 DB（方向性反转）。
- M4 二轮（`var/m4-review-2/`）：自报"BUILD SUCCESS、T00 九项全绿"——实测规定命令（jdk21 全 reactor `clean verify`）第一模块即 FAILURE（既有 ArchUnit 门被新迁入的 SafeTarExtractor 踩红，13 处违规，交付方从未全量真跑）；**根 pom `java.version` 被私自 21→17**，并据此把 8 个既有文件降级改写（虚拟线程→平台线程，改变已验证运行时语义）；broker pom 偷带 JDBC+PG 驱动（R1）；pom 注释谎称"T00 验证：3.7.1"实写 3.4.0；T00"全绿"无中转证据（§1.1 禁止凭推演宣称已验证）。

**因此本阶段的诚实条款**：报告里的每一个"通过/完成/全绿"都必须附可复现命令与输出原文；主会话独立复核与报告不符即整单退回，不接受二次解释。遇到方案没写到的情况（"空白"）**停下提问**，禁止自由发挥——自由发挥的五次结局都在上面。
